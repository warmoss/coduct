== prompt写作指南

Prompt(提示词) 是与大语言模型交互的核心媒介. 一个精心设计的 Prompt 能让模型准确理解意图、生成高质量输出; 而一个模糊的 Prompt 则可能导致答非所问、幻觉频发. 本文系统讲解 Prompt 的设计原则、构成要素和工程化方法.

参考: <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>

=== 什么是 Prompt

Prompt:: 用户提供给大语言模型的**输入文本**, 用于引导模型生成特定类型的输出. 它本质上是一种**指令编码**方式——将人类意图转化为模型可理解的 tokens 序列.

从 <<大模型原理讲解.adoc#大模型的工作流程-训练与推理, 大模型的工作流程>> 可知, 模型在推理阶段根据 Prompt 计算下一个最可能的 token. 因此, Prompt 的质量直接决定了输出的质量.

=== Prompt 的核心构成要素

一个完整的 Prompt 通常由以下要素组合而成:

角色:: 为模型设定一个身份或立场, 约束其回答视角和语气. 例如: "你是一名资深网络安全工程师".

指令:: 明确告诉模型需要完成的任务. 指令应当**清晰、具体、无歧义**. 例如: "请用三句话总结以下文章".

上下文:: 为模型提供完成任务所需的**背景信息**. 可以是历史对话、相关文档或外部数据.

输入数据:: 模型需要处理的具体信息, 如一段文本、一个问题或一组数据.

输出格式:: 指定模型返回结果的格式要求. 例如: JSON 格式、Markdown 表格、代码块等.

约束条件:: 限制模型行为的边界, 如字数限制、禁止提及的内容、必须使用的语言等.

[source,text]
----
# 一个完整 Prompt 示例

你是一名资深的 Java 开发者.                    # 角色
请审查以下代码, 找出潜在的性能问题.             # 指令
项目使用 Spring Boot 3.2 + MySQL 8.0.         # 上下文

代码:
public List<User> findAll() {
    return userRepository.findAll();
}                                              # 输入数据

请按以下格式输出:                              # 输出格式
- 问题位置: (类名:行号)
- 风险等级: (高/中/低)
- 优化建议: (具体方案)
- 预期收益: (性能提升百分比)

不要建议升级框架版本.                          # 约束条件
----

=== Prompt 设计核心原则

==== 清晰具体, 避免模糊

模糊的指令导致不可控的输出. 比较以下两个 Prompt:

* **不推荐:** "帮我改进这段代码"
* **推荐:** "将以下 Java 代码的时间复杂度从 O(n^2) 优化到 O(n log n), 保持原有接口不变"

==== 分步拆解, 降低复杂度

复杂任务应拆解为多个简单步骤, 引导模型逐步推理. 这被称为**思维链(Chain-of-Thought, CoT)** 方法.

* **一次性提问:** "这个系统的架构有什么问题?"
* **分步引导:**
. 请先分析当前系统的模块划分
. 然后评估各模块间的耦合度
. 最后给出重构建议和优先级排序

==== 提供示例, 少样本学习

大模型具有**少样本学习(Few-shot Learning)** 能力. 通过提供输入-输出对示例, 可以显著提升输出的一致性.

[source,text]
----
将以下中文地址转换为 JSON 格式.

示例1:
输入: 北京市海淀区中关村大街1号
输出: {"province": "北京", "city": "北京", "district": "海淀区", "street": "中关村大街", "number": "1"}

示例2:
输入: 广东省深圳市南山区科技南路18号
输出: {"province": "广东", "city": "深圳", "district": "南山区", "street": "科技南路", "number": "18"}

输入: 上海市浦东新区陆家嘴环路1000号
输出:
----

==== 否定规避, 正面引导

模型对"不要做什么" 的理解不如"要做什么" 准确. 优先使用**正面指令**而非否定约束.

* **不推荐:** "不要使用复杂的术语, 不要写太长"
* **推荐:** "请用初中生能理解的语言解释, 控制在 100 字以内"

=== 进阶 Prompt 技术

==== 思维链(Chain-of-Thought)

让模型在给出最终答案前, 先展示**中间推理步骤**. 这对数学、逻辑推理等复杂任务尤其有效.

[source,text]
----
问题: 一个水池, 进水管5小时注满, 出水管8小时排空.
如果同时打开进水管和出水管, 需要多少小时注满?

请逐步推理:
1. 进水管每小时注水 1/5 池
2. 出水管每小时排水 1/8 池
3. 净注水速率 = 1/5 - 1/8 = 3/40 池/小时
4. 注满所需时间 = 1 / (3/40) = 40/3 小时

答案: 13.33 小时
----

==== 思维树(Tree-of-Thought)

在 CoT 基础上, 让模型同时探索**多条推理路径**, 并在每条路径上评估其可行性, 最终选择最优路径. 适用于开放性问题和创意生成.

==== 角色扮演

通过**身份设定**约束模型的回答视角, 使输出在特定领域内更具专业性.

[source,text]
----
你是一名20年经验的数据库管理员(DBA).
现在需要你分析以下 SQL 查询的执行计划, 并给出索引优化建议.
请使用 DBA 的专业术语和诊断思路.
----

==== 结构化输出

要求模型以特定格式返回结果, 便于程序化处理.

[source,text]
----
请分析以下日志中的错误, 以 JSON 数组格式返回:

[
  {
    "timestamp": "错误发生时间",
    "level": "错误级别(ERROR/WARN/INFO)",
    "message": "错误摘要",
    "suggestion": "修复建议"
  }
]
----

=== Prompt 工程工作流

编写高质量 Prompt 是一个**迭代优化**的过程, 而非一次性完成.

. **需求分析:** 明确任务目标、输出要求和使用场景

. **初版编写:** 根据核心构成要素编写第一个版本

. **快速验证:** 用典型输入测试 Prompt, 评估输出质量

. **问题诊断:** 分析输出与期望的差距, 定位 Prompt 缺陷

** 输出过于泛化 -> 增加约束条件和具体示例

** 输出格式不符 -> 明确指定输出格式并提供模板

** 输出包含错误 -> 补充背景知识和上下文

** 输出偏离主题 -> 强化角色设定和指令

. **优化迭代:** 根据诊断结果调整 Prompt, 重复步骤 3-4

. **固化版本:** 达到预期效果后, 锁定 Prompt 版本并使用变量化管理

=== Prompt 版本管理

随着 Prompt 复杂度提升, 需要引入版本管理机制:

* **变量化:** 将角色、指令、上下文等要素定义为独立变量, 便于复用和修改
* **模板化:** 使用模板引擎(如 Jinja2、Mustache)构建动态 Prompt
* **版本控制:** 记录每次修改的 diff 和测试结果, 追踪 Prompt 演变历史
* **A/B 测试:** 对不同版本的 Prompt 进行对比测试, 量化评估输出质量

[source,python]
----
# 变量化 Prompt 模板示例
prompt_template = """
你是一名{role}.
请完成以下任务: {task}
约束条件: {constraints}
输出格式:
{output_format}
输入数据:
{input_data}
"""
----

=== 常见误区与注意事项

* **过度指令:** 一次性给出过多指令会导致模型注意力分散. 优先遵循**奥卡姆剃刀原则**——用最少的指令达到最佳效果
* **假设模型有记忆:** 每次对话都是独立的, 关键上下文应在当前 Prompt 中重复提供, 而非依赖于历史对话
* **忽略 Token 限制:** Prompt 过长会挤占输出空间. 需控制 Prompt 长度, 为模型输出留足 token 预算
* **缺乏测试:** 同一个 Prompt 在不同模型上的表现可能差异显著, 应针对目标模型进行测试调优
* **忽视安全性:** 避免在 Prompt 中泄露敏感信息(如密码、API Key), 防范 Prompt 注入攻击

=== 总结

Prompt 写作是**大模型应用开发**的核心技能之一. 高质量的 Prompt 需要:

* 明确的角色定位和清晰的指令
* 充分的上下文和具体的约束条件
* 合适的示例引导和输出格式要求
* 持续的迭代测试和版本管理

优秀的 Prompt 设计, 能够将大模型从一个"概率生成器" 转变为可靠的智能工具, 显著提升输出质量和任务完成效率.
