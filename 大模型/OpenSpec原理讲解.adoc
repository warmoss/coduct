== OpenSpec原理讲解

OpenSpec 是一个轻量级的**规范驱动开发框架**, 核心思想是在 AI 编写任何代码之前, 先就"要构建什么"达成明确的、机器可读的共识规范. 它通过锁定意图而非依赖模糊的聊天记录, 将不可预测的 AI 转变为按规范执行的可靠工程伙伴.

=== 核心原理: 以规范为"单一事实源"

OpenSpec 的工作模式根植于规范驱动开发(Spec-Driven Development, SDD)的理念, 其核心是让AI精确理解并执行需求. 它会创建一个 openspec/ 目录, 并通过该目录的闭环流程来规范开发行为.

其底层架构的核心是一套**产物依赖图**(Artifact Dependency Graph), 用于精确控制每个阶段的状态:

* **节点(Nodes):** 代表各个阶段的产物, 如 proposal, specs, design, tasks.

* **有向边(Edges):** 定义产物间的依赖关系(例如 specs 依赖 proposal), 由此构建出**有向无环图**(DAG), 确保工作流按逻辑有序推进.

* **状态跟踪:** 系统会扫描文件系统, 为每个产物自动计算状态, 以此驱动AI或开发者的下一步操作.

=== 目录结构: 将思想转化为文档

该目录位于你的项目根目录下, 结构清晰地将"当前事实"与"未来提案"分离开.

[source, text]
----
your-project/
├── AGENTS.md              # 为AI助手提供的全局指令
└── openspec/
    ├── AGENTS.md          # OpenSpec工作流的详细说明
    ├── project.md         # 项目上下文和技术栈信息
    ├── specs/             # 【当前真实规范】: 描述系统"当前"已构建完成的行为[reference:10]
    │   ├── auth/
    │   │   └── spec.md
    │   └── payment/
    │       └── spec.md
    ├── changes/           # 【提案变更】: 存放所有待实施的变更提案[reference:11]
    │   ├── add-2fa/       # 每个变更都有独立的文件夹
    │   │   ├── proposal.md   # 提案文档, 解释"为什么"和"改什么"[reference:12]
    │   │   ├── design.md     # 技术设计文档[reference:13]
    │   │   ├── tasks.md      # 具体的实施任务清单[reference:14]
    │   │   └── specs/        # 增量规范变更, 描述对主规范的修改[reference:15]
    │   └── archive/       # 已完成变更的归档文件夹[reference:16]
    └── schemas/           # (可选)自定义工作流模式
----

=== 标准工作流: 四步闭环

OpenSpec 定义了一个清晰的"提案-审查-实施-归档"闭环, 有效锁定开发意图.

==== 步骤一: 创建变更提案(Propose)

描述你想要的功能或修改, AI助手会根据你的描述, 在 changes/ 目录下创建一个独立的文件夹(如 add-dark-mode/), 并生成 proposal.md、design.md、tasks.md 以及 specs/ 增量规范等文件.

==== 步骤二: 审查与对齐(Review & Align)

AI生成的所有产物都与你和团队成员共享. 这是一个核心反馈环节, 所有人可以一起审查、讨论和编辑这些文档, 确保大家对"做什么"和"怎么做"达成100%一致. 这个阶段可以避免因需求理解偏差导致的返工, 实现"计划审查"而非"代码审查".

==== 步骤三: 实施任务(Apply)

共识达成后, AI助手进入执行阶段. 它会严格按照 tasks.md 清单逐项完成任务, **不会偏离预定规范**, 从而产出确定、可控的代码.

==== 步骤四: 归档变更(Archive)

功能开发完成并部署后, archive 命令会将 changes/add-dark-mode/specs/ 下的增量规范**合并**到 specs/ 主规范库中, 更新系统的"真实规范". 同时, 该变更文件夹会被移动到 changes/archive/ 下并加上日期戳, 完整保留所有历史决策, 实现完整的审计轨迹.

=== 与AI工具链的集成

OpenSpec 通过其 **OPSX 工作流系统**(OpenSpec eXperience), 提供了一套**行动导向**、**状态感知**的全新协作范式. 它通过CLI命令和斜杠命令(Slash Commands)与AI交互. AI助手可随时通过命令查询项目状态, 并获取为当前上下文动态生成的指令, 而非依赖固定的提示词.

它原生集成了超过20种主流AI编程工具, 如 Claude Code、Cursor、Windsurf、GitHub Copilot 等, 并提供了对应的斜杠命令.

[cols="1,3"]
|===
|命令|作用

|/opsx:propose |根据你的描述生成初始变更提案.
|/opsx:apply |指导AI按照tasks.md清单实施代码变更.
|/opsx:archive |完成变更归档, 将增量规范合并到主规范中.
|/opsx:verify |验证任务是否真正完成.
|/opsx:sync |当代码变更但规范未更新时, 用于同步规范.
|/opsx:onboard |扫描现有代码库以生成初始规范, 尤其适合为既有项目(棕地项目)初始化.
|===

=== 总结

OpenSpec 通过引入"先规范、后代码"的工作流, 并利用目录结构、产物依赖图、状态机等机制, 将AI编程从一种随机的、基于猜测的过程, 转变为一种确定的、可预测的、工程化的规范驱动开发范式. 它不仅约束了AI的行为, 更重要的是**沉淀了设计决策, 让项目的所有参与者在任何时候都能对齐目标**, 从而在享受AI效率的同时, 确保了软件的质量和可维护性.
