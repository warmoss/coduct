== 大模型RAG原理讲解

大模型虽然在语言理解和生成上表现出色, 但存在三个天然缺陷: **知识截止日期**(训练数据只到某个时间点)、**幻觉问题**(可能编造不存在的"事实")、**无法访问私有数据**(企业内部文档、用户个人信息均不在训练集中). RAG(Retrieval-Augmented Generation, 检索增强生成) 正是为解决这些问题而生.

参考: <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>, <<大模型/大模型记忆原理讲解.adoc#, 大模型记忆原理讲解>>

=== 什么是 RAG

RAG(Retrieval-Augmented Generation):: 一种将**信息检索**与**大模型生成**相结合的技术框架. 在模型回答之前, 先从外部知识库中检索与当前问题最相关的信息片段, 将其作为上下文注入到 Prompt 中, 让模型基于这些检索到的信息生成回答.

RAG 的核心思想: **不依赖模型记住所有知识, 而是在需要时去查**.

[cols="2,3,4"]
|===
| 要解决的问题 | 传统大模型方案 | RAG 方案

| 知识过时
| 只能依赖训练截止日期前的知识
| 检索最新资料, 知识永远新鲜

| 幻觉
| 模型可能编造事实
| 检索结果提供事实依据, 大幅降低幻觉

| 私有数据
| 模型从未见过企业内部文档
| 检索企业知识库, 精确回答内部问题

| 专业性不足
| 通用模型在垂直领域表现有限
| 检索专业文档, 提升领域准确性

|===

=== RAG 的核心架构

一个完整的 RAG 系统由三个核心阶段组成: **索引(Indexing)**、**检索(Retrieval)** 和 **生成(Generation)**. 这三大阶段也被称为 RAG 的"三驾马车".

[[rag-three-stages]]
[plantuml, "RAG 三阶段架构", format=png]
----

  (3. 向量化嵌入) as Embed
  (4. 存入向量库) as Store
  Load --> Split
  Split --> Embed
  Embed --> Store
}

package "检索阶段 (Retrieval)" {
  (5. 查询向量化) as QueryEmbed
  (6. 相似度检索) as Search
  (7. 结果重排序) as Rerank
  QueryEmbed --> Search
  Search --> Rerank
}

package "生成阶段 (Generation)" {
  (8. Prompt 组装) as Prompt
  (9. 模型生成) as Generate
  (10. 输出回答) as Output
  Prompt --> Generate
  Generate --> Output
}

database "向量数据库" as VectorDB

Store --> VectorDB : 存储向量
VectorDB --> Search : 检索向量

Rerank --> Prompt : 注入 Top-K 结果
@enduml
----

. **离线阶段 - 索引:** 将原始文档(如 PDF、Word、网页)清理、切分成小块, 用 Embedding 模型转换为向量, 存入向量数据库. 这一步只需做一次(或定期更新).

. **在线阶段 - 检索:** 收到用户查询后, 同样用 Embedding 模型将其转换为向量, 在向量数据库中搜索最相似的文档块, 返回 Top-K 结果, 并可进行重排序优化.

. **在线阶段 - 生成:** 将检索到的文档块作为上下文, 与原始问题一起组装成 Prompt, 交给大模型生成最终回答.

=== 索引阶段: 构建知识库

索引阶段决定了 RAG 系统**知识质量的上限**. 如果索引阶段没有做好, 后续检索和生成的质量都会受影响. 索引阶段包含四个关键步骤.

==== 文档切分 (Chunking)

切分是索引阶段最关键也最易忽视的环节. 切分粒度的选择直接影响检索质量:

* **切分过小**(如 50 tokens): 每个片段信息量不足, 检索到的片段可能不包含完整上下文, 导致模型无法理解.

* **切分过大**(如 2000 tokens): 每个片段包含太多信息, 精确度下降, 而且容易超过 Embedding 模型的输入限制.

* **常见策略:**

* **固定长度切分:** 按固定 token 数切分, 加 overlap(重叠)防止关键信息被切断

* **递归字符切分:** 先按段落切, 段落过大再按句子切, 句子过大再按固定字符切——这是 LangChain 的 `RecursiveCharacterTextSplitter` 实现方式

* **语义切分:** 利用 Embedding 模型判断语义边界, 在主题切换处自然断开

* **结构化切分:** 按文档结构(标题、章节)切分, 保留层级信息

[source,python]
----
# LangChain 递归字符切分示例
from langchain.text_splitter import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,        # 每个块的目标大小(字符数)
    chunk_overlap=128,     # 块之间的重叠量, 防止跨块信息丢失
    separators=["\n\n", "\n", ".", "!", "?", ",", " ", ""],  # 切分优先级
)

chunks = text_splitter.split_text(document)
----

==== 向量化嵌入 (Embedding)

切分后的文本块需要转换为稠密向量, 才能进行语义检索. Embedding 模型的质量直接决定检索效果.

Embedding 模型:: 将文本映射到固定维度的向量空间中, 语义相近的文本在向量空间中的距离也相近.

选择 Embedding 模型的考量因素:

. **维度:** 越高维越能捕捉细微语义差异, 但存储和检索成本也越高. 常见维度: 384(BGE-small)、768(BGE-base)、1024(text-embedding-3-small)、3072(text-embedding-3-large).

. **最大输入长度:** 模型能一次处理的 token 数, 决定了 chunk_size 的上限.

. **语言支持:** 中英双语 vs 纯英文. 中文推荐 BGE、m3e、text-embedding-3 系列.

. **领域适配:** 通用领域 vs 代码/法律/医疗等垂直领域. 垂直领域建议用领域数据微调过的 Embedding 模型.

[source,python]
----
# 使用 OpenAI Embedding API
from openai import OpenAI

client = OpenAI()
text = "RAG 检索增强生成的核心原理"

response = client.embeddings.create(
    model="text-embedding-3-small",
    input=text,
)

vector = response.data[0].embedding
print(f"向量维度: {len(vector)}")  # 输出: 1536 或 3072，取决于模型
----

==== 向量存储

向量数据库负责存储向量并支持高效的相似度检索:

Vector Database:: 专门为向量相似度搜索优化的数据库, 支持 **近似最近邻搜索(ANN)** 以极低精度损失、极高速度返回 Top-K 相似向量.

[cols="2,3,3"]
|===
| 向量数据库 | 特点 | 适用场景

| Pinecone
| 全托管 SaaS, 无需运维
| 快速原型、生产级应用

| Weaviate
| 内置混合搜索(向量+关键词)
| 需要灵活检索策略的场景

| Milvus
| 分布式高可用, 支持千亿级向量
| 大规模企业级部署

| Qdrant
| Rust 编写, 性能优异, 支持过滤
| 对性能要求高的场景

| Chroma
| 轻量级嵌入, 支持内存模式
| 开发原型、小型项目

| FAISS (Meta)
| 纯向量检索库(非数据库)
| 实验研究、离线推理

|===

WARNING: 向量数据库的 **索引类型** 和 **距离度量** 选择对检索性能影响很大. 主流距离度量: **余弦相似度**(Cosine, 最常用)、**欧氏距离**(L2)、**点积**(IP). 选择哪种取决于 Embedding 模型的训练目标.

=== 检索阶段: 找到相关信息

检索阶段的目标是: 给定用户问题, 从知识库中找到最相关的 K 个文档块. 检索质量直接决定生成质量——没有人希望模型基于无关信息生成回答.

==== 向量检索

向量检索(Vector Search) 是 RAG 最核心的检索方式. 它将用户查询转换为向量, 在向量数据库中搜索最相似的 Top-K 向量.

相似度计算:: 查询向量与库中每个向量的距离计算. 主流度量包括余弦相似度(最常用)、欧氏距离、点积.

近似最近邻(ANN):: 为加速检索, 向量数据库使用 ANN 算法牺牲微量精度换取数量级的速度提升. 核心算法包括:

* **IVF (Inverted File Index):** 先对向量空间聚类, 检索时只搜索最近的几个聚类. 召回率可控, 适合百亿级规模.

* **HNSW (Hierarchical Navigable Small World):** 构建多层级图结构, 从顶层快速定位到底层. 检索速度极快(毫秒级), 是当前最主流的 ANN 算法.

* **DiskANN:** 微软设计的基于 SSD 的图索引, 支持在内存不足以容纳全部向量时, 从磁盘读取.

[source,python]
----
# 向量检索伪代码
def vector_search(query: str, k: int = 10) -> list[Document]:
    # 1. 查询向量化
    query_vector = embedding_model.embed(query)

    # 2. 向量数据库 ANN 搜索
    results = vector_db.search(
        vector=query_vector,
        top_k=k,
        metric="cosine",       # 距离度量
        index_type="hnsw",     # 索引类型
    )

    # 3. 返回文档片段
    return [doc for doc, score in results]
----

==== 稀疏检索 (关键词检索)

密集向量检索擅长语义匹配, 但有时用户需要**精确关键词匹配**. 例如搜索"BERT 模型论文标题" 时, 关键词 "BERT" 和 "论文" 比语义相似的"预训练模型出版物" 更可靠.

稀疏检索(BM25):: 基于词频-逆文档频率(TF-IDF)的传统检索方法. 不依赖向量, 精确匹配用户关键词. 与向量检索互补.

|===
| 对比项 | 稠密检索(Dense) | 稀疏检索(Sparse/BM25)

| 匹配方式
| 语义匹配
| 精确关键词匹配

| 优点
| 理解同义词、语义近似
| 精确命中关键词, 无需训练

| 缺点
| 可能漏掉精确关键词匹配
| 无法理解同义不同词

| 适用场景
| 开放域问答、含义匹配
| 代码搜索、人名/地名/专有名词搜索

| 冷启动
| 需要 Embedding 模型
| 开箱即用

|===

==== 混合检索 (Hybrid Search)

最佳实践是将向量检索和 BM25 结合起来, 即**混合检索**:

. 向量检索: 找到语义相似的结果
. BM25 检索: 找到关键词精确匹配的结果
. 结果融合: 用 **倒数秩融合(RRF, Reciprocal Rank Fusion)** 或 **加权平均** 合并两个结果集, 生成最终排序

[source,python]
----
# 混合检索伪代码
def hybrid_search(query: str, k: int = 10) -> list[Document]:
    # 1. 稠密检索
    dense_results = vector_search(query, k=k * 2)  # 多取一些, 供融合

    # 2. 稀疏检索
    sparse_results = bm25_search(query, k=k * 2)

    # 3. RRF 融合
    # RRF 评分 = 1 / (k + rank)
    # 一个文档在两个结果集中排名越高, 最终得分越高
    combined = reciprocal_rank_fusion(
        dense_results,
        sparse_results,
        k=60  # RRF 的常数, 通常 60
    )

    # 4. 取 Top-K
    return combined[:k]
----

==== 检索后处理

检索到的结果不一定直接可用, 通常需要后续处理:

* **重排序(Re-ranking):** 使用专门的交叉编码器(Cross-encoder)模型对 Top-K 结果重新评分. 交叉编码器一次处理一对(查询, 文档), 精度远高于双编码器(Bi-encoder)的向量检索, 但速度慢, 因此只适合对 Top-K 小范围重排.

* **过滤:** 根据元数据(如日期、来源、文档类型)过滤结果. 例如"只检索 2024 年之后的文档" .

* **压缩:** 对过长的检索结果进行摘要, 保留关键信息, 减少上下文占用.

=== 生成阶段: 合成回答

生成阶段将检索到的文档块注入到 Prompt 中, 引导模型基于提供的事实生成回答.

==== Prompt 模板设计

典型的 RAG Prompt 结构如下:

[source,python]
----
prompt_template = """
你是一个基于给定文档回答问题的助手. 请严格依据以下文档内容回答问题.
如果文档中没有足够信息, 请直接说"文档中未找到相关信息", 不要自行编造.

文档内容:
{context}

用户问题: {question}

回答:
"""
----

==== 设计原则

. **明确约束:** 告诉模型"只基于给定文档回答", 禁止自行编造, 这是控制幻觉的关键.

. **来源引用:** 要求模型在回答中标注信息来源(如文档编号、章节), 增强可信度.

. **拒绝机制:** 检索文档信息不足时, 模型应主动承认不知, 而非强行回答.

. **上下文窗口管理:** 检索到的文档总长度不能超过模型的上下文窗口减去预留空间. 通常限制检索结果的总 token 数, 避免"噪声淹没信号".

==== 回答方式

根据应用场景, RAG 的回答方式可以有三种:

* **直接抽取:** 从检索到的文档中直接提取答案, 适合"事实性问题". 例如"公司的注册地址是什么?"——只需从文档中提取一句话.

* **多文档总结:** 多个文档块各包含部分答案, 需要综合归纳. 例如"公司去年的整体表现如何?"——需要综合财务数据、市场报告等多个片段.

* **多步推理:** 需要跨越多个文档进行推理, 发现文档间的关系. 例如"公司的利润率下降是否与原材料成本上升有关?"——需要关联财务报表和采购报告.

[source,python]
----
from openai import OpenAI

def rag_answer(question: str, context_docs: list[str]) -> str:
    client = OpenAI()

    # 将多个文档合并为上下文, 限制总 token 数
    context = "\n---\n".join(context_docs)

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {
                "role": "system",
                "content": (
                    "你是一个基于文档回答问题的助手. "
                    "严格依据以下文档内容回答. 文档不足时告知用户. "
                    "请用中文回答."
                ),
            },
            {
                "role": "user",
                "content": f"文档内容:\n{context}\n\n问题: {question}",
            },
        ],
        temperature=0.1,  # 低温度减少创造性, 增加事实性
    )

    return response.choices[0].message.content
----

=== 高级 RAG 技术

基础 RAG 只是"检索 + 生成"的简单组合, 在实际应用中往往不够. 业界发展出了多种高级 RAG 技术来提升系统质量.

==== Query 改写与扩展

用户的问题往往简短而不精确. 在检索之前对查询进行优化可以显著提升效果:

* **查询重写(Query Rewriting):** 用 LLM 将用户模糊的问题改写为更适合检索的形式. 例如 "它的价格是多少?" -> "iPhone 15 Pro Max 256GB 的官方售价是多少?".

* **查询分解(Query Decomposition):** 将复杂问题拆解为多个子问题, 分别检索后合并. 例如 "北京和上海哪个城市人口更多?" -> 子问题 1: "北京人口", 子问题 2: "上海人口".

* **假设性文档嵌入(HyDE, Hypothetical Document Embeddings):** 先让 LLM 基于用户问题生成一个"假设的理想答案", 然后用这个生成的答案去检索, 而不是用原始问题. 因为生成的答案在语义空间上更接近目标文档.

[source,python]
----
# HyDE 实现示意
def hyde_retrieve(question: str) -> list[Document]:
    # 1. 让 LLM 生成一个假设性答案
    hypothetical_answer = llm.generate(
        f"请回答以下问题: {question}"
    )

    # 2. 用生成的答案(而非原问题)去检索
    # 假设答案在语义上更接近真正的参考文献
    query_vector = embedding_model.embed(hypothetical_answer)
    results = vector_db.search(query_vector, top_k=10)

    return results
----

==== 多轮检索与迭代优化

单次检索可能信息不足, 多次检索可以层层深入:

* **迭代检索(Iterative Retrieval):** 先检索一批文档, 从中提取关键词或新的查询方向, 再检索第二批, 如此反复. 适合多跳推理(Multi-hop Reasoning)场景.

* **检索中反思:** 检索后, 让 LLM 判断检索结果是否足够回答. 如果不够, 生成新的检索查询继续检索. 直到 LLM 认为信息充分才开始生成回答.

* **纠正性检索(Corrective RAG):** 检索后评估文档的相关性, 对不相关的文档进行二次检索替换, 而非简单丢弃.

==== RAPTOR: 分层检索

RAPTOR 由斯坦福大学提出, 核心思想是: 对文档进行**层次化摘要**, 构建一棵"文档树". 

* 叶子节点: 原始文档块
* 中间节点: 多个文档块的摘要
* 根节点: 全文档摘要

检索时, 根据问题复杂度选择合适的层级——简单问题在叶节点检索即可, 复杂问题在中高层检索.

==== Graph RAG

Graph RAG 由微软研究院提出, 旨在解决传统 RAG 在处理**关系密集型问题**时的不足——例如 "公司的各个部门之间存在哪些协作关系?".

Graph RAG 在索引阶段先用 LLM 从文档中提取**实体**(人、组织、概念)和**关系**, 构建知识图谱. 检索时, 既检索文本块又检索相关实体和关系, 让模型获得结构化的关系上下文.

[source,text]
----
# 传统 RAG 检索结果: 文本块列表
[
  "市场部与研发部合作开发新产品",
  "研发部向生产部移交技术方案",
  "销售部从生产部获取库存信息"
]

# Graph RAG 检索结果: 文本块 + 知识图谱
实体: [市场部, 研发部, 生产部, 销售部]
关系:
  市场部 --合作--> 研发部
  研发部 --移交--> 生产部
  销售部 --获取--> 生产部
----

==== Agentic RAG

Agentic RAG 将 RAG 系统从"被动的检索-生成" 升级为"主动的信息代理". Agent 可以自主决定:

. 是否需要检索? 还是直接回答即可.
. 应该检索哪个知识源? 是向量库、SQL 数据库还是搜索引擎?
. 是否需要调用工具? 如执行代码、查询 API.
. 检索一次够不够? 是否需要多轮迭代.
. 何时开始生成最终回答?

Agentic RAG 的核心是让 LLM 具备**工具调用(Tool Calling)** 能力, 将检索视为一个可调用的工具, 结合其他工具(如计算器、代码解释器)一起使用.

=== 总结与最佳实践

RAG 已成为大模型落地应用最主流的范式, 它巧妙地结合了信息检索的**精确性**和语言模型的**生成能力**, 有效解决了大模型的知识时效性、幻觉和私有数据访问三大难题.

==== 常见误区

. **"向量检索结果一定相关"** - 向量检索是语义近似, 不是精确匹配. 检索结果中可能混入无关内容. 需要配合重排序和过滤来提高精度.

. **"一次检索就够"** - 复杂问题往往需要多轮检索或查询分解. 单次检索的信息量可能不足以回答完整问题.

. **"结果越多越好"** - 检索结果过多会引入噪声, 反而降低生成质量. 研究表明, Top-3 到 Top-5 通常是最佳数量.

. **"Embedding模型随便选"** - Embedding 模型是 RAG 的基石, 选型不当会导致检索质量全面下降. 建议在目标任务上做 Recall@K 评估后再确定.

==== 最佳实践清单

[cols="2,4"]
|===
| 环节 | 推荐实践

| 切分
| 按语义边界切分, 保留段落完整性; chunk_size 500-1000 tokens, overlap 10-20%
| 向量模型
| 选择领域适配的双语模型, 如 BGE、m3e、text-embedding-3
| 检索策略
| 采用混合检索(向量 + BM25), 再用交叉编码器重排
| 检索数量
| 向量检索 Top-50, 重排后取 Top-3 ~ Top-5
| Prompt 设计
| 明确约束"仅依据文档回答", 设计来源引用和拒绝回答机制
| 温度参数
| 事实问答用 low temperature (0.0-0.2), 创造性任务适当升高
| 评估
| 用 RAGAS、TruLens 等框架量化评估检索质量和生成质量
| 监控
| 记录检索结果和生成回答, 便于回溯分析失败案例
|===

==== 评估指标

评估 RAG 系统质量需要区分检索阶段和生成阶段:

* **检索质量:** **Recall@K**(前 K 个结果中相关文档的召回率)、**MRR**(平均倒数排名, 第一个相关结果的位置)、**NDCG@K**(考虑排序位置的归一化折损累计增益).

* **生成质量:** **忠实度(Faithfulness)**(回答是否基于检索文档, 而非编造)、**答案相关性(Answer Relevance)**(回答是否针对问题)、**上下文精度(Context Precision)**(检索结果中的噪声比例).

==== 总结

RAG 的成功实施需要在**索引**、**检索**和**生成**三个环节都做到位. 它不是一个"装上一个向量数据库就够了"的简单方案, 而是一整套系统工程——从文档切分策略、Embedding 模型选型、检索算法设计到 Prompt 模板工程, 每个环节都可能成为性能瓶颈.

随着 LLM 上下文窗口的不断扩展和 Agent 框架的成熟, RAG 正在从"检索-生成" 范式的初级阶段向 **Agentic RAG** 和 **Graph RAG** 等更智能的形态演进. 但无论技术如何演进,"在生成时提供相关上下文" 这一核心思想不会改变.
