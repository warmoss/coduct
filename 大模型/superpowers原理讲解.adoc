== superpowers原理讲解

Superpowers 是 Jesse Vincent(obra)与 Prime Radiant 团队开源的**面向 AI 编码代理的完整软件开发方法论**, 将头脑风暴, 任务规划, 测试驱动开发(TDD), 子代理执行与代码评审等实践打包为一组**可组合的技能(Skill)**, 配合一段启动引导指令, 让编码代理自动遵循规范流程, 而非直接"上手写代码". 本文系统讲解 Superpowers 的设计理念, 核心架构, 自动触发机制与标准工作流.

参考: <<大模型/skills写作指南.adoc#, skills写作指南>>, <<大模型/Agent Instructions讲解.adoc#, Agent Instructions讲解>>, <<大模型/prompt写作指南.adoc#, prompt写作指南>>, <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>

=== 什么是 Superpowers

Superpowers:: 一个基于 **Claude Code 插件机制**构建的技能集合, 当前稳定版为 6.3.0, 通过 `.claude-plugin/plugin.json` 清单声明, 将多个 `SKILL.md` 技能打包为插件分发. 它同时兼容 Codex, Cursor, Gemini CLI, GitHub Copilot CLI 等多种编码代理平台.

其核心定位不是"又一个工具库", 而是为编码代理注入一套**强制性的开发纪律**:

* **不是**提供零散的代码片段, **而是**规定"动手前先做什么"的流程约束
* **不是**让用户手动逐条调用, **而是**通过 `description` 字段让代理**自动匹配**并加载
* **不是**只解决单个任务, **而是**覆盖从需求澄清到分支收尾的完整生命周期

Superpowers 与其他配置概念的关系:

Prompt:: 用户手动触发的一次性指令, 面向特定对话任务
Skill:: 代理自动匹配的领域知识包, 是 Superpowers 的**基本组成单元**
Agent Instructions:: 始终生效的全局上下文文件, 适用于项目大多数工作
Superpowers:: 一组经过精心设计的 Skill 的**集合**, 外加启动引导指令, 构成完整方法论

=== 为什么需要 Superpowers

通用编码代理在执行开发任务时存在几个系统性缺陷, Superpowers 正是针对这些缺陷设计:

* **急于写代码** - 代理看到需求就直接产出实现, 跳过需求澄清与设计, 导致返工
* **跳过测试** - 代理倾向"先写实现再补测试", 甚至不写测试, 无法证明代码正确
* **缺少可执行计划** - 大型任务被一次性生成, 缺乏可验证的小步拆解
* **上下文污染** - 长时间对话积累的上下文使代理逐渐偏离最初方案

Superpowers 的答案是把"正确的做事方式"固化为**强制工作流**, 让代理在每一步都有章可循. 其哲学可以概括为四点:

* **Test-Driven Development** - 始终先写测试
* **Systematic over ad-hoc** - 用流程取代猜测
* **Complexity reduction** - 以简单为首要目标
* **Evidence over claims** - 先验证再宣布成功

=== 核心架构

Superpowers 的工程结构由三个层次组成:

. **插件清单** - `.claude-plugin/plugin.json` 声明插件元数据, 是插件的分发入口
. **技能库** - `skills/` 目录下每个子目录包含一个 `SKILL.md`, 是知识的最小封装单元
. **引导技能** - `using-superpowers` 技能在会话启动时注入, 确立"先查技能再行动"的总规则

[source,json]
----
{
  "name": "superpowers",
  "description": "Core skills library for Claude Code: TDD, debugging, collaboration patterns, and proven techniques",
  "version": "6.3.0",
  "author": {
    "name": "Jesse Vincent",
    "email": "jesse@fsck.com"
  },
  "license": "MIT"
}
----

每个技能文件遵循标准 Skill 结构: YAML frontmatter 声明 `name` 与 `description`, 正文使用 Markdown 描述知识说明与操作指令. 其中 `description` 是代理发现技能的唯一依据, 其写法直接决定技能能否被正确触发:

[source,yaml]
----
---
name: test-driven-development
description: Use when implementing any feature or bugfix, before writing implementation code
---
----

=== 自动触发机制

Superpowers "自动获得超能力"的特性源于引导技能 `using-superpowers` 确立的**铁律**:

IMPORTANT: **在做出任何响应或动作之前, 必须先调用相关技能**, 包括提出澄清问题, 探索代码库或查看文件之前.

这条规则由以下机制支撑:

* **强制调用** - 只要存在哪怕 1% 可能相关的技能, 代理就必须调用, 不允许以"任务太简单"等理由跳过
* **优先级排序** - 多个技能同时适用时, **流程类技能**优先(如 brainstorming, systematic-debugging), 因为流程类技能决定整体打法, 实现类技能随后执行
* **用户指令优先** - 用户直接指令(如 `CLAUDE.md`, `AGENTS.md`, 显式要求)高于技能, 技能高于默认行为

[source,text]
----
"Let's build X" -> brainstorming 优先, 然后才是实现类技能
"Fix this bug"  -> systematic-debugging 优先, 然后才是领域技能
----

=== 标准工作流

Superpowers 将一次完整的开发任务拆解为七个阶段, 每个阶段由一个技能驱动:

[plantuml, "Superpowers 标准工作流", format=png]
----
@startuml
start
:brainstorming
需求澄清与设计;
:using-git-worktrees
创建隔离工作树;
:writing-plans
拆解实施计划;
:subagent-driven-development
执行任务;
:test-driven-development
RED-GREEN-REFACTOR;
:requesting-code-review
按计划评审;
:finishing-a-development-branch
合并或收尾;
stop
@enduml
----

. **brainstorming** - 写代码前先激活, 通过提问澄清需求, 探索替代方案, 分块呈现设计供确认, 并保存设计文档
. **using-git-worktrees** - 设计确认后激活, 在新分支上创建隔离工作区, 运行项目初始化并验证测试基线干净
. **writing-plans** - 拿到已确认设计后, 将工作拆解为 2 到 5 分钟一个的原子任务; 每个任务包含精确文件路径, 完整代码与验证步骤
. **subagent-driven-development** 或 **executing-plans** - 按计划执行; 前者为每个任务派发全新子代理并做两阶段评审, 后者批量执行并设人工检查点
. **test-driven-development** - 实现过程中强制 RED-GREEN-REFACTOR 循环: 先写失败测试, 看它失败, 写最小代码, 看它通过, 提交
. **requesting-code-review** - 任务之间激活, 对照计划评审, 按严重程度上报问题; 关键问题阻断后续进度
. **finishing-a-development-branch** - 任务完成后激活, 验证测试, 提供合并, 发 PR, 保留或丢弃等收尾选项

=== 两个关键机制

==== 子代理驱动开发

`subagent-driven-development` 是 Superpowers 实现"长时自主执行"的关键: 它为每个工程任务派发一个**全新的子代理**, 并执行**两阶段评审**:

. **规格符合性评审** - 检查实现是否严格符合任务规格
. **代码质量评审** - 检查代码本身的质量

这种设计带来两个收益:

* **上下文隔离** - 每个子代理只携带当前任务所需的最小上下文, 避免长会话的上下文污染
* **可审查性** - 每一步产出都经过独立评审, 问题在提交前被发现

==== TDD 铁律

Superpowers 的 TDD 技能确立了一条**不可妥协的铁律**:

[source,text]
----
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
----

其含义是: 没有亲眼看到测试失败, 就不知道它是否测对了目标. 违反流程提前写出的代码必须**删除重写**, 不允许"留作参考"或"先写代码再补测试".

[source,text]
----
RED      -> 写一个最小失败测试, 必须亲眼看到它失败
GREEN    -> 写最少的代码让测试通过, 必须亲眼看到它通过
REFACTOR -> 保持测试全绿的前提下清理重复, 改进命名
----

=== 总结与注意事项

==== 要点归纳

* Superpowers 的本质是**用技能库加引导指令为编码代理注入开发纪律**, 而非提供现成代码
* 核心机制是 **`description` 驱动的自动触发**与**强制调用铁律**, 让用户无感地"获得超能力"
* 标准工作流遵循 **brainstorm -> plan -> TDD 实现 -> 评审 -> 收尾** 的闭环
* 支持 Claude Code, Codex, Cursor, Gemini CLI, GitHub Copilot CLI 等多种平台, 安装方式各异

==== 常见误区

* 误以为 Superpowers 是一个"代码生成器", 它不生成业务代码, 只约束**如何**写代码
* 误以为技能可以随意跳过, `using-superpowers` 明确禁止以"任务简单"等理由合理化跳过
* 误以为 TDD 是仪式而非实质, Superpowers 强调"违反规则的字面含义就是违反其精神"
* 误以为 `description` 不重要, 它是代理发现技能的唯一入口, 写得模糊技能就形同虚设

==== 最佳实践

* 先安装并让 `using-superpowers` 生效, 确保技能从会话第一条消息起就自动触发
* 允许代理在 brainstorming 阶段充分提问, 再进入 planning, 避免返工
* 严格执行 RED-GREEN-REFACTOR, 亲手确认每次测试先失败后通过
* 利用 `writing-skills` 元技能扩展团队专属流程, 使方法论随项目演进
