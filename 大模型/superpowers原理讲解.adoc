== superpowers原理讲解

大模型本质上是一个"文本生成器"——它根据输入概率性地预测下一个 token. 然而, 通过一系列**能力扩展机制**, 大模型得以突破自身局限, 获得执行真实世界任务的能力. 这些扩展能力统称为大模型的 **Superpowers(超能力)**. 本文系统讲解 Superpowers 的概念体系、核心能力维度及各机制间的协作原理.

参考: <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>, <<大模型/大模型如何做到调用工具的.adoc#, 大模型如何做到调用工具的>>, <<大模型/大模型MCP原理讲解.adoc#, 大模型MCP原理讲解>>, <<大模型/大模型RAG原理讲解.adoc#, 大模型RAG原理讲解>>, <<大模型/大模型记忆原理讲解.adoc#, 大模型记忆原理讲解>>, <<大模型/大模型工作流原理讲解.adoc#, 大模型工作流原理讲解>>

=== 什么是 Superpowers

Superpowers(超能力):: 大模型通过**外部机制获得的增强能力集合**, 使其超越"文本生成器"的原生角色, 具备感知外部世界、操作真实系统、保持持续记忆和自主决策的能力.

大模型的原生能力与 Superpowers 的对比:

[cols="2,3,3"]
|===
| 能力维度 | 原生大模型(无 Superpowers) | 具备 Superpowers 的大模型

| 信息来源
| 仅依赖训练数据(知识截止于训练时间)
| 可实时检索外部知识库、数据库和网络
| 执行能力
| 仅能输出文本
| 可调用 API、执行代码、操作文件系统
| 记忆能力
| 无状态, 每次对话独立
| 可保持跨会话记忆和上下文
| 决策能力
| 单次推理, 无流程控制
| 可编排多步工作流, 自主决策
| 行为控制
| 依赖一次性提示词
| 通过分层的指令体系精确控制行为
|===

=== 大模型 Superpowers 的五大核心能力

大模型的 Superpowers 可以归纳为五个核心维度, 每个维度对应一种能力扩展机制.

==== 感知能力: RAG 与外部知识检索

大模型的知识受限于训练数据的截止日期, 无法获取实时信息. **RAG (Retrieval Augmented Generation)** 通过检索外部知识源, 赋予模型感知实时信息的能力.

RAG 的核心流程:

. 用户提出问题
. 系统将问题转换为向量, 在知识库中检索最相关的文档片段
. 将检索到的文档片段作为上下文注入到模型输入中
. 模型基于原始问题 + 检索到的上下文生成回答

[plantuml, "RAG 赋予大模型感知能力", format=png]
----
@startuml
actor "用户" as User
rectangle "RAG 系统" as RAG {
  (嵌入模型) as Embed
  (向量数据库) as VectorDB
  (检索模块) as Retriever
}
participant "大模型" as LLM

User -> RAG: 提问
RAG -> Embed: 向量化问题
Embed -> VectorDB: 相似度检索
VectorDB --> Retriever: 返回相关文档
Retriever -> LLM: 注入检索结果作为上下文
LLM --> User: 基于实时知识的回答
@enduml
----

详细原理请参考 <<大模型/大模型RAG原理讲解.adoc#, 大模型RAG原理讲解>>.

==== 行动能力: 工具调用与 MCP

大模型无法主动执行操作——它只能输出文本. **工具调用(Tool Calling / Function Calling)** 让模型能够"驱动"外部工具完成实际操作, 而 **MCP (Model Context Protocol)** 则标准化了工具的描述、发现和调用方式.

工具调用赋予的行动能力包括:

* **查询操作** - 查询数据库、搜索网络、获取文件内容
* **写入操作** - 创建文件、发送邮件、更新数据库记录
* **计算操作** - 执行精确数学运算、运行代码
* **控制操作** - 控制系统服务、触发 CI/CD 流水线

[plantuml, "工具调用赋予大模型行动能力", format=png]
----
@startuml
participant "大模型" as LLM
participant "MCP Client" as Client
participant "MCP Server" as Server
participant "外部系统" as Ext

note over LLM: 上下文包含工具定义
LLM -> LLM: 分析意图, 决策调用工具
LLM --> Client: 输出函数调用 JSON
Client -> Server: 协议转换并转发
Server -> Ext: 执行实际操作
Ext --> Server: 返回结果
Server --> Client: 返回执行结果
Client -> LLM: 注入结果到上下文
LLM -> LLM: 基于结果生成最终回答
@enduml
----

详细原理请参考 <<大模型/大模型如何做到调用工具的.adoc#, 大模型如何做到调用工具的>> 和 <<大模型/大模型MCP原理讲解.adoc#, 大模型MCP原理讲解>>.

==== 记忆能力: 上下文管理与持久存储

大模型每次推理的上下文窗口有限, 且默认无状态. **记忆机制**让模型能够跨越单次对话的限制, 保持长期上下文.

记忆分为三个层次:

短期记忆:: 当前对话历史, 在上下文窗口中维护. 模型通过不断追加对话轮次来保持对话的连贯性. 受限于上下文窗口大小.

长期记忆:: 跨会话的持久化信息, 存储于外部系统(文件、数据库). 通过 RAG 或专门的记忆模块在需要时检索注入.

工作记忆:: 当前任务中的临时状态, 如已执行的步骤、中间结果. 通常由工作流框架管理.

[plantuml, "大模型记忆分层架构", format=png]
----
@startuml
rectangle "大模型推理" as Inference {
  (上下文窗口) as Context
}

rectangle "短期记忆" as STM {
  (当前对话轮次) as Turns
}

rectangle "长期记忆" as LTM {
  (用户偏好) as Prefs
  (项目知识) as Project
  (历史决策) as History
}

rectangle "工作记忆" as WM {
  (任务状态) as State
  (中间结果) as Temp
}

Inference --> STM: 直接访问
STM ..> LTM: 按需检索注入
Inference --> WM: 流程控制读写
@enduml
----

详细原理请参考 <<大模型/大模型记忆原理讲解.adoc#, 大模型记忆原理讲解>>.

==== 行为能力: 指令体系与行为控制

大模型的行为由其输入决定. **分层指令体系**让开发者能够精确控制模型的行为, 确保输出符合预期.

指令体系从"临时"到"永久"分为四个层次:

[cols="2,3,3"]
|===
| 层次 | 载体 | 作用范围

| 一次性指令
| Prompt (用户手动输入)
| 单次对话, 特定任务
| 全局指令
| Agent Instructions (.instructions.md / copilot-instructions.md)
| 整个项目, 始终生效
| 领域指令
| Skill (SKILL.md)
| 特定领域的任务, 按需加载
| 启动配置
| AGENT.md
| Agent 的身份、工具和行为约束
|===

这套分层体系让开发者能够:

* **精确约束** - 通过 Agent Instructions 定义项目级行为规范, 如"所有代码输出使用 TypeScript"
* **按需扩展** - 通过 Skill 为特定任务加载专业知识, 如数据库迁移、安全审查
* **灵活控制** - 通过 Prompt 在每次对话中给出临时指令, 覆盖或补充全局规则

详细原理请参考 <<大模型/prompt写作指南.adoc#, prompt写作指南>>, <<大模型/Agent Instructions讲解.adoc#, Agent Instructions讲解>>, <<大模型/skills写作指南.adoc#, skills写作指南>>, <<大模型/AGENT.md写作指南.adoc#, AGENT.md写作指南>>.

==== 协调能力: 工作流与多步编排

单次 LLM 调用只能完成一步操作. **工作流(Workflow)** 将多个 LLM 调用、工具执行和条件判断编排为完整的执行流程, 使模型能够完成复杂的多步任务.

常见的工作流模式:

链式调用(Chain):: 将任务分解为线性顺序的步骤, 前一步输出作为后一步输入. 适用于文档生成、数据处理等可自然分解的任务.

路由(Routing):: 根据输入特征选择不同的处理路径. 适用于客服分流、内容分类等需要定向处理的场景.

并行(Parallel):: 同时执行多个独立操作, 再汇总结果. 适用于多维度分析、批量处理等场景.

循环/迭代(Loop):: 反复执行某一步骤直到满足条件. 适用于代码调试、内容优化等需要迭代改进的任务.

编排(Orchestration):: 通过有向图定义步骤间的复杂依赖关系, 支持分支、循环和并行. 由 LangGraph 等框架实现, 适用于复杂业务逻辑.

[plantuml, "工作流编排模型", format=png]
----
@startuml
start
:分析用户请求;
if (需要外部信息?) then (是)
  :调用检索工具;
  if (检索成功?) then (是)
    :生成回答;
  else (否)
    :尝试备用工具;
  endif
else (否)
  :直接生成回答;
endif
:质量检查;
if (通过?) then (是)
  :输出结果;
  stop
else (否)
  :重新生成;
  detach
endif
@enduml
----

=== Superpowers 的协作机制

五大 Superpowers 并非孤立运作, 而是**协同配合**构成完整的 AI Agent 能力体系. 以一个实际场景为例:

User Prompt: "帮我查一下上周的销售数据, 对比去年同期, 然后生成一份分析报告并保存到我的文档中."

[plantuml, "Superpowers 协作示例", format=png]
----
@startuml
|工作流引擎|
:解析用户意图;
|指令体系|
:应用项目级约束\n(输出格式、文件路径);
|感知能力 - RAG|
:检索销售数据库;\n获取上周和去年同期数据;
|行动能力 - 工具调用|
:调用数据分析工具;\n计算同比变化;
:调用文件写入工具;\n保存报告到文档目录;
|记忆能力|
:保存结果到长期记忆;\n更新工作记忆状态;
|协调能力 - 工作流|
:条件判断是否成功;\n汇总结果生成报告;
:返回最终结果给用户;
@enduml
----

各能力的协作关系:

* **指令体系**为所有其他能力提供行为边界和格式约束
* **感知能力(RAG)** 为模型提供实时外部信息, 弥补知识截止的局限
* **行动能力(工具调用 + MCP)** 将模型的决策转化为真实操作
* **记忆能力**让模型保持跨步骤和跨对话的上下文连续性
* **协调能力(工作流)** 编排所有能力的调用顺序和依赖关系

=== 总结

大模型的 Superpowers 本质上是**通过外部机制扩展模型能力边界**的设计模式集合. 其核心思想可以概括为:

* **不改造模型本身** - Superpowers 不修改模型的参数或架构, 而是通过输入控制(指令)、上下文注入(RAG/记忆)、外部队列(工具调用)和工作流编排来扩展能力
* **分层解耦** - 各 Superpower 职责清晰: 感知层(RAG)解决信息获取, 行动层(工具/MCP)解决操作执行, 记忆层解决状态保持, 控制层(指令)解决行为约束, 协调层(工作流)解决流程编排
* **协同增效** - 单一 Superpower 的能力有限, 但组合使用时产生质的飞跃: 模型+RAG 得到有知识的模型, +工具得到能行动的模型, +工作流得到能自主任务的模型, +记忆得到能持续学习的模型

正是这些 Superpowers 的组合, 使得大模型从"文本生成器"进化为能够执行真实世界任务的 **AI Agent**.
