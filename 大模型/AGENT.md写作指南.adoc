== AGENT.md写作指南

AGENT.md 是 AI 编码助手中用于定义 **agent 行为和能力**的配置文件. 一个精心设计的 AGENT.md 能让 AI agent 准确理解项目上下文、遵循约定的工作流程、使用正确的工具; 而一个缺失或混乱的 AGENT.md 则可能导致 agent 行为不可控、输出质量不稳定. 本文系统讲解 AGENT.md 的设计原则、文件结构和编写方法.

参考: <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>, <<大模型/prompt写作指南.adoc#, prompt写作指南>>, <<大模型/skills写作指南.adoc#, skills写作指南>>

=== 什么是 AGENT.md

AGENT.md:: 一个放置在项目特定位置的 **agent 配置清单**, 使用 YAML frontmatter + Markdown 内容体定义 agent 在项目中的行为规则、可用工具和上下文信息. 它是 AI agent 在进入项目时的"行为守则".

AGENT.md 与 Prompt、Skill、Agent Instructions 共同构成了 AI agent 的定制化配置体系, 但各有明确分工:

* **Prompt(.prompt.md):** 用户手动触发的**一次性指令**, 面向特定对话任务
* **Skill(SKILL.md):** agent **自动匹配**的领域知识包, 按需加载
* **Agent Instructions(.instructions.md / copilot-instructions.md):** **始终生效**的全局上下文, 适用于项目中的大多数工作
* **AGENT.md:** agent 的**启动配置**, 定义 agent 的身份、可用工具、行为约束和适用场景

=== AGENT.md 的核心构成要素

一个完整的 AGENT.md 由 **YAML frontmatter**(元数据)和 **Markdown/AsciiDoc 内容体**两部分组成.

==== YAML frontmatter

文件开头的 YAML 元数据块, 用 `---` 包裹. 不同平台支持的字段有所差异, 但核心字段如下:

`name`:: (必填) agent 的名称, 用于标识该配置所属的 agent 角色. 例如: `name: code-reviewer`.

`description`:: (必填) agent 的能力描述和使用场景. 该字段是 agent 调度系统决定是否激活该配置的关键依据. 应包含触发场景关键词.

`instructions`:: (可选) 指向指令文件的路径, 或内联指令文本. agent 加载配置后会执行这些指令.

`tools`:: (可选) 允许 agent 使用的工具列表. 用于限制 agent 的能力范围, 防止其执行越权操作.

`applyTo`:: (可选) 指定该配置适用的文件模式(glob pattern). 例如 `applyTo: "src/**/*.py"` 表示仅在处理 Python 文件时生效.

`agent`:: (可选) 指定该配置对应的 agent 类型或模式. 用于多 agent 协作场景.

[source,yaml]
----
---
name: code-reviewer
description: '负责代码审查的 agent. 当用户提交 Pull Request 或要求审查代码时激活. 支持 Java, Python, TypeScript 代码审查.'
instructions: |
  作为一名资深代码审查员, 你需要在审查时重点关注:
  1. 代码安全性 - 是否存在 SQL 注入、XSS 等漏洞
  2. 性能问题 - 是否存在 N+1 查询、内存泄漏等
  3. 代码规范 - 是否遵循项目约定的编码风格
tools:
  - read_file
  - grep_search
  - vscode_listCodeUsages
applyTo: "**/*.{java,py,ts,js}"
---
----

==== 内容体

frontmatter 之后的主体内容, 使用 Markdown(默认)或 AsciiDoc 编写. 内容体定义 agent 的具体行为规则, 包括:

角色定位:: agent 的身份和职责范围. 例如: "你是一名资深的 Java 架构师".

工作流程:: agent 在激活后应遵循的操作步骤.

知识约束:: 领域特定的背景知识、技术选型约束、架构决策记录等.

输出规范:: agent 输出的格式要求、语言要求、长度限制等.

交互规则:: agent 与用户的交互方式, 如是否需要确认后再执行、是否允许修改文件等.

[source,markdown]
----
# 角色定位
你是一名资深的 Java 架构师, 专注于 Spring Boot 微服务架构.

# 工作流程
1. 收到代码审查请求后, 先分析整体架构
2. 然后逐模块检查代码质量
3. 最后输出审查报告

# 知识约束
- 项目使用 Spring Boot 3.2 + MyBatis + MySQL
- 遵循阿里巴巴 Java 开发手册
- 禁止引入额外的外部依赖

# 交互规则
- 在修改文件前必须先向用户确认
- 输出使用简体中文
----

=== AGENT.md 的放置位置

AGENT.md 可以放置在项目中的多个位置, 不同位置对应不同的作用范围和作用域:

[cols="2,1,3"]
|===
| 放置位置 | 作用范围 | 说明

| `AGENT.md` (项目根目录)
| 整个项目
| 最高优先级的 agent 配置, 对整个仓库生效

| `.github/AGENT.md`
| 整个项目
| GitHub 生态的标准位置, 与 GitHub Copilot 等工具集成

| `.agents/AGENT.md`
| 整个项目
| 部分 AI 编程工具(如 Cursor)默认读取的位置

| `.github/prompts/<name>.agent.md`
| 特定场景
| 按文件命名的 agent 配置, 支持 `applyTo` 模式匹配

| `openspec/AGENTS.md`
| OpenSpec 工作流
| OpenSpec 框架下的 agent 专属配置
|===

AGENT.md 的**优先级规则**: 越靠近项目根目录的配置优先级越高. 当多个位置的 AGENT.md 共存时, 根目录的 `AGENT.md` 会覆盖底层目录中的同名配置.

=== AGENT.md 编写核心原则

==== 描述精准, 触发明确

`description` 字段是 agent 调度系统判断是否激活该配置的关键依据. 描述应覆盖所有可能的触发场景.

* **不推荐:** `description: '代码审查 agent'`
* **推荐:** `description: '负责代码审查和质量检查. 当用户要求: 审查代码、review PR、检查代码质量、Code Review、代码走查时激活. 支持 Java, Python, TypeScript 代码审查.'`

使用 **"当...时激活"** 句式, 配合具体关键词枚举, 覆盖 agent 可能遇到的各种触发场景.

==== 职责单一, 聚焦明确

一个 AGENT.md 应只定义一个 **agent 角色的行为**. 职责混杂的配置会导致 agent 行为混乱.

* **不推荐:** 一个 AGENT.md 同时定义代码审查、数据库迁移、部署发布的规则
* **推荐:** 拆分为 `code-review.agent.md`, `db-migration.agent.md`, `deploy.agent.md` 三个独立文件

==== 工具最小化原则

`tools` 字段应只列出 agent 完成任务**必需**的工具. 过度授权的工具集可能导致 agent 执行预期之外的操作.

* **代码审查 agent:** 只给读操作工具(`read_file`, `grep_search`, `vscode_listCodeUsages`)
* **代码修改 agent:** 给予读写工具(`read_file`, `replace_string_in_file`, `create_file`)
* **部署 agent:** 给予执行工具(`run_in_terminal`, `run_vscode_command`)

==== 指令明确, 减少歧义

内容体中的指令应**清晰、具体、可执行**. 避免模糊表述.

* **不推荐:** "审查时要仔细检查代码"
* **推荐:** "审查时按以下优先级检查: (1) 安全漏洞 (2) 性能问题 (3) 可读性. 每个问题必须标注风险等级(高/中/低)."

==== 分层配置, 合理覆盖

结合不同作用范围和优先级规则, 设计分层配置策略:

* **项目级配置(根目录 AGENT.md):** 定义项目通用的 agent 行为规范, 如编码规范、技术栈约束
* **场景级配置(.github/prompts/*.agent.md):** 定义特定场景的 agent 行为, 如代码审查、重构、测试生成

=== AGENT.md 的加载与执行流程

AI agent 在启动或切换上下文时, 按照以下流程加载 AGENT.md 配置:

. **上下文感知:** agent 检测到用户进入项目或执行特定操作

. **配置发现:** agent 扫描约定位置的 AGENT.md 文件, 按优先级排序

. **匹配评估:** agent 将当前任务与每个 AGENT.md 的 `description` 和 `applyTo` 字段进行匹配

. **配置加载:** 匹配成功的 AGENT.md 被加载到 agent 的上下文窗口中

. **指令执行:** agent 依据配置中的 `instructions`, `tools` 限制和内容体规则执行任务

. **行为约束:** agent 在整个对话周期中受已加载的配置约束, 直到上下文切换或会话结束

[plantuml, "AGENT.md 加载与执行流程", format=png]
----
@startuml
actor User as U
participant "AI Agent" as A
database "项目目录" as P

U -> A: 提出任务请求
A -> P: 扫描 AGENT.md 文件
P --> A: 返回配置文件列表
A -> A: 按优先级排序并匹配任务
A -> A: 加载匹配的配置
A -> A: 应用 tools 限制
A -> A: 按照 instructions 执行任务
A --> U: 返回结果
@enduml
----

=== 常见误区与注意事项

* **description 过于宽泛:** description 必须精准描述 agent 的能力和触发场景, 否则 agent 可能在不该激活时激活, 或在该激活时不激活
* **过度授权工具:** 给予 agent 不必要的工具权限可能导致意外操作. 始终遵循"最小权限原则"
* **职责混杂:** 一个 AGENT.md 试图覆盖多个 agent 角色的行为, 导致配置臃肿且难以维护
* **忽略 applyTo 限制:** 未设置 `applyTo` 字段可能导致配置在无关文件上被加载, 浪费上下文窗口
* **与 Instructions 冲突:** AGENT.md 中的指令与 `copilot-instructions.md` 中的指令矛盾时, agent 行为不可预测. 应保持一致性
* **遗忘 YAML 语法:** frontmatter 的 YAML 语法必须严格正确. 格式错误(如缩进不一致、缺少冒号)会导致整个配置被忽略
* **忽略多平台兼容性:** 不同 AI 编程工具(VS Code Copilot, Cursor, Windsurf 等)对 AGENT.md 的支持程度和字段含义可能存在差异. 需查阅目标平台的文档

=== 总结

AGENT.md 是 **AI agent 定制化配置**的核心文件之一. 高质量的 AGENT.md 需要:

* 精准的 `description` 描述, 确保 agent 能正确匹配触发场景
* 明确的职责边界, 一个配置只定义一个 agent 角色的行为
* 最小化的工具授权, 遵循安全最佳实践
* 清晰的指令和规则, 减少 agent 行为的不可预测性
* 合理的分层配置策略, 平衡通用性和场景特定性

优秀的 AGENT.md 设计, 能够将通用的 AI agent 转化为符合项目需求的**专属智能助手**, 在与 Prompt、Skill、Agent Instructions 的协同配合下, 显著提升 AI 编码助手在特定项目中的表现和可控性.
