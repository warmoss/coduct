== 大模型如何做到调用工具的

大模型本身是一个"信息孤岛"——它的知识截止于训练数据, 且无法主动与外部世界交互. 然而, 通过**工具调用(Tool Calling / Function Calling)**机制, 大模型可以"驱动"外部工具完成自身无法完成的操作, 如查询数据库、执行代码、发送 API 请求等. 本文深入剖析大模型实现工具调用的核心原理: 模型如何学习调用工具、推理时如何决策调用哪个工具, 以及工具调用在系统层面的完整流程.

参考: <<大模型/大模型MCP原理讲解.adoc#, 大模型MCP原理讲解>>, <<大模型/大模型工作流原理讲解.adoc#, 大模型工作流原理讲解>>, <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>

=== 什么是工具调用

工具调用(Tool Calling):: 大模型的一种特殊输出模式, 模型不直接生成最终回答, 而是生成一个**结构化的函数调用请求**(通常为 JSON 格式), 指明需要调用的工具名称和参数. 外部系统(客户端框架)拦截该请求并执行实际调用, 将结果返回给模型, 由模型生成最终回复.

此能力在 OpenAI 的 API 中称为 **Function Calling**, 在 Anthropic 的 API 中称为 **Tool Use**, 在不同框架中名称各异, 但底层原理相同.

工具调用解决了大模型的三个核心局限:

* **知识固化** - 模型无法访问实时信息(天气、股价、数据库记录)
* **无执行能力** - 模型只能输出文本, 无法操作文件、发送请求或执行代码
* **精确计算** - 模型不擅长精确数学运算和确定性逻辑

=== 训练机制: 模型如何学会调用工具

模型的工具调用能力并非天生, 而是通过**有监督微调(Supervised Fine-Tuning, SFT)** 让模型学会在需要时生成函数调用格式的输出. 这个过程分为两个关键阶段.

==== 阶段一: 构造工具调用训练数据

首先需要构建大量"指令 → 函数调用"的配对数据. 每一条训练样本包含:

* **用户输入(User Input):** 可能触发工具调用的自然语言请求, 如"北京的天气怎么样?"
* **目标输出(Target Output):** 模型应该生成的函数调用 JSON, 而非最终回答

[source,json]
----
{
  "messages": [
    {"role": "system", "content": "你是一个助手, 可以使用以下工具:\n- get_weather(city: string, date?: string)"},
    {"role": "user", "content": "北京的天气怎么样?"},
    {"role": "assistant", "content": null,
     "tool_calls": [{
       "id": "call_123",
       "type": "function",
       "function": {
         "name": "get_weather",
         "arguments": "{\"city\": \"北京\"}"
       }
     }]
    }
  ]
}
----

关键点在于: 训练时, 模型不仅要学习"何时调用工具", 还要学习**调用的格式**(函数名、参数 JSON schema)和**调用的时机**(什么类型的问题应该调用什么工具).

==== 阶段二: 监督微调

将构造好的训练数据用于对预训练模型进行微调. 微调过程中的核心技术要点:

* **格式约束:** 模型需要学会输出严格符合 JSON Schema 的参数格式. 训练数据中会混入大量"函数定义 + 参数描述"的示例, 让模型理解每个参数的取值约束(如枚举值、数值范围、嵌套结构)
* **选择策略:** 训练数据中需包含**需要调用工具**和**不需要调用工具**两者的混合样本, 让模型学会区分何时该调用、何时直接回答. 例如 "什么是人工智能?" 直接回答, 而 "最新的新闻有哪些?" 则调用搜索工具
* **拒绝调用:** 某些训练样本中的用户问题超出了可用工具的能力范围, 模型应该回答"我无法完成此操作", 而不是强行调用不合适的工具

==== 模型内化: 非训练方法

除了微调, 部分模型(如较早期的 GPT-3 或未经过工具调用训练的模型)也可以通过**提示工程(Prompt Engineering)** 实现工具调用:

[source,text]
----
你是一个助手. 当你需要获取外部信息时, 请输出以下格式:
{"tool": "get_weather", "args": {"city": "北京"}}
否则直接回答.
----

但这种方法的可靠性远低于经过专门微调的模型, 因为模型的输出分布没有被针对性地调整过, 容易出现格式错误、幻觉调用或遗漏调用.

=== 推理时机制: 模型如何决定调用工具

当模型完成了工具调用的微调训练后, 推理时的行为遵循以下机制:

==== 上下文注入: 工具定义作为输入

推理时, 工具的描述作为**系统消息(System Message)** 的一部分注入到模型的输入上下文(Context Window)中. 这些描述包括工具的 name, description, 以及参数 schema(JSON Schema).

[source,json]
----
{
  "role": "system",
  "content": "可用工具:\n" +
    "[{\"type\":\"function\",\"function\":{\n" +
    "  \"name\":\"get_weather\",\n" +
    "  \"description\":\"获取指定城市的天气信息\",\n" +
    "  \"parameters\":{\n" +
    "    \"type\":\"object\",\n" +
    "    \"properties\":{\n" +
    "      \"city\":{\"type\":\"string\",\"description\":\"城市名称\"},\n" +
    "      \"date\":{\"type\":\"string\",\"description\":\"日期, 格式 YYYY-MM-DD\"}\n" +
    "    },\n" +
    "    \"required\":[\"city\"]\n" +
    "  }\n" +
    "}}]"
}
----

模型在生成回答时, 会基于以下信息做出决策:

* **工具描述:** 模型阅读每个 tool 的 name 和 description, 理解工具的功能
* **参数 Schema:** 模型理解每个参数的类型、取值范围和约束
* **用户意图:** 模型分析用户问题, 判断是否需要外部信息

==== 生成工具调用

当模型判定需要调用工具时, 它不生成文本 token(如 "让我查一下..."), 而是直接生成一个**特殊的函数调用 token 序列**. 这个序列的结构由训练阶段确定的格式决定.

以 OpenAI 的 Function Calling 为例, 模型输出的 hidden states 会以特定概率分布选择生成 `{"function": "get_weather", "arguments": {"city": "北京"}}` 这样的 JSON 字符串, 而不是自然语言回复.

客户端框架(如 OpenAI SDK、LangChain、MCP Client)会通过以下方式检测到模型输出了工具调用:

* 检测特殊标记: 某些模型会输出 `{"type": "function"}` 或 `<function_call>` 等特殊结构
* Parse 响应格式: 客户端解析模型输出的 JSON 结构, 判断是否是工具调用

==== 结果注入与二次生成

工具执行返回结果后, 该结果以 **Tool 角色消息**注入回模型的上下文:

[source,json]
----
{
  "role": "tool",
  "content": "{\"temperature\": 25, \"humidity\": 60%, \"condition\": \"晴\"}",
  "tool_call_id": "call_123"
}
----

模型基于原始用户问题 + 工具调用历史 + 工具返回结果, 进行**第二次生成**, 用自然语言组织最终回答.

[plantuml, "工具调用推理流程", format=png]
----
@startuml
participant "用户" as User
participant "模型" as LLM
participant "客户端框架" as Client
participant "外部工具" as Tool

User -> LLM: "北京的天气怎么样?"
note right of LLM: 上下文包含工具定义
LLM -> LLM: 分析意图: 需要 get_weather 工具
LLM --> Client: 输出工具调用 JSON
Client -> Tool: 执行 get_weather("北京")
Tool --> Client: {"temperature": 25, "condition": "晴"}
Client -> LLM: 注入工具结果(tool role)
LLM --> User: "北京今天 25°C, 晴"
@enduml
----

=== 工具调用的关键技术挑战

==== 幻觉调用

模型可能在不需要工具时错误地调用了工具. 例如用户问"什么是人工智能?", 模型却调用了搜索工具. 原因往往是训练数据中**调用工具的比例过高**, 导致模型产生了调用偏好.

* **解决:** 训练数据中保持合理的调用/非调用样本比例(通常 1:1 或 2:3), 并在系统提示中明确说明"仅在必要时调用工具"

==== 参数幻觉

模型可能生成工具不支持的参数, 如给一个只接受 city 参数的 `get_weather` 传了 country 参数. 这是因为模型对 JSON Schema 的理解不够精确, 或参数描述不够清晰.

* **解决:** 工具定义的 description 要详细准确, 参数 schema 要严格约束(使用 enum, min/max 等); 客户端框架对参数进行**预校验**, 拒绝不符合 schema 的调用

==== 多次工具调用

复杂任务需要连续调用多个工具, 且后续调用依赖前序结果. 例如查询一个商品的运费需要先查商品重量, 再查运费规则.

[source,json]
----
// 第一轮: 查商品重量
{"tool": "get_product_weight", "args": {"product_id": "123"}}
// 工具返回: {"weight": "2.5kg", "category": "电子产品"}
// 第二轮: 查运费规则(依赖第一轮结果)
{"tool": "calculate_shipping", "args": {"weight": "2.5", "category": "电子产品", "destination": "上海"}}
----

* **解决:** 客户端框架维护推理循环, 每次工具调用后自动将结果注入上下文, 让模型决定是继续调用还是生成最终回答; 同时设置**最大迭代次数**(如 10 次)防止无限循环

==== 并行工具调用

现代模型(如 GPT-4o, Claude 3.5+)支持在一次推理中同时调用多个独立的工具, 大幅减少延迟.

[source,json]
----
{
  "tool_calls": [
    {"id": "call_1", "function": {"name": "get_weather", "arguments": "{\"city\": \"北京\"}"}},
    {"id": "call_2", "function": {"name": "get_weather", "arguments": "{\"city\": \"上海\"}"}},
    {"id": "call_3", "function": {"name": "get_weather", "arguments": "{\"city\": \"广州\"}"}}
  ]
}
----

模型在训练阶段就已经学会了在一次输出中生成多个函数调用 token 序列. 客户端收到后, **并行执行**这些调用, 再将所有结果一起注入上下文.

=== 工具调用的完整系统流程

将上述机制整合, 一个完整的工具调用工作流如下:

[plantuml, "完整工具调用工作流", format=png]
----
@startuml
|系统初始化|
:注册工具定义;
:注入工具定义到系统消息;

|用户输入|
:用户发送请求;

|模型推理|
:模型分析用户意图;
if (需要调用工具?) then (是)
  :生成工具调用 JSON;
  |客户端框架|
  :解析工具调用;
  :校验参数合法性;
  :执行外部工具;
  |模型|
  :注入工具结果;
  :二次推理生成回答;
else (否)
  :直接生成回答;
endif

|输出|
:返回最终回复给用户;
@enduml
----

=== 主流模型的工具调用实现对比

不同模型在工具调用的实现上略有差异, 主要体现在**输出格式**和**训练方式**上:

[cols="2,3,3,3"]
|===
| 特性 | OpenAI Function Calling | Anthropic Tool Use | Google Gemini Function Calling

| 调用格式
| `tool_calls` 数组 + JSON arguments
| `tool_use` content block
| `functionCall` 部分
| 参数约束
| JSON Schema
| JSON Schema
| JSON Schema + 自动补全
| 并行调用
| 原生支持
| 原生支持
| 原生支持
| 强制调用
| `tool_choice: "required"`
| `tool_choice: {"type": "any"}`
| `function_calling_config`
| 训练方式
| SFT + RLHF
| SFT + Constitutional AI
| SFT + RLHF

|===

其中**强制调用(Forced Calling)**是一个重要特性: 当开发者指定 `tool_choice: "required"` 时, 模型**一定会调用工具**, 不会直接生成回复. 这在需要保证每次请求都触发工具的场景中非常有用, 如数据提取(Always extract entities)和内容审核(Always check with moderation tool).

=== 总结

大模型的工具调用能力从根本上扩展了模型的应用边界, 使其从纯粹的文本生成器转变为能够执行真实操作的"智能代理". 其核心原理可以归纳为:

**训练层面:** 通过有监督微调, 让模型学会在需要时生成结构化函数调用, 而非自然语言回复. 训练数据的质量(工具的覆盖度、参数描述的精确性、调用/非调用比例的平衡)直接影响工具调用的可靠性.

**推理层面:** 工具定义作为系统消息注入上下文, 模型基于此决定是否调用工具、调用哪个工具、传什么参数. 客户端框架负责执行工具并返回结果, 模型再基于结果生成最终回答.

**工程层面:** 良好的工具定义、参数校验、重试机制和推理循环控制是生产环境下工具调用稳定运行的保障.

工具调用区别于 MCP 的核心在于: 工具调用是**模型的能力**, 而 MCP 是**工具的协议**. 模型学会了怎么调用工具(MCP或其他协议定义的工具), 而 MCP 标准化了工具的描述和发现方式. 两者相辅相成, 共同构建了现代 AI Agent 的能力基础.
