== 大模型记忆原理讲解

大模型虽然在语言理解、代码生成等领域展现了惊人的能力, 但它有一个根本性的局限: **原生不具备持久记忆**. 每次对话, 模型都从零开始理解上下文——它"记得"你刚才说的话, 只是因为那些内容仍在当前上下文中, 而非真正被"记住"了. 本文系统讲解大模型的记忆机制、核心挑战以及主流的记忆增强方案.

参考: <<大模型/大模型原理讲解.adoc#, 大模型原理讲解>>, <<大模型/LangGraph原理讲解.adoc#, LangGraph原理讲解>>

=== 什么是大模型的"记忆"

在传统计算机中, 记忆是分层级的——寄存器、L1/L2缓存、RAM、磁盘, 每层容量更大但速度更慢. 大模型的记忆也存在类似的层级结构, 但机制完全不同.

大模型存在三种不同性质的"记忆":

模型参数:: 训练完成后固化在神经网络权重中的**知识记忆**. 它存储了语法规则、事实知识、推理模式等, 相当于人的长期记忆. 参数记忆是**静态的**, 训练完成后不再变化(除非微调).

上下文窗口:: 当前对话中模型能"看到"的所有 token 序列, 相当于人的**工作记忆**. 这是模型在推理时**唯一能够感知的动态信息**. 用户输入的 Prompt + 历史消息 + 模型已生成的回答, 都在这个窗口中.

KV 缓存:: **计算过程**中产生的瞬态记忆. Transformer 推理时, 每个 token 的 Key 和 Value 向量会被缓存下来, 避免重复计算已生成的 token.

[cols="2,3,3,3"]
|===
|记忆类型 |存储位置 |生命周期 |容量

|模型参数
|神经网络权重
|训练完成后固定
|百GB ~ 万亿参数

|上下文窗口
|输入序列
|单次推理会话
|几千 ~ 百万 token

|KV 缓存
|GPU 显存
|单次推理的逐 token 过程
|与序列长度线性增长
|===

WARNING: **上下文窗口 ≠ 人类记忆.** 模型"记得"前文只是因为前文仍被塞在输入窗口中, 而非因为模型将其存储到了某个记忆中. 一旦窗口滚动或对话结束, 这些信息就彻底丢失了.

=== 上下文窗口: 模型的工作记忆

上下文窗口(Context Window) 是最直观、最重要的记忆机制. 它决定了模型在单次推理中能"同时看到"多少信息.

==== 工作原理

当用户与模型对话时, 所有历史消息——包括用户的提问和模型的回答——都会被追加到输入序列中. 模型在处理下一个 token 时, 会通过自注意力机制同时关注序列中的所有 token.

[source,text]
----
用户: 我今天去了北京
模型: 北京有什么好玩的?
用户: 我去了故宫
模型: 故宫确实很壮观
# 此时 "故宫" 可以通过注意力关注到前面的 "北京"
# 但如果这个对话过长, 越过窗口边界, 前面的内容就丢失了
----

==== 核心挑战: 注意力复杂度的平方增长

Transformer 的自注意力机制的时间复杂度和空间复杂度都是 stem:[O(n^2)], 其中 stem:[n] 是序列长度. 这意味着:

* 上下文长度翻倍, 计算量变成 4 倍
* 上下文长度变成 4 倍, 计算量变成 16 倍

这使得单纯扩大上下文窗口面临严峻的算力和显存挑战.

==== Lost in the Middle 现象

即使上下文窗口足够大, 模型对窗口中不同位置的信息**关注度也不均匀**. 研究表明, 模型对开头和结尾部分的信息利用最好, 但对**中间部分的内容常常"遗忘"**——这就是 **Lost in the Middle** 现象.

[plantuml, "模型对上下文不同位置的关注度", format=png]
----
@startuml
title 模型在不同上下文位置的回答准确率
left to right direction
rectangle "窗口开头 <b>高准确率</b>" as start
rectangle "窗口中间 <b>低准确率</b>" as middle
rectangle "窗口末尾 <b>最高准确率</b>" as end
start -right-> middle : 位置后移, 准确率下降
middle -right-> end : 位置靠近末尾, 准确率回升
@enduml
----

这意味着关键信息应放在提示词的**开头或末尾**, 而非中间. 这是 Prompt Engineering 中的一个重要原则.

=== KV 缓存: 推理时的计算记忆

KV 缓存(KV Cache) 是大模型推理过程的**副产品**, 但它是理解模型效率的关键.

==== 产生原理

Transformer 解码时, 每个 token 都会经历注意力计算: 生成该 token 对应的 Query(Q), 并与之前所有 token 的 Key(K) 和 Value(V) 做注意力计算. 当生成下一个 token 时, 前一个 token 的 K 和 V 可以**复用**.

[[kv-cache-mechanism]]
[plantuml, "KV 缓存工作机制", format=png]
----
@startuml
participant "生成第1个token" as t1
participant "生成第2个token" as t2
participant "生成第3个token" as t3
database "KV Cache" as cache

t1 -> cache: 存储 K1, V1
t2 -> cache: 复用 K1, V1; 存储 K2, V2
t3 -> cache: 复用 K1, V1, K2, V2; 存储 K3, V3
@enduml
----

==== 显存占用

KV 缓存的大小 = stem:[2 \times n_{layers} \times n_{heads} \times d_{head} \times sequence\_length \times precision\_bytes]. 对于一个 70B 参数的模型, 推理时每生成一个 token 需要约几 MB 的 KV 缓存. 当上下文窗口为 128K 时, 单次推理的 KV 缓存可能占用**数十 GB 显存**.

WARNING: KV 缓存是**逐请求隔离**的. 一个用户的 KV 缓存不能给另一个用户复用. 因此在高并发场景下, KV 缓存的显存占用是部署成本的核心因素之一.

==== 优化技术

* **Multi-Query Attention (MQA):** 多个注意力头共享同一组 K 和 V, 大幅减少缓存量
* **Grouped-Query Attention (GQA):** 将多个头分组, 每组共享 K 和 V, 是 MQA 和全量注意力之间的折中
* **PagedAttention (vLLM):** 将 KV 缓存分页管理, 类似操作系统虚拟内存, 消除显存碎片
* **KV 缓存量化:** 将缓存从 FP16 压缩到 INT8 或 INT4, 减少存储量

=== 记忆增强方案

原生大模型只能依赖上下文窗口, 这远远不能满足实际应用的需求. 业界发展出了多种记忆增强方案.

==== 检索增强生成

RAG(Retrieval-Augmented Generation) 是目前最成熟的方案: 将外部知识(如文档、数据库)编码为向量存储, 在推理时检索与当前问题最相关的内容, 注入到上下文窗口中.

[[rag-architecture]]
[plantuml, "RAG 架构", format=png]
----
@startuml
actor 用户 as User
rectangle "应用层" {
  (用户查询) as Query
  (检索模块) as Retriever
  (增强 Prompt) as Augmented
}
database "向量数据库" as VectorDB
rectangle "大模型" as LLM

User -> Query: 提出
Query -> Retriever: 输入
Retriever -> VectorDB: 向量检索
VectorDB --> Retriever: 相关片段
Retriever -> Augmented: 注入上下文
Augmented -> LLM: 生成回答
LLM --> User: 输出
@enduml
----

RAG 的核心优势:

* **知识可更新** - 只需更新向量数据库, 无需重新训练模型
* **可追溯** - 可溯源回答的依据, 降低幻觉
* **无限扩展** - 向量数据库可存储远超上下文窗口的知识量

==== 长上下文模型

通过改进注意力机制和位置编码, 部分模型将上下文窗口扩展到百万 token 级别:

* **RoPE (Rotary Position Embedding):** 通过旋转变换编码位置信息, 支持一定程度的外推(extrapolation)
* **YaRN:** 改进 RoPE 的插值方法, 更高效地扩展上下文
* **Ring Attention:** 将注意力计算分布到多个 GPU 上, 突破单卡显存限制
* **ALiBi:** 使用线性偏置替代位置编码, 让模型在训练时未见过的长度上也能推理

==== 上下文压缩

当历史对话过长时, 可以通过**压缩**减少上下文占用:

* **摘要式压缩:** 定期将历史对话摘要为一段文本, 替代原始对话
* **自然语言压缩:** 用 LLM 将长文本改写为更短的版本, 保留关键信息
* **Evolving Compression:** 渐进式压缩, 越早的历史被压缩得越狠
* **激活选择(Activation Selection):** 只保留注意力分值高的 token 的 KV 缓存

==== Agent 记忆系统

在 Agent 场景(如 <<大模型/LangGraph原理讲解.adoc#, LangGraph>> 或多 Agent 系统)中, 记忆管理升维为系统级问题. 代表性方案:

[[agent-memory-hierarchy]]
[plantuml, "Agent 记忆层级", format=png]
----
@startuml
rectangle "核心记忆(Core Memory)" as Core {
  (Agent 身份定义)
  (行为约束规则)
  (不可修改)
}
rectangle "工作记忆(Working Memory)" as Work {
  (当前对话上下文)
  (正在处理的任务状态)
  (短期, 会话级)
}
rectangle "长期记忆(Long-term Memory)" as Long {
  (历史对话摘要)
  (用户偏好档案)
  (知识卡片库)
}
rectangle "外部存储(External Storage)" as Ext {
  (向量数据库)
  (文件系统)
  (API 缓存)
}

Core --> Work : 约束
Work <-> Long : 读写
Long <-> Ext : 持久化
@enduml
----

**MemGPT / Letta** 是这一方向的代表性工作. 它借鉴操作系统的虚拟内存分页思想, 将大模型的上下文窗口视为"内存", 将向量数据库视为"磁盘", 通过**分页(paging)** 机制在两者之间交换数据.

* 当上下文窗口满时, MemGPT 将早期内容**换出(evict)** 到外部存储
* 当需要回顾时, 再将相关内容**换入(swap in)** 到上下文窗口
* 通过**中断(interrupt)** 机制, 模型可以主动触发记忆管理操作

=== 工作流程: 对话中的记忆生命周期

以下展示一个典型的带记忆 agent 如何处理一次对话:

. **接收输入:** 用户发送新消息

. **载入工作记忆:** agent 将当前对话历史(来自 KV 缓存)和新消息组装为上下文

. **检索长期记忆:** agent 从向量数据库中检索与当前话题相关的历史记录, 注入上下文

. **生成回答:** LLM 根据完整上下文生成回答

. **更新记忆:** agent 将本次交互的关键信息(用户偏好、重要事实等)压缩后写入长期记忆

. **管理上下文:** 如果上下文即将超长, agent 触发记忆管理系统, 压缩或换出早期内容

[plantuml, "带记忆的 agent 对话流程", format=png]
----
@startuml
|用户|
start
:发送问题;
|Agent|
:组装上下文;
:检索长期记忆;
:注入检索结果;
:调用 LLM 生成;
:提取关键信息;
if (上下文接近上限?) then (是)
  :压缩/换出早期内容;
else (否)
endif
:写入长期记忆;
|用户|
:返回回答;
stop
@enduml
----

=== 总结

[cols="2,3"]
|===
|概念 |核心要点

|模型参数
|训练后固化的长期记忆, 可理解为"知识储备", 不可在推理时修改

|上下文窗口
|模型的工作记忆, 决定了单次推理能"看到"的信息量, 是记忆系统的瓶颈

|KV 缓存
|推理过程的计算记忆, 用显存换时间, 是部署成本的核心因素

|RAG
|通过外部向量存储扩展记忆, 成本低、可更新、可溯源, 是当前最成熟的方案

|长上下文
|通过架构创新扩大窗口, 但算力成本可观, 且 Lost in the Middle 仍是开放问题

|Agent 记忆
|借鉴 OS 虚拟内存思想, 多层级管理记忆, 是实现自主 agent 的关键基础设施
|===

大模型的记忆系统是一个从**硬件显存**到**模型架构**再到**系统设计**的多层问题. 短期看, RAG 是最实用的方案; 中长期看, 长上下文模型和 agent 记忆系统的结合将推动更强大的智能体应用. 理解不同层级的记忆机制, 是设计可靠、高效的 LLM 应用的基础.
