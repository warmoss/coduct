== Redis的bitfields原理讲解

接下来, 我们来详细讲解一下 Redis BitFields 的原理.

=== 核心概念

首先, 要理解 BitField, 我们需要把它拆解为两部分: "**Bit**" 和 "**Field**".

* **Bit:** 操作的基本单位是**位**, 而不是字节或字符串. 这意味着你可以精确地操作一个二进制位.

* **Field:** 一个"字段"指的是一段连续的位. 你可以把一个 Redis 字符串看作一个巨大的、连续的位数组(bit array), 然后在这个数组上划分出多个不同长度、不同位置的"字段".

所以, **BitField 的本质是: 将一个 Redis 字符串(String)视为一个虚拟的、紧凑的位数组, 并在这个数组上定义多个指定长度和偏移量的整数字段, 然后对这些字段进行原子性的读、写和自增操作**.

=== 底层存储: Redis 字符串

BitField 的所有操作都基于 Redis 的 String **类型**. String 在 Redis 中不仅仅是存储文本, 它本质上是**二进制安全**的, 意味着它可以存储任何字节序列.

当你对一个 Key 使用 BitField 命令时, 你实际上是在操作这个 Key 对应的 String 值. 如果这个 Key 不存在, Redis 会将其视为一个全零的、足够长的字符串来处理.

**示例:**

假设我们执行:

[source, text, linenums]
----
BITFIELD mykey SET u8 0 255
----

* mykey 对应的值现在是一个 1 字节长的字符串.

* 这个字节的所有位都被设置为 1(因为 255 的二进制是 11111111).

=== 命令语法和参数解析

BITFIELD 命令的核心语法如下:

[source, text, linenums]
----
BITFIELD key [GET type offset] [SET type offset value] [INCRBY type offset increment] [OVERFLOW WRAP|SAT|FAIL]
----
最关键的是理解 type 和 offset:

==== type - 字段类型

它定义了字段的**宽度**和**符号性**. 格式为 u 或 i 后面跟一个数字.

* u: 无符号整数.

* i: 有符号整数.

* 数字: 表示该字段占用的**位数**. 例如 u8(8位无符号整数, 0~255), i16(16位有符号整数, -32768~32767), i5(5位有符号整数, -16~15)等.

* **为什么支持任意位?** 这正体现了 "Bit" 的精髓. 你可以定义一个 3 位的字段来存储 0-7 的值, 或者一个 1 位的字段作为布尔标志, 极大地节省内存.

==== offset - 字段偏移量

它定义了字段在虚拟位数组中的**起始位置**.

* 如果 offset 是一个数字(如 0), 它表示从位数组的第 0 位开始.

* 如果 offset 带有 # 前缀(如 #1), 它表示从第几个 type 定义的字段之后开始. 这是一种更高级的用法, 用于自动对齐字段.

** 例如, BITFIELD key SET u8 #0 100 SET u8 #1 200. 第一个 u8 字段从偏移 0 开始, 第二个 u8 字段会自动从偏移 8(即第一个字段之后)开始.

=== 操作类型

. GET type offset

** **原理:** 在位数组的指定 offset 处, 读取一个长度为 type 的位序列.

** **过程:** Redis 根据偏移量找到对应的字节, 然后通过位操作(如移位、掩码)提取出指定位, 并将其解释为 type 指定类型的整数返回.

** **示例:** BITFIELD mykey GET u8 0 读取从第 0 位开始的 8 个位, 并将其解释为无符号整数.

. SET type offset value

** **原理:** 在位数组的指定 offset 处, 写入一个长度为 type 的位序列, 其值为 value.

** **过程:** Redis 首先确保字符串足够长以容纳这个字段(如果需要则扩展并用 0 填充). 然后, 它使用位操作将新的值"刻录"到指定位置, 覆盖旧的位, 而不会影响相邻的位.

** **示例:** BITFIELD mykey SET i4 8 -5 将从第 8 位开始的 4 个位设置为有符号整数 -5 的二进制补码形式.

. INCRBY type offset increment

** **原理:** 这是一个原子性的读-修改-写操作. 它先读取字段的值, 加上 increment, 然后将结果写回去.

** **关键点:** 原子性保证了在并发环境下, 这个操作是安全的, 不会出现竞态条件.

=== 溢出控制

这是 BitField 一个非常强大且精细的特性. 当 INCRBY 或 SET 操作导致字段的值超出其 type 所能表示的范围时, 就会发生溢出.

OVERFLOW 子句让你决定如何处理这种情况:

* WRAP(**默认**): 环绕模式. 使用标准的二进制回绕.

** 对于无符号数: 最大值 + 1 = 最小值. 例如, u8 的 255 + 1 = 0.

** 对于有符号数: 最大值 + 1 = 最小值. 例如, i8 的 127 + 1 = -128.

* SAT: 饱和模式. 值会被固定在类型的极值上.

** 上溢: u8 的 250 + 10 = 255.

** 下溢: i8 的 -120 - 10 = -128.

* FAIL: 失败模式. 如果会发生溢出, 则操作不执行, 命令返回 nil.

你可以在一次 BITFIELD 命令中指定 OVERFLOW 来影响后续的所有 INCRBY 操作.

=== 实际应用示例

假设我们要用一个 Redis Key `user:1000:flags` 来紧凑地存储一个用户的多个状态.

* 位 0-2: 用户等级 (0-7, 3位无符号整数)

* 位 3: 是否已验证邮箱 (1位布尔值)

* 位 4-7: 积分 (0-15, 4位无符号整数)

**初始化并设置值:**

[source, text, linenums]
----
> BITFIELD user:1000:flags SET u3 #0 5 SET u1 #1 1 SET u4 #2 10
1) (integer) 0  // 初始值
2) (integer) 0  // 初始值
3) (integer) 0  // 初始值
----

现在这个 Key 的值是一个 1 字节(8位)的字符串, 其二进制布局大致是: 1010 1 101

**读取邮箱验证状态:**

[source, text, linenums]
----
> BITFIELD user:1000:flags GET u1 3
1) (integer) 1
----

**原子性地增加积分(使用饱和溢出):**

[source, text, linenums]
----
> BITFIELD user:1000:flags OVERFLOW SAT INCRBY u4 4 5
1) (integer) 15  // 10 + 5 = 15, 没有溢出

> BITFIELD user:1000:flags OVERFLOW SAT INCRBY u4 4 1
1) (integer) 15  // 15 + 1 发生上溢, 被饱和在最大值15
----

=== 总结

[cols="1,3"]
|===
|特性|原理

|**底层存储**
|基于 Redis 字符串, 将其视为一个可动态扩展的位数组.

|**核心思想**
|在位数组上定义任意长度和位置的整数"字段".

|**类型 (type)**
|定义字段的位宽和符号性(u/i), 支持非标准位宽(如 i5, u1).

|**偏移 (offset)**
|定义字段的起始位, 支持以 # 为前缀的自动对齐.

|**原子性**
|GET/SET/INCRBY 都是原子操作, INCRBY 是读-修改-写原子操作.

|**溢出控制**
|通过 OVERFLOW 精细控制超出范围时的行为(环绕、饱和、失败).

|**优势**
|极致的内存效率(存储多个小整数)、高性能的位级原子操作.

|===
	
简单来说, **Redis BitField 就像是在 C 语言中定义一个 struct, 里面的成员是位域(bit-field), 然后 Redis 提供了对这个 struct 进行原子操作的远程命令**. 它是在分布式系统中进行紧凑数据存储和高效状态管理的强大工具.
