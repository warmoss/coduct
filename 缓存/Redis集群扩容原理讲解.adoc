== Redis集群扩容原理讲解

接下来, 我们来详细讲解一下 Redis 集群的扩容原理. 理解扩容, 就需要先理解 Redis 集群的核心数据分布机制.

=== 核心概念: 哈希槽(Hash Slot)

Redis 集群没有使用一致性哈希, 而是引入了 **哈希槽** 的概念, 这是理解所有数据分布和迁移操作的基础.

. **槽的数量:** 一个 Redis 集群固定有 **16384** (2^14) 个哈希槽.

. **数据分片:** 集群中的每个主节点负责处理一部分哈希槽.

. **数据映射:** 当客户端存储一个键值对时, 会使用 CRC16 算法对 key 进行计算, 然后对 16384 取模, 得到一个介于 0 到 16383 之间的槽位号. 公式为: slot = CRC16(key) % 16384.

. **寻址:** 客户端和服务端都知道每个槽由哪个节点负责, 从而能将命令路由到正确的节点.

**举个例子:**

一个由 3 个主节点组成的集群, 槽的分配可能是:

* 节点 A: 0 - 5500

* 节点 B: 5501 - 11000

* 节点 C: 11001 - 16383

这样, 整个 16384 个槽都被覆盖, 数据也就均匀地分布在了三个节点上.

=== 扩容的核心步骤

假设我们要从一个 3主3从 的集群扩容到 4主4从, 即新增一个主节点(我们称之为 D)和一个它的从节点.

整个扩容过程可以概括为以下几个核心步骤:

==== 步骤一: 准备新节点并加入集群

. **启动新节点:** 启动两个新的 Redis 服务实例, 并以集群模式配置, 但此时它们是独立的, 不属于任何集群.

. **加入集群:** 使用 redis-cli --cluster add-node 命令将新节点加入现有集群.

** 命令示例: redis-cli --cluster add-node <新节点D的IP:端口> <现有集群任意节点的IP:端口>

** **此时, 新节点 D 是一个空节点, 不负责任何哈希槽.** 它作为集群的一部分, 开始接收集群的配置信息, 但暂时不承担数据写入工作.

==== 步骤二: 迁移数据(重新分片 - Resharding)

这是扩容最核心、最复杂的环节. 目标是 **从现有的各个主节点中转移一部分哈希槽到新节点 D, 使得数据分布重新平衡.**

. **规划槽迁移:** 决定从原有节点(A, B, C)中分别拿出多少个槽迁移到 D. 例如, 从 A、B、C 各拿大约 1365 个槽给 D, 这样 D 最终会拥有 4096 个槽(约占 1/4), A、B、C 各剩下 4096 个槽.

. **执行迁移:**
+
使用 redis-cli --cluster reshard 命令启动重新分片过程. 你需要告诉工具:

** 集群中任意一个节点的地址.

** 要迁移的**总槽数量**(例如 4096).

** **目标节点 ID**(即新节点 D 的 ID).

** **源节点:** 是从所有现有节点中随机抽取(all), 还是指定特定的源节点.

. **迁移的微观过程(对单个 Key 而言):**
+
迁移是以槽为单位的, 但实际执行是逐个 Key 进行的. 对于要迁移的某个槽(例如 Slot 1000):

** **设置迁移状态:** 源节点(例如 A)和目标节点(D)会将 Slot 1000 标记为 "迁移中" 状态.

** **原子化迁移 Key:**

*** 对 Slot 1000 中的每一个 Key, 集群管理工具会向节点 A 发送 MIGRATE 命令.

*** MIGRATE 命令会**原子性地**将指定 Key 序列化, 然后传输到目标节点 D. 传输成功后, 节点 A 会删除本地的这个 Key.

*** 这个过程是逐个 Key 进行的, 但 MIGRATE 命令本身是原子的, 保证了同一个 Key 在迁移过程中不会存在于两个节点.

** **更新槽映射:** 当 Slot 1000 中的所有 Key 都迁移完毕后, 集群的配置信息(元数据)会被更新, **将 Slot 1000 的负责权正式从节点 A 移交到节点 D**. 这个更新会通过 Gossip 协议传播到整个集群的所有节点.

==== 步骤三: 处理客户端请求 during 迁移

在某个槽的迁移过程中, 客户端的请求是如何处理的呢? 这体现了 Redis 集群的"智能"之处.

* **情况一: 客户端访问未迁移的 Key**

** 客户端根据本地缓存的槽映射, 将请求发送到正确的节点(源节点), 一切正常.

* **情况二: 客户端访问已迁移的 Key**

** 客户端根据旧的槽映射, 将请求发送到了源节点(A).

** 节点 A 在自身数据中找不到这个 Key(因为它已经被迁移到 D 了).

** 节点 A 会检查这个 Key 所属的槽(1000)的迁移状态.

** 节点 A 会向客户端返回一个 -ASK **重定向错误**, 并告知目标节点 D 的地址.

** 客户端收到 -ASK 错误后, 会先向节点 D 发送一个 ASKING 命令(这是一个一次性的授权), 然后重新执行原来的命令.

** **注意:** 客户端在收到 -ASK 重定向后, **不会立即更新本地的槽映射缓存**. 它只是针对这一次请求进行重定向.

* **情况三: 客户端访问正在迁移的 Key**

** 如果客户端在 Key 被 MIGRATE 命令从 A 删除之前访问 A, 那么 A 仍然能处理.

** 如果客户端在 Key 被删除之后访问 A, 那么就会触发情况二中的 -ASK 重定向.

**-ASK 与 -MOVED 的区别:**

* -MOVED: 表示槽的负责权已经**永久地**转移到了另一个节点. 客户端收到后应该**更新本地槽映射缓存**, 以后所有对该槽的请求都直接发往新节点. 这通常发生在迁移完成之后.

* -ASK: 只是一个**临时性重定向**. 表示"这个请求你现在应该去那边问, 但仅此一次, 别更新你的缓存". 这发生在迁移过程中.

==== 步骤四: 添加从节点并设定主从关系

当主节点 D 的数据迁移完毕并稳定运行后, 需要为其添加一个从节点以实现高可用.

. **启动并加入从节点:** 同样使用 add-node 命令将新的从节点加入集群.

. **指定主从关系:** 使用 cluster replicate <主节点D的ID> 命令, 告诉这个新从节点它要复制的主节点是 D.

=== 总结与关键点

* **核心是槽的移动:** Redis 集群扩容的本质是 **将一部分哈希槽及其对应的数据从一个或多个现有节点迁移到新节点**.

* **在线操作:** 整个扩容过程可以在集群**不停机**的情况下进行, 服务保持可用. 客户端通过重定向机制来适应数据的移动.

* **自动化工具:** redis-cli --cluster 工具集封装了所有复杂的步骤, 使得管理员可以通过简单的命令完成扩容, 无需手动执行 MIGRATE 等底层命令.

* **数据安全与一致性:** MIGRATE 命令的原子性保证了在迁移单个 Key 时不会丢失数据. 整个迁移过程是渐进式的, 对集群性能影响可控.

* **客户端兼容性:** 需要支持集群协议的客户端(如 JedisCluster, Lettuce)才能正确处理 -MOVED 和 -ASK 重定向.

通过这种方式, Redis 集群实现了平滑、可控的水平扩展, 能够通过增加节点来线性地提升整体的数据存储容量和请求处理能力.
