== Redis的bitmaps原理讲解

=== 什么是 Bitmaps?

首先, 要明确一个核心概念: **Redis 的 Bitmaps 本身不是一种新的数据结构, 它本质上是 String 类型.** 只不过 Redis 提供了一套面向"位"的操作命令, 让你可以把 String 值当作一个巨大的"位数组"来使用.

你可以把它想象成一个非常长的、只由 0 和 1 组成的数组.

关键特点::

* **每个 Key 对应一个 Bitmap.**

* **偏移量(offset)可以看作是数组的索引, 从 0 开始.**

* **每个位(bit)的值只能是 0 或 1.**

=== 核心原理剖析

==== 底层存储: 字节数组

Redis 的 String 类型在底层是用一个称为 SDS (Simple Dynamic String) 的字节数组来存储的. 当我们操作 Bitmap 时, 实际上是在操作这个字节数组中的每一个 bit.

**存储模型:**

* Redis 会为每个 Key 分配一个字节数组.

* 当你使用 `SETBIT key offset value` 命令时, Redis 会:

. **计算偏移量 offset 所在的字节位置:** byte = offset / 8 (因为 1 byte = 8 bits)

. **计算在该字节中的位位置:** bit = (offset % 8) + 1 (注意: Redis 内部可能使用大端序或小端序, 但这对用户透明)

. **定位并修改:** 找到第 byte 个字节, 修改其第 bit 位的值为 0 或 1.

. **扩容:** 如果 offset 超出了当前字节数组的长度, Redis 会自动对字节数组进行扩容, 并将中间未设置的位全部初始化为 0.

**举个例子:**

执行 `SETBIT mybitmap 10 1`

* `offset = 10`

* `字节位置 = 10 / 8 = 1` (取整, 即第 1 个字节, 索引从 0 开始)

* `位位置 = 10 % 8 = 2` (即第 1 个字节的第 2 个 bit)

* Redis 会确保 mybitmap 的值至少有两个字节, 然后将第二个字节(索引为1)的第2位(从0或1开始计, 取决于实现)设置为 1.

==== 核心优势: 极致的空间效率

这是 Bitmap 最强大的地方. 假设你要记录用户的签到情况, 用户 ID 为 1 千万.

* **传统数据库方案:** 如果用一个 user_id 和一个 boolean 字段来存储, 每个用户至少需要几十个字节.

* **Redis String 方案:** 如果用 String 直接存 "true"/"false", 同样需要大量内存.

* **Redis Bitmap 方案:** 你只需要一个 Key, 比如 user:signin:20240515. 用户 ID 作为 offset, 签到就设为 1. 那么存储 1 千万用户只需要 10,000,000 / 8 / 1024 / 1024 ≈ 1.19 MB 的内存! 这对于统计海量数据来说是极其高效的.

=== 常用命令与示例

让我们通过一个具体的场景来理解命令: 统计用户的每日签到.

[source, bash, linenums]
----
# 用户 ID 为 1000 的用户在 2024年5月15日 签到
127.0.0.1:6379> SETBIT signin:20240515 1000 1
(integer) 0

# 用户 ID 为 15 的用户签到
127.0.0.1:6379> SETBIT signin:20240515 15 1
(integer) 0

# 检查用户 ID 1000 是否签到
127.0.0.1:6379> GETBIT signin:20240515 1000
(integer) 1

# 检查用户 ID 2000 是否签到 (未设置过, 默认是0)
127.0.0.1:6379> GETBIT signin:20240515 2000
(integer) 0

# 统计 2024年5月15日 总共有多少用户签到(计算位图中值为1的个数)
127.0.0.1:6379> BITCOUNT signin:20240515
(integer) 2

# 现在我们还有 5月16日 的签到记录
127.0.0.1:6379> SETBIT signin:20240516 1000 1
(integer) 0
127.0.0.1:6379> SETBIT signin:20240516 2000 1
(integer) 0

# 进行位运算: 找出这两天都签到的用户(逻辑与操作)
# 结果会存储到一个新的 Bitmap ‘signin:and' 中
127.0.0.1:6379> BITOP AND signin:and signin:20240515 signin:20240516
(integer) 250 # 返回结果 Bitmap 的字节数

# 查看结果, 用户1000两天都签到了
127.0.0.1:6379> GETBIT signin:and 1000
(integer) 1
# 用户15只在15号签到, 所以结果里没有他
127.0.0.1:6379> GETBIT signin:and 15
(integer) 0
# 用户2000只在16号签到, 所以结果里也没有他
127.0.0.1:6379> GETBIT signin:and 2000
(integer) 0
----

**其他重要命令:**

* **BITOP:** 支持 AND(与), OR(或), XOR(异或), NOT(非) 四种位运算, 非常适合做人群交集、并集等分析.

* **BITPOS:** 查找第一个被设置为 0 或 1 的位的位置.

=== 适用场景

* **用户签到统计:** 如上例所示.

* **用户活跃度分析:** 统计连续签到的用户(通过 BITOP AND 计算连续几天的 Bitmap).

* **判断用户是否在线:** 用一个 Bitmap 记录当前在线的用户 ID.

* **布隆过滤器 (Bloom Filter):** Bitmap 是构建布隆过滤器的基础数据结构, 用于高效地判断一个元素是否可能存在于一个集合中.

* **特征标记:** 给商品、内容等打上各种标签(如: 男性向、数码产品、100元以下), 用 Bitmap 存储每个标签下的物品 ID, 可以快速进行多标签筛选.

=== 注意事项与缺点

. **稀疏性问题:** 如果你的 offset 非常大且非常稀疏(比如, 只设置了 offset 为 1 和 10,000,000 的两个位), Bitmap 仍然会分配 10,000,000 / 8 ≈ 1.19MB 的内存. 在这种情况下, 直接使用 Set 等其他数据结构可能更节省空间.

. **偏移量限制:** offset 必须是无符号整数, 理论上最大为 2^32 - 1(约42亿), 这意味着一个 Bitmap 最多可以表示 40 多亿个位.

. **大 Key 问题:** 当 Bitmap 很大时(例如, 用于统计全中国用户的签到), 对其进行 BITCOUNT, BITOP 等操作可能会阻塞 Redis 较长时间(单线程模型), 影响其他请求. 可以考虑分片(例如, 按用户ID范围分成多个Bitmap)或在从节点上执行这些计算.

=== 总结

Redis Bitmap 的原理是 "**将 String 类型的字节数组用作位数组**". 它通过将信息压缩到 bit 级别, 实现了对海量布尔值信息的高效存储和统计. 其核心价值在于**空间效率**和**强大的位运算能力**, 使其成为大数据量下进行二元状态统计和集合运算的利器, 但在使用时需要注意其稀疏性和大 Key 可能带来的性能问题.
