== Redis的Time series原理讲解

接下来, 我们来深入浅出地讲解一下 Redis Time Series(简称 TS)的原理.

Redis Time Series 是一个专门用于处理时间序列数据的 Redis 模块. 它不是一个用 Redis 原生数据结构(如 Sorted Set 或 Hash)简单封装的上层应用, 而是一个从底层 C 语言实现的高度优化的嵌入式时序数据库.

其核心设计目标可以概括为:

* **高性能写入**

* **高效存储(压缩)**

* **快速范围查询和聚合**

下面我们从几个关键维度来解析其原理.

=== 核心数据模型

一个 Time Series 由一系列 **数据点** 组成, 每个数据点是一个二元组:

`(timestamp, value)`

* **timestamp:** 毫秒级精度的时间戳. 可以自动填充为服务器时间, 也可以由用户指定.

* **value:** 双精度浮点数.

每个时间序列还有一个唯一的 Key 和可选的 **标签集**, 标签用于对序列进行分组和过滤, 类似于 Prometheus 的维度标签.

=== 存储引擎与压缩原理(核心亮点)

这是 Redis TS 最核心、最巧妙的部分. 它没有为每个数据点都存储一个完整的键值对, 那样会带来巨大的内存开销. 相反, 它采用了 "**面向列的存储**" 思想和高效的压缩算法.

想象一下, 一个时间序列的数据在内存中是这样被组织的:

[source, text, linenums]
----
Timestamps: [t0, t1, t2, t3, t4, t5, ...]
Values:     [v0, v1, v2, v3, v4, v5, ...]
----

它实际上是**将时间戳和数值分别存储在两个独立的、动态的压缩块(Chunk)中**.

==== 时间戳的压缩 - Delta-of-Delta & RLE

时间戳通常是单调递增的. 对于等间隔采样的数据(如每秒钟采集一次的监控数据), 其时间戳的差值(Delta)是恒定的.

. **计算 Delta-of-Delta:**

** 第一个时间戳 `t0` 直接存储.

** 计算第一个差值 `d1 = t1 - t0`.

** 从第二个点开始, 计算 **二阶差值:** `d2 = (t2 - t1) - (t1 - t0)`.

. **压缩:**

** 对于等间隔数据, 这个 `Delta-of-Delta` 值 **为 0**.

** 连续出现的 0 可以使用 **游程编码(RLE)** 进行高效压缩, 即存储为 `(0, 出现次数)`.

** 即使时间戳不完全等间隔, 这些差值通常也是非常小的整数, 可以使用更少的比特位来编码(如使用可变长整数).

==== 数值的压缩 - XOR 压缩

数值的压缩同样非常高效, 基于 XOR(异或)运算.

**原理:**

* 许多监控指标(如 CPU、内存)在短时间内变化很小.

* 将当前值 stem:[v_n] 与前一个值 stem:[v_{n-1}] 进行 XOR 运算.

* 如果值没有变化, XOR 结果为 0, 可以高效压缩.

* 如果值只有很小的变化(比如浮点数的尾数部分只有最后几位不同), XOR 结果中会出现大量的前导零和后导零, 这非常适合使用一种叫 "Delta-of-Delta" 类似的编码方式来压缩这些零.

**压缩的好处:**

* **极大减少内存占用:** 相比为每个数据点存储一个 Redis Key, 内存使用量可以降低 1~2 个数量级.

* **保持数据精度:** 压缩是无损的, 解压后与原数据完全一致.

=== 内存结构与写入流程

. **最新数据块:** Redis TS 总是在内存中维护一个 **未压缩的、活动的数据块**. 新的数据点会直接追加到这个块中.

. **块满压缩:** 当这个活动数据块达到其预设大小(默认 4KB 的压缩后大小, 可通过 CHUNK_SIZE 参数调整)时, 这个块会被标记为已满.

. **创建新块:** 系统会立即创建一个新的活动数据块来接收后续的写入.

. **后台压缩:** 已满的块会被后台的压缩线程(如果启用)或在下一次需要访问它时, 使用上述算法进行压缩.

这种"一个活动块 + 多个压缩历史块"的设计, 完美平衡了 **写入速度**(直接追加到内存)和 **存储效率**(历史数据被压缩).

=== 自动过期与下采样

==== 自动过期

你可以在创建时间序列时通过 RETENTION 参数指定数据的保留期限(如 3600 秒). Redis TS 会**自动清理**超过保留期限的压缩数据块. 这比使用 Redis 的 TTL 功能更高效, 因为它是基于时间范围批量删除整个块, 而不是逐个删除数据点.

==== 下采样与聚合规则

这是面向生产环境的一个强大功能. 它允许你定义一个规则: "自动地, 将高精度的原始数据, 聚合成一个低精度的、长期保留的汇总数据".

* **例如:** `CREATE RULE "raw:temperature" AGGREGATION avg 60000 "agg:temperature:1min"`

** 这条规则的意思是: 每 60000 毫秒(1分钟), 对 raw:temperature 这个原始序列中 1 分钟内的所有数据点计算平均值(avg), 并将结果写入到 agg:temperature:1min 这个新的时间序列中.

* **工作原理:** Redis TS 内部有一个聚合器, 会根据你定义的规则, 在原始数据被压缩或过期之前, 自动执行聚合计算, 并将结果写入目标序列.

* **好处:**

** **节省空间:** 只保留长期的汇总数据, 丢弃高精度的原始数据.

** **提升查询性能:** 查询长时间范围的数据时, 直接查询下采样后的序列, 数据点更少, 速度更快.

=== 查询与聚合

Redis TS 提供了强大的查询命令, 如 `TS.RANGE` 和 `TS.MRANGE`.

* **过滤:** 可以通过标签(FILTER)来查询一组序列.

* **聚合:** 在查询时可以直接指定聚合函数(avg, sum, max, min, count 等)和桶大小(bucket duration).

** **例如:** `TS.RANGE key start end AGGREGATION avg 3600000` 会返回每小时的平均值.

** **查询时聚合的原理:** 引擎会定位到查询时间范围内的所有相关数据块(包括压缩的和活动的), 将其解压, 然后在内存中对每个"桶"内的数据点进行实时计算. 由于数据是按时间顺序存储的, 这个操作非常高效.

=== 总结: Redis Time Series 的优势

[cols="1,3,3"]
|===
|特性|原理|带来的优势

|**高性能写入**
|追加到内存中的活动数据块, 顺序 I/O.
|吞吐量极高, 适合高频数据采集.

|**高效存储**
|对时间戳和数值分别进行 Delta-of-Delta 和 XOR 压缩.
|内存占用极低, 成本效益高.

|**快速范围查询**
|数据按时间排序, 可直接定位到相关数据块; 压缩块在内存中, 解压速度快.
|毫秒级的查询响应.

|**自动过期**
|基于整个数据块进行批量删除.
|清理效率高, 无需后台扫描.

|**下采样规则**
|在数据生命周期内自动执行聚合, 生成低精度长期数据.
|实现数据降精和长期存储, 平衡成本与价值.

|**标签索引**
|为标签创建倒排索引.
|支持高效的多序列查询和分组(TS.MGET, TS.MRANGE).

|===

总而言之, Redis Time Series 的成功在于它**为时间序列数据模型量身定制了存储和压缩算法**, 而不是简单地复用 Redis 的通用数据结构. 它通过在内存中维护一个"写优化的"结构, 并对历史数据实施"高度压缩的"列式存储, 完美地解决了时间序列场景下的高写入、低存储、快查询的核心诉求.
