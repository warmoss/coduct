== Redis的geospatial原理讲解

=== 什么是 Redis Geospatial?

Redis Geospatial 是 Redis 在 3.2 版本中引入的一种数据类型, 专门用于存储和操作地理位置信息. 你可以把它想象成一个"地理位置地图", 它允许你:

* **添加位置:** 记录一个成员(如"天安门广场"、"公司")及其经纬度坐标.

* **计算距离:** 计算两个成员在地球上的距离.

* **范围查询:** 查找某个指定点指定半径内的所有成员.

* **获取经纬度:** 获取某个成员的经纬度.

其基本命令是 GEOADD, GEODIST, GEORADIUS, GEORADIUSBYMEMBER 等.

=== 核心原理: 它到底是什么?

最重要的一点是: Redis 并没有为 Geospatial 数据类型设计一个全新的底层数据结构. 它实际上是基于 Redis 的 Sorted Set(有序集合)实现的.

当你执行:

[source, bash, linenums]
----
GEOADD cities 116.405285 39.904989 "Beijing" 121.473701 31.230416 "Shanghai"
----

实际上, Redis 在底层创建(或使用)了一个 Sorted Set, 这个集合的:

* **Member(成员):** 就是你添加的地理位置名称, 如 "Beijing", "Shanghai".

* **Score(分数):** 是一个经过特殊编码的整数值. 这个整数值代表了该位置的经纬度.

这个"特殊编码"就是 Geospatial 实现的核心技术--**Geohash**.

=== 核心技术: Geohash 算法

要理解原理, 必须理解 Geohash.

==== Geohash 的目标

将二维的(纬度, 经度)坐标转换成一个一维的字符串. 这个字符串有一个重要特性: **字符串前缀匹配的两个点, 在地理位置上是相近的.**

==== Geohash 的编码过程(简化版)

我们通过一个例子来理解. 假设我们要编码 **北京的坐标 (39.904989, 116.405285)**.

===== 步骤 1: 对纬度进行编码

* 纬度范围是 [-90, 90].

* 我们进行"二分法"切割, 并给区间编号:

** 如果目标在左半区间 [-90, 0), 则编码为 0.

** 如果目标在右半区间 [0, 90], 则编码为 1.

** 注意: 为了处理边界, 通常使用 [low, high) 区间, 但原理相通.

我们来对纬度 39.904989 进行编码:

. 第一次: [-90, 90), 39.9 在右半部分 [0, 90), 编码 1. 新区间 [0, 90).

. 第二次: [0, 90), 39.9 在右半部分 [45, 90), 编码 1. 新区间 [45, 90).

. 第三次: [45, 90), 39.9 在左半部分 [45, 67.5), 编码 0. 新区间 [45, 67.5).

. 第四次: [45, 67.5), 39.9 在左半部分 [45, 56.25), 编码 0. 新区间 [45, 56.25).

. 第五次: [45, 56.25), 39.9 在左半部分 [45, 50.625), 编码 0. 新区间 [45, 50.625).

. ...(继续下去, 比如进行 15 次)

假设我们只进行 5 次, 得到的纬度编码是: 11000.

===== 步骤 2: 对经度进行编码

* 经度范围是 [-180, 180].

* 同样方法对经度 116.405285 进行编码:

. [-180, 180), 116.4 在右半部分 [0, 180), 编码 1.

. [0, 180), 116.4 在右半部分 [90, 180), 编码 1.

. [90, 180), 116.4 在右半部分 [135, 180), 编码 1.

. [135, 180), 116.4 在左半部分 [135, 157.5), 编码 0.

. [135, 157.5), 116.4 在左半部分 [135, 146.25), 编码 0.

* 得到的经度编码是: 11100.

===== 步骤 3: 合并编码

* 现在我们有纬度编码 11000 和经度编码 11100.

* **合并规则:** **按位交错合并, 奇数位放经度, 偶数位放纬度(从0开始计数).**

** 第0位(偶): 取纬度第1位 1

** 第1位(奇): 取经度第1位 1

** 第2位(偶): 取纬度第2位 1

** 第3位(奇): 取经度第2位 1

** 第4位(偶): 取纬度第3位 0

** 第5位(奇): 取经度第3位 0

** 第6位(偶): 取纬度第4位 0

** 第7位(奇): 取经度第4位 0

** ...(以此类推)

* 最终合并后的二进制串是: 11 11 00 00 -> 11110000.

===== 步骤 4: 转换为 Base32 字符串

* 将上面的二进制串 11110000 每 5 位一组进行分割.

* 11110 和 000(第二组不足5位用0补齐).

* 将 11110 转换为十进制是 30, 查 Base32 表(0-9, b-z去掉a,i,l,o), 30 对应的是 e.

* 将 00000 转换为十进制是 0, 对应的是 0.

* 所以, 北京坐标 (39.9, 116.4) 的低精度 Geohash 值就是 e0. 精度越高, 编码次数越多, Geohash 字符串越长.

最终, Redis 会将这个 Geohash 值(一个 52 位的整数, 因为 Redis 的 double 类型有 52 位有效数字)作为该成员的 Score, 存入 Sorted Set 中.

=== 基于 Geohash 和 Sorted Set 的查询原理

==== 如何实现 GEORADIUS(查询半径内的成员)?

当你要查找 (lon, lat) 半径 r 范围内的所有成员时, Redis 的底层操作如下:

. **计算查询区域的 Geohash 框:**

** 根据中心点和半径, 计算出一个大致的外接正方形区域.

** 将这个正方形区域的经纬度范围, 转换为一个 Geohash 值范围. 因为 Geohash 的"前缀匹配"特性, 处于这个正方形内的点, 它们的 Geohash 值会落在某个连续的区间内.

. **在 Sorted Set 中扫描候选集:**

** 由于 Sorted Set 的 Score 就是 Geohash 整数, 并且是有序排列的. Redis 可以非常高效地通过 ZRANGEBYSCORE 命令, 找到所有 Score 落在上一步计算出的 Geohash 值区间的成员. 这些成员就是"候选集".

. **进行精确过滤:**

** Geohash 的"框"是一个近似矩形, 并不是一个完美的圆形. 所以候选集中可能包含一些在矩形角上但不在圆形范围内的点.

** Redis 会遍历候选集中的每一个成员, 取出其原始的经纬度(Redis 在存储时会同时保存原始的经纬度, 以便进行精确计算).

** 使用Haversine公式精确计算该成员与中心点的实际球面距离.

** 如果距离小于等于指定半径 r, 则将其放入最终结果集; 否则过滤掉.

==== 为什么使用 Sorted Set?

* **高效范围查询:** Sorted Set 基于跳表实现, 按 Score(即 Geohash)排序后, 可以快速进行区间查询, 这正是 GEORADIUS 第一步所需要的.

* **复用与简洁:** Redis 团队无需开发全新的数据结构, 直接复用成熟稳定的 Sorted Set, 大大减少了开发和维护成本.

* **兼容性:** 因为你实际上拥有一个 Sorted Set, 所以你仍然可以使用 ZREM, ZRANGE, ZSCORE 等所有有序集合的命令来操作它(尽管 ZSCORE 返回的是 Geohash 整数, 对人类不友好). 这也带来了灵活性.

=== 总结与要点

[cols="2,15"]
|===
|层面|原理

|**数据结构**
|基于 Sorted Set. Member 是位置名, Score 是经纬度编码后的 52 位整数.

|**核心算法**
|Geohash. 将二维经纬度编码为一维字符串/整数, 利用其前缀匹配特性进行高效的地理邻近搜索.

|**查询过程**
|1. 粗筛: 利用 Geohash 和 Sorted Set 的范围查询, 快速找到大致在一个方形区域内的候选集. +
2. 精筛: 使用 Haversine 公式对候选集中的每个点进行精确的距离计算, 过滤出最终在圆形区域内的结果.

|**优点**
|实现简单, 复用现有数据结构. +
查询效率高, 先粗后精, 避免了全量扫描. +
非常适用于"附近的人"、"附近的店铺"这类轻量级、高并发的实时查询场景.

|**缺点**
|不是专业 GIS 数据库, 不支持复杂的地理要素(如多边形、线). +
地球模型为球体, 有计算误差, 但在大多数应用中可接受. +
当数据量极其庞大时, 半径查询的候选集可能会很大, 需要注意性能.

|===
