== Redis Streams原理讲解

Redis Streams 是 Redis 5.0 引入的一种新的数据结构, 它的核心定位是一个**持久化的、可多消费者、支持消息回溯的、高性能的消息队列**. 可以把它看作是 Redis 之前用于实现简单消息队列的 PUB/SUB、Lists 的增强版, 它解决了这些数据结构在消息持久化、可靠性投递等方面的短板.

=== 核心概念类比

为了更好地理解, 我们先把它和一个成熟的消息队列系统(如 Apache Kafka, RabbitMQ)进行类比:

|===
|Redis Streams 概念|对应 Kafka/RabbitMQ 概念|简单解释

|Stream
|Topic / Queue
|一个消息流/频道, 消息的集合.

|Entry
|Message
|一条消息, 由唯一的 ID 和多个键值对组成.

|Consumer Group
|Consumer Group
|消费者组, 组内消费者共同消费同一个 Stream, 实现负载均衡.

|Consumer
|Consumer
|组内的具体消费者.

|Last Delivered ID
|Offset
|消费者组在每个 Stream 上的消费进度.

|Pending Entries List (PEL)
|-
|已投递给消费者但尚未被确认 (ACK) 的消息列表.

|===

=== 数据结构和存储原理

==== 消息(Entry)

每个 Stream 消息由两部分组成:

* **唯一递增的 ID:** 格式为 <millisecondsTime>-<sequenceNumber>(例如 1640995200000-0). 这个 ID 基于时间戳和序列号生成, 保证了严格递增和有序性. 客户端可以自定义, 但必须大于上一个 ID.

* **内容:** 一个或多个键值对(类似于 Hash), 用于存储实际的数据(例如 `{"name": "Alice", "action": "login"}`).

==== 底层结构: Radix Tree (基数树)

这是 Redis Streams 高性能的关键. Stream 的底层实现是一个叫做 **Radix Tree** 的数据结构.

* **是什么?** 一种压缩的前缀树, 特别适合存储具有公共前缀的键.

* **为什么用它?**

** **高效存储:** 由于消息 ID 是连续递增的, 它们的前缀(时间戳部分)通常相同, Radix Tree 可以极大地压缩存储空间.

** **快速范围查询:** 对于 XRANGE、XREAD 这类需要按 ID 范围查找的操作, Radix Tree 提供了非常高的性能, 时间复杂度近似 O(log(N)).

可以把 Stream 想象成一个**只追加的日志文件**, 所有新消息都追加到末尾, 而 Radix Tree 是这个日志的高效索引.

=== 核心工作机制

==== 生产者发布消息

使用 XADD 命令向指定 Stream 追加一条新消息.

[source, bash]
----
XADD mystream * sensor-id 1234 temperature 19.8
----

`*` 表示让 Redis 自动生成一个唯一 ID.

==== 消费者读取消息

有两种主要模式:

===== 独立消费者模式 (XREAD)

* 类似于 LRANGE, 但更强大.

* 可以**阻塞等待**新消息 (BLOCK 选项).

* 可以从一个给定的 ID 开始读取, $ 表示只读取新消息.

[source, bash]
----
# 非阻塞读取, 从ID 0开始, 最多读2条
XREAD COUNT 2 STREAMS mystream 0

# 阻塞读取, 等待新消息, 超时时间3000毫秒
XREAD BLOCK 3000 STREAMS mystream $
----

===== 消费者组模式 (XREADGROUP)

这是 Streams 最强大的功能, 实现了**竞争消费**和**消息可靠性**.

**创建消费者组:**

[source, bash]
----
XGROUP CREATE mystream mygroup 0
# 从Stream头部开始消费
# 使用 `$` 表示只消费新消息
----

**组内消费者读取消息:**

[source, bash]
----
# 属于 mygroup 组的 consumer1 从 mystream 读取消息, 不确认, 最多读1条
XREADGROUP GROUP mygroup consumer1 COUNT 1 STREAMS mystream >
----

`>` 这个特殊的 ID 表示"读取尚未分配给其他消费者的新消息".

==== 消费者组的工作原理(核心中的核心)

. **负载均衡:** 当一个 Stream 有多个消费者时, 消息会**平均分配**给组内的不同消费者, 而不是每个消费者都收到全量消息. 这实现了"竞争消费", 保证了处理能力的水平扩展.

. **消息确认 (ACK):** 消费者处理完一条消息后, 必须向 Redis 发送一个确认 (XACK).
+
[source, bash]
----
XACK mystream mygroup 1640995200000-0
----

. **待处理消息列表 (Pending Entries List, PEL):**

** 消息被投递给消费者后, 在消费者确认之前, 会进入这个消费者的 PEL.

** PEL 记录了"哪些消息被谁拿走了但还没确认".

. **故障转移与重投:**

** 如果一个消费者崩溃了, 它 PEL 中的消息会一直处于"待确认"状态.

** 经过一段时间后, 这些消息可以被自动或手动重新投递给组内的其他健康消费者进行处理, 从而保证了"At Least Once"(至少一次)的交付语义, 避免了消息丢失.

. **消费进度 (Last Delivered ID):**

** 消费者组会为每个 Stream 维护一个 Last Delivered ID, 类似于 Kafka 的 Offset. 这个 ID 标记了组整体消费到了哪个位置. 即使所有消费者都重启, 也能从这个 ID 之后继续消费.

=== 消息ID与裁剪

==== ID 生成规则

<ms>-<seq> 的格式确保了:

* 在同一毫秒内, 可以生成多个序列号, 避免冲突.

* ID 是全局有序的, 可以用于排序和范围查询.

==== Stream 的裁剪

Stream 是只追加的, 如果不加控制, 会无限增长. Redis 提供了两种裁剪策略:

* 定长裁剪 (XTRIM): 只保留最近 N 条消息.
+
[source, bash]
----
XTRIM mystream MAXLEN 1000
----

* 近似定长裁剪: 为了性能, 可以使用 ~ 进行近似裁剪, Redis 会找一个更高效的时间点进行裁剪.
+
[source, bash]
----
XTRIM mystream MAXLEN ~ 1000
----

* 在 XADD 时指定最大长度:
+
[source, bash]
----
XADD mystream MAXLEN ~ 1000 * ...
----

=== 总结: 优点与适用场景

优点::

* **高性能:** 基于内存和 Radix Tree, 读写速度极快.

* **数据持久化:** 消息会保存在 RDB 和 AOF 中, 不像 PUB/SUB 那样重启就丢失.

* **强大的消费者组:** 支持负载均衡、消息确认和重试, 实现了可靠的消息队列.

* **消息回溯:** 可以随意读取任意历史消息, 而 Lists 弹出后即消失.

* **轻量级:** 如果你已经在使用 Redis, 引入 Streams 无需额外的基础设施和运维成本.

适用场景::

* **实时消息流:** 聊天室、直播评论、弹幕.

* **事件溯源:** 记录用户操作、系统状态变更的事件日志.

* **数据采集与监控:** 收集传感器数据、应用日志, 供多个后端服务消费.

* **异步任务队列:** 替代 Celery + RabbitMQ/Kombu 的轻量级方案.

不适用场景::

* 需要复杂的路由规则(如 RabbitMQ 的 Exchange).

* 消息体非常大或需要磁盘级海量存储(应使用 Kafka).

* 对消息顺序有绝对严格要求, 且不能容忍任何因网络分区或主从切换可能带来的极小概率顺序问题(在分布式系统中, 这是一个普遍挑战, 而非 Streams 独有).
