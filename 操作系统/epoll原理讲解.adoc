== epoll原理讲解

epoll 是 Linux I/O 的一种多路复用机制.

=== 为什么需要 epoll? —— 从 select/poll 的瓶颈说起
在 epoll 出现之前, 我们主要使用 select 和 poll 来处理大量的网络连接. 但它们都有一个共同的性能瓶颈:

* **线性扫描:** 每次调用 select/poll 时, 都需要将整个要监视的文件描述符集合从**用户态**拷贝到**内核态**.

* **线性遍历:** 内核需要**线性遍历**整个集合, 检查每个 fd 是否有事件就绪. 当连接数很多(比如成千上万), 但活跃连接很少时, 这种遍历方式效率极低, 时间复杂度为 O(n).

epoll 的设计目标就是为了解决这个瓶颈, 它只关心那些"活跃"的连接, 因此在高并发、低活跃的场景下, 性能优势极其明显.

=== epoll 的核心思想与三个关键系统调用
epoll 的核心思想是: "**当我不需要的时候, 你别通知我; 只有当我想知道的事情发生时, 你再告诉我.**" 它通过三个系统调用实现.

==== epoll_create - 创建一个 epoll 实例

[source, c, linenums]
----
int epoll_create(int size); // 旧版本, size 是建议值, 现在已忽略
int epoll_create1(int flags); // 新版本, flags 可设置为 0 或 EPOLL_CLOEXEC
----

这个调用会创建一个 epoll 实例, 在内核中会初始化一个核心数据结构, 并返回一个指向该实例的文件描述符(epfd). 这个实例将成为后续所有操作的中心.

**内核数据结构:**

* **红黑树 (Red-Black Tree):** 用于存储所有通过 epoll_ctl 添加进来的、需要被监视的文件描述符. 红黑树的作用是高效地管理和查找 fd, 其插入、删除、查找的时间复杂度都是 O(log n).

* **就绪链表 (Ready List):** 一个双向链表, 用于存放那些已经就绪(有事件发生)的 fd.

==== epoll_ctl - 管理 epoll 实例中的 fd

[source, c, linenums]
----
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
----

这个调用用于向 epoll 实例(epfd)中添加、修改或删除要监视的 fd.

* op: 操作类型:

** EPOLL_CTL_ADD: 添加一个 fd 到监视列表(添加到红黑树).

** EPOLL_CTL_MOD: 修改一个已监视 fd 的监听事件.

** EPOLL_CTL_DEL: 从监视列表中删除一个 fd(从红黑树中移除).

* fd: 要操作的目标文件描述符(如 socket).

** event: 告诉 epoll 关心这个 fd 的什么事件(如可读 EPOLLIN、可写 EPOLLOUT 等), 以及一个用户数据 data(通常用来存储与连接相关的信息, 如指针).

**关键点:** 所有需要监视的 fd 都只在 epoll_ctl 阶段被**一次性**地加入到内核的红黑树中. 这避免了 select/poll 中每次调用都要传递整个 fd 集合的巨大开销.

==== epoll_wait - 等待事件发生

[source, c, linenums]
----
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
----

这是程序阻塞和等待的地方.

* epfd: epoll 实例.

* events: 一个由**用户预先分配好内存**的数组, epoll_wait 会把就绪的事件填充到这个数组中.

* maxevents: 告诉内核这个 events 数组最多能接收多少个事件, 不能大于数组大小.

* timeout: 超时时间(毫秒), -1 表示阻塞等待, 0 表示立即返回.

**工作流程:**

. 程序调用 epoll_wait 并进入阻塞(或超时阻塞)状态.

. 当被监视的 fd 上有事件发生时(例如 socket 收到数据), 内核的网络协议栈会回调一个函数, 将这个 fd **添加到就绪链表**中.

. epoll_wait 被唤醒, 它**不再需要扫描所有** fd, 而是直接查看就绪链表是否为空.

. 如果链表不为空, epoll_wait 就将就绪链表中的事件拷贝到用户提供的 events 数组中, 并返回就绪事件的数量.

. 应用程序只需要**线性处理**这个 events 数组(0 到 return_value - 1)即可, 这里全都是已经就绪的连接, 效率极高.

=== epoll 的底层关键技术

==== 回调机制 (Callback)
这是 epoll 高效的核心. 内核为每个被监视的 fd 设置一个回调函数(ep_poll_callback). 当该 fd 上有事件发生时(例如数据到达), 设备驱动或协议栈就会调用这个回调函数. 这个函数的工作很简单: **将对应的 fd 加入到就绪链表中**.

这避免了 select/poll 中 O(n) 的遍历过程, 将事件检测的复杂度从 fd 总数降到了**活跃 fd 数**.

==== 红黑树 (Red-Black Tree)
红黑树用于管理所有被监视的 fd, 它保证了:

* **高效的增删改查 (O(log n)):** 这对于需要动态管理大量连接的服务器至关重要.

==== 就绪链表 (Ready List)
一个简单的双向链表, 用于临时存放"已就绪"的事件. 当 epoll_wait 被调用时, 内核将链表内容拷贝给用户, 然后清空链表, 为下一次事件通知做准备.

=== epoll 的工作模式
epoll 提供了两种工作模式, 在 epoll_ctl 的 event.events 中设置.

==== 水平触发 (Level-Triggered, LT) - 默认模式
**特点:** 只要 fd 对应的读/写缓冲区处于"就绪"状态(非空/非满), epoll_wait 就会一直通知你.

**例子:**

* 假设 socket 接收缓冲区有 2KB 数据.

* 调用 epoll_wait, 它会通知你 fd 可读.

* 你只读了 1KB 数据.

* 再次调用 epoll_wait, 它**依然会通知你**这个 fd 可读, 因为缓冲区里还有 1KB 数据.

**优点:** 编程更简单, 可以分多次处理数据, 不容易发生事件丢失.

**缺点:** 可能会导致不必要的重复通知, 如果程序员不处理, 会频繁唤醒 epoll_wait.

==== 边缘触发 (Edge-Triggered, ET)
**特点:** 只在 fd 状态**发生变化时**才通知一次. 比如, 缓冲区从空变为非空(有数据新到来).

**例子:**

* 假设 socket 接收缓冲区由空变为有 2KB 数据.

* 调用 epoll_wait, 它会通知你 fd 可读.

* 你只读了 1KB 数据.

* 再次调用 epoll_wait, 它**不会通知你**, 因为状态没有发生新的变化(缓冲区从空变非空只有一次).

**使用 ET 模式的必要要求:**

. 必须使用**非阻塞 (non-blocking)** 的 fd.

. 必须一直读/写, 直到返回 EAGAIN 或 EWOULDBLOCK 错误(表示本次通知的数据已全部读完/写完).

**优点:** 减少了 epoll_wait 被重复唤醒的次数, 性能更高.
缺点: 编程更复杂, 如果一次没处理完, 就可能永远丢失这次事件.

=== 总结: epoll 的高效性体现在哪里?
. **避免了重复的拷贝:** 通过 epoll_ctl 一次性注册 fd, 而不是每次调用都传递整个集合.

. **避免了重复的遍历:** 通过回调机制, 内核只将活跃的 fd 加入就绪列表, 使得 epoll_wait 的返回复杂度是 O(1)(相对于就绪事件数).

. **高效的内核数据结构:** 使用红黑树管理海量 fd, 保证了增删改查的效率.

. **用户态与内核态的高效交互:** epoll_wait 返回的已经是就绪的事件, 应用程序可以直接处理, 无需再次判断.

因此, 在需要管理数万甚至数十万并发连接的场景下(如 Web 服务器、即时通讯服务器), epoll 成为了 Linux 平台上无可替代的高性能网络编程核心.
