== socket状态讲解

TCP socket 是网络通信的核心抽象. 一次 TCP 连接从建立到关闭, 会经历一系列可观测的中间状态, 这些状态统称为 **socket 状态**. 理解这些状态, 是排查网络故障、定位连接泄漏和优化服务器性能的基础.

=== 为什么需要理解 socket 状态

* **定位连接异常:** 当连接无法建立或无法关闭时, socket 状态直接揭示流程卡在哪一步.

* **发现资源泄漏:** `CLOSE_WAIT` 大量堆积通常意味着应用没有正确关闭连接, `TIME_WAIT` 过多则反映存在大量短连接.

* **防御攻击:** `SYN_RECV` 状态堆积往往是 SYN Flood 攻击的典型特征.

=== 核心概念

socket::
  操作系统提供的网络编程端点, 由 IP 地址和端口号标识. 一条 TCP 连接由四元组 (源 IP, 源端口, 目的 IP, 目的端口) 唯一确定.

TCP 状态机::
  描述 TCP 连接在生命周期内各阶段之间转换规则的有限状态机. 状态转换由协议事件 (报文到达) 和应用调用共同驱动.

MSL::
  Maximum Segment Lifetime, 报文段在网络中存活的最长时间. Linux 默认 30 秒, 2MSL 即 60 秒.

=== TCP 连接状态总览

TCP 共定义 11 种连接状态, 汇总如下:

[cols="2,5,3"]
|===
| 状态 | 含义 | 典型位置

| LISTEN | 监听端口, 等待连接请求 | 服务端
| SYN_SENT | 已发送 SYN, 等待对端确认 | 客户端
| SYN_RECV | 已收到 SYN 并回复 SYN+ACK, 等待对端 ACK | 服务端
| ESTABLISHED | 连接建立, 可双向传输数据 | 双方
| FIN_WAIT_1 | 主动关闭方已发送 FIN, 等待 ACK 或对方 FIN | 主动关闭方
| FIN_WAIT_2 | 已收到对端 ACK, 等待对端发送 FIN | 主动关闭方
| CLOSE_WAIT | 已收到对端 FIN 并回复 ACK, 等待本地应用关闭 | 被动关闭方
| CLOSING | 双方同时关闭, 收到对端 FIN 但 ACK 未被确认 | 双方 (罕见)
| LAST_ACK | 被动关闭方已发送 FIN, 等待最后 ACK | 被动关闭方
| TIME_WAIT | 主动关闭方已回复最后 ACK, 等待 2MSL | 主动关闭方
| CLOSED | 连接完全关闭 | 不可见
|===

=== 三次握手与状态流转

客户端与服务端通过三次握手建立连接, 双方状态依次变化:

[plantuml,"TCP 三次握手与状态流转",format=png]
----
@startuml
participant "客户端" as C
participant "服务端" as S

C -> S : ① SYN=1, seq=x\n(CLOSED → SYN_SENT)
S -> C : ② SYN=1, ACK=1, seq=y, ack=x+1\n(LISTEN → SYN_RECV)
C -> S : ③ ACK=1, seq=x+1, ack=y+1\n(双方 → ESTABLISHED)
@enduml
----

. 客户端调用 `connect()`, 发送 SYN 报文, 自身从 CLOSED 进入 **SYN_SENT**.

. 服务端收到 SYN 后回复 SYN+ACK, 自身从 LISTEN 进入 **SYN_RECV**.

. 客户端收到 SYN+ACK 后回复 ACK, 进入 **ESTABLISHED**; 服务端收到 ACK 后也进入 **ESTABLISHED**.

NOTE: 握手只需三个报文段, 因为服务端把 SYN 与 ACK 合并为同一个报文发送.

=== 四次挥手与状态流转

连接关闭时双方状态变化更复杂, 需要四个报文段:

[plantuml,"TCP 四次挥手与状态流转",format=png]
----
@startuml
participant "主动方 A" as A
participant "被动方 B" as B

A -> B : ① FIN=1, seq=u\n(ESTABLISHED → FIN_WAIT_1)
B -> A : ② ACK=1, ack=u+1\n(ESTABLISHED → CLOSE_WAIT)
note right of A : A → FIN_WAIT_2
B -> A : ③ FIN=1, seq=w\n(CLOSE_WAIT → LAST_ACK)
A -> B : ④ ACK=1, ack=w+1\n(FIN_WAIT_2 → TIME_WAIT)
note right of B : B 收到 ACK 后 → CLOSED
note right of A : A 等待 2MSL 后 → CLOSED
@enduml
----

. 主动方 A 调用 `close()` 发送 FIN, 进入 **FIN_WAIT_1**.

. 被动方 B 收到 FIN 后回复 ACK, 进入 **CLOSE_WAIT**; A 收到 ACK 后进入 **FIN_WAIT_2**.

. B 的应用随后调用 `close()`, 发送 FIN, 进入 **LAST_ACK**.

. A 收到 FIN 后回复最后 ACK, 进入 **TIME_WAIT**; B 收到 ACK 后进入 **CLOSED**.

IMPORTANT: 被动方 B 必须依赖上层应用调用 `close()` 才会发出 FIN, 这正是 `CLOSE_WAIT` 容易长时间停留的原因.

=== 完整状态机

将握手与挥手合并, 得到完整的 TCP 连接状态机:

[plantuml,"TCP 连接完整状态机",format=png]
----
@startuml
hide empty description
[*] --> CLOSED : 初始状态
CLOSED --> LISTEN : 被动打开\nbind()+listen()
CLOSED --> SYN_SENT : 主动打开\nconnect()
LISTEN --> SYN_RECV : 收到 SYN\n回 SYN+ACK
SYN_SENT --> ESTABLISHED : 收到 SYN+ACK\n回 ACK
SYN_RECV --> ESTABLISHED : 收到 ACK
SYN_SENT --> SYN_RECV : 同时打开\n收到 SYN
SYN_RECV --> SYN_SENT : 同时打开\n收到 SYN
ESTABLISHED --> FIN_WAIT_1 : 主动关闭\nclose() 发 FIN
ESTABLISHED --> CLOSE_WAIT : 收到 FIN\n回 ACK
FIN_WAIT_1 --> FIN_WAIT_2 : 收到 ACK
FIN_WAIT_1 --> CLOSING : 收到 FIN\n回 ACK
FIN_WAIT_1 --> TIME_WAIT : 收到 FIN+ACK\n回 ACK
FIN_WAIT_2 --> TIME_WAIT : 收到 FIN\n回 ACK
CLOSING --> TIME_WAIT : 收到 ACK
CLOSE_WAIT --> LAST_ACK : 应用 close()\n发 FIN
LAST_ACK --> CLOSED : 收到 ACK
TIME_WAIT --> CLOSED : 等待 2MSL 超时
@enduml
----

=== 关键状态详解

LISTEN::
  服务端调用 `listen()` 后进入的状态. 表示套接字正在监听端口, 等待连接请求. 此时内核已分配半连接队列 (SYN 队列) 和全连接队列 (accept 队列).

SYN_SENT::
  客户端调用 `connect()` 后立即进入的状态. 表示已发送 SYN, 等待服务端确认. 若对端不可达, 连接会在此状态按 `tcp_syn_retries` 重试后超时.

SYN_RECV::
  服务端收到 SYN 并回复 SYN+ACK 后进入的状态. 连接处于半连接状态, 尚未完成三次握手. 大量 SYN_RECV 堆积通常意味着 SYN Flood 攻击或 accept 队列已满.

ESTABLISHED::
  三次握手完成后双方进入的稳定状态. 数据可双向可靠传输, 是连接生命周期中最长的阶段.

FIN_WAIT_1::
  主动关闭方调用 `close()` 发送 FIN 后进入的状态. 等待对端 ACK, 或对端同时发来的 FIN.

FIN_WAIT_2::
  主动关闭方收到对端 ACK 后进入的状态. 本端已不再发送数据, 但仍在等待对端发送 FIN. 若对端一直不关闭, 会在此状态停留, 直到 `tcp_fin_timeout` 超时 (默认 60 秒).

CLOSE_WAIT::
  被动关闭方收到 FIN 并回复 ACK 后进入的状态. 对端已关闭, 但本地应用尚未调用 `close()`. 此状态大量堆积说明应用存在遗漏关闭套接字的 bug.

CLOSING::
  双方同时发送 FIN 时出现的罕见状态. 表示已收到对端 FIN, 但自己的 ACK 尚未被对端确认.

LAST_ACK::
  被动关闭方调用 `close()` 发送 FIN 后进入的状态. 等待对端最后 ACK, 收到后立即进入 CLOSED.

TIME_WAIT::
  主动关闭方收到对端 FIN 并回复 ACK 后进入的状态. 需等待 2MSL 后进入 CLOSED, 详见 <<#time-wait, TIME_WAIT 深入分析>>.

CLOSED::
  连接的最终状态, 表示连接已完全关闭, 套接字不再存在, 也无法被观测到.

=== 如何查看 socket 状态

使用 `ss` (推荐) 或 `netstat` 查看当前系统连接状态:

[source,shell]
----
ss -tan                                         # 查看所有 TCP 连接及状态
ss -tan | awk '{print $1}' | sort | uniq -c     # 按状态统计数量
netstat -tan                                    # 传统方式, 功能等价
----

[source,text]
----
State      Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN     0      128    0.0.0.0:8080        0.0.0.0:*
ESTAB      0      0      192.168.1.5:8080    192.168.1.10:53421
TIME-WAIT  0      0      192.168.1.5:8080    192.168.1.20:43210
----

TIP: `ss` 输出中的 `ESTAB` 即 `ESTABLISHED`, `TIME-WAIT` 即 `TIME_WAIT`, 只是缩写形式不同.

=== TIME_WAIT 深入分析

[[time-wait]]
==== 为什么必须等待 2MSL

主动关闭方在发送最后一个 ACK 后进入 TIME_WAIT, 等待时长为:

stem:[T_(TIME_WAIT) = 2 xx MSL]

其中 MSL 默认 30 秒, 因此 Linux 上 TIME_WAIT 默认为 60 秒. 原因有二:

. **确保最后 ACK 可靠送达:** 若最后的 ACK 丢失, 对端会重发 FIN. TIME_WAIT 期间本端仍可重发 ACK, 保证连接可靠终止.

. **让旧报文从网络中消亡:** 等待 2MSL 可确保本连接产生的旧报文段都已从网络中消失, 避免其影响复用同一四元组的新连接.

==== TIME_WAIT 的影响

* **占用端口资源:** 服务器端大量 TIME_WAIT 会消耗连接四元组, 客户端则可能耗尽本地临时端口.

* **占用内存:** 每个 TIME_WAIT 连接占用的内核结构体很小 (约百余字节), 但数量巨大时仍不可忽视.

==== 优化手段

[source,shell]
----
# 允许复用处于 TIME_WAIT 的 socket 发起新连接 (仅对主动连接方有效)
sysctl -w net.ipv4.tcp_tw_reuse=1

# 限制系统 TIME_WAIT 连接总数, 超出后新关闭的连接会被直接释放
sysctl -w net.ipv4.tcp_max_tw_buckets=262144

# 查看当前相关设置
sysctl net.ipv4.tcp_fin_timeout net.ipv4.tcp_tw_reuse net.ipv4.tcp_max_tw_buckets
----

WARNING: `tcp_tw_recycle` 参数曾在旧版本用于快速回收 TIME_WAIT, 但在 NAT 环境下会导致连接异常, 已在 Linux 4.12 中移除. 不要再使用该参数.

=== 常见问题与排查

[cols="3,3,4"]
|===
| 异常现象 | 常见原因 | 排查方向

| CLOSE_WAIT 堆积 | 应用未调用 close() | 检查代码是否遗漏关闭套接字
| TIME_WAIT 过多 | 短连接频繁建立与主动关闭 | 开启连接复用或改用长连接
| SYN_RECV 堆积 | SYN Flood 攻击或 accept 队列满 | 检查 tcp_syncookies 与 accept 队列长度
| FIN_WAIT_2 堆积 | 对端不发送 FIN | 检查 tcp_fin_timeout 与对端实现
|===

其中 `CLOSE_WAIT` 堆积最为常见. 它不会自动消失, 只能等待应用主动关闭, 因此一旦发现堆积, 应优先排查应用代码中的连接管理逻辑.

=== 总结

. 三次握手与四次挥手是 socket 状态流转的两条主线, 11 种状态覆盖了连接的全生命周期.

. 主动关闭方依次经历 FIN_WAIT_1, FIN_WAIT_2, TIME_WAIT; 被动关闭方依次经历 CLOSE_WAIT, LAST_ACK.

. `CLOSE_WAIT` 堆积通常指向应用 bug, `TIME_WAIT` 过多通常指向连接管理策略问题.

. 使用 `ss` 或 `netstat` 实时观测状态分布, 是定位网络问题的第一步.
