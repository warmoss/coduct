== WAF原理讲解

=== 引言

Web 应用防火墙(WAF)解决的是**应用层攻击**的防护问题. 传统网络防火墙主要在 OSI 第 3 层(网络层)与第 4 层(传输层)过滤数据包, 检查源/目标 IP, 端口, 协议等"信封信息", 却无法识别隐藏在 HTTP 请求正文中的攻击载荷. 而 SQL 注入, 跨站脚本(XSS), 文件包含等攻击完全通过合法的 80/443 端口传输, 可以毫无阻碍地穿过传统防火墙, 直达 Web 应用. WAF 正是为填补这一层防护空白而生.

=== 什么是 WAF?

WAF:: Web Application Firewall, Web 应用防火墙. 部署在 Web 应用前方, 通过解析 HTTP/HTTPS 请求与响应内容, 依据安全策略检测并阻断应用层攻击的安全系统.

传统防火墙与 WAF 的关系如下:

防火墙:: 工作在网络层/传输层, 相当于小区的"大门保安", 控制"谁能进出网络".

WAF:: 工作在应用层, 相当于展馆的"安检员", 检查"进出 Web 应用的数据里是否夹带恶意内容".

两者不是替代关系, 而是纵深防御体系中的不同层次, 通常配合部署.

=== 核心原理

WAF 的核心能力是**深度解析 HTTP 协议**并对内容执行安全检测. 一次完整检测通常包含以下环节:

. 解析请求行, 请求头, 请求体, 提取 URL, 参数, Cookie, Header 等结构化要素.
. 对每个要素执行规则匹配或语义分析, 识别攻击特征.
. 根据匹配结果执行放行, 拦截, 改写, 挑战验证等动作.
. 记录访问与拦截日志, 供审计和告警使用.

==== 检测方法

WAF 的检测引擎主要分为以下几类, 现代 WAF 通常组合使用:

* **基于规则(签名)匹配:** 使用正则表达式或规则语言描述攻击特征, 例如匹配 `UNION SELECT`, `<script>` 等关键字. 优点是准确, 可解释; 缺点是对变体攻击易被绕过, 规则库需持续维护.
* **基于语义/语法分析:** 对 SQL, JS 等片段做语法解析, 判断参数是否构成真实注入语义, 而非仅做字符串匹配. 可显著降低误报与绕过率.
* **基于行为/异常检测:** 建立正常访问基线, 对偏离基线的行为(如高频访问, 异常参数结构)进行告警或拦截, 常用于 CC 攻击与爬虫防护.
* **基于机器学习:** 用模型对请求打分, 自动发现未知攻击模式. 优点是能应对未知威胁; 缺点是误报较难控制, 可解释性弱.

==== 防护能力

[cols="1,3"]
|===
|攻击类型 |WAF 的防护方式

|SQL 注入
|解析请求参数, 识别 SQL 关键字, 注释符, 语义拼接等注入特征

|跨站脚本(XSS)
|检测请求与响应中的恶意脚本标签, 事件属性及各种编码绕过

|跨站请求伪造(CSRF)
|校验 Token, Referer, SameSite 等要素, 阻断伪造请求

|文件上传攻击
|校验扩展名, MIME 类型与文件内容, 拦截 WebShell 上传

|CC 攻击
|基于访问频率与行为基线做限速, 验证码等挑战验证

|敏感信息泄露
|检查响应内容, 拦截身份证, 手机号, 密钥等敏感数据外泄
|===

=== 工作流程

WAF 通常以**反向代理**方式串联在客户端与源站之间, 所有流量必须经 WAF 转发. 典型处理流程如下:

[plantuml, "WAF 请求处理流程", format=png]
----
@startuml
actor 客户端 as C
participant "WAF" as W
participant "Web 应用" as S

C -> W: 发起 HTTP 请求
W -> W: 解析请求(URL, Header, Body)
W -> W: 规则匹配与语义分析
alt 命中攻击规则
  W --> C: 拦截并返回 403
else 未命中规则
  W -> S: 转发请求
  S --> W: 返回响应
  W -> W: 检测响应(敏感信息, XSS)
  W --> C: 返回响应
end
@enduml
----

=== 部署模式

[cols="1,3,2"]
|===
|部署模式 |说明 |特点

|反向代理(串联)
|WAF 作为源站代理入口, 客户端直连 WAF, 由 WAF 转发至源站
|可拦截可改写, 需调整 DNS 与网络拓扑

|透明代理
|部署在网络路径上, 对客户端与源站透明
|无需改拓扑, 但部署复杂, HTTPS 场景需解密支持

|旁路镜像
|将流量镜像一份给 WAF, 只检测不拦截
|不影响业务, 只能告警, 无法实时阻断
|===

=== 规则示例

开源 WAF 引擎(如 Coraza)使用类 ModSecurity 的规则语言描述防护策略. 以下是一条拦截 SQL 注入特征的简化规则:

[source,text]
----
SecRule ARGS "@rx (?i)(union\s+select|sleep\s*\(|benchmark\s*\()" \  <1>
    "id:100001, phase:2, deny, log, msg:'SQL Injection Detected'"   <2>
----
<1> `ARGS` 表示对所有请求参数执行匹配, `@rx` 表示正则匹配, `(?i)` 表示忽略大小写.
<2> `id` 为规则编号, `phase:2` 表示在请求体解析后执行, `deny` 表示命中即拦截, `log` 表示记录日志.

NOTE: ModSecurity 已被 Trustwave 宣布停止维护(EOL), 新项目建议使用 OWASP 旗下的 Coraza 作为现代替代引擎, 二者规则语法兼容.

=== 总结与注意事项

* **定位:** WAF 防护应用层攻击, 与传统网络防火墙互补, 是纵深防御的一环.
* **不是银弹:** WAF 无法替代安全编码, 输入校验, 权限控制等应用自身的安全措施.
* **误报与漏报:** 规则过严会误杀正常业务, 过松则漏放攻击, 需持续调优规则与白名单.
* **HTTPS 解密:** 串联模式必须解密 HTTPS 才能检测加密流量, 需关注证书管理与合规要求.
* **绕过风险:** 攻击者可通过编码, 分块传输, 协议走私等手段绕过检测, 规则库需持续更新.
* **最佳实践:** 遵循默认拒绝与最小授权原则, 结合日志监控与告警, 定期复盘拦截策略.
