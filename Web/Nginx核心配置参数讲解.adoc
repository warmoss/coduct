== Nginx核心配置参数讲解

=== worker_connections

==== 定义与作用

worker_connections 用于设置 **每个 worker 进程能够同时处理的最大连接数**.

这里的"连接"是一个广义的概念, 它不仅包括与客户端(如浏览器)的连接(前端连接), 还包括 Nginx 为了获取后端资源(如 PHP-FPM、上游服务器、静态文件等)而建立的连接(后端连接).

==== 配置上下文
events

==== 示例

[source, nginx, linenums]
----
events {
    worker_connections 1024;
}
----

==== 理解连接数计算::
理解这个参数的关键在于明白 Nginx 是如何处理一个完整请求的. 一个典型的动态请求可能涉及:

. **1个** 来自客户端的连接(例如浏览器).

. **1个或多个** 到后端服务(如 PHP-FPM, Tomcat, 或另一个 upstream server)的连接.

因此, 一个请求可能会同时占用 2 个或更多的连接.

==== 最大客户端连接数估算
Nginx 作为一个反向代理时, 它能服务的最大并发客户端数(即 max_clients)并不是简单地 worker_connections * worker_processes. 更准确的估算公式是:

max_clients = worker_processes * worker_connections / 2

为什么除以 2? 因为在反向代理场景下, 每个客户端请求至少需要两个连接: 一个进来(客户端到Nginx), 一个出去(Nginx到后端). 在理想情况下, 平均每个请求占用 2 个连接.

**举个例子:**

如果你的配置是:

[source, nginx, linenums]
----
worker_processes 2; # 2个worker进程
events {
    worker_connections 1024; # 每个worker处理1024个连接
}
----

那么, 理论上 Nginx 能处理的最大并发连接数(所有连接的总和)是 2 * 1024 = 2048.
而能同时服务的最大客户端数(并发用户数)大约是 2 * 1024 / 2 = 1024.

==== 如何设置
* **默认值:** 通常为 512.

* **调整依据:**

** **系统限制:** 每个进程能打开的文件描述符(File Descriptor)数量是有限的. worker_connections 不能超过这个限制. 你可以通过 ulimit -n 命令查看当前限制. 需要在操作系统层面(如 /etc/security/limits.conf)和 Nginx 配置中同时调整.

** **服务器资源:** 更多的连接会消耗更多的内存和 CPU. 你需要根据服务器的可用内存来设定.

** **实际需求:** 根据你网站的预期并发访问量来设定. 对于高并发网站, 这个值通常会设置得非常高, 比如 4096, 8192 甚至更高.

=== sendfile

==== 定义与作用
sendfile 是一个用于优化静态文件传输的指令. 它允许 Nginx 使用操作系统内核的 sendfile() 系统调用来直接传输文件, 而不是使用传统的读写方式.

==== 配置上下文
http, server, location

==== 示例:

[source, nginx, linenums]
----
http {
    sendfile on;
}
----

==== 传统方式 vs Sendfile 方式

**传统方式(sendfile off):**

. Nginx 将目标文件从磁盘**读取**到内核空间的缓冲区.

. 内核空间将数据**拷贝**到用户空间(Nginx 进程所在的内存).

. Nginx 再将数据从用户空间**拷贝**回内核空间的 socket 缓冲区.

. 最后, 操作系统将数据从 socket 缓冲区发送到网络.
** **过程:** 磁盘 -> 内核缓冲区 -> 用户空间 -> socket缓冲区 -> 网络
** **问题:** 涉及两次不必要的上下文切换和数据拷贝(步骤2和3), 消耗 CPU 和内存.

**Sendfile 方式(sendfile on):**

. Nginx 直接调用 sendfile() 系统调用.

. 操作系统内核直接从磁盘读取文件数据, 并直接将其写入到 socket 缓冲区, 准备发送到网络.
** **过程:** 磁盘 -> 内核缓冲区 -> socket缓冲区 -> 网络

** **优势:**

*** **零拷贝:** 避免了数据在内核空间和用户空间之间的来回拷贝.

*** **高效:** 减少了上下文切换, 显著降低了 CPU 和内存的占用.

*** **速度快:** 极大地提升了静态文件(如图片、CSS、JS)的传输效率.

==== 使用场景与注意事项
* **适用场景:** 绝大多数情况下, 尤其是提供大量静态资源服务的场景, 都应该开启 sendfile on.

* **注意事项:**

** 在某些不支持文件描述符传递的虚拟化文件系统上(如较老版本的 NFS), 启用 sendfile 可能会导致问题.

** 当使用 Nginx 作为反向代理, 并且启用了 **数据压缩(Gzip)** 或 **AIO(异步IO)** 时, 在特定 Linux 内核版本下, sendfile 可能会与这些功能冲突. 在这种情况下, 通常的解决方案是在负责代理的 location 块中关闭 sendfile.
+
[source, nginx, linenums]
----
location / {
    proxy_pass http://backend;
    sendfile off; # 在代理位置关闭sendfile
}
----
+
对于非常小的文件, sendfile 的优势可能不明显, 但它对于大文件的传输性能提升是巨大的.
