== HTTP2讲解

=== 为什么需要 HTTP/2? —— HTTP/1.1 的痛点
要理解 HTTP/2 的好处, 我们首先要看看它要解决 HTTP/1.1 的哪些问题.

. **队头阻塞**

** **描述:** 在 HTTP/1.1 中, 虽然可以开启多个 TCP 连接(通常是 6-8 个)来并行请求, 但在**同一个连接**里, 请求和响应必须是**串行**的. 这意味着前一个请求没有处理完, 后面的请求就会被阻塞.

** **比喻:** 一个收银台(一个TCP连接)前排了一支队伍, 即使第一个人只买一瓶水, 第二个人推了一满车货物, 收银员也必须先结完一瓶水的账, 才能开始处理满车货物. 后面的人只能干等着.

. **冗余的头部信息**

** **描述:** HTTP/1.1 的请求和响应头部是纯文本格式, 且不会压缩. 每次请求都会带上 Cookie、User-Agent、Accept 等大量相同的头部字段, 造成带宽浪费.

. **并发连接数限制**

** **描述:** 为了减轻服务器压力, 浏览器会对同一个域名限制同时打开的 TCP 连接数(通常是 6 个). 当页面需要加载几十个资源时, 必须等到前面的连接空闲出来, 才能发起新的请求, 导致资源排队.

. **服务器无法主动推送**

** **描述:** 通信只能由客户端发起, 服务器只能被动响应. 如果服务器知道客户端接下来需要某个资源(比如一个 CSS 文件), 它也无法主动发送, 必须等客户端来请求.

=== 什么是 HTTP/2?
HTTP/2 是 HTTP 协议自 1999 年 HTTP/1.1 发布后的首个重大更新, 旨在更**高效地利用网络资源, 降低延迟**. 它由 Google 的 SPDY 协议演化而来, 并于 2015 年正式发布.

**核心目标: 兼容 HTTP/1.1**

* HTTP/2 没有改变 HTTP 的语义(方法、状态码、头部字段等).

* 它主要改变了**数据在客户端和服务器之间传输的格式和方式**.

* 这意味着你的所有 Web 应用代码都无需修改, 就可以在 HTTP/2 上获得性能提升.

=== HTTP/2 的核心特性与工作原理

==== 二进制分帧层
这是 HTTP/2 所有高级功能的基础, 是它和 HTTP/1.1 的**根本区别**.

* **HTTP/1.1:** 使用纯文本(字符串)来传输数据, 用换行符来分隔.

* **HTTP/2:** 在应用层(HTTP)和传输层(TCP)之间引入了一个二进制分帧层.

**工作流程:**

* 你的 HTTP 请求(方法、头、体)会被 HTTP/2 分解成更小的、独立的数据结构, 称为**帧**.

* 常见的帧类型有:

** HEADERS 帧: 存放请求头/响应头.

** DATA 帧: 存放请求体/响应体.

* 这些帧被乱序发送到 TCP 连接上, 然后在另一端根据**流标识符**被重新组装.

**好处:** 二进制协议解析起来更高效、更紧凑, 且不易出错.

==== 多路复用
基于二进制分帧, 多路复用成为了可能.

* **描述:** 在一个 TCP 连接中, 可以同时交错地发送多个请求和响应消息. 每个请求/响应被称为一个"流", 每个流由多个帧组成.

* **比喻:** 现在只有一个收银台(一个TCP连接), 但每个顾客的商品都被拆成了小包裹(帧), 上面贴了标签(流ID). 收银员可以同时处理多个顾客的包裹, 先扫一个顾客的牛奶, 再扫另一个顾客的面包, 然后再回来扫第一个顾客的饼干. 最终, 系统会根据标签把包裹重新分拣给对应的顾客.

**好处:**

* **彻底解决了队头阻塞:** 一个请求的缓慢不会阻塞其他请求.

* **减少了 TCP 连接数量:** 只需一个连接就能处理所有请求, 减少了内存和 CPU 消耗, 也為 TLS 握手节省了时间.

* **提升了网络利用率:** 避免了多个 TCP 连接之间的竞争和慢启动过程.

==== 头部压缩
HTTP/2 使用 **HPACK** 算法来压缩请求和响应头元数据.

* **原理:**

** **维护静态表和动态表:** 静态表包含了 61 个常见的头部字段(如 :method: GET).

** **静态哈夫曼编码:** 对字符串进行高效编码.

** **增量索引:** 双方共同维护一个动态表, 如果遇到一个新的头部字段(如 custom-header: value), 双方会将其存入动态表并分配一个索引. 下次传输相同的头部时, 只需发送这个索引号即可.

* **效果:** 头部大小通常可以被压缩 90% 以上, 显著减少了开销.

==== 服务器推送
这是 HTTP/2 一个非常强大的功能, 允许服务器在客户端尚未请求时, 就"猜测"并主动向客户端推送资源.

* **场景:** 当客户端请求 index.html 时, 服务器知道这个页面必定会引用 style.css 和 app.js. 于是, 服务器在返回 index.html 的同时, 可以主动发起推送, 将 style.css 和 app.js 也发送给客户端.

* **流程:**

** 服务器发送一个 PUSH_PROMISE 帧, 告知客户端: "我要推送一个你还没请求的资源, 这个资源属于 X 流".

** 客户端可以接收这个推送, 或者如果它已经在缓存里了, 可以发送一个 RST_STREAM 帧来拒绝.

* **好处:** 将资源提前推送到客户端缓存, 避免了额外的请求往返, 进一步降低了页面加载时间.

==== 流优先级
客户端可以为每个"流"指定一个依赖关系和权重.

* **描述:** 客户端可以告诉服务器: "请优先处理 CSS 文件, 因为它是渲染页面的关键; 图片可以稍后加载".

* **好处:** 允许浏览器更精细地控制资源加载顺序, 优化用户体验(如首屏加载时间).

=== 如何启用 HTTP/2?
HTTP/2 的普及度已经非常高. 启用它主要需要:

. **使用 HTTPS:** 虽然标准不强制要求, 但所有主流浏览器(Chrome, Firefox, Safari, Edge)都只在其加密版本(基于 TLS 的 HTTP/2)上实现 HTTP/2. 这既是为了推广加密网络, 也是因为协商过程更顺畅.

. **客户端支持:** 所有现代浏览器都已支持 HTTP/2.

. **服务器支持:** 现代 Web 服务器(如 Nginx, Apache, Caddy)都已内置对 HTTP/2 的支持, 通常只需在配置文件中开启一个选项即可.

** **Nginx 示例:** 在 server 块中添加 http2 指令.
+
[source, nginx, linenums]
----
server {
    listen 443 ssl http2;
    server_name example.com;
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/private.key;
    ... 
}
----

=== 总结: HTTP/2 的优势

[cols="1,3,3"]
|===
|特性|HTTP/1.1|HTTP/2

|**二进制分帧**
|文本解析低效、易出错
|解析高效、紧凑

|**多路复用**
|队头阻塞、连接数过多
|一个连接并行传输, 低延迟, 高吞吐

|**头部压缩**
|冗余头部浪费带宽
|显著减少开销

|**服务器推送**
|服务器无法主动发送资源
|预测并推送资源, 减少请求往返

|**流优先级**
|资源加载顺序不智能
|优化关键资源加载, 提升用户体验

|===
		
总而言之, **HTTP/2 通过引入二进制分帧和多路复用, 在保持 HTTP 语义不变的前提下, 极大地提升了 Web 性能, 解决了 HTTP/1.1 固有的几个核心性能瓶颈**. 它是现代 Web 高速发展的关键技术基石.

**注意:** HTTP/2 解决了应用层的队头阻塞, 但**未能解决 TCP 层的队头阻塞**(一个 TCP 包丢失会导致所有流等待重传). 这正是其继任者 **HTTP/3** 要解决的问题, 它使用 QUIC 协议(基于 UDP)来代替 TCP.
