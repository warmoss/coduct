== QUIC讲解

=== 为什么需要 QUIC? —— TCP 的瓶颈
要理解 QUIC, 首先要明白我们长期以来使用的 **TCP/TLS/HTTP** 协议栈在当今的互联网环境下存在哪些问题.

. **队头阻塞**

** **问题:** 在 HTTP/1.1 中, 一个 TCP 连接只能处理一个请求, 浏览器为了提速会开启多个 TCP 连接. 在 HTTP/2 中, 多个请求可以复用同一个 TCP 连接. 然而, TCP 是一个按序传输的协议, 如果其中一个数据包丢失, 后续的所有数据包即使已经到达, 也必须等待丢失的包重传成功, 这就像一条单车道上有一辆车抛锚, 后面的车全部被堵住.

** **影响:** 在网络状况不佳时, 一个微小的丢包就可能导致整个页面的加载速度大幅下降.

. **建立连接的延迟高**

** **TCP 三次握手:** 建立一个 TCP 连接需要 1.5 RTT(往返时间).

** **TLS 握手:** 建立一个安全的 TLS 连接(如 HTTPS)又需要 1~2 RTT.

** **总延迟:** 在发送任何实际应用数据(如 HTTP 请求)之前, 就已经消耗了 2~3.5 RTT 的时间. 对于网络延迟较高的场景(如移动网络), 这个开销非常可观.

. **协议僵化**

** TCP 和 TLS 都是操作系统内核或库实现的协议, 更新和部署非常缓慢. 想要优化 TCP 或部署新的加密算法, 需要等待所有终端用户升级其操作系统, 这几乎是不可能的. 中间网络设备(如防火墙、路由器)也严重依赖并期望 TCP 的行为是固定的, 任何修改都可能被它们视为异常而拦截.

=== QUIC 是什么?
QUIC 是由 Google 最初提出, 后由 IETF 标准化的一个基于 UDP 的通用、安全、可靠的传输层协议. 它的核心目标是解决上述 TCP 的瓶颈, 并为现代 Web 应用提供更快的、更安全的底层连接.

现在, HTTP/3 就是运行在 QUIC 之上的应用层协议, 它取代了 HTTP/2 和 TCP/TLS 的组合.

=== QUIC 的核心特性与工作原理

==== 基于 UDP, 用户空间实现
* **绕过协议僵化:** QUIC 建立在 UDP 之上, UDP 是一个无连接的、简单的协议. 这意味着 QUIC 可以完全在用户空间的应用程序(如浏览器、服务器软件)中实现, 而不需要修改操作系统内核.

* **快速迭代:** 协议改进和错误修复可以像更新 Chrome 或 Nginx 一样快速部署, 无需等待系统更新.

==== 内置加密与安全
* **默认加密:** QUIC 将 TLS 1.3 作为其核心的一部分, **所有数据(包括握手信息和载荷)都是加密的**.

* **安全优势:** 这使得中间网络设备无法看到和解析协议头中的任何信息(如序列号、确认号), 从而防止了中间设备对其进行"优化"或干扰, 也增强了用户隐私.

* **对抗劫持和篡改:** 加密的包头使得伪造 QUIC 数据包变得极其困难.

==== 连接迁移
* **问题:** 使用 TCP 时, 连接由四元组标识(源 IP、源端口、目标 IP、目标端口). 当你的手机从 Wi-Fi 切换到 4G/5G 时, 你的 IP 地址改变了, 导致所有现有的 TCP 连接中断, 需要重新建立.

* **解决方案:** QUIC 使用一个独立于 IP 地址的、加密的**连接 ID** 来标识一个连接. 即使你的网络环境发生变化, 只要连接 ID 不变, 连接就可以无缝地保持下去, 应用层完全感知不到.

==== 零 RTT 和 1 RTT 连接
得益于 TLS 1.3 的优化, QUIC 在连接建立方面实现了显著的提速:

* **1-RTT 握手:** 对于首次连接, 客户端可以利用 TLS 1.3 的特性, 在第一个消息中就发送加密的应用数据, 将握手延迟降低到 **1 RTT**.

* **0-RTT 握手:** 对于重连的客户端, 它可以将之前从服务器获取的"预共享密钥"缓存起来. 在重新连接时, 它可以在第一个数据包中就发送应用数据, 实现 0 RTT 的延迟. 这对于像 HTTP GET 请求这样的操作是巨大的性能提升.

**注意:** 0-RTT 在带来性能优势的同时, 也存在重放攻击的风险, 需要应用层协议设计时予以考虑.

==== 解决队头阻塞
这是 QUIC 最引人注目的特性之一.

* **在流级别解决:** QUIC 借鉴了 HTTP/2 的"流"概念, 在一个 QUIC 连接内可以同时创建多个独立的、有序的字节流(例如, 每个 HTTP 请求可以是一个流).

* **每个流独立传输:** 每个流的数据帧是独立封装和传输的. 如果一个流中的数据包丢失, **它只会阻塞该流本身的数据**, 其他流的数据可以继续处理和交付给应用层.

* **对比:** 在 HTTP/2 over TCP 中, TCP 层不知道"流"的概念, 任何一个 TCP 包的丢失都会阻塞所有流.

**一个简单的比喻:**

* **TCP:** 一条单行道, 所有车必须按顺序通过.

* **QUIC:** 一条有多条车道的高速公路, 其中一条车道发生事故, 其他车道仍然可以正常通行.

=== QUIC 与 HTTP/3 的关系
这是一个非常重要的概念:

* HTTP/1.x -> 运行在 TCP 之上.

* HTTP/2 -> 运行在 TLS over TCP 之上.

* HTTP/3 -> 运行在 QUIC 之上.

HTTP/3 本质上就是 HTTP 语义(请求、响应、头、体)在 QUIC 协议上的映射. 它继承了 HTTP/2 的多路复用、头部压缩等高级特性, 但底层的传输协议从"TCP + TLS"换成了"QUIC", 从而一举获得了 QUIC 带来的所有好处.

=== 现状与挑战
* **广泛支持:** 目前, 所有主流浏览器(Chrome, Firefox, Edge, Safari)、大型云服务商(Google Cloud, Cloudflare, Fastly)和 Web 服务器(Nginx, Apache, Caddy)都已支持 HTTP/3.

* **逐步普及:** 越来越多的网站和应用程序开始启用 HTTP/3, 以提升用户体验, 尤其是在高延迟和易丢包的网络环境中.

* **挑战:**

** **网络中间件兼容性:** 一些旧的或配置严格的企业防火墙、路由器可能不识别或不正确处理 QUIC 流量, 导致连接失败.

** **CPU 开销:** 由于在用户空间处理所有加密和协议逻辑, QUIC 的 CPU 消耗通常略高于成熟的 TCP 实现, 但随着硬件发展和软件优化, 这个差距正在缩小.

=== 总结

[cols="1,2,2,2"]
|===
|特性|TCP/TLS|QUIC|优势

|**基础**
|内核实现, 基于 IP
|用户空间实现, 基于 UDP
|快速迭代, 绕过协议僵化

|**安全**
|TLS 在 TCP 之上
|TLS 1.3 内置, 全加密
|更强隐私, 防中间设备干扰

|**握手延迟**
|2-3 RTT
|0/1 RTT
|连接建立更快

|**队头阻塞**
|在传输层存在
|**在流级别解决**
|网络不佳时性能更稳定

|**连接迁移**
|不支持
|**支持**
|网络切换时连接不中断
			
|===

QUIC 不是对 TCP 的微小改进, 而是一次传输层的革命性重构. 它通过将速度、安全性和可靠性深度整合到一个基于 UDP 的协议中, 为下一代互联网应用(尤其是 Web、移动应用和实时通信)奠定了坚实的基础. 随着 HTTP/3 的普及, QUIC 正逐渐成为互联网数据传输的新标准.
