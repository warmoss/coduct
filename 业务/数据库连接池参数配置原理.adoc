== 数据库连接池参数配置原理

数据库连接池是应用层与数据库之间的**连接管理器**, 它维护一组已建立的数据库连接, 供应用程序重复使用, 避免频繁创建和销毁连接带来的巨大开销. 合理配置连接池参数, 是保障系统性能和稳定性的关键环节.

=== 为什么需要连接池?

建立数据库连接(如 MySQL TCP 连接)是一个**耗时较长的操作**, 通常需要:

. TCP 三次握手
. 数据库服务端认证(用户名/密码校验)
. 连接初始化(设置字符集、事务隔离级别等)

在高并发场景下, 每次请求都新建连接会导致严重的性能瓶颈. 连接池通过**复用已有连接**, 大幅降低连接建立的开销.

=== 核心参数详解

连接池的核心参数决定了它的行为和性能表现. 以下以 **HikariCP**(业界性能最好的 Java 连接池实现) 为例, 但各参数的含义在所有连接池实现中通用.

==== minimumIdle

定义:: 连接池中**最少保持的空闲连接数**.

原理:: 当空闲连接数低于此值时, 连接池会积极创建新连接, 直到达到 `minimumIdle` 的数量. 设置为 0 时, 连接池会在空闲连接超时后将其全部关闭, 仅在请求到来时创建.

建议::
* **高并发稳定服务:** 设置为 `maximumPoolSize` 的 20%-50%, 减少频繁创建连接的延迟.
* **无持续流量的服务:** 设置为 0, 避免空闲连接浪费资源.
* HikariCP 默认值与 `maximumPoolSize` 相同(即"袖珍模式", 始终保持连接池满载).

==== maximumPoolSize

定义:: 连接池中**允许的最大连接数**, 包括空闲连接和正在使用的连接.

原理:: 当所有连接都在使用中, 且有新请求到来时, 连接池会创建新连接, 直到达到 `maximumPoolSize`. 到达上限后的请求会进入等待队列, 直到 `connectionTimeout` 超时.

建议::
* 计算公式: **maximumPoolSize = ((core_count * 2) + effective_spindle_count)** (经验公式, 源自 PostgreSQL 社区的推荐)
  * `core_count`: CPU 核心数
  * `effective_spindle_count`: 硬盘数量(对于 SSD 时代通常为 1-2)
* 实践中推荐通过**压力测试**确定最佳值, 一般从 10-50 开始, 逐步调高.
* **并非越大越好:** 过多的连接会增加数据库服务端的上下文切换开销, 反而降低吞吐量.

. 一个常见的误解
****
很多人认为连接池越大, 性能越好. 实际上, 连接数超过某个阈值后, 数据库的并发处理能力会因**锁竞争**和**上下文切换**而急剧下降. 例如, PostgreSQL 在 50-100 个连接时达到最佳性能, 超过后性能不增反降.
****

==== connectionTimeout

定义:: 调用者等待从连接池获取连接的最长等待时间(毫秒). 超时则抛出异常.

原理:: 当连接池中没有可用连接时, 请求线程会阻塞等待, 直到有空闲连接释放或超时. 这个参数**保护了应用不被无限阻塞**.

建议::
* **默认值:** 30000 毫秒(30 秒, HikariCP 默认值).
* **延迟敏感的服务:** 可设为 1000-5000 毫秒, 快速失败, 避免用户长时间等待.
* **批处理任务:** 可延长至 30-60 秒, 容忍短暂的连接饥饿.
* 配合 **Fallback 机制**: 超时后返回降级响应, 而非无限等待.

==== idleTimeout

定义:: 空闲连接在连接池中**保持存活, 不被回收的最长时间**(毫秒). 仅在 `minimumIdle < maximumPoolSize` 时生效.

原理:: 当连接的空闲时间超过 `idleTimeout` 时, 连接池会关闭该连接, 释放资源. 空闲连接数会逐渐下降到 `minimumIdle`.

建议::
* HikariCP 默认值: 600000 毫秒(10 分钟).
* 数据库侧也有空闲超时设置(如 MySQL 的 `wait_timeout`, 默认 8 小时), 池内 `idleTimeout` 应**小于**数据库侧的超时时间, 避免连接被数据库端意外关闭.
* 如果连接数少且连接稳定, 可适当延长; 否则可缩短至 5-15 分钟.

==== maxLifetime

定义:: 连接在池中的**最大存活时间**(毫秒). 超过此时间后, 连接会被关闭并移除, 即使它一直处于活动状态.

原理:: 这是为了**规避数据库或网络基础设施(如防火墙、负载均衡器)对长连接的限制**. 许多网络设备会静默关闭空闲超时的 TCP 连接, 导致连接池持有"死连接". 定期老化连接可以避免此问题.

建议::
* HikariCP 默认值: 1800000 毫秒(30 分钟).
* 需要比数据库侧的最长连接超时时间**短 2-5 秒**, 避免连接池持有已被数据库端关闭的连接.
* 对于 MySQL, 建议设为小于 `wait_timeout`(默认 28800 秒)的值, 如 1800000 毫秒(30 分钟).

==== validationTimeout

定义:: 连接有效性检测的超时时间(毫秒). HikariCP 在获取连接时会执行 `connectionTestQuery` 来验证连接是否有效.

原理:: 如果在此时间内没有收到数据库的响应, 则认为连接无效, 将其从池中移除并创建新连接.

建议::
* 默认值: 5000 毫秒(5 秒).
* 一般不需要修改, 除非网络延迟极高.
* 配合 `connectionTestQuery`(默认: `SELECT 1`) 使用.

==== leakDetectionThreshold

定义:: **连接泄漏检测阈值**(毫秒). 当一个连接被持有超过此时间未归还时, 连接池会输出警告日志并记录堆栈信息.

原理:: 这**不是**一个强制回收机制, 而是一个**诊断工具**. 它帮助开发者发现"借了不还"的连接泄漏问题.

建议::
* 默认值: 0(禁用).
* 建议设置为 `maximumPoolSize` 对应的超时时间, 如 60000 毫秒(开启检测), 开启后在测试环境中定位连接泄漏.
* **生产环境**建议在问题排查时临时启用, 平时关闭, 避免轻微的性能开销.

=== 工作流程

以下时序图展示了连接池的核心工作流程:

[plantuml, "数据库连接池连接获取流程", format=png]
----
@startuml
actor 应用线程 as App
participant 连接池 as Pool
database 数据库 as DB

== 正常获取连接 ==
App -> Pool: 请求连接
alt 有空闲连接
    Pool -> Pool: 检查连接有效性(如 maxLifetime/validationTimeout)
    Pool --> App: 返回有效连接
else 无空闲连接且未达上限
    Pool -> DB: 创建新连接
    DB --> Pool: 返回新连接
    Pool --> App: 返回新连接
else 无空闲连接且已达上限
    App -> Pool: 等待 connectionTimeout
    alt 超时前有连接归还
        Pool --> App: 返回释放的连接
    else 超时
        Pool --> App: 抛出 ConnectionTimeoutException
    end
end

== 连接归还 ==
App -> Pool: 归还连接
Pool -> Pool: 判断空闲连接数 > minimumIdle?
alt 超过 minimumIdle
    Pool -> DB: 关闭连接, 释放资源
else
    Pool -> Pool: 保持连接, 进入空闲队列
end

== 空闲回收 ==
note right of Pool: 后台线程定时扫描
Pool -> Pool: 检查空闲连接 idleTimeout
alt 空闲时间超过 idleTimeout
    Pool -> DB: 关闭连接
end
Pool -> Pool: 检查连接 maxLifetime
alt 存活时间超过 maxLifetime
    Pool -> DB: 关闭连接
end
@enduml
----

=== 不同场景的配置参考

==== 高并发 Web 服务

[source,java]
----
// HikariCP 配置示例: 高并发 Web 服务
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/db");
config.setUsername("user");
config.setPassword("pass");
config.setMinimumIdle(20);           // 保持 20 个空闲连接
config.setMaximumPoolSize(50);       // 最大 50 个连接
config.setConnectionTimeout(5000);   // 5 秒获取超时, 快速失败
config.setIdleTimeout(300000);       // 5 分钟空闲回收
config.setMaxLifetime(1800000);      // 30 分钟最大存活时间
config.setLeakDetectionThreshold(60000); // 开启泄漏检测
----

配置要点::
* `minimumIdle` 设置较高, 应对突发流量.
* `connectionTimeout` 较短, 避免用户长时间等待.
* 配合数据库连接池监控(如 HikariCP 的 Metrics), 持续观察连接使用率.

==== 定时批处理任务

[source,java]
----
// HikariCP 配置示例: 定时批处理任务
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/db");
config.setUsername("user");
config.setPassword("pass");
config.setMinimumIdle(2);            // 少量空闲连接
config.setMaximumPoolSize(10);       // 最大 10 个连接
config.setConnectionTimeout(30000);  // 30 秒获取超时
config.setIdleTimeout(600000);       // 10 分钟空闲回收
config.setMaxLifetime(1800000);      // 30 分钟最大存活时间
----

配置要点::
* 连接要求不高, 维持少量空闲连接即可.
* 超时时间较长, 容忍短暂的连接等待.
* 减少资源占用, 避免与主业务争抢数据库资源.

==== 微服务(无状态, 低并发)

[source,java]
----
// HikariCP 配置示例: 微服务(低并发)
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/db");
config.setUsername("user");
config.setPassword("pass");
config.setMinimumIdle(2);            // 少量空闲连接
config.setMaximumPoolSize(10);       // 最大 10 个连接
config.setConnectionTimeout(5000);   // 5 秒获取超时
config.setIdleTimeout(300000);       // 5 分钟空闲回收
config.setMaxLifetime(1800000);      // 30 分钟最大存活时间
----

配置要点::
* `minimumIdle` 和 `maximumPoolSize` 较小, 降低资源占用.
* 多数场景下 10 个连接已足够, 微服务不求吞吐量极限, 而求资源效率.

=== 常见问题与排查

==== 连接泄漏

当应用获取连接后忘记归还(未在 finally 块中调用 `close()`), 会导致连接池不断创建新连接, 最终耗尽数据库连接数.

排查手段::
* 开启 `leakDetectionThreshold`, 查看日志中的泄漏堆栈.
* 使用数据库端的 `SHOW PROCESSLIST`(MySQL) 查看活跃连接数.
* 检查代码中 `try-with-resources` 的使用是否完整.

==== 连接池耗尽

当所有连接都被占用且 `connectionTimeout` 频繁触发时, 说明连接池过小或查询执行过慢.

排查手段::
* 检查数据库端是否有慢查询拖长连接占用时间.
* 查看数据库连接池监控, 确认实际连接使用率是否接近上限.
* 排查是否存在**长事务**或**锁等待**, 导致连接长时间被持有.

==== 连接闲置断开

当数据库端主动关闭空闲连接后, 连接池仍持有"死连接", 下次请求时触发 `CommunicationsException`.

解决方案::
* 确保 `maxLifetime` 小于数据库端的 `wait_timeout`(MySQL) 或 `idle_in_transaction_session_timeout`(PostgreSQL).
* 确保 `idleTimeout` + 连接池后台检查间隔 < 数据库端空闲超时.
* HikariCP 默认 30 秒检查一次连接活性, 可自动处理此问题.

=== 总结

* 数据库连接池的核心价值在于**复用连接**和**控制并发**, 而非简单地创建一堆连接.
* 参数配置需遵循 **"先理解, 再配置, 后验证"** 原则, 不要盲目套用模板.
* 关键参数 `maximumPoolSize` **不是越大越好**, 需要通过压力测试找到系统的最佳并发值.
* `maxLifetime` 和 `idleTimeout` 的配置需**与数据库端超时配置协同**, 避免产生死连接.
* `leakDetectionThreshold` 是排查连接泄漏的有力工具, 建议在开发和测试环境中开启.
* 最终参数配置应结合**业务场景**(高并发 Web / 批处理 / 微服务) 和 **数据库性能基准** 确定.
