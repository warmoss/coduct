== 阿里云MySQL字段加密原理讲解

在阿里云数据库体系里, "MySQL字段加密"是一个容易混淆的说法: 很多人把它和**透明数据加密(TDE)**混为一谈, 但二者解决的攻击面完全不同. TDE 是**表级落盘加密**, 只防"绕过数据库直接读文件"; 字段加密则是**列级加密**, 目标是让 DBA 越权, 账号泄露, 逻辑拖库等"从库里直接拿明文"的路径全部失效. 在阿里云 MySQL 上, 真正承担字段级加密的产品是**全密态数据库(EncDB)**, 本文以其为主线拆解原理, 并厘清它与 TDE, 云盘加密的分工.

参考: <<../../其他/KMS密钥管理服务讲解.adoc, KMS密钥管理服务讲解>>, <<../../其他/阿里云磁盘加密原理讲解.adoc, 阿里云磁盘加密原理讲解>>, <<../../安全算法/aes讲解.adoc, AES讲解>>

=== 字段加密要解决什么问题

先看落盘加密管不到的场景:

* **DBA 越权:** 云盘加密与 TDE 都挡不住有权限的 DBA 直接对明文列执行 `SELECT`
* **账号泄露:** 应用账号一旦泄露, 攻击者可连库查询, 落盘是密文也没用, 因为数据库返回的是解密后的明文
* **逻辑拖库:** 全表 `SELECT` 导出(俗称拖库)不受落盘加密约束, 密文在引擎层早已还原成明文
* **链路窃听:** 明文结果在返回链路上被截获
* **数据副本泄露:** 明文备份, 导出文件, 同步副本外泄

字段加密的思路与落盘加密正相反: **不让数据库把明文"说出去"**, 加密点从"写入路径"移到"读取返回路径", 使未授权方即便拿到查询结果也只能得到密文.

=== 三层加密如何分工

阿里云 MySQL 的加密能力按作用层级分为三层, 可叠加组合:

----
@startuml

  component "业务应用 + 加密驱动(EncJDBC/EncDB SDK)" as enccli
}
rectangle "数据库层" as db {
  component "数据库代理 Proxy(PolarDB)" as proxy
  component "MySQL 引擎(全密态 EncDB)" as engine
  component "TDE 落盘加密" as tde
}

  component "云盘加密(块存储)" as clouddisk
}

  component "KMS / HSM" as kms
}

enccli --> proxy: 集群地址
enccli --> engine: 直连地址(RDS)
proxy --> engine
engine --> tde: 写盘前加密
tde --> clouddisk
engine --> kms: 信封加密分发密钥
enccli --> kms: 获取并解密主密钥
@enduml
----

[cols="1,3,3,4"]
|===
| 维度 | 云盘加密 | 透明数据加密(TDE) | 全密态数据库(字段加密)

| 加密层级 | IaaS 块存储层 | 数据库引擎层(表/表空间) | 引擎或代理层(列/字段)
| 加密时机 | 数据写入云盘前 | 内存落盘前 | 查询结果返回时
| 加密粒度 | 整个实例 | 表 | 库/表/列, 精确到字段
| 明文可见性 | DBA 与 PaaS 运维可见 | DBA 可见明文 | DBA 不可见
| 主要防护对象 | 磁盘介质泄露, IaaS 运维 | Bypass 数据库/OS 直接读文件 | 账号泄露, DBA 越权, 链路窃听, 逻辑拖库
| 应用改造 | 无 | 无 | 需接入加密驱动
| 是否列级 | 否 | 否 | 是

|===

三个关键区分:

* **粒度不同:** 云盘加密整实例, TDE 到表, 全密态到列
* **加密点不同:** 前两者加密"存储", 全密态加密"返回结果"
* **可见明文的人不同:** 层级越深, 能看见明文的人越少

全密态负责"出口防泄露", 但官方建议叠加 TDE 或云盘加密保护"落盘", 两者组合才构成全链路密文.

=== 核心概念

全密态数据库(EncDB):: 阿里云 RDS MySQL / PolarDB MySQL 提供的**字段级(列级)加密**能力, 官方亦称"选择列加密". 加密粒度精确到库, 表, 列, 通过加密规则声明哪些字段需要保护
加密规则:: 描述"库 -> 表 -> 字段"匹配关系的策略, 决定查询结果中哪些列在返回前被加密. RDS 版规则持久化在系统表 `mysql.encdb_sensitive_rules` 中
主密钥(MEK):: 用户自行持有并管理的密钥(RDS 版为 16 字节), 用于保护字段数据. 数据库**不保存, 不管理, 不备份** MEK
信封加密:: 先用随机会话密钥加密 MEK, 再经 KMS 用用户主密钥加密会话密钥, 形成层层包裹的密文信封, 实现密钥的安全分发
加密驱动:: 位于客户端的透明组件, 如 EncJDBC, EncDB SDK 与 GoLang 驱动. 驱动负责解密服务端返回的密文, 业务代码无需感知
保属性加密(Property-Preserving Encryption):: 一类在加密后仍保持比较/计算属性的加密技术, 是加密列上仍可执行模糊匹配等 SQL 计算的原理支撑
超管 / 运维管理员 / 普通管理员:: 全密态下的三类角色: 超管可见明文, 运维管理员可见密文并可解密, 其他管理员仅见密文

=== 加密发生的时刻: 结果路径加密

字段加密与传统存储加密的本质差异在于**加密点位置**:

* **存储加密(加密写入路径):** 数据写盘前加密, 读盘后解密, 数据库内部始终是明文, 加密对查询执行无感
* **字段加密(加密返回路径):** 查询照常执行, 但在**结果集返回给客户端之前**, 按加密规则对命中字段的值加密. 明文只存在于数据库内部, 出库即密文

阿里云两种实现版本在此原则上一致, 差别仅在"规则在哪里生效":

==== RDS MySQL: 引擎层 EncDB

RDS MySQL 版通过内核参数 `loose_encdb=ON` 开启, 加密规则由引擎在执行路径上识别并执行. 官方宣称其在密文形态下仍支持全部 SQL 算子, 明文 SQL 也可对加密列执行模糊匹配查询, 可行性依赖**保属性加密**等高级密码学能力.

NOTE: RDS MySQL 全密态当前处于公测阶段, 具体支持规格与内核小版本下限以控制台为准.

==== PolarDB MySQL: 代理层

PolarDB MySQL 版在**数据库代理(Proxy)**层生效, 官方明确此功能**不改变数据的物理存储状态**, 即文件与云盘上仍以明文存放; 代理在结果返回客户端前对命中字段加密. 因此它防护的是账号泄露, 运维窃取与链路窃听, 落盘防护需另外叠加 TDE 或云盘加密.

由于库内是明文, 代理版的索引, 排序, 范围查询天然不受影响, 但加密只在**集群地址/自定义地址**生效, 直连主地址会绕过代理使加密失效.

=== 密钥体系

字段加密采用**用户自持主密钥(MEK)**体系:

* **MEK 不离开用户控制:** 数据库侧不落盘 MEK, 密钥丢失将导致数据无法解密
* **本地生成或 KMS 托管:** MEK 可由 `openssl rand -hex 16` 本地生成, 也可从 KMS 拉取. 接入 KMS 时必须使用 KMS 实例 + 用户主密钥(支持硬件主密钥/HSM), 不支持默认密钥与别名
* **会话级安全分发:** 连接建立时, 客户端将 MEK 以**信封加密**方式下发到服务端, 会话结束即销毁, 避免密钥长期驻留
* **RAM 授权:** 使用 KMS 时需为账号授予 `KMS:Decrypt`, 凭证可使用 AK 或 STS 临时凭证

字段加密算法支持国际算法与国密算法两套:

[cols="1,2"]
|===
| 算法族 | 支持模式
| 国际算法 | AES-128-GCM / AES-128-CTR / AES-128-CBC / AES-128-ECB
| 国密算法 | SM4-128-GCM(默认) / SM4-128-CTR / SM4-128-CBC / SM4-128-ECB

|===

其中带认证的 GCM 模式可同时保证数据的机密性与完整性, ECB 模式不提供此类保护.

NOTE: ECB 模式安全性较弱, 官方明确不推荐在字段加密中使用. 各模式的具体 IV/Nonce 生成与处理由加密驱动及密钥分发机制实现, 官方文档未逐项披露.

=== 字段加解密工作流程

以 PolarDB 代理版 + EncJDBC 为例, 读取受保护字段的完整链路如下:

[plantuml,"字段加密读取时序图",format=png]
----
@startuml
participant "应用(EncJDBC)" as app
participant "KMS" as kms
participant "数据库代理 Proxy" as proxy
participant "MySQL 引擎" as engine

app -> kms: 连接时完成信封解密, 获得会话密钥
app -> proxy: 标准 SQL(明文)
proxy -> engine: 转发 SQL
engine --> proxy: 返回明文结果集
proxy -> proxy: 命中加密规则, 加密字段值
proxy --> app: 返回密文结果
app -> app: EncJDBC 自动解密
app --> app: 业务拿到明文
@enduml
----

. **建立会话:** 应用通过加密驱动连接, 结合 MEK 与 KMS 完成信封加密分发, 会话密钥仅在连接期间有效
. **下发 SQL:** 业务发送普通 SQL(如 `SELECT id, phone FROM user`), 无需改动语句本身
. **引擎执行:** MySQL 引擎正常执行查询, 返回明文结果集
. **命中规则:** 代理(或引擎)检查加密规则, 对命中字段(如 `phone`)的值进行加密
. **客户端解密:** 加密驱动自动解密, 应用拿到明文; 未接入驱动的客户端只会看到密文

三类角色的可见性各不相同:

* **超管:** 不受加密规则限制, 直接读取明文, 建议为其设置过期时间
* **运维管理员:** 可见密文, 使用专属密钥解密
* **普通管理员/普通账号:** 只能看到密文, 且无法解密

=== 加密字段上的 SQL 检索

字段加密最大的工程难点是"加密之后还能不能查". 官方给出的能力分两种实现路径:

* **引擎层(RDS EncDB):** 宣称在密文形态下仍支持全部 SQL 算子, 明文 SQL 可对加密列做模糊匹配查询, 其可行性依赖**保属性加密/可检索加密**等密码学技术
* **代理层(PolarDB):** 因数据在库内本就是明文, 索引, 范围查询, 排序等不受任何影响; 但协议受限, 仅支持普通 `COM_QUERY` 文本协议, 不支持 `COM_STMT_PREPARE` 二进制协议, EncJDBC 的预编译语句实际也走文本协议

[WARNING]
====
普通(未接入加密驱动)客户端对加密列执行写入, 会把明文或密文以错误格式写回, 导致数据不可用. 非只读场景必须接入加密驱动, 才能形成"读密文 -> 解密 -> 再加密写回"的闭环.
====

同时注意两条限制:

* 字段加密与**动态脱敏**功能互斥, 不能同时启用
* 代理版加密规则只在集群地址生效, 直连主地址会绕过加密

=== 性能影响

字段加密的开销集中在结果集加密与客户端解密上, 与查询涉及的敏感字段数量, 返回数据量相关. 官方对 PolarDB 全密态的 TPCC 测试口径如下:

[cols="1,1,3"]
|===
| 加密字段占比 | 相对明文库性能 | 说明
| 20% | 约 93% | 损耗约 7%
| 50% | 约 86% | 损耗约 14%
| 100% | 约 79% | 损耗约 21%

|===

作为参照, TDE 在多数场景的性能损耗低于 5%, 仅在低并发写场景可达约 20%. 因此建议**落盘加密用 TDE/云盘加密, 出口防护用字段加密**, 按数据敏感度与查询负载权衡组合.

=== 应用接入方式

客户端接入的核心是替换驱动, 官方提供三种方式:

* **EncJDBC:** 替换 JDBC 驱动, 连接串前缀为 `jdbc:mysql:encdb://`, 驱动类为 `com.aliyun.encdb.mysql.jdbc.EncDriver`
* **EncDB SDK:** 配合社区 MySQL JDBC 与 BouncyCastle 使用, 可配置多种密钥管理类型(`RDS_MYSQL` / `POLARDB_MYSQL` / `PG` / `KEYSTORE_SERVER`)
* **GoLang 驱动:** 面向 Go 应用

[source,java]
----
// 接入示意: 用加密驱动替换普通驱动, 其余业务代码不变
String url = "jdbc:mysql:encdb://rm-xxxx.mysql.rds.aliyuncs.com:3306/db";  // <1>
Class.forName("com.aliyun.encdb.mysql.jdbc.EncDriver");                    // <2>
// 按所选方案注入主密钥: 本地密钥或 KMS 实例 + 用户主密钥
Connection conn = DriverManager.getConnection(url, props);                 // <3>
----
<1> 连接串使用 `encdb` 前缀, 指向集群地址而非直连地址
<2> 驱动类替换为阿里云加密驱动
<3> `props` 中配置密钥管理类型与加密算法, 具体参数见官方 EncJDBC 文档

[source,shell]
----
# 本地生成 16 字节主密钥 MEK
openssl rand -hex 16
----

=== 常见误区与最佳实践

常见误区:

* **把 TDE 当字段加密:** TDE 是表级落盘加密, DBA 仍能读明文列; 字段加密才是列级出口防护
* **以为全密态能防一切:** 若底层落盘为明文, PaaS/IaaS 层运维仍可能读到数据. 官方能力矩阵显示, 列加密主要防"用户/应用/账号/链路/数据副本"维度, IaaS 运维维度需叠加 TDE 或云盘加密
* **用普通客户端读写加密列:** 会读到乱码甚至写坏数据, 必须接入加密驱动
* **丢失 MEK:** 数据库不备份主密钥, 密钥丢失等于数据永久丢失

最佳实践:

* **多层叠加:** 云盘加密 + TDE + 字段加密组合, 实现从存储到出口的全链路密文
* **权限分离:** 加密规则账号与在线业务账号分离, 超管账号设置过期时间
* **密钥托管 KMS:** 使用 KMS 实例 + 用户主密钥(硬件主密钥)并配置自动轮转
* **以控制台为准:** 全密态处于公测, 开启前核对实例内核小版本与支持规格
* **先规则后流量:** 先在测试库验证加密规则的匹配范围, 再应用到生产

=== 总结

阿里云 MySQL 字段加密(全密态数据库/EncDB)的核心原理是**把加密点从"写入路径"移到"返回路径"**: 数据库照常计算, 却在结果集出口按加密规则加密命中字段, 再由客户端加密驱动透明解密. 配合**用户自持 MEK + KMS 信封加密**的密钥体系和**保属性加密**等密码学技术, 它能在不改变业务 SQL 的前提下, 让 DBA, 账号泄露与逻辑拖库都拿不到明文. 它与表级 TDE, 块级云盘加密分工明确且可叠加, 共同构成阿里云 MySQL 的全链路数据加密体系.
