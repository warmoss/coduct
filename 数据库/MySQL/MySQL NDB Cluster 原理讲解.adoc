== MySQL NDB Cluster 原理讲解

=== NDB 是什么?

**MySQL NDB Cluster** 不是一个单独的数据库, 而是一个在**无共享架构上实现的**、**基于内存的**、**分布式的数据库集群解决方案**.

它主要由以下两部分组成:

* **MySQL Server(SQL 节点):** 我们熟悉的 MySQL 实例, 但它的存储引擎不是常用的 InnoDB, 而是 NDB(或 NDBCLUSTER). 这个 MySQL 节点负责处理 SQL 接口、查询解析、优化等.

* **NDB 数据节点:** 这才是集群的核心. 它负责实际存储数据、处理事务、处理复制、提供故障恢复等. 数据是分布在多个数据节点上的.

简单来说, 你可以把 NDB Cluster 理解为: **用多个 MySQL 服务器(SQL节点)作为"入口", 去访问一个高性能、高可用的分布式内存数据库(NDB引擎).**

=== 为什么需要 NDB? —— 设计目标

NDB 的设计初衷是为了解决传统单点 MySQL 数据库的瓶颈:

* **高可用性:** 要求 99.999% 的在线时间, 不能有单点故障.

* **线性可扩展性:** 通过增加机器, 能近乎线性地提升数据库的读写性能和处理能力.

* **高性能:** 极低的读写延迟, 适用于实时性要求高的场景.

这些目标催生了 NDB 的"无共享"架构和内存存储的设计.

=== 核心架构与组件

一个完整的 NDB 集群至少包含三种节点, 它们各司其职, 可以分布在不同的服务器上.

. **管理节点**

** **作用:** 集群的"**配置中心**"和"**管家**". 它负责集群的启动、关闭、配置、备份、以及节点故障时的仲裁. 它存储着集群的元数据(配置信息).

** **特点:** 这个节点本身不存储业务数据, 负载很轻. 在生产环境中, 通常建议配置两个管理节点以实现其自身的高可用. 客户端(应用程序)不直接连接它.

. **数据节点**

** **作用:** 集群的"心脏". 所有表的数据和索引都实际存储在这里. 数据节点是内存型的, 所有数据主要驻留在内存中(但可以配置为异步持久化到磁盘).

** **工作模式:** 数据节点总是成对出现, 形成一个Node Group. 同一个 Node Group 内的两个(或多个)数据节点存储完全相同的数据副本, 互为实时镜像. 这提供了数据冗余和高可用.

** **进程名:** 在操作系统上, 你看到的进程是ndbd(单线程)或ndbmtd(多线程, 性能更好).

. **SQL 节点**

** **作用:** 集群的"大门". 这就是标准的 MySQL 服务器进程(mysqld), 只是编译时链接了 NDB 存储引擎.

** **功能:** 应用程序像连接普通 MySQL 一样连接它. 它接收 SQL 请求, 进行解析、优化, 然后通过 NDB API 与底层的数据节点进行通信, 获取或修改数据, 最后将结果返回给客户端.

** **特点:** SQL 节点本身是无状态的. 你可以部署多个 SQL 节点, 应用程序可以随机连接任何一个, 它们看到的数据都是一致的. 这提供了负载均衡.

=== 核心原理详解

==== 数据分布与分片

NDB 通过**数据分片**来实现可扩展性.

* 当你创建一张表并指定引擎为 NDB 时, 这张表的数据会被水平分割成多个Fragment(分片).

* 分片的数量由Node Group的数量决定. 默认情况下, 每个 Node Group 会存储一份完整的数据副本, 而数据分片会均匀分布在各个 Node Group 中.

* **分片算法:** 默认使用主键的哈希值来决定一条记录属于哪个分片. 这保证了数据在各个数据节点间的均匀分布.

**示例:** 假设一个 4 个数据节点的集群, 配置为 2 个 Node Group(Node Group A: 节点1,2; Node Group B: 节点3,4). 一张表的数据会被分成 2 个分片(因为只有 2 个 Node Group):

* Fragment 1 存储在节点1和节点2上(互为镜像).

* Fragment 2 存储在节点3和节点4上(互为镜像).

==== 数据一致性、复制与故障恢复

这是 NDB 高可用的基石.

* **同步复制:** 在同一个 Node Group 内, 数据的写入是同步的. 当一个事务要提交时, 它必须等待同一个 Node Group 内所有镜像节点都确认写入成功, 事务才算完成. 这保证了数据的强一致性.

* **故障切换:** 如果某个数据节点(例如节点1)宕机, 会发生什么?

. 集群会立刻检测到节点1失效.

. 所有指向节点1的请求会自动、透明地路由到它的镜像节点(节点2).

. 节点2现在独立承担所有读写任务, 集群仍然可用.

. 当节点1恢复后, NDB 会自动从节点2同步数据, 使其重新跟上进度, 然后重新加入集群提供服务.

* **这个过程的延迟极低**, 通常在几秒钟内完成, 对应用几乎是透明的.

==== 事务处理

一个 SQL 语句(例如 `UPDATE ... WHERE ...`)在 NDB 中是如何执行的?

. **SQL 解析:** SQL 节点接收到请求, 进行解析和优化.

. **生成 NDB API 请求:** SQL 节点将复杂的 SQL 操作分解为一系列对 NDB 数据节点的低级操作.

. **事务协调器:** SQL 节点本身充当了事务协调器. 它需要与涉及到的所有数据分片进行通信.

. **两阶段提交:** 为了在分布式环境下保证事务的 ACID 特性, NDB 通常使用两阶段提交协议.

** **阶段一(Prepare):** 协调器询问所有相关数据节点: "你们能执行这个操作吗? " 各节点预写日志, 并回复"可以".

** **阶段二(Commit):** 如果所有节点都回复"可以", 协调器发送提交指令, 所有节点正式提交更改.

. **返回结果:** 所有操作完成后, SQL 节点将最终结果返回给客户端.

==== 内存与持久化

* **内存存储:** 数据节点的核心数据存储在内存中, 这是其高性能的主要原因.

* **持久化保障:** 为了防止断电导致数据丢失, NDB 采用了多种机制:

** **重做日志:** 所有数据更改都会先写入重做日志缓冲区, 然后定期刷新到磁盘的重做日志文件. 这用于在节点重启后恢复内存中的数据状态.

** **检查点:** 定期将内存中所有数据的快照(检查点)写入磁盘. 这减少了恢复时需要重放的日志量.

** **操作日志:** 管理节点会记录集群的操作历史, 用于系统范围的恢复.

** 所以, NDB 是**内存数据库**, 但通过日志和检查点机制实现了 **ACID 持久性**.

=== 优缺点与适用场景

优点::

* **极高可用性:** 无单点故障, 自动故障转移.

* **线性可扩展性:** 通过增加数据节点和 SQL 节点, 轻松扩展读写能力.

* **极低延迟:** 内存存储带来微秒级的读写延迟.

* **高吞吐量:** 支持高并发读写.

缺点::

* **复杂性:** 架构复杂, 部署、配置和维护都比单机 MySQL 困难.

* **成本高:** 需要多台服务器, 且对内存容量要求高.

* **SQL 功能限制:** 不支持外键约束, 复杂的 JOIN 查询可能性能不佳(因为涉及跨网络数据拉取).

* **网络依赖:** 对内部网络的速度和稳定性要求极高.

典型适用场景::

* **电信领域:** 用户状态会话、实时计费系统.

* **实时在线游戏:** 玩家状态、排行榜.

* **需要极高可用性的 Web 服务.**

* **高速缓存层**, 但其功能远不止缓存.

=== 总结

MySQL NDB Cluster 的核心原理可以概括为: **通过"无共享"架构, 将数据分片并同步复制到多个内存数据节点中, 再通过标准的 MySQL SQL 节点提供 SQL 接口, 从而同时实现了高性能、高可用性和线性可扩展性.** 它是一个为特定苛刻场景(高并发、低延迟、高可用)设计的强大但复杂的解决方案. 在选择它之前, 务必仔细评估其优缺点是否与你的业务需求相匹配.
