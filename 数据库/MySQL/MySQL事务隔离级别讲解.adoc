== MySQL事务隔离级别讲解

=== 什么是事务隔离级别?
在多个事务同时执行(并发)时, 可能会引发以下问题:

. **脏读:** 一个事务读到了另一个 **未提交事务** 修改的数据.

. **不可重复读:** 一个事务内, 多次读取同一条数据, 结果不一致(因为被其他已提交事务 **修改** 了).

. **幻读:** 一个事务内, 多次按相同条件查询, 得到的记录数不一致(因为被其他已提交事务 **新增或删除** 了).

事务隔离级别就是为了解决这些问题而生的, 它定义了事务与事务之间的"隔离"程度. SQL标准定义了四种隔离级别, 隔离强度从低到高依次为:

. **读未提交**

. **读已提交**

. **可重复读 - MySQL 的默认隔离级别**

. **串行化**

隔离级别越高, 数据一致性越好, 但并发性能越低.

=== 原理深入: MVCC 与 锁
MySQL(特指 InnoDB 引擎)实现事务隔离级别的核心技术是 **MVCC** 和 **锁**. 它们协同工作, 在不同场景下发挥作用.

==== 核心技术一: MVCC
**MVCC** 的英文全称是 **Multi-Version Concurrency Control**, 即多版本并发控制. 它是一种"无锁"的并发控制技术, 通过创建数据快照来提供一致性读.

**不同隔离级别下 MVCC 的表现:**

* **读已提交:** **每次**执行快照读时, 都会生成一个新的 Read View. 这就是为什么它能读到其他已提交事务的最新数据, 从而可能引发"不可重复读".

* **可重复读:** 只在**第一次**执行快照读时生成一个 Read View, 后续的读操作都复用这个 View. 因此, 在整个事务期间, 它看到的数据都是一致的, 就像事务开始时的一个快照, 从而避免了不可重复读.

==== 核心技术二: 锁
MVCC 主要解决了"读"的并发问题, 但对于"写"操作(INSERT, UPDATE, DELETE), 仍然需要 **锁** 来保证数据的一致性.

* **共享锁:** 也叫读锁. 事务A对数据加了共享锁后, 其他事务可以继续加共享锁读, 但不能加排他锁写.

* **排他锁:** 也叫写锁. 事务A对数据加了排他锁后, 其他事务既不能加共享锁读, 也不能加排他锁写.

**不同隔离级别下锁的表现:**

* **读未提交:** 通常不加读锁, 所以会读到未提交的数据(脏读).

* **读已提交:** 在语句执行期间加锁, 执行完就释放(行锁). 这可能导致不可重复读.

* **可重复读:**

** **为了解决幻读**, InnoDB 引入了 Next-Key Lock(临键锁). 它是 **记录锁**(锁住某一行)和 **间隙锁**(锁住一个范围, 但不包括记录本身)的结合.

** 例如, `SELECT * FROM t WHERE id > 10 FOR UPDATE;` 在"可重复读"级别下, 不仅会锁住所有 `id > 10` 的现有行, 还会锁住 (10, +∞) 这个间隙. 这样, 其他事务就无法在这个范围内插入新的 `id > 10` 的行, 从而避免了幻读.

* **串行化:** 所有读操作都会隐式地转换为加共享锁的 `SELECT ... LOCK IN SHARE MODE`. 读写、写写都会相互阻塞, 完全串行执行, 性能最低.

=== 如何查看和设置隔离级别?

[source, sql, linenums]
----
-- 查看当前会话隔离级别
SELECT @@transaction_isolation;

-- 查看全局隔离级别
SELECT @@global.transaction_isolation;

-- 设置当前会话隔离级别为 读已提交
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 设置全局隔离级别为 可重复读
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;
----

**结论:**

理解 MySQL 事务隔离级别的关键在于理解 **MVCC** 和 **锁** 的协同工作机制. MVCC 通过版本链和 Read View 实现了高效的"无锁读", 而锁(特别是 Next-Key Lock)则确保了"写"操作的正确性和对幻读的防止. 默认的"可重复读"级别在性能和一致性上取得了很好的平衡, 是适用于绝大多数场景的选择.
