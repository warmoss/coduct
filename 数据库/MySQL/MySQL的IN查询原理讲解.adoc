== MySQL的IN查询原理讲解

=== 核心结论
MySQL 对 **IN** 子句的处理并非一成不变, **查询优化器会根据 IN 列表中值的数量、列的数据类型、索引情况等因素, 动态选择最优的执行策略**. 主要策略有以下三种:

. **对少量值, 使用多个范围扫描**

. **对大量值, 使用物化**

. **对相关子查询, 使用 EXISTS 策略**

=== 对于简单的、值较少的 IN 列表(例如: IN (1, 2, 3))
当 IN 列表中的值是明确的、且数量较少时, 查询优化器会将其等价地转换为**多个等值查询的 OR 组合**.

**例如:**

[source, sql, linenums]
----
SELECT * FROM users WHERE id IN (1, 5, 10);
----

**优化器会将其重写为:**

[source, sql, linenums]
----
SELECT * FROM users WHERE id = 1 OR id = 5 OR id = 10;
----

**执行过程:**

* 如果 id 列上有索引(例如主键索引), MySQL 会**分别对每个值执行一次索引查找**.

* 它会先查找 id=1 的记录, 再查找 id=5, 最后查找 id=10.

* 然后将三次查找的结果合并(Union)起来, 并去除可能的重复项(如果数据库允许重复且OR条件可能重复, 但主键不会).

* 这个过程非常高效, 因为每次查找都是高效的索引范围扫描(range access).

**特点:**

* **速度快:** 适用于值少且有索引的情况.

* **EXPLAIN** 输出中的 **type** 列会显示 **range**.

=== 对于值很多的 IN 列表(例如: IN (1, 2, 3, ..., 10000))

当 **IN** 列表中的值非常多时(成千上万), 如果还使用第一种方式, 优化器需要生成一个极其冗长的 OR 条件, 解析和优化这个SQL语句本身就会成为瓶颈. 此时, MySQL 会采用一种叫做**物化(Materialization)** 的策略.

**物化过程:**

. **创建临时表:** MySQL 会先在磁盘(或内存, 如果足够小)上创建一个临时的、只读的 **MyISAM 存储引擎** 的表.

. **填充数据:** 将 **IN** 列表中的所有值逐行插入到这个临时表中.

. **哈希索引:** 为了加速后续的连接操作, MySQL 会**自动为这个临时表的所有列创建一个哈希索引**. 哈希索引对于等值查询非常快(O(1)复杂度).

. **执行连接查询:** **将原查询重写为一个标准的表连接(Join)**.

**例如:**

[source, sql, linenums]
----
SELECT * FROM users WHERE id IN (1, 2, 3, ..., 10000);
----

优化器会将其重写为:

[source, sql, linenums]
----
SELECT users.* FROM users
JOIN  ON users.id = temp_table.id;
----

(这里的 **temp_table** 就是物化后的临时表)

**执行过程:**

* 对于 users 表的每一行, 使用其 id 值去**物化表(临时表)的哈希索引中进行查找**.

* 由于哈希索引的超高效率, 这个连接操作的速度非常快.

**特点:**

* 适用于 IN 列表值非常多的情况, 避免了冗长SQL的解析开销.

* 物化表的过程有额外开销(创建表、插入数据、建索引), 但一旦完成, 后续的查询效率很高.

* 如果 IN 列表是子查询的结果(IN (SELECT ...)), 且子查询结果集很大, 也会优先使用此策略.

* EXPLAIN 输出中, 你可能看到:

** **select_type 可能出现 MATERIALIZED**

** **额外创建了一个子查询的 id, 其 table 列显示为 ``**

=== 对于不相关的子查询(IN (SELECT ...))

当 **IN** 里面是一个子查询时, 情况更为复杂. 优化器会尝试将子查询**半连接(Semi-join)** 优化或使用上述的物化策略.

**半连接优化:**

半连接是一种特殊的连接, 它只关心外表中的记录在内表中是否存在匹配项, 而不关心内表有多少条匹配记录(即不会重复外表记录). **IN** 和 **EXISTS** 天生就是半连接语义.

MySQL支持多种半连接策略, 如:

* **Table pullout:** 如果子查询基于唯一索引, 则子查询会被提升为连接.

* **FirstMatch:** 对于外表的每一行, 一旦在内表找到第一个匹配项, 就停止扫描内表.

* **LooseScan:** 使用索引来松散地扫描子查询表.

* **Materialization:** 如上所述, 将子查询结果物化.

优化器会根据成本估算选择它认为最好的半连接策略.

=== 对于相关的子查询(WHERE col IN (SELECT ... WHERE outer_col = ...))

当子查询依赖于外部查询的列时, 称为相关子查询. 物化和半连接优化可能不再适用, 因为子查询的结果对于外部查询的每一行都可能不同.

在这种情况下, MySQL 最常用的策略是**将 IN 子查询重写为 EXISTS 子查询**.

**例如:**

[source, sql, linenums]
----
SELECT * FROM departments d
WHERE d.id IN (
    SELECT e.dept_id FROM employees e
    WHERE e.salary > 100000
    AND e.dept_id = d.id -- 依赖外部查询的 d.id
);
----

**优化器可能会将其重写为:**

[source, sql, linenums]
----
SELECT * FROM departments d
WHERE EXISTS (
    SELECT 1 FROM employees e
    WHERE e.salary > 100000
    AND e.dept_id = d.id -- 依赖关系不变
);
----

**执行过程(通常是最慢的):**

* 对于 departments 表的**每一行**, 都**执行一次**内部的子查询.

* 如果 departments 表有10000行, 那么这个子查询就会被执行10000次!

* 这种方式的性能高度依赖于子查询本身的效率和外部表的大小. 通常需要确保子查询内的表(employees)在连接列(dept_id)和过滤条件(salary)上有合适的索引.

**特点:**

* 这是性能最容易出问题的场景.

* **EXPLAIN** 输出中, 你会看到 **DEPENDENT SUBQUERY**, 这是一个警告信号, 意味着"N+1查询"问题.

=== 总结

[cols="2,2,1,2"]
|===
|场景|可能策略|性能|优化建议

|IN (const1, const2...) (值少)
|多个范围扫描
|**高**
|确保 IN 的列上有索引

|IN (const1, const2...) (值多)
|**物化(Materialization)**
|中
|无法避免, 但物化本身有成本

|IN (SELECT ...) (不相关)
|半连接 / 物化
|中到高
|信任优化器, 确保子查询有索引

|IN (SELECT ... WHERE ...) (相关)
|EXISTS 策略
|**通常很低**
|**极力避免!** 考虑重写为 JOIN

|===

=== 最佳实践:

. **为 IN 条件的列建立索引:** 这是最重要的优化手段.

. **尽量避免相关子查询:** 尽可能将相关子查询重写为 JOIN, 性能通常会有数量级的提升.

** **不好:** SELECT ... WHERE id IN (SELECT ... WHERE x = outer.x)

** **好:** SELECT ... FROM table1 JOIN table2 ON ...

. **控制 IN 列表的大小:** 如果程序需要传入大量ID, 评估是否真的需要一次查询, 或者是否可以分批次查询.

. **使用 EXPLAIN 分析:** 任何时候对性能有疑问, 都使用 EXPLAIN 查看MySQL的执行计划, 确认它选择了哪种策略. 关注 type、Extra 和 select_type 列.
