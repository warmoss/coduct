== MySQL全文索引原理讲解

=== 为什么需要全文索引?

在了解原理之前, 我们先要知道它解决了什么问题.

传统的 `LIKE` 语句进行模糊匹配有很多弊端:

. **效率低下:** `LIKE '%keyword%'` 这种前置模糊匹配无法利用普通的 B-Tree 索引, 会导致全表扫描. 当数据量庞大时, 性能极差.

. **功能单一:** 无法进行复杂的文本查询, 比如:

** **自然语言搜索:** 查找包含"数据库"或"原理"的文档.

** **布尔搜索:** 查找包含"MySQL"但不包含"Oracle"的文档.

** **相关性排序:** 无法根据匹配程度对结果进行排序, 只能返回布尔值(匹配或不匹配).

**全文索引就是为了高效、灵活地解决这些文本搜索需求而设计的.**

=== MySQL 全文索引的核心原理

MySQL 全文索引的核心是 **倒排索引**. 我们通过一个简单的例子来理解它.

假设我们有一个 `articles` 表, 其中 `content` 字段有如下两条记录:

[cols="1,5"]
|===
|ID|content

|1|I love databases and machine learning.
|2|Machine learning is fascinating.
|===

==== 分词

这是构建全文索引的第一步. MySQL 会将文本内容分割成一个个独立的词元.

* **对 ID=1 的内容分词:** `I`, `love`, `databases`, `and`, `machine`, `learning`

* **对 ID=2 的内容分词:** `Machine`, `learning`, `is`, `fascinating`

**注意:**

* MySQL 有自己的分词器, 它会:

** 忽略常见的 **停用词**, 如 "I", "and", "is", "the" 等. 这些词因为出现频率太高, 没有实际的搜索价值.

** 根据**最小/最大词长**设置(`ft_min_word_len`, `ft_max_word_len`)来过滤过短或过长的词.

** 将单词 **统一为小写**(对于不区分大小写的校对规则).

所以, 经过分词和过滤后, 我们得到的有意义的词是:

* ID=1: `love`, `databases`, `machine`, `learning`

* ID=2: `machine`, `learning`, `fascinating`

==== 构建倒排索引

现在, 我们不再关心"哪条记录包含了什么文本", 而是关心"哪个词出现在哪条记录中". 这就是"倒排"的含义.

我们将上面分词后的结果, 构建成这样的结构:

[cols="1,2"]
|===
|关键词|出现的文档ID列表

|databases|1
|fascinating|2
|learning|1, 2
|love|1
|machine|1, 2

|===
这个"关键词"到"文档ID列表"的映射, 就是 **倒排索引**. 它本质上是一个 **关键词词典**.

==== 搜索过程

当用户执行全文搜索时, 例如查询 `MATCH(content) AGAINST(‘machine learning' )`, 过程如下:

. **对查询词分词:** 将查询字符串 ‘machine learning' 也进行分词, 得到 machine 和 learning.

. **查找倒排索引:** 在倒排索引表中分别查找 machine 和 learning 这两个词.

** 找到 machine, 对应的文档ID是 [1, 2]

** 找到 learning, 对应的文档ID是 [1, 2]

. **合并结果:** 因为默认是自然语言模式, 可以理解为 OR 操作, 所以合并两个集合, 得到最终匹配的文档ID是 [1, 2].

. **相关性计算与排序:** 这是全文索引的另一个强大功能. MySQL 会计算每个匹配文档的相关性得分. 计算因素通常包括:

** **词频:** 一个词在文档中出现的次数越多, 得分越高.

** **逆文档频率:** 一个词在所有文档中出现的频率越低(越稀有), 它的权重就越高. 例如, fascinating 只出现在一篇文章中, 那么搜索它时, ID=2 的文章得分会很高.

** **字段长度:** 词在较短的字段中出现比在较长的字段中出现权重更高.

. **返回结果:** 根据计算出的相关性得分进行降序排列, 返回最终结果.

=== MySQL 全文索引的技术细节

==== 两种不同的实现

MySQL 的全文索引实现经历过重要演变:

* **MyISAM 全文索引(MySQL 5.6 之前):**

** 仅 MyISAM 存储引擎支持.

** 索引与数据文件是分离的.

** 不支持事务.

* **InnoDB 全文索引(MySQL 5.6 及之后):**

** InnoDB 存储引擎也开始支持, **现在推荐使用**.

** 支持事务.

** 内部实现上, 它将倒排索引存储在称为 **辅助表** 的特殊表中, 并通过 FTS Doc ID 与主表关联.

**现在开发基本都应使用 InnoDB 及其全文索引.**

==== 三种搜索模式

===== 自然语言模式

默认模式. 像日常说话一样输入关键词, MySQL 会理解你的意图, 自动处理词干、停用词等, 并返回相关性排序的结果.

[source, sql, linenums]
----
MATCH (title, body) AGAINST ('database performance' IN NATURAL LANGUAGE MODE)
----

===== 布尔搜索模式

可以使用操作符进行更精确、复杂的控制.

* `+`: 必须包含

* `-`: 必须排除

* `>`: 提高该词的贡献度

* `*`: 通配符(只能放在词尾)

[source, sql, linenums]
----
-- 查找包含"MySQL"但不包含"Oracle"的记录
MATCH (title, body) AGAINST ('+MySQL -Oracle' IN BOOLEAN MODE)
----

===== 查询扩展模式

分两阶段搜索. 首先进行常规的自然语言搜索, 然后以第一阶段的结果中的高频词作为新的查询词, 再次进行搜索. 主要用于扩大搜索范围, 解决同义词问题, 但可能会引入不相关的噪音.

[source, sql, linenums]
----
MATCH (title, body) AGAINST ('database' WITH QUERY EXPANSION)
----

=== 如何使用与注意事项

=== 创建全文索引

可以在建表时创建, 也可以后期添加.

[source, sql, linenums]
----
-- 建表时创建
CREATE TABLE articles (
    id INT UNSIGNED AUTO_INCREMENT NOT NULL PRIMARY KEY,
    title VARCHAR(200),
    body TEXT,
    FULLTEXT (title, body) -- 在 title 和 body 上创建联合全文索引
) ENGINE=InnoDB;

-- 为已存在的表添加全文索引
ALTER TABLE articles ADD FULLTEXT INDEX ft_index (title, body);
-- 或者
CREATE FULLTEXT INDEX ft_index ON articles (title, body);
----

=== 关键配置参数

* `ft_min_word_len`: 最小词长, 默认通常是 4. 意味着像 "and", "how" 这种 3 个字母的词会被忽略. **修改此参数后必须重建全文索引**.

* `ft_max_word_len`: 最大词长.

* `innodb_ft_min_token_size`: InnoDB 引擎的最小词长, 同上.

* `innodb_ft_enable_stopword`: 是否启用停用词.

=== 注意事项

* **词库限制:** MySQL 的分词器对中文等东亚语言支持不佳, 因为它默认按空格和标点分词. 处理中文需要插件(如 MeCab 解析器)或在外层进行分词处理(如利用 IK 分词器等).

* **性能代价:** 虽然查询快, 但维护倒排索引本身需要开销. 对表进行大量 INSERT, UPDATE, DELETE 操作时, 会影响性能.

* **索引重建:** 修改了与全文索引相关的服务器变量(如 ft_min_word_len)后, **必须重建全文索引才能生效**.
+
[source, sql, linenums]
----
REPAIR TABLE table_name QUICK;
----

* **内存与缓存:** 全文索引的词典可能很大, 确保有足够的内存来缓存它, 以获得最佳性能.

=== 总结

[cols="1,5"]
|===
|特性|原理概述

|**核心思想**
|**倒排索引**, 从"词"映射到"文档ID列表".

|**工作流程**
|1. 分词 -> 2. 过滤(停用词、词长) -> 3. 构建索引表 -> 4. 查询时同样分词并查找 -> 5. 计算相关性并排序.

|**相比 LIKE**
|**高效**(利用索引)、**功能强**(布尔搜索、相关性排序).

|**适用场景**
|文章搜索、博客评论搜索、产品描述搜索等需要进行复杂文本匹配的应用.

|===
