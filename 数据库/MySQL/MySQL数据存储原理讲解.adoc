== MySQL数据存储原理讲解

=== 引言

MySQL 的数据存储涉及从逻辑表到物理文件的完整映射过程. 理解 InnoDB 的存储原理, 有助于优化表结构设计、索引策略和 I/O 性能.

InnoDB 的存储层次为: **表空间(tablespace)** -> **段(segment)** -> **区(extent)** -> **页(page)** -> **行(row)**. 下文逐层展开.

=== 表空间(Tablespace)

表空间是 InnoDB 存储结构的最高逻辑层次, 一个表空间对应一个或多个物理文件.

表空间类型::

* **系统表空间(system tablespace):** 即 `ibdata1` 文件, 存储数据字典、Undo Log 等系统数据
* **独立表空间(file-per-table tablespace):** 每个 `.ibd` 文件对应一个 InnoDB 表, 存储表的数据和索引
* **通用表空间(general tablespace):** 使用 `CREATE TABLESPACE` 创建的共享表空间
* **临时表空间(temporary tablespace):** 存储临时表数据, 路径为 `ibtmp1`

详细原理参见 <<MySQL表空间原理讲解.adoc, MySQL表空间原理讲解>>.

=== 段(Segment)

段是对表空间中特定类型数据的进一步细分, 一个表空间包含多个段.

段类型::

* **叶子节点段(leaf segment):** 存储 B+ 树叶子节点的数据和索引
* **非叶子节点段(non-leaf segment):** 存储 B+ 树非叶子节点的索引页
* **回滚段(rollback segment):** 存储 Undo Log

InnoDB 中的每个索引都会创建两个段: 一个叶子节点段和一个非叶子节点段. 段是**区(extent)** 的集合.

=== 区(Extent)

区是段的基本管理单位, 由 **64 个连续页** 组成.

区关键特性::

* **默认大小:** 1MB (`64 × 16KB`)
* **分配策略:** InnoDB 会先在 `.ibd` 文件中为段分配碎片页(单页), 累积到 32 个碎片页后才开始整区分配, 避免小表浪费空间
* **压缩表:** 压缩表的区大小随页大小变化, 当页大小为 8KB 时, 区大小为 512KB; 页大小为 4KB 时, 区大小为 256KB

=== 页(Page)

页是 InnoDB **磁盘 I/O 的最小单位**. InnoDB 以页为单位读写数据.

页类型::

* **数据页:** 存储表数据行
* **索引页(也叫目录页):** 存储索引条目, 即 B+ 树的非叶子节点
* **Undo 页:** 存储 Undo Log 记录
* **系统页:** 存储系统元数据(如数据字典)
* **插入缓冲位图页:** 管理 Change Buffer 的位图
* **BLOB 页:** 存储溢出的长字段数据

==== 页结构

一个数据页(默认 16KB)内部结构如下:

[source, text]
----
+---------------------------+ <- Page Offset 0
| File Header (38 bytes)   | 文件头, 记录页号、校验和、上下页指针
+---------------------------+
| Page Header (56 bytes)   | 页头, 记录页状态信息
+---------------------------+
| Infimum + Supremum        | 虚拟记录, 定义页内记录边界
+---------------------------+
| User Records              | 用户数据行(按主键顺序排列)
|   (插入到 Free Space)     |
+---------------------------+
| Free Space                | 空闲空间, 用于插入新记录
+---------------------------+
| Page Directory            | 页目录, 记录槽(slot)位置, 加速二分查找
+---------------------------+
| File Trailer (8 bytes)    | 文件尾, 校验和检测页完整性
+---------------------------+
----

File Header 关键字段::

* `FIL_PAGE_OFFSET`: 页号(4 字节), 全局唯一标识
* `FIL_PAGE_PREV / FIL_PAGE_NEXT`: 上一页/下一页指针(4 字节), 将数据页组织成双向链表
* `FIL_PAGE_LSN`: 最近修改该页的 Log Sequence Number(8 字节)
* `FIL_PAGE_TYPE`: 页类型(2 字节)

Page Directory::

* 将页内记录分组, 每组最后一个记录的偏移量记录在 **槽(slot)** 中
* 查找记录时, 先通过二分法在 Page Directory 中定位槽, 再在槽内顺序遍历
* 每个槽至少包含 4 条记录(压缩表为 2 条), 最多包含 8 条记录

=== 行格式(Row Format)

InnoDB 支持四种行格式, 决定了数据行在页内的物理存储方式.

[%header,cols="2,4,4,3"]
|===
|行格式|特点|适用场景|冗余度

|**REDUNDANT**
|最早的行格式, 存储了较多元数据, 如偏移量列表
|MySQL 5.0 之前遗留表
|高

|**COMPACT**
|减少约 20% 的行存储空间, 变长字段使用长度列表
|通用场景(MySQL 5.6 默认)
|中

|**DYNAMIC**
|与 COMPACT 类似, 但长字段(BLOB/TEXT)完全行外存储
|有大量 BLOB/TEXT 字段的表(MySQL 5.7+ 默认)
|低

|**COMPRESSED**
|在 DYNAMIC 基础上对页进行压缩(zlib), 节省磁盘空间但消耗 CPU
|日志、归档表
|最低
|===

可通过以下语句查看和设置行格式:

[source,sql]
----
-- 查看表行格式
SHOW TABLE STATUS LIKE 'table_name'\G

-- 创建表时指定行格式
CREATE TABLE t1 (
    id INT PRIMARY KEY,
    name VARCHAR(100)
) ROW_FORMAT=DYNAMIC;

-- 修改表行格式
ALTER TABLE t1 ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8;
----

==== COMPACT/DYNAMIC 行结构

一行记录在页内的物理布局如下:

[source,text]
----
+-----------------------+------------------+----------------+--------------------+
| 变长字段长度列表       | NULL 标志位       | 记录头信息      | 列1值 | 列2值 | ... |
| (可变,最多2字节/字段) | (1字节/NULL字段数) | (5字节)         | 实际列数据           |
+-----------------------+------------------+----------------+--------------------+
----

变长字段长度列表::

* 按 **逆序** 存储各变长字段(VARCHAR, VARBINARY, BLOB, TEXT)的字节长度
* 每个字段占 1~2 字节: 当列最大长度 <= 255 字节且实际长度 <= 127 字节时占 1 字节, 否则占 2 字节
* 逆序存储的设计使变长字段列表能在固定偏移处获取到第一列数据

NULL 标志位::

* 每个允许为 NULL 的列占用 1 bit, 按 **逆序** 排列
* 如果没有任何列为 NULL, 此标志位占用 0 字节
* 查询时通过位运算直接判断列是否为 NULL, 无需扫描数据

记录头信息(5 字节, 40 bit)::

各 bit 含义如下:

[%header,cols="2,3,3"]
|===
|bit 位|名称|说明

|1
|`delete_flag`
|该记录是否被删除(标记删除, 实际还在页中)

|1
|`min_rec_flag`
|该记录是否为非叶子节点中的最小记录

|1
|`n_owned`
|该记录拥有的记录数(用于 Page Directory 分组)

|13
|`heap_no`
|该记录在页堆中的位置(排序序号)

|3
|`record_type`
|0=普通记录, 1=非叶子节点索引, 2=Infimum, 3=Supremum

|16
|`next_record`
|下一条记录的相对位置(以当前记录为基点的偏移量, **可正可负**)
|===

`next_record` 设计亮点::

* 记录之间通过 **相对偏移量** 连接, 而非绝对地址, 这使得页内的记录可以通过物理拷贝移动到其他页
* 记录的链表顺序是 **物理无序但逻辑有序** 的, 按主键排列

==== 行溢出( Off-page 存储)

当一行数据过大无法在一个页内完整存放时, InnoDB 会将部分数据存储在溢出页中:

* **COMPACT 格式:** 长字段的前 768 字节存储在数据页中, 剩余部分存储在 BLOB 页中(称为"行内存储 + 溢出")
* **DYNAMIC 格式:** 长字段完全存储在 BLOB 页中, 数据页只保留 20 字节的指针(称为"完全行外存储")
* 溢出页通过 B+ 树的链指针连接, 读取大字段时需要额外 I/O

=== B+ 树在存储中的应用

InnoDB 使用 B+ 树组织索引和数据, 详细原理参见 <<B+树原理讲解.adoc, B+树原理讲解>>.

==== 聚簇索引(Clustered Index)

InnoDB 将数据与主键索引存储在一起, 称为聚簇索引:

* 叶子节点: 存储**完整的数据行**(所有列)
* 非叶子节点: 存储**主键值 + 子页指针**, 用于索引查找

[source,text]
----
         [非叶子节点]
         [10 | 20 | 30]
        /    |    |    \
      ...  [10-19] [20-29] [30-...]
              |
         叶子节点(数据页)
         [id=10, name='A', ...]
         [id=11, name='B', ...]
         [id=12, name='C', ...]
         ↓
         [next page pointer] -> 下一个数据页
----

聚簇索引特性::

* **物理有序性:** 数据页按主键顺序通过双向链表连接, 主键范围查询直接顺序扫描数据页, 效率极高
* **插入性能:** 插入主键接近当前最大值时(如自增主键), 追加写入当前页; 插入中间值时可能触发**页分裂**, 产生额外 I/O

==== 二级索引(Secondary Index)

二级索引的叶子节点不存储完整数据行, 只存储 **索引列 + 主键值**:

[source,text]
----
-- 对 name 列建立二级索引
CREATE INDEX idx_name ON t1(name);

-- 查询流程
SELECT * FROM t1 WHERE name = 'Alice';
1. 在 idx_name 的 B+ 树中查找叶子节点
2. 找到 name='Alice' 的记录, 得到主键 id
3. 通过主键 id 回表查询聚簇索引获取完整行
----

二级索引的回表问题::

* 当二级索引查询需要回表且要访问的行数较多时(如超过全表的 20%), MySQL 优化器可能选择**全表扫描**而非索引扫描
* 可以使用**覆盖索引**避免回表: 如果 SELECT 的列都在索引中, 则直接从二级索引返回, 无需回表

=== 页分裂与页合并

==== 页分裂

向 B+ 树插入记录时, 如果目标页已满, InnoDB 会将页内约 50% 的记录移动到新页:

页分裂触发条件::

* 当前页的 Free Space 不足以容纳新插入的记录
* 插入的记录按主键顺序应落在当前页的中间位置

页分裂过程::

. 分配一个新的页
. 将原页中后 50% 的记录复制到新页
. 调整链表指针, 建立 Prev/Next 关系
. 在父节点(非叶子节点)中插入新页的边界键
. 如果父节点也满了, 则递归分裂, 直到根节点

==== 页合并

当页内记录删除或更新导致记录减少时, InnoDB 会尝试与相邻页合并:

页合并触发条件::

* 页内记录数低于 MERGE_THRESHOLD(默认 50% 的页空间)
* 相邻页有足够的空闲空间容纳本页数据

页合并的好处::

* 减少数据页数量, 降低 B+ 树高度
* 提升缓存命中率, 减少 I/O

=== 物理存储结构

一个独立表空间 `.ibd` 文件的物理布局:

[source,text]
----
+---------------------------+
| 页 0: FSP_HDR             | 文件空间头: 管理整个表空间的区信息
+---------------------------+
| 页 1: IBUF_BITMAP         | Insert Buffer 位图页
+---------------------------+
| 页 2: INODE               | 段(segment) 信息管理页
+---------------------------+
| 页 3: SYS                 | 数据字典头页(存储索引根页位置等)
+---------------------------+
| 页 4: INDEX               | 第一个索引(Primary Key)的根页
+---------------------------+
| 页 5+: 数据+索引页        | B+ 树的叶子/非叶子节点
+---------------------------+
| ...                       |
+---------------------------+
| 页 N: 分配的空间          | 表空间随数据增长扩展
+---------------------------+
----

XDES(Extent Descriptor) 页结构::

* 存储在 FSP_HDR 页和后续的 XDES 页中
* 每隔 16384 个区(约 16GB)会插入一个新 XDES 页
* 每个 XDES Entry 占 40 字节, 记录区的状态(FREE/FREE_FRAG/FULL_FRAG)和位图

=== 总结

MySQL InnoDB 的数据存储原理可以归纳为以下几个要点:

* **分层架构:** 表空间 -> 段 -> 区 -> 页 -> 行, 每层都有明确的管理职责
* **页为核心:** 页是 I/O 和存储的最小单位(16KB), 其内部通过 Page Directory、记录链表等机制实现高效查找
* **B+ 树组织:** 聚簇索引将数据行直接存储在叶子节点, 二级索引存储主键引用, 通过回表获取完整行
* **行格式选择:** DYNAMIC 是最通用的选择, COMPRESSED 适合归档场景, REDUNDANT 仅用于兼容
* **页分裂与合并:** 自动维护 B+ 树的平衡性, 但频繁的页分裂会影响写入性能, 建议使用自增主键减少分裂
* **数据文件结构:** `.ibd` 文件以页为单位顺序组织, 固定页(0~4)管理元数据, 后续页存储数据和索引
