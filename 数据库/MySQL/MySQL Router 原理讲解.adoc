== MySQL Router 原理讲解

=== MySQL Router 是什么?

MySQL Router 是 MySQL 官方提供的一个轻量级、透明中间件, 它位于应用程序和 MySQL 数据库集群之间. 它的核心目标是**实现高可用性和可扩展性**, 对应用程序来说, 连接数据库的体验几乎和无 Router 时一样.

您可以把它理解为一个**智能的数据库流量指挥员**. 应用程序不再需要关心后端到底有多少个数据库节点、哪个是主、哪个是从. 它只需要连接 Router 提供的统一入口, Router 会自动将请求引导到正确的目标服务器.

=== 核心设计目标与工作原理概述

**设计目标:**

. **高可用性:** 自动检测后端数据库节点的故障, 并在主节点失效时, 将写请求路由到新的主节点.

. **负载均衡:** 将读请求分散到多个从节点, 提升整体读取性能.

. **应用透明:** 应用程序无需修改代码, 只需更改连接地址为 Router 的地址.

. **轻量级:** 本身不持久化数据, 资源消耗小, 部署简单.

**工作原理概述:**

MySQL Router 启动时, 会读取配置文件并连接到**元数据服务器**, 获取整个数据库集群的拓扑结构(谁是主, 谁是从, 他们的状态如何). 然后, Router 开始监听指定的网络端口.

当应用程序连接到 Router 时, Router 并不会立即与后端 MySQL 建立连接. 它只是接受了这个连接. 只有当应用程序发送了第一个 SQL 请求时, Router 才会根据**路由策略**, 选择一个合适的后端 MySQL 服务器, 并与它建立连接. 此后, Router 就在应用程序和 MySQL 服务器之间扮演一个**双向转发通道**的角色.

=== 核心架构与组件

MySQL Router 的核心架构可以分为两个主要部分: **启动时的引导阶段** 和 **运行时的路由核心**.

==== 引导阶段

这个阶段发生在执行 `mysqlrouter bootstrap` 命令时. Router 会做以下几件关键事情:

* **连接元数据:** 使用你提供的元数据服务器地址(通常是当前的主节点)进行连接.

* **获取集群拓扑:** 从 `mysql_innodb_cluster_metadata` 库中查询集群的完整信息, 包括所有节点的地址、角色(主/从)、状态等.

* **生成配置文件:** 基于获取的拓扑信息, 自动生成一个配置文件 `mysqlrouter.conf`. 这个文件包含了路由策略、监听端口和后端服务器列表.

* **生成启动脚本:** (可选)生成用于系统管理的启动/停止脚本.

**关键点:** Router 高度依赖元数据. 元数据是所有 Router 和集群节点的"事实来源".

==== 路由核心

Router 运行后, 其核心是一个异步的、基于事件驱动的网络框架. 主要组件包括:

* **路由插件:** 这是 Router 的"大脑". 不同的插件实现了不同的路由逻辑. 最常见的两个是:

** **routing:read_write:** 用于读写分离. 通常监听一个端口(如 6446), 将写请求和事务性读请求发往主节点, 将只读请求发往从节点.

** **routing:read_only:** 用于只读负载均衡. 通常监听另一个端口(如 6447), 将所有连接请求以轮询方式发往从节点.

* **目标服务器池:** 每个路由插件都维护着一个它可用的后端 MySQL 服务器列表. 这个列表会根据节点的健康状态动态更新.

* **连接池:** (可选)Router 可以维护一个到后端服务器的空闲连接池, 以减少建立新连接的开销.

* **健康检查模块:** 定期对后端服务器列表中的节点执行健康检查(例如, 发送一个简单的 SELECT 1 查询). 如果节点连续失败, 则将其标记为不可用, 并从可用服务器池中移除.

=== 详细工作流程

我们以一个典型的读写分离场景为例, 描述一次完整的 SQL 请求流程:

. **应用发起连接:**

** 应用程序使用数据库连接字符串(如 jdbc:mysql://router-host:6446/my_db)连接到 Router 的 6446 端口(读写端口).

. **Router 接受连接:**

** Router 接受 TCP 连接, 但此时并未与任何后端 MySQL 建立连接. 连接处于"待命"状态.

. **应用发送 SQL 请求:**

** 应用程序发送第一条 SQL 语句, 例如 INSERT INTO t1 VALUES (1);.

. **Router 分析并路由:**

** **routing:read_write** 插件开始工作.

** **SQL 解析与分类:** Router 会对 SQL 语句进行一个轻量级的解析. 它主要关注 SQL 的关键字, 而不是完整解析.

*** 如果语句以 SELECT 开头, 并且不包含 FOR UPDATE 或 LOCK IN SHARE MODE 等锁定语法, 同时不在一个显式事务中(BEGIN / START TRANSACTION), 它可能被归类为只读.

*** 如果语句是 INSERT, UPDATE, DELETE, CREATE, DROP 等, 或者任何在显式事务中的语句, 都会被归类为读写.

** **选择目标服务器:**

*** 对于读写请求, Router 从服务器池中选择主节点.

*** 对于只读请求, Router 使用配置的负载均衡策略(如轮询、第一个可用等)从健康的从节点中选择一个.

** **建立后端连接:** Router 与选定的 MySQL 服务器建立连接. 如果连接池中有可用连接, 则直接复用.

. **数据转发:**

** Router 将应用程序发来的 INSERT 语句通过新建立的连接发送给主节点.

** Router 接收主节点的返回结果, 并将其原封不动地转发回应用程序.

. **连接生命周期管理:**

** 此后, 这个应用连接和 Router 到后端 MySQL 的连接将绑定在一起, 直到应用断开连接.

** 在该连接的生命周期内, 所有后续请求(即使有 SELECT)默认都会发送到同一个主节点, 以保证会话一致性(例如, 读取刚写入的数据).

. **故障转移:**

** 假设主节点突然宕机.

** Router 的健康检查模块会迅速检测到主节点不可用.

** Router 会立即联系元数据服务器, 获取新的集群拓扑, 发现新的主节点已经选举产生.

** 对于**新的连接请求**, routing:read_write 插件会自动将其路由到**新的主节点**.

** 对于**已经存在的连接到旧主的连接**, 这些连接会中断. 应用程序会收到一个错误, 需要应用程序具备**重连机制**. 重连后, 新的连接就会被路由到新的主节点.

=== 关键特性与深入理解

. **路由粒度:** Router 的**路由粒度是连接级别, 而不是语句级别**. 它在连接建立时或第一个请求时做出路由决策, 之后该连接通常固定在一个后端节点上. 这与某些在语句级别进行路由的代理(如 ProxySQL)不同.

. **元数据依赖:** Router 本身是无状态的, 它强烈依赖于外部的元数据. 在 MySQL InnoDB Cluster / MGR 环境中, 这个元数据由 Group Replication 提供和保证一致性.

. **轻量级代理:** Router 不解析完整的 SQL 语法, 不缓存数据, 不重写查询. 它只做最基本的协议分析和数据包转发, 因此延迟很低, 性能很好.

. **与 MGR 的深度集成:** 这是 Router 最大的优势. 它能理解 MGR 的语义, 比如:

** 知道只有主节点可写.

** 在 `group_replication_single_primary_mode` 模式下, 自动将写请求路由到单一主节点.

** 在 `group_replication_multi_primary_mode` 模式下, 可以将写请求负载均衡到所有节点.

=== 总结

MySQL Router 的原理可以概括为:

**基于元数据感知集群拓扑, 通过轻量级 SQL 解析和预定义的路由策略, 在连接级别上将应用程序的请求智能地分发到后端合适的 MySQL 节点上, 同时通过持续的健康检查来保证高可用性.**

它通过一种简单而有效的方式, 为 MySQL 集群(尤其是 InnoDB Cluster)提供了一个不可或缺的接入层, 极大地简化了应用程序对后端复杂数据库架构的访问和管理.
