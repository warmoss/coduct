== MySQL Next-Key Lock 原理讲解

理解 Next-Key Lock 是理解 MySQL InnoDB 在 **可重复读(REPEATABLE-READ)** 隔离级别下如何避免**幻读(Phantom Read)** 问题的关键.

=== 为什么需要 Next-Key Lock?

在讨论"是什么"之前, 我们先要明白"为什么".

* **读已提交(READ-COMMITTED)** 隔离级别下, 只使用记录锁(Record Lock), 无法解决幻读问题. 因为记录锁只锁住已有的行, 如果有新插入的行(正好在查询范围内), 就会被读到, 产生幻读.

* **可重复读(REPEATABLE-READ)** 隔离级别要求在一个事务中, 多次执行相同的查询, 结果集必须一致. 因此, 必须有一种机制来防止其他事务插入新的、满足查询条件的记录.

Next-Key Lock 就是 InnoDB 为了解决这个问题而设计的锁机制. 它不仅仅是锁住记录本身, 还锁住了记录之间的"间隙".

=== Next-Key Lock 是什么?

Next-Key Lock 本质上是 **记录锁(Record Lock)** 和 **间隙锁(Gap Lock)** 的组合.

* **记录锁(Record Lock):** 锁住索引树上具体的一条记录.

* **间隙锁(Gap Lock):** 锁住索引树中两条记录之间的间隙, 或者第一个记录之前/最后一个记录之后的"开区间". 它是一个"范围锁", 禁止在这个范围内插入任何新记录.

**Next-Key Lock = 间隙锁(Gap Lock) + 下一记录的记录锁(Record Lock)**

它锁定的是一个 **左开右闭** 的区间 `(A, B]`.

举个例子, 假设我们有一个表, 其索引值有: 5, 10, 15.

那么, Next-Key Lock 可能锁定的区间包括:

* (-∞, 5]

* (5, 10]

* (10, 15]

* (15, +∞]

=== Next-Key Lock 是如何工作的?

我们通过一个经典例子来演示.

**表结构:**

[source, sql]
----
CREATE TABLE `users` (
  `id` int(11) NOT NULL,
  `age` int(11) DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_age` (`age`)
) ENGINE=InnoDB;

-- 数据
INSERT INTO `users` VALUES (1, 5), (5, 10), (10, 15), (15, 20);
----

假设 age 上有一个普通二级索引 `idx_age`. 索引树上的数据大概是这样的:

[source, text]
----
[5] -> [1]
[10] -> [5]
[15] -> [10]
[20] -> [15]
----

**场景: 在可重复读隔离级别下, 执行范围查询**

**事务A:**

[source, sql]
----
BEGIN;
SELECT * FROM users WHERE age BETWEEN 10 AND 15 FOR UPDATE;
----

这条 SQL 的目的是锁住 age 在 10 到 15 之间的所有记录(包括边界), 并且防止其他事务插入这个范围内的新数据.

此时, InnoDB 会为事务A加上如下的 Next-Key Lock:

. **在 idx_age 索引上:**

** 找到 age=10 的记录, 加上 Next-Key Lock, 锁定区间 (5, 10].

*** 这个锁包括 (5, 10) 的间隙(防止插入 age=6,7,8,9 的记录)和 age=10 这条记录的记录锁.

** 找到 age=15 的记录, 加上 Next-Key Lock, 锁定区间 (10, 15].

*** 这个锁包括 (10, 15) 的间隙(防止插入 age=11,12,13,14 的记录)和 age=15 这条记录的记录锁.

. **锁优化/退化:**

** 对于 age=15 这条记录, 因为我们的查询条件是 age <= 15, 所以 InnoDB 知道 age=15 是范围内的最后一个值. 它会将 (10, 15] 这个 Next-Key Lock 退化(降级) 为一个 间隙锁(Gap Lock), 锁定 (10, 15), 再加上一个 age=15 的记录锁. 效果上依然是锁住了 (10, 15], 但内部实现有细微差别.

** 同时, 为了确保范围查询的完整性, InnoDB 还会在 age=15 的下一个值 age=20 上加一个 间隙锁(Gap Lock), 锁定区间 (15, 20). 这是为了防止其他事务插入 age=18 这样的记录, 因为 age=18 虽然大于15, 但如果插入成功, 可能会在后续查询中"幻影"般地出现(取决于具体实现和数据扫描方式).

**最终, 事务A在 idx_age 索引上锁定的范围是:**

* (5, 10] (Next-Key Lock)

* (10, 15] (可以理解为 (10, 15) 的 Gap Lock + 15 的 Record Lock)

* (15, 20) (Gap Lock)

**现在, 我们来看其他事务的操作是否会阻塞:**

**事务B:**

[source, sql]
----
-- 会被阻塞. 因为想插入 age=9, 落在 (5, 10) 的间隙里.
INSERT INTO users VALUES (100, 9);

-- 会被阻塞. 因为想插入 age=12, 落在 (10, 15) 的间隙里.
INSERT INTO users VALUES (101, 12);

-- 会被阻塞. 因为想插入 age=18, 落在 (15, 20) 的间隙里.
INSERT INTO users VALUES (102, 18);

-- 会被阻塞. 因为 age=10 的记录上有记录锁.
UPDATE users SET name = 'test' WHERE age = 10;

-- 成功. 因为 age=5 不在锁范围内.
INSERT INTO users VALUES (103, 3);
-- 成功. 因为 age=25 不在锁范围内.
INSERT INTO users VALUES (104, 25);
----

=== 加锁规则的精炼与特例

Next-Key Lock 的加锁规则非常复杂, 但可以总结一些核心要点:

. **加锁基本单位是 Next-Key Lock:** 默认情况下, InnoDB 都会以 Next-Key Lock 为单位进行加锁.

. **索引上的等值查询:**

** **如果匹配到记录:** Next-Key Lock 会退化为记录锁(Record Lock).

*** 例如: SELECT * FROM users WHERE age = 10 FOR UPDATE;

*** 如果 age=10 存在, 则只锁 age=10 这一行记录.

** **如果未匹配到记录:** Next-Key Lock 会退化为间隙锁(Gap Lock).

*** 例如: SELECT * FROM users WHERE age = 12 FOR UPDATE;

*** 如果表中没有 age=12, 则锁住 (10, 15) 这个间隙.

. **索引上的范围查询:**

** 会访问到不满足条件的第一个值为止.

** 就像上面的例子, BETWEEN 10 AND 15 会一直锁到 age=20 的前面.

. **唯一索引 vs 非唯一索引:**

** **唯一索引** 上的等值查询, 由于能唯一确定一条记录, 更容易退化为记录锁.

** **非唯一索引** 上的等值查询, 即使匹配到记录, 也可能会锁住记录和其前后的间隙, 因为它无法保证唯一性, 需要防止其他事务插入相同的值.

=== 注意事项

* **锁是基于索引的:** 如果查询没有使用到索引, MySQL 就不得不进行全表扫描, 这会导致对所有扫描过的记录(甚至是全表)都加上 Next-Key Lock, 极易引发性能问题和死锁. **所以, 生产环境一定要避免无索引的范围更新/查询.**

* **目的是解决幻读:** Next-Key Lock 的核心目标是防止幻读, 它通过锁定"可能产生新记录的间隙"来实现.

* **只在可重复读(REPEATABLE-READ)下生效:** 在读已提交(READ-COMMITTED) 隔离级别下, 间隙锁(Gap Lock)会被禁用, Next-Key Lock 也就失效了, 只剩下记录锁, 所以无法避免幻读.

=== 总结

Next-Key Lock 是 InnoDB 在可重复读隔离级别下的核心并发控制机制. 它通过 "记录锁 + 间隙锁" 的组合拳, 不仅锁住了已经存在的记录, 还锁住了记录之间的空隙, 从而有效地防止了幻读现象. 理解它的原理, 对于设计高性能、高并发的数据库应用, 以及分析和解决复杂的死锁问题至关重要.
