== MySQL Gap Lock 原理讲解

MySQL Gap Lock(间隙锁) 是理解 InnoDB 在 可重复读(Repeatable Read) 隔离级别下如何防止幻读的关键.

=== 什么是 Gap Lock?

Gap Lock 是一种**锁住索引记录之间的"间隙"**的锁, 或者锁住第一个索引记录之前或最后一个索引记录之后的"间隙"的锁.

这里的关键词是 "**间隙**" 和 "**索引**".

* **间隙:** 指的是在一个索引树中, 两个已存在的索引值之间的区间.

** 例如, 一个表有一个 id 主键, 现有记录为 5, 10, 15. 那么产生的间隙就有:

*** (-∞, 5)

*** (5, 10)

*** (10, 15)

*** (15, +∞)

* **作用:** Gap Lock 的唯一目的就是**防止其他事务在这个"间隙"中插入新的数据**. 它不锁定任何已存在的记录本身.

**一个重要的特性:** Gap Lock 是"共享"的. 这意味着, 一个事务持有一个 Gap Lock, 并不会阻止另一个事务也获取同一个 Gap Lock. 它们的目的都不是为了独占数据, 而是为了共同"守护"这个区间, 不让新数据插入.

=== 为什么需要 Gap Lock? —— 解决幻读

Gap Lock 主要是为了在 **可重复读(RR)** 隔离级别下解决"幻读"问题.

* **幻读:** 一个事务在重新执行同一个查询时, 发现了其他事务新提交的、满足查询条件的记录("幻影行").

**举例说明:**

假设我们有一张表 t, 其中 id 是主键.

|===
|id

|5
|10
|15
|===

**事务 A 执行:**

[source, sql]
----
START TRANSACTION;
SELECT * FROM t WHERE id BETWEEN 10 AND 15 FOR UPDATE;
----

这条语句会返回 id=10 和 id=15 这两条记录. 在 RR 隔离级别下, InnoDB 不仅会给 id=10 和 id=15 的记录加上行锁(Record Lock), 还会给它们周围的间隙加上 Gap Lock.

* 锁住的区间是: `(5, 10)`, `(10, 15)`, `(15, +∞)`.

* 更准确地说, 这里使用的是 Next-Key Lock(临键锁, 它是行锁 + 间隙锁的组合), 锁住了 `(5, 10]`, `(10, 15]`,` (15, +∞)`.

**此时, 事务 B 尝试执行:**

[source, sql]
----
INSERT INTO t (id) VALUES (12); -- 被阻塞!
INSERT INTO t (id) VALUES (6);  -- 被阻塞!
INSERT INTO t (id) VALUES (20); -- 被阻塞!
----

所有这些插入操作都会被阻塞, 因为它们要插入的位置(6, 12, 20)都落在了事务 A 锁定的间隙范围内.

**当事务 A 提交后(COMMIT;), 它释放了所有的锁, 事务 B 的插入操作才能继续.**

通过锁定整个可能插入"幻影行"的区间, Gap Lock 确保了在事务 A 执行期间, 没有任何新的记录可以插入到 BETWEEN 10 AND 15 这个条件所覆盖的范围内, 从而彻底防止了幻读的发生.

=== Gap Lock 与 Next-Key Lock

在 InnoDB 的 RR 隔离级别下, 默认的加锁单位是 **Next-Key Lock**.

* Next-Key Lock = Record Lock(行锁) + Gap Lock(间隙锁)

* 它锁定的范围是 一个索引记录以及该记录之前的间隙.

* 例如, 对于索引记录 10, Next-Key Lock 会锁定 (5, 10] 这个左开右闭的区间.

在之前的例子中:

* 对 id=10 加锁, 实际上是加了 (5, 10] 的 Next-Key Lock.

* 对 id=15 加锁, 实际上是加了 (10, 15] 的 Next-Key Lock.

* 同时, 为了防止在最大记录之后插入, 还会对 supremum 伪记录加一个 (15, +∞) 的 Gap Lock.

=== 特殊情况与优化

==== 唯一索引的等值查询

**如果查询条件使用了唯一索引, 并且是等值查询(例如 WHERE id = 10), 并且数据存在, InnoDB 会进行优化, 仅使用 Record Lock(行锁), 而不会使用 Gap Lock.**

**原因:** 既然索引是唯一的, 等值查询最多只可能返回一条记录. 只要锁住这条记录本身, 就能防止其他事务修改它, 同时因为唯一性约束, 也不可能在同一个位置插入新记录, 所以无需加间隙锁.

**但是:**

* 如果等值查询的记录**不存在**, 它仍然会加 Gap Lock.

** 例如: SELECT * FROM t WHERE id = 12 FOR UPDATE;

** 因为记录 12 不存在, 它会锁住 (10, 15) 这个间隙, 防止其他事务插入 id=12 的记录, 从而保证了下次执行相同查询时结果集依然为空.

==== 非唯一索引

对于非唯一索引, Gap Lock 的行为非常关键.

假设表 t 有一个非唯一索引 score, 记录如下:

|===
|id (PK)|score (INDEX)

|1|60
|2|80
|3|80
|4|100
|===

事务 A 执行:

[source, sql]
----
SELECT * FROM t WHERE score = 80 FOR UPDATE;
----

为了防止幻读, InnoDB 必须锁定所有 score = 80 的记录, 以及它们周围的间隙, 防止新的 score = 80 的记录被插入. 它会锁定:

* (60, 80] 区间(第一个80)

* (80, 80] 区间(第二个80, 实际上和第一个锁定的区间可能合并)

* (80, 100) 区间(防止在80和100之间插入新的80)

这显示了在非唯一索引上, 加锁范围会大得多, 也是并发问题容易发生的地方.

=== 读已提交(Read Committed)隔离级别的不同

在 **读已提交(RC)** 隔离级别下, **Gap Lock 被禁用了**.

* **原因:** RC 隔离级别不要求解决幻读.

* **效果:** 在 RC 级别下, SELECT ... FOR UPDATE 或 UPDATE 语句通常只使用 Record Lock(行锁), 而不会锁定间隙.

* **后果:** 这会导致更高的并发性, 因为插入操作很少被阻塞, 但代价是可能会出现幻读.

=== 总结

[cols="1,5"]
|===
|特性|说明

|**本质**
|锁定索引记录之间的"间隙", 防止插入.

|**目的**
|在 可重复读(RR) 隔离级别下防止幻读.

|**锁特性**
|共享锁, 多个事务可以同时持有同一个间隙的 Gap Lock.

|**默认单位**
|在 RR 级别下, 与行锁组合成为 Next-Key Lock.

|**特殊情况**
|唯一索引的等值查询且记录存在时, 会优化为仅加行锁.

|**RC级别**
|被禁用, 因此 RC 级别下会发生幻读.

|===

**排查 Gap Lock 引起的死锁:**

由于 Gap Lock 是共享的, 它本身不直接导致死锁. 但当一个事务要插入数据时(需要获取插入意向锁), 可能会等待另一个事务释放 Gap Lock. 如果多个事务形成了这种循环等待, 就会发生死锁. 通过 SHOW ENGINE INNODB STATUS 命令可以查看死锁日志, 其中 lock_mode X locks gap before rec 就表示一个排他的 Gap Lock(插入意向锁与已存在的 Gap Lock 冲突时的等待状态).
