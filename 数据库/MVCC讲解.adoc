== MVCC讲解

=== 什么是 MVCC?
**MVCC** 的全称是 **Multi-Version Concurrency Control**, 中文是**多版本并发控制**.

它是一种**并发控制**的方法, 通过对数据行创建多个版本来实现. 其核心思想是: **当需要修改一条数据时, 它不会直接覆盖原有数据, 而是创建一个新的版本. 因此, 在同一个时间点, 数据库中可能同时存在同一个数据的多个版本(快照)**.

这样, 读操作和写操作就可以互不干扰地进行:

* **读操作:** 读取的是某个特定时间点的数据快照(一个旧的、一致的版本).

* **写操作:** 创建新的数据版本, 不会阻塞读操作去读取旧版本的数据.

这极大地提高了数据库在多用户、高并发场景下的性能和吞吐量.

=== 为什么需要 MVCC? 为了解决什么问题?
在没有 MVCC 的数据库(或使用锁机制的并发控制)中, 通常通过加锁来保证数据的一致性. 这会带来几个问题:

** **读写冲突:** 写操作会阻塞读操作(写锁是排他锁, 读锁是共享锁).

** **写写冲突:** 写操作之间会相互阻塞.

** **性能瓶颈:** 大量的锁竞争会严重降低数据库的并发性能, 导致吞吐量下降.

MVCC 就是为了解决**读写冲突**而生的. 它通过" 数据多版本" 的方式, 几乎完全消除了读操作和写操作之间的相互阻塞, 使得:

** **读不阻塞写:** 读一个数据的同时, 允许其他事务修改该数据(读的是旧版本).

** **写不阻塞读:** 修改一个数据的同时, 允许其他事务读取该数据的旧版本.

**注意:** MVCC 并没有完全解决**写写冲突**. 两个事务试图同时修改同一行数据时, 仍然需要通过锁(如行锁)或其它机制(如乐观锁)来串行化处理, 以保证数据一致性.

=== MVCC 是如何工作的? (以 InnoDB 为例)
不同的数据库实现 MVCC 的细节略有不同, 但思想一致. 这里以最流行的 MySQL 的 InnoDB 存储引擎为例来讲解其核心机制.

InnoDB 通过以下三个核心组件来实现 MVCC:

. **隐藏字段**
+
InnoDB 为每行数据(记录)添加了三个隐藏的系统字段:
+
** **DB_TRX_ID** (6字节): 事务ID. 表示最后修改(INSERT 或 UPDATE)这条记录的事务ID.

** **DB_ROLL_PTR** (7字节): 回滚指针. 指向该记录的上一个版本在 Undo Log 中的地址.

** **DB_ROW_ID** (6字节): 行ID. 随着新行插入而单调递增的行ID. 如果表没有定义主键, InnoDB 会使用这个字段来创建聚簇索引.

. **Undo Log (回滚日志)**
+
Undo Log 保存了数据被修改前的多个**历史版本**. 当一条记录被更新时, 它的旧版本数据会被写入 Undo Log 中, 形成一个链表. DB_ROLL_PTR 指针就指向这个链表, 可以通过它找到该记录的所有历史版本.

. **Read View (读视图)**
Read View 是**事务在进行快照读(SELECT)**时产生的, 它定义了当前事务能看到哪个版本的数据.
+
Read View 主要包含以下几个关键属性:
+
** **m_ids:** 生成 Read View 时, 系统中活跃(尚未提交)的事务ID列表.
+
** **min_trx_id:** m_ids 中最小的事务ID.
+
** **max_trx_id:** 生成 Read View 时, 系统应该分配给下一个事务的ID.
+
** **creator_trx_id:** 创建这个 Read View 的事务ID.

**数据可见性规则**

当一个事务执行快照读时, 对于每一条记录, 会按照以下规则判断哪个版本对它可见:

. 如果记录的 **DB_TRX_ID** < **min_trx_id**, 说明该版本在 Read View 创建前已提交, **可见**.

. 如果记录的 **DB_TRX_ID** >= **max_trx_id**, 说明该版本在 Read View 创建后才生成, **不可见**. 需要根据 **DB_ROLL_PTR** 找到上一个版本再次判断.

. 如果 **min_trx_id** &lt;= **DB_TRX_ID** < **max_trx_id**, 则需检查 **DB_TRX_ID** 是否在 **m_ids**(活跃事务列表)中:

*** 如果在, 说明创建 Read View 时, 该版本所属事务还未提交, 该版本**不可见**.

*** 如果不在, 说明创建 Read View 时, 该版本所属事务已提交, 该版本**可见**.

. 如果记录的 **DB_TRX_ID** = **creator_trx_id**, 说明这个版本是由当前事务自己修改的, **可见**.

如果某个版本对当前事务不可见, 就顺着 Undo Log 链表找到上一个版本, 重复上述判断规则, 直到找到最早的一个可见版本或确认都不可见.

=== MVCC 与隔离级别
MVCC 与事务的隔离级别紧密相关, 主要应用于 **READ COMMITTED (RC)** 和 **REPEATABLE READ (RR)** 这两个级别.

* **READ COMMITTED (RC):** **每次**执行快照读时, 都会生成一个新的 Read View. 这会导致同一个事务中两次查询可能看到不同的数据(因为期间有其他事务提交了), 即**不可重复读**.

* **REPEATABLE READ (RR):** 只在**第一次**执行快照读时生成一个 Read View, 后续所有的读操作都复用这个 View. 这样就保证了在同一个事务中, 每次读到的数据都是一致的, 解决了不可重复读的问题.

**注意:** InnoDB 通过 **Next-Key Lock** 机制(临键锁), 在 RR 级别下还避免了幻读.

=== 优点与缺点
优点::
* **高并发:** 极大地提高了读性能, 读写操作几乎不会相互阻塞, 非常适合读多写少的场景.

* **避免死锁:** 读操作不需要加锁, 减少了因锁竞争导致的死锁概率.

缺点::
* **额外存储:** 需要为每行数据存储多个版本, 会消耗更多的存储空间(主要是 Undo Log).

* **维护开销:** 数据库需要定期清理不再需要的旧版本数据(Purge 操作), 有维护开销.

* **可能读到旧数据:** 由于读的是历史快照, 无法实时读取到最新的已提交数据(但可以通过加锁读 SELECT ... FOR UPDATE 来实现).

=== 总结
[cols="1,5"]
|===
|特性|解释

|**核心思想**
|通过维护数据的多个版本来实现非阻塞的读操作.

|**实现组件**
|隐藏字段 (TRX_ID, ROLL_PTR)、Undo Log、Read View.

|**解决核心问题**
|读写冲突, 大幅提升数据库并发性能.

|**主要应用**
|支持 READ COMMITTED 和 REPEATABLE READ 隔离级别.

|**代表数据库**
|MySQL (InnoDB), PostgreSQL, Oracle 等主流数据库都实现了 MVCC.
