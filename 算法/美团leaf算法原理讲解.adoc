== 美团leaf算法原理讲解

=== 概述

在分布式系统中, 生成全局唯一 ID 是一个基础但关键的问题. 自增主键无法跨库使用, UUID 虽简单但无序且过长, <<百度UID原理讲解.adoc, 百度 UidGenerator>> 解决了高性能问题, 但其秒级精度和固定位宽限制并不适用于所有场景.

美团 Leaf 是一个**分布式唯一 ID 生成系统**, 由美团点评开源. 它提供了**两种独立的 ID 生成模式**, 分别应对不同场景:

* **Leaf-segment(号段模式):** 基于数据库段号分配, 生成**有序递增的数值型 ID**, 适合对 ID 有序性要求高的业务.
* **Leaf-snowflake(雪花算法模式):** 基于改进的 Snowflake 算法, 生成**64位长整型 ID**, 适合对高性能、高并发有要求的场景.

两种模式可以独立部署为 REST 或 RPC 服务, 供业务方调用.

=== Leaf-segment(号段模式)

==== 问题背景

最直接的分布式 ID 方案是用数据库自增主键: 每次插入获取 ID, 但这种方式存在明显的性能瓶颈:

* 每次请求都需一次数据库 IO, 延迟高.
* 数据库单点成为系统瓶颈, 无法应对高并发.

**号段模式**(segment)的核心思想是: **批量获取, 内存生成**. 不再每次请求都访问数据库, 而是一次性从数据库获取一段 ID 区间, 然后在内存中分配.

==== 基本原理

Leaf-segment 在数据库中维护一张 `leaf_alloc` 表:

[source,sql]
----
CREATE TABLE leaf_alloc (
    biz_tag VARCHAR(128) NOT NULL COMMENT '业务标识',
    max_id BIGINT NOT NULL DEFAULT 0 COMMENT '当前已分配的最大ID',
    step INT NOT NULL COMMENT '每次获取的号段长度',
    update_time TIMESTAMP NOT NULL,
    PRIMARY KEY (biz_tag)
) ENGINE=InnoDB;
----

核心字段解释:

biz_tag:: 业务标识, 不同的业务(如订单号、用户号)使用不同的 tag, 实现隔离.
max_id:: 当前已分配的最大 ID, 初始为 0.
step:: 号段步长, 即每次从数据库获取的 ID 数量.

**工作流程:**

. 服务启动时, 向数据库请求 `biz_tag` 对应的号段: `UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = ?`.

. 更新成功后, 读取更新后的 `max_id`, 获得可用号段 `[max_id - step + 1, max_id]`.

. 将号段载入内存, 每次请求从中取出一个 ID(原子递增), 无需再访问数据库.

. 当号段快耗尽(如剩余 10%)时, 异步发起下一次号段获取, 保证 ID 供应不中断.

**特点:**

* **趋势递增:** 由于号段是连续递增的, 生成的 ID 整体趋势递增, 对 MySQL B+ 树索引友好.
* **可定制步长:** `step` 越大, 号段越大, 数据库访问频率越低. 可根据 QPS 预估设置合适的步长.
* **业务隔离:** 不同 `biz_tag` 的号段互不影响, 避免单一业务耗尽 ID 资源.

==== 双 Buffer 优化

基本的号段模式存在一个问题: 当号段用完的时刻正好有大量并发请求涌入, 所有请求都会等待数据库号段更新, 导致**毛刺延迟**.

Leaf-segment 的解决方案是 **双 Buffer 机制**:

[plantuml, "Leaf-segment 双 Buffer 结构", format=png]
----
@startuml
skinparam rectangle {
    BackgroundColor LightBlue
    BorderColor DarkBlue
}

rectangle "Buffer1\n(segment: [1001, 2000]\n剩余: 60%)" as buf1
rectangle "Buffer2\n(segment: [2001, 3000]\n剩余: 100%)" as buf2

rectangle "ID Consumer" as consumer

rectangle "DB (leaf_alloc)" as db

buf1 --> consumer : 分配ID
consumer --> buf1 : 请求ID
buf1 ..> db : 剩余<10%,\n触发异步加载
db --> buf2 : 加载新号段 [2001, 3000]
buf2 --> buf1 : 角色切换

note right of buf2
  当 Buffer1 消耗到阈值时,
  Buffer2 接管服务,
  Buffer1 异步加载新号段
end note
@enduml
----

**双 Buffer 的工作流程:**

. **初始化阶段:** 同时加载两个 Buffer: Buffer1 和 Buffer2, 分别持有前后两个号段.

. **运行阶段:** 从 Buffer1 分配 ID, 同时每个 Buffer 维护当前使用量. 当 Buffer1 消耗到阈值(如 10%)时, 触发异步线程去数据库加载新号段.

. **切换阶段:** Buffer1 耗尽后, 立即切换到 Buffer2 继续分配, 同时 Buffer2 触发异步加载新的号段到已耗尽的 Buffer1.

. 如此反复, 两个 Buffer 交替使用, **消费者始终无感知**, 彻底消除毛刺.

**核心优势:** 号段的**生产**和**消费**完全解耦, 即使数据库临时抖动, 内存中的 Buffer 也能继续响应请求.

==== 优缺点

**优点:**

* ID 有序递增, 对数据库索引友好.
* 无时钟依赖, 不存在时钟回拨问题.
* 支持业务隔离, 不同 tag 互不影响.
* 双 Buffer 机制消除了毛刺延迟.

**缺点:**

* ID 长度取决于数据库步长设定, 趋势递增而非严格单调递增(重启或切换 Buffer 时可能跳跃).
* 依赖数据库可用性, 若数据库宕机且内存号段耗尽, 则无法生成 ID.
* 不适合需要绝对保序的场景(如分布式事务的严格排序).

=== Leaf-snowflake(雪花算法模式)

==== 原理概述

Leaf-snowflake 基于经典的 **Snowflake(雪花算法)**, 生成一个 **64 位 long 型 ID**, 结构如下:

[cols="2,2,3,7"]
|===
|部分|位长|说明|特性

|**符号位**
|1
|固定为 0
|保证 ID 为正数

|**时间戳**
|41
|当前时间与纪元(如 2010-11-04)的毫秒差
|支持约 69 年, 毫秒精度

|**工作机器 ID**
|10
|唯一标识一台工作节点
|最多支持 1024 个节点

|**序列号**
|12
|同一毫秒内的自增序号
|单节点每毫秒最多 4096 个 ID

|===

其中, 工作机器 ID 在 Leaf 中需要借助第三方组件(如 ZooKeeper)自动分配, 避免人工配置.

==== 时间戳与序列号

* **时间戳**使用毫秒级精度, 41 位可表示 stem:[2^{41}] 毫秒(约 69 年), 足以覆盖绝大多数业务的长期需求.
* **序列号**为 12 位, 即每毫秒最多生成 stem:[2^{12}=4096] 个 ID. 如果一毫秒内请求超过 4096, 则阻塞至下一毫秒.

[source,java]
----
// Snowflake 核心伪代码
long id = (timestamp << 22)        // 时间戳左移 22 位
         | (workerId << 12)        // 机器 ID 左移 12 位
         | sequence;               // 序列号
----

==== 时钟回拨处理

Snowflake 算法的最大隐患是**时钟回拨** —— 如果系统时钟突然回退, 可能导致生成的 ID 与之前重复. Leaf-snowflake 的解决方案是:

. **检查回拨幅度:** 启动时和运行中持续检查当前时间与上次生成 ID 的时间. 如果发现时钟回拨:
   * **小幅度回拨(小于阈值):** 等待时钟追上后再提供服务.
   * **大幅度回拨:** 直接抛出异常或启用备用策略(如拒绝服务).

. **使用 ZooKeeper 持久化:** Leaf-snowflake 在 ZK 中保存每个节点的 `workerId` 和**上次生成 ID 的时间戳**. 启动时读取 ZK 中的时间戳, 若当前时间小于该值, 则判定发生了回拨.

. **回拨容忍:** 实际部署中, Leaf 配置了合理的时钟同步策略(NTP), 时钟回拨概率极低. Leaf 的处理策略是在可接受范围内等待, 超出范围则快速失败.

==== 优缺点

**优点:**

* **高性能:** 纯内存计算, 无网络开销, 单节点 QPS 可达百万级.
* **全局有序(ID 递增):** 时间戳在前, 生成 ID 严格递增.
* **去中心化:** 节点独立生成 ID, 不依赖中心化存储.

**缺点:**

* **时钟依赖:** NTP 时钟回拨可能导致 ID 冲突.
* **节点数限制:** 10 位 workerId 最多支持 1024 个节点.
* **ID 趋势递增但不连续:** 不同毫秒之间 ID 可能跳跃(自然流逝), 对索引仍友好.

=== Leaf-segment vs Leaf-snowflake 对比

[cols="2,5,5"]
|===
|维度|Leaf-segment(号段模式)|Leaf-snowflake(雪花算法)

|**ID 类型**
|数据库自增值(数值型)
|64 位长整型

|**有序性**
|趋势递增(重启后可能跳跃)
|严格时间递增

|**性能**
|取决于步长和双 Buffer 大小(内存分配)
|纯内存位运算, 极高(百万级 QPS)

|**数据库依赖**
|强(号段需从数据库获取)
|弱(仅 workerId 需 ZK 协调)

|**时钟依赖**
|无
|强(需 NTP 同步, 防回拨)

|**业务隔离**
|支持(biz_tag)
|不支持(全局共享)

|**适用场景**
|ID 需有序且可读的数值型业务(如订单号)
|高并发、去中心化、对 ID 格式无要求

|===

=== 部署架构

Leaf 支持两种部署方式:

* **REST 服务:** 通过 HTTP API 提供 ID 生成, 适合异构语言. 如 `GET /api/segment/get/{biz_tag}`.
* **RPC 服务:** 基于 Netty 的 Thrift 或自定义协议, 适合同语言内高吞吐调用.

生产环境中通常**两种模式共存**: 对有序性要求高的业务(如订单 ID)使用 Leaf-segment, 对高并发要求高的业务(如消息 ID)使用 Leaf-snowflake.

=== 总结

美团 Leaf 通过**号段模式**和**雪花算法模式**双引擎设计, 覆盖了分布式 ID 生成的绝大多数场景:

* **Leaf-segment** 以数据库为中心, 用空间换取时间, 双 Buffer 机制确保了平滑无毛刺的 ID 分配. 适合对 ID 有序性、可读性有要求的业务.
* **Leaf-snowflake** 以时间为锚, 用位运算实现极致的性能. 适合对高并发、低延迟有极致要求的场景.

选择时, 应结合自身业务对**有序性要求、ID格式偏好、性能需求、时钟稳定性**等维度综合考量. 对于新项目, 建议优先评估 Leaf-segment 的号段模式, 因其简单可靠且规避了时钟回拨风险.
