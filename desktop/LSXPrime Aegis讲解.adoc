== LSXPrime Aegis讲解

商业软件与 To B 应用通常需要按用户, 按机器或按时间段售卖授权, 而一个不加保护的许可证文件可被轻易复制, 篡改甚至伪造. 本文讲解开源 .NET 授权库 **LSXPrime Aegis** 的设计思路: 如何用 RSA 签名 + AES 加密的组合, 让许可证文件做到"不可伪造, 不可篡改", 并介绍其六种授权模型, 客户端与服务端整体架构, 功能开关以及二次开发扩展点.

参考: <<安全算法/rsa原理讲解.adoc#, RSA原理讲解>>, <<安全算法/aes讲解.adoc#, AES原理讲解>>

=== 什么是 Aegis

许可证 (License):: 授权方签发给使用方的电子凭证, 记录"谁在什么条件下可以使用哪个软件的哪些功能"这些信息.
授权模型 (Licensing Model):: 决定许可证与使用方绑定粒度的规则, 如绑定用户名, 绑定硬件或绑定服务器席位.
Aegis:: 由 GitHub 组织 LSXPrime 维护的 .NET 许可证解决方案, 作者为 Ahmed Abdallah. 以 "Aegis(神盾)" 命名, 寓意对软件权益的守护. 使用 MIT 许可证开源, 面向 net8.0 构建.
Aegis.Server:: Aegis 的可选后端组件, 用于承载浮动与并发授权模型的席位管理, 提供签发, 激活, 吊销, 心跳等能力.

Aegis 解决的核心问题是 **软件授权生命周期管理**: 从许可证的签发, 下发, 加载校验, 到功能开关判定, 再到并发席位的心跳保活. 它提供两个 NuGet 包:

[cols="2,6"]
|===
| NuGet 包 | 职责

| Aegis
| 客户端库, 内嵌进被授权的 .NET 应用. 负责生成, 保存, 加载, 校验许可证与功能开关查询

| Aegis.Server
| 授权服务端核心逻辑 (不含 Web 框架). 负责浮动/并发授权的签发, 激活, 吊销与心跳管理, 可被任何 Web 框架宿主
|===

=== 整体架构

Aegis 采用 **客户端库 + 可选服务端** 的两段式架构. 离线场景只依赖客户端库即可完成全部校验; 浮动与并发授权才需要引入服务端做集中式席位管理.

客户端库以静态类为主, 核心入口如下:

| 类型 | 职责

| LicenseGenerator
| 以工厂方法生成六种模型的基础 License 对象

| LicenseBuilder
| 以 Fluent 扩展方法补充密钥, 签发方, Feature, 到期时间并落盘

| LicenseManager
| 加载, 保存与在线/离线校验许可证, 维护心跳定时器

| FeatureManager
| 基于当前许可证做功能开关查询与强制

| LicenseUtils
| 签发密钥对 (LicensingSecrets) 的生成, 加解密与加载
|===

=== 六种授权模型

Aegis 通过不同的 License 子类表达不同的绑定粒度, 核心字段决定各自的约束:

[cols="3,5,4"]
|===
| 授权模型 | 关键约束 | 典型场景

| Standard (标准)
| 绑定 UserName + LicenseKey, 可选到期时间
| 单用户买断软件

| Trial (试用)
| 带试用时长, 到期即失效
| 新用户评估

| NodeLocked (节点锁定)
| 绑定机器硬件 ID
| 单机授权, 防止拷到别的机器

| Subscription (订阅)
| 记录订阅起始时间与时长, 到点自动失效
| 订阅制服务

| Floating (浮动)
| 由服务器集中管理, 组织内限定的并发用户数
| 企业内网共享授权池

| Concurrent (并发)
| 限定同时在线用户数的上限
| 按并发席位售卖
|===

其中 **浮动与并发** 属于"席位型"授权, 许可证文件本身只记录用户名与最大并发数上限, 真正的"当前占用几个席位"必须在服务器端统计, 因此这类授权必须配合 Aegis.Server 在线使用.

=== 密钥体系

Aegis 的安全根基是一对 **RSA 非对称密钥**, 全部由 `LicenseUtils.GenerateLicensingSecrets` 一次性生成.

生成与保护密钥的流程:

. 生成 RSA 密钥对, 得到 PublicKey 与 PrivateKey.
. 将私钥, 公钥与服务器 API Key 序列化为 JSON.
. 用口令派生 AES 密钥后加密该 JSON, 写入本地 `signature.bin` 文件.

其中 AES 密钥由口令经 SHA256 派生:

stem:[K_{AES} = SHA256(secretKey)]

[source,csharp]
----
// 生成并保存加密后的密钥文件
LicenseUtils.GenerateLicensingSecrets("your-secret-key",
    @"C:\Path\To\signature.bin", "your-server-api-key");   // <1>

// 运行时用同一口令解密加载
var secrets = LicenseUtils.LoadLicensingSecrets("your-secret-key",
    @"C:\Path\To\signature.bin");                          // <2>
----
<1> 生成 RSA 密钥对与 API Key, 用口令加密后写盘
<2> 客户端启动时加载, 后续许可证验签直接使用内存中的公钥

[IMPORTANT]
====
私钥只允许出现在**签发端**(你的构建或服务进程)与加密后的 `signature.bin` 中. 客户端应用只需内置公钥即可完成离线验签, 永远不要随客户端分发私钥.

文件口令保护的是"磁盘上的密钥文件"本身, 而非许可证; 真正防止许可证被伪造的是 RSA 私钥的独占性.
====

=== 许可证的签发与文件结构

==== 签发流程

签发(保存)一个许可证时, Aegis 采用 **AES 加密 + RSA 签名** 的混合方案:

. 将 License 对象序列化为 JSON 字节.
. 为该许可证生成一次性随机 AES 密钥.
. 用 AES 加密许可证数据得到密文.
. 计算密文的 SHA256 哈希.
. 用 RSA 私钥对哈希签名.
. 将哈希, 签名, 密文, AES 密钥按"长度前缀"打包写入文件.

stem:[h = SHA256(ciphertext)], stem:[sig = RSA.Sign_{private}(h, SHA256, PKCS1)]

[plantuml, "许可证签发与落盘流程", format=png]
----
@startuml
start
:构建 License 对象 (模型/用户/到期日/Feature);
:序列化为 JSON (JsonLicenseSerializer);
:生成一次性随机 AES 密钥;
:AES 加密许可证数据;
:h = SHA256(密文);
:sig = RSA 私钥对 h 签名;
:按长度前缀打包 [h][sig][密文][AES密钥] 写盘;
stop
@enduml
----

对应核心代码 (已精简):

[source,csharp]
----
public static byte[] SaveLicense<T>(T license, string? privateKey = null) where T : BaseLicense
{
    var licenseData = Encoding.UTF8.GetBytes(_serializer.Serialize(license));   // <1>
    var aesKey = SecurityUtils.GenerateAesKey();                                 // <2>
    var encryptedData = SecurityUtils.EncryptData(licenseData, aesKey);          // <3>
    var hash = SecurityUtils.CalculateSha256Hash(encryptedData);                 // <4>
    var signature = SecurityUtils.SignData(hash,
        privateKey ?? LicenseUtils.GetLicensingSecrets().PrivateKey);            // <5>
    return CombineLicenseData(hash, signature, encryptedData, aesKey);           // <6>
}
----
<1> 默认以 JSON 序列化许可证
<2> 每张许可证生成独立 AES 密钥
<3> AES 加密正文
<4> 对密文求 SHA256
<5> RSA 私钥签名哈希
<6> 四段数据拼装为最终字节流

最终文件为 `[长度 + hash] [长度 + signature] [长度 + 密文] [长度 + aesKey]` 的顺序拼接, 每段前用 4 字节记录本段长度, 便于解析.

[NOTE]
====
值得强调的是, 随机 AES 密钥就存放在许可证文件中, 因此 **AES 并不提供真正的机密性**, 只是混淆与完整性绑定的一环. 该方案的安全性内核是 RSA 签名: 攻击者即使解开密文, 修改内容并重新加密, 也无法在没有私钥的情况下生成合法签名.

签名只作用于 32 字节哈希而非整段数据, 正是为了规避 RSA 对大数据的性能劣势, 这是混合加密的典型动机.
====

==== 生成许可证的示例

[source,csharp]
----
using Aegis;
using Aegis.Models;

// 标准授权: 绑定用户名与许可证号
var standard = LicenseGenerator.GenerateStandardLicense("John Doe")

    .WithExpiryDate(DateTime.UtcNow.AddDays(30))

// 节点锁定授权: 绑定当前机器硬件 ID

    .WithFeature("PremiumFeatures", Feature.FromBool(true))
    .SaveLicense(@"C:\Path\To\subscription_license.bin");
----

=== 校验流程

==== 离线校验

离线校验不依赖网络, 是 Aegis 最常用的场景. 客户端启动时加载许可证文件, 依次完成 **完整性校验, 来源校验与业务校验**:

. 按长度前缀拆包, 取出哈希, 签名, 密文与 AES 密钥.
. 用内置 RSA 公钥验证签名是否有效 (伪造/篡改防护).
. 重算密文 SHA256 并与文件内哈希比对 (篡改防护).
. 用 AES 密钥解密并反序列化为 License 对象.
. 按授权模型做业务校验: 到期时间, 用户名, 硬件 ID, 并发数等.
. 若注册了自定义规则, 再逐一执行.

[plantuml, "离线校验流程", format=png]
----
@startuml
start
:读取许可证文件字节;
:拆包得到 h, sig, 密文, aesKey;
if (RSA 公钥验签 sig 通过?) then (否)
  :Invalid (来源不可信);
  stop
else (是)
endif
if (SHA256(密文) == h?) then (否)
  :Invalid (数据被篡改);
  stop
else (是)
endif
:AES 解密并反序列化;
:按类型做业务校验 (到期/用户名/硬件ID/并发上限);
if (业务校验通过?) then (否)
  :Invalid / Expired;
  stop
else (是)
endif
:执行自定义校验规则;
:Valid;
stop
@enduml
----

[source,csharp]
----
var result = await LicenseManager.LoadLicenseAsync(@"C:\Path\To\license.bin");
if (result.Status == Aegis.Enums.LicenseStatus.Valid)
{
    var license = result.License!;
    Console.WriteLine($"类型: {license.Type}, 到期: {license.ExpirationDate}");
}
else
{
    Console.WriteLine($"校验失败: {result.Status} - {result.Exception?.Message}");
}
----

离线校验的每个环节抛出的异常类型不同, 便于上层精确处理, 例如 `InvalidLicenseSignatureException` 表示签名非法, `ExpiredLicenseException` 表示已过期, `HardwareMismatchException` 表示硬件不匹配.

==== 在线校验

在线校验面向浮动/并发授权, 客户端将许可证文件与许可证号提交到 Aegis.Server, 由服务器结合数据库状态做最终裁决. 服务器会额外检查: 许可证是否被吊销, 是否过期, 许可证号是否与数据库记录一致, 激活数是否已达上限等.

[plantuml, "在线校验与心跳保活时序图", format=png]
----
@startuml
actor "客户端应用" as C
participant "Aegis.Server" as S
database "许可证数据库" as DB

C -> S: POST /api/licenses/validate (licenseKey + 文件 + X-API-KEY)
S -> DB: 查询许可证状态
DB --> S: 记录 (过期/吊销/一致)
S --> C: 校验结果
C -> S: POST /api/licenses/activate
S -> S: ActiveUsersCount + 1 (不超过上限)
C -> S: POST /api/licenses/heartbeat (周期心跳)
S --> C: 续租成功
... 心跳超时 ...
S -> S: 踢除空闲用户, 释放席位
@enduml
----

客户端只需两行代码即可切换到在线校验:

[source,csharp]
----
LicenseManager.SetServerBaseEndpoint("https://your-aegis-server-url");          // <1>
var result = await LicenseManager.LoadLicenseAsync(
    @"C:\Path\To\license.bin", ValidationMode.Online);                          // <2>
----
<1> 指定授权服务端地址
<2> 使用在线模式加载, 默认间隔 5 分钟自动发送心跳

**心跳保活** 是席位型授权的关键机制: 客户端以 `SetHeartbeatInterval` 配置的周期(默认 5 分钟)持续上报心跳, 服务端后台监控心跳, 一旦超时未收到即判定该用户空闲并断开, 从而让"并发上限"在断线, 宕机等异常场景下也能被准确回收.

==== Aegis.Server 的落地形态

`Aegis.Server` 包只提供领域服务与抽象, 仓库内置 `Aegis.Server.AspNetCore` 示例工程展示标准接入方式: 将 `DbContext` 继承自 `AegisDbContext`, 注册服务后即可获得一组 REST API.

[source,csharp]
----
// Program.cs
builder.Services.AddAegisServer();                          // <1>
builder.Services.AddDbContext<ApplicationDbContext>(...);   // <2>

public class ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
    : AegisDbContext(options) { }                           // <3>
----
<1> 注册授权服务与后台心跳监控
<2> 配置数据库 (示例使用 SQLite)
<3> 应用自己的上下文继承 AegisDbContext, 复用其表结构

服务端核心接口如下:

[cols="3,3,6"]
|===
| 接口 | 角色 | 说明

| generate
| Admin
| 按请求生成许可证文件并入库

| validate
| Admin/User
| 结合数据库状态校验许可证

| activate
| Admin
| 激活席位型授权, 递增占用数

| revoke
| Admin
| 吊销许可证

| renew
| Admin
| 续期 (如订阅授权)

| disconnect
| User
| 主动断开某并发用户

| heartbeat
| User
| 客户端周期心跳, 接口做了限流
|===

服务端接口通过 JWT 承载 Admin/User 角色实现鉴权, 客户端在线校验则使用 `X-API-KEY` 请求头携带签发时生成的 API Key 认证.

=== 功能开关与 FeatureManager

除了整张许可证的可用性, Aegis 还支持 **细粒度功能授权 (Feature)**: 把"某个功能是否可用"作为键值写入许可证, 运行时用 `FeatureManager` 查询, 从而实现同一软件按付费档位开放不同功能.

Feature 支持六种值类型:

[cols="3,2,5"]
|===
| 工厂方法 | 存储类型 | 读取 API

| Feature.FromBool(true)
| bool
| FeatureManager.IsFeatureEnabled

| Feature.FromInt(5)
| int
| FeatureManager.GetFeatureInt

| Feature.FromString("Premium")
| string
| FeatureManager.GetFeatureString

| Feature.FromFloat(10.5f)
| float
| FeatureManager.GetFeatureFloat

| Feature.FromDateTime(...)
| DateTime
| FeatureManager.GetFeatureDateTime

| Feature.FromByteArray(...)
| byte[]
| FeatureManager.GetFeatureByteArray
|===

[source,csharp]
----
// 启动时加载许可证成功后, FeatureManager 即绑定当前许可证
if (FeatureManager.IsFeatureEnabled("BasicReporting"))
{
    Console.WriteLine("基础报表功能可用.");
}

int users = FeatureManager.GetFeatureInt("NumberOfUsers");   // 未授权时返回默认值 0

// 硬性拦截: 功能未授权时抛出 FeatureNotLicensedException
FeatureManager.ThrowIfNotAllowed("AdvancedAnalytics");
----

注意: Feature 名称区分大小写; 当许可证中未定义某功能时, `IsFeatureEnabled` 返回 false, 类型化取值方法返回默认值(数值返回 0, 字符串返回 null 等).

=== 扩展与自定义

Aegis 在保持开箱即用的同时, 把关键环节抽象为可替换接口, 允许深度定制:

==== 自定义校验规则

实现 `IValidationRule` 可注入任意业务校验, 例如校验硬件指纹的组合, 对接外部黑名单等.

[source,csharp]
----
public class MyCustomRule : IValidationRule
{
    public LicenseLoadResult<T> Validate<T>(T license,
        Dictionary<string, string?>? parameters) where T : BaseLicense
    {
        // 自定义校验逻辑...
        return new LicenseLoadResult<T>(Aegis.Enums.LicenseStatus.Valid, license);
    }
}

LicenseValidator.AddValidationRule(new MyCustomRule());
----

==== 自定义硬件标识

默认的 `DefaultHardwareIdentifier` 由机器名, 用户名, 系统版本与 MAC 地址组合生成硬件 ID. 可通过实现 `IHardwareIdentifier` 换成 CPU ID, 主板序列号等更强指纹:

[source,csharp]
----
public class MyHardwareIdentifier : IHardwareIdentifier
{
    public string GetHardwareIdentifier() => /* CPU ID + 主板序列号组合 */ "...";
    public bool ValidateHardwareIdentifier(string id) => GetHardwareIdentifier() == id;
}

LicenseManager.SetHardwareIdentifier(new MyHardwareIdentifier());
----

==== 其他可替换点

* **序列化器:** 默认 `JsonLicenseSerializer`, 可实现 `ILicenseSerializer` 换成 XML 或二进制, 经 `LicenseManager.SetSerializer` 注入.
* **内置校验开关:** 调用 `LicenseManager.SetBuiltInValidation(false)` 可关闭内置业务校验, 完全交由自定义规则接管, 适用于高度定制化场景.
* **服务器宿主:** `Aegis.Server` 与 Web 框架解耦, 可嵌入 ASP.NET Core, 也可自研控制器暴露相同能力.

=== 总结

Aegis 把软件授权抽象为"**签发 - 下发 - 校验 - 功能开关 - 席位回收**"的完整闭环, 其设计要点可归纳如下:

* **安全内核是 RSA 签名**, 而非文件内 AES: 公钥内置客户端即可离线验签, 私钥独占签发端, 从根本上防止伪造与篡改; AES 只承担混淆与完整性绑定, 其密钥随文件分发.
* **两种校验模式互补:** 离线模式适合单机/标准授权, 在线模式结合数据库裁决吊销状态, 并通过心跳实现并发席位在异常断线时的自动回收.
* **授权模型与授权粒度解耦:** 六种 License 子类表达不同绑定粒度, Feature 机制在同一张许可内再做功能级细分.
* **扩展点开放:** 校验规则, 硬件标识, 序列化器均可替换, 服务器宿主自由, 适合作为自研授权体系的起点.

实践中还应注意: 离线授权无法抵御"改系统时间续命试用期"这类本地攻击, 高价值场景应优先采用节点锁定 + 在线校验的组合; 签发私钥与 `signature.bin` 必须离线保管, 一旦泄露意味着整个授权体系可被伪造.
