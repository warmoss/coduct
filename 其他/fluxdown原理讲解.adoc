== fluxdown原理讲解

=== 概述

**FluxDown** 是一款 Rust 实现的开源多协议下载管理器, 目标是做 IDM 的免费替代. 它的技术核心不是"开更多线程", 而是把**分段下载**做成一套闭环的自适应系统: 连接数按文件大小、CPU 核数、实测吞吐和服务器反馈动态调整, 单段过慢时还能在运行期被拆分.

它要解决的典型问题:

* **单连接跑不满带宽:** 大量服务器按连接限速, 单条 TCP 流只能拿到链路容量的一小部分
* **协议形态各异:** HTTP/FTP 是字节流, BitTorrent/eD2K 是分块 P2P, HLS/DASH 是分片清单
* **多端需要共享引擎:** 桌面、移动端、NAS 服务端、CLI 必须复用同一套下载逻辑
* **中断必须可续:** 暂停、崩溃、换网络后要能精确接续, 而不是从头重下

=== FluxDown 是什么?

**FluxDown**:: 一套 Rust + Tokio 编写的下载引擎, 配合多个宿主与客户端(桌面 GPUI、原生移动端、无头服务器、CLI、浏览器扩展), 支持 HTTP/HTTPS、FTP、BitTorrent、eD2K、HLS 与 DASH.

**分段 (Segment)**:: 文件按字节区间切出的连续块, 记作 `[start_byte, end_byte]`, 由一个下载 worker 负责.

**Range 请求**:: HTTP 的局部取数机制, 通过 `Range: bytes=start-end` 只取文件的一段, 服务器以 `206 Partial Content` 应答. 它是多段下载的前提.

**渐进启动 (Ramp)**:: 连接数从较小值起步, 每个评估窗口测量一次总吞吐, 有增益就扩容, 无增益就冻结当前规模.

**宿主 (Host)**:: 持有并驱动引擎的进程, 例如纯下载核心 `fluxdownd`, 或负责账户与 UI 网关的 `fluxdown-agent`.

WARNING: 文中"连接数"、"线程数"、"分段数"含义不同. FluxDown 中**段只是工作队列项**, 并发连接数由 worker 池与 ramp 决定, 两者解耦.

=== 整体架构: 一个引擎, 多个宿主

FluxDown 采用"**一个引擎 + 多个宿主 + 多个客户端**"的结构. 所有下载逻辑集中在 `fluxdown_engine`, 它不依赖 UI、FFI 或 HTTP 框架, 上层通过契约 trait 与引擎交互.

[plantuml,"FluxDown 整体架构",format=png]
----

[React Web] --> [fluxdown-agent]

[CLI] --> [fluxdown_api] : HTTP
[浏览器扩展] --> [fluxdown-agent] : Native Messaging

各层职责:

* **客户端层:** 只消费协议 DTO 与事件, 不感知下载实现
* **宿主层:** `fluxdownd` 独占引擎与下载数据库, 拥有任务、队列、RSS、插件; `fluxdown-agent` 独占账户凭据、配置同步与设备协同, 只经 JSON-RPC 调 daemon
* **契约层:** `fluxdown_protocol` 是与传输无关的 wire 基线, `fluxdown_api` 把 REST、aria2 JSON-RPC、MCP 适配到统一的 `ApiHost`
* **引擎层:** 协议实现、分段调度、读写盘、数据库、队列、订阅与插件

|===
| crate

| `fluxdown_engine`

这种划分的直接收益: 同一套引擎可以在**没有 UI 的宿主**里运行, 也可以在移动端进程内运行, 而界面永远拿不到引擎内部状态.

=== 引擎的三个契约

引擎与外界只通过三个 trait 沟通:

[cols="2,2,5"]
|===
| trait
| 方向
| 作用

| `EventSink`
| 引擎 -> 宿主
| 推送进度、分段拆分、队列变化、任务组变化

| `HostSelection`
| 引擎 -> 宿主
| 请求用户决策: HLS 画质、BT 文件选择、插件变体、同名文件如何处理

| `ApiHost`
| 客户端 -> 引擎
| REST / aria2 / MCP 的能力面
|===

`HostSelection` 使用三态语义: **用户选择**、**超时取默认**、**无交互宿主直接短路**. 因此无头服务器不会因为"等待用户点确认"而卡死.

并发模型有三条硬约束:

* **actor 串行化写:** daemon 用单线程 Tokio actor 持有引擎, 所有状态变更串行执行, 不存在并发改同一份任务状态
* **每个下载独立任务:** 下载运行在独立 task 中并配 `CancellationToken`, 暂停与删除只取消对应任务
* **慢操作离开 actor:** 插件解析、哈希计算、BT 数据搬移都在 actor 之外执行, 结果经通道回流. 解析期间 actor 仍能响应其他请求

=== 一次下载的完整链路

理解各子系统之前, 先看一个任务从提交到落盘的完整路径:

. **提交与规范化:** 客户端经 HTTP 或 RPC 提交链接, 引擎先做迅雷链接解码、磁力识别、同名去重与站点凭据注入
. **单事务落库:** 任务行、队列位置与 RSS 回链在同一事务内写入, 随后广播一次"任务列表变化"事件; 分段行在启动时按规划批量落库
. **插件预解析:** Resolver 插件在协议判定前惰性执行, 返回直链、清单或磁力; 清单会被裂变为任务组
. **调度与探测:** 队列按并发上限挑选任务, 任务进入 `preparing`, 探测源站的总长度、Range 能力、文件名与校验信息
. **协议接管:** HTTP 交给分段协调器, HLS/DASH 交给分片调度, BT/eD2K 交给对应会话
. **持续反馈:** 进度按约 200ms 节拍推送, 分段与检查点按秒级节流落盘, 状态边沿立即持久化
. **收尾认领:** 按需校验 checksum, 按同名文件策略认领目标名, 把临时文件转为最终产物, 再发布完成事件与 webhook
. **失败处理:** 按重试配额指数退避; 耗尽后写入错误状态, 保留断点供手动重试

=== 协议分发

引擎在启动或恢复任务的同一条分支链上选择协议实现, 每个分支用 `catch_unwind` 隔离 panic, 单个协议的缺陷不会拖垮整个进程.

[cols="1,3,4"]
|===
| 协议
| 判定谓词
| 实现要点

| HTTP/HTTPS
| 兜底分支
| 分段协调器 + worker 池, 支持 Range 与续传

| FTP
| URL scheme 为 `ftp`
| 同步 FTP 客户端在阻塞线程池中运行

| BitTorrent
| `magnet:` 或 `torrent-file://` 哨兵
| 基于 librqbit 的共享会话

| HLS
| 链接指向 `.m3u8` 或清单内容
| 多码率变体、AES-128 解密、分片乱序窗口

| DASH
| 链接指向 `.mpd` 或带独立音轨
| 音视频轨分别下载, 由 ffmpeg 无损封装

| eD2K
| `ed2k://` 链接
| 服务器 + Kad 找源, 分块 MD4 校验
|===

两个容易踩坑的判定细节:

* **BT 只认磁力与种子哨兵:** 指向 `.torrent` 的 HTTP 链接会先抓取种子字节, 再以种子建任务; 否则它会被当成普通文件下载, 只得到一个种子文件而不是内容
* **插件在协议判定之前执行:** Resolver 插件可能把网页地址改写成直链、清单或磁力, 必须先解析再分发

=== HTTP 分段下载原理

HTTP 是使用频率最高的路径, 也是"动态加速"设计最集中的地方.

==== 前提: 服务器支持 Range

[source,shell]
----
# 1. 探测: 看是否声明支持字节范围
curl -I https://example.com/big.iso
# HTTP/1.1 200 OK
# Accept-Ranges: bytes
# Content-Length: 1073741824

# 2. 取第一段: 应答必须是 206, 且 Content-Range 分母与总长一致
curl -r 0-1048575 https://example.com/big.iso -o part0
# HTTP/1.1 206 Partial Content
# Content-Range: bytes 0-1048575/1073741824
----

三个条件缺一不可: **总长度已知**、**服务器接受 Range**、**分段请求确实返回 206**. 任一条不满足, 都会退化为单连接下载.

NOTE: 有些配额型端点对带 `Range` 的请求直接返回 400 并作废会话令牌. 因此 FluxDown 把"Range 是否可用"做成三态裁决(`UNKNOWN` / `SUPPORTED` / `UNSUPPORTED`): 未裁决前先发不带 Range 的普通 GET, 从首个响应学习, 绝不先制造一轮 Range 风暴.

==== 分段上限: 容量规划

分段不是越多越好. 每段至少要够摊薄一次 TLS 握手与 TCP 慢启动的开销, 同时连接数还受 CPU 核数与平台上限约束.

[source,python]
----
by_size  = max(1, total_bytes // (1024 * 1024))   # 每段至少 1 MiB
io_cap   = min(4 * cpu_cores, 64)                  # 下载是 I/O 密集, 放宽到 4 倍核数
segments = clamp(min(by_size, io_cap), 1, 64)
----

写成公式:

stem:[n = min(floor(S / 1 "MiB"), min(4C, 64))]

其中 stem:[S] 是文件总字节数, stem:[C] 是逻辑 CPU 核数.

三条边界:

* 文件不超过 2 MiB、总长未知、或不支持 Range 时, 直接单段
* 自动模式下桌面上限 64, 移动端 32
* 用户显式指定线程数时硬上限 512

关键点: 这个结果是**连接数上限**, 不是启动并发. 启动并发由渐进启动决定.

==== 渐进启动: 从 4 条连接开始爬坡

一次性打满 64 条连接会触发服务器风控, 也会让小文件把时间浪费在建连上. 因此引擎从 4 条连接起步, 每 2 秒一个评估窗口, 用实测吞吐决定下一步.

[plantuml,"FluxDown 连接数渐进调整状态机",format=png]
----
@startuml
[*] --> Active : 起步 4 条连接
Active --> Active : 窗口吞吐增益 >= 5%, 连接数倍增
Active --> SoftFreeze : 增益不足, 冻结当前规模
Active --> Rollback : 吞吐跌破扩容前 50%
Rollback --> Active : 回滚规模并记录域名上限
SoftFreeze --> Active : 冷却 30s 后 +1 试探成功
SoftFreeze --> HardFreeze : 两次试探失败或预算耗尽
Active --> Shrink : 冻结或到顶后连续 2 窗跌破峰值 50%
Shrink --> Active : 收缩后无回升, 撤销收缩
HardFreeze --> [*] : 本任务不再扩容
@enduml
----

判定规则:

* 扩容后吞吐高于扩容前 5% 以上, 继续倍增
* 落在 50% 到 105% 之间, 判为"没有净收益", 冻结在当前规模
* 跌破扩容前 50%, 判为服务器对新增连接施加**惩罚性限速**, 立即回滚到扩容前规模

回滚不是猜测: 惩罚型限速的跌幅通常是数量级级别, 而正常网络抖动极少让 2 秒窗口吞吐腰斩, 阈值留足了余量.

冻结之后仍有两种再调整:

* **软试探:** 冷却约 30 秒后加 1 条连接试探, 成功则解冻, 两次失败即转硬冻结
* **持续劣化收缩:** 额度被用满、且连续两个窗口吞吐跌破峰值 50% 时, 把额度乘性减半. 这条专治"起步规模就触发惩罚"的场景, 此时从未发生扩容, 回滚判据不可达

==== 运行期再拆分: 谁来救慢段

固定分段的通病是"木桶效应": 某一段卡住, 其他 worker 即使空闲也帮不上. FluxDown 用**工作队列 + 运行期拆分**解决.

[plantuml,"慢段拆分时序",format=png]
----
@startuml
participant "worker A\n持段 3" as A
participant "coordinator" as C
participant "worker B\n空闲" as B

A -> C : 段 3 进度 200/800 MiB
B -> C : 请求新工作
C -> C : 选出预计最晚完成的段 3
C -> C : 按双方速率比例计算拆分点
C -> A : 缩短 end_byte 到拆分点之前
C -> B : 派发新段 [拆分点, 原 end]
A -> A : 只写到新的 end_byte
B -> B : 从拆分点继续下载
@enduml
----

四个步骤:

. worker 完成一段后不退出, 向 coordinator 要下一份工作
. 有 Pending 段就领取; 没有则挑选**预计最晚完成**的活动段
. 按持段者与帮手的实测速率比例切分剩余区间, 使两者近似同时完成
. 原段缩短, 新段(高位区间)交给空闲 worker; 持段者通过共享状态看到新的结束位置并停止写入

三个约束保证拆分"划算":

* **最小可拆长度随吞吐自适应:** 低于 1 MB/s 用 512 KiB, 1 到 10 MB/s 用 1 MiB, 10 MB/s 以上用 2 MiB
* **尾部例外:** 剩余不足 64 KiB 也允许拆, 专治最后一个慢连接拖尾
* **计入建连成本:** 若持段者在帮手收到首字节前就能下完, 则不拆, 避免多付一次握手换不到收益

coordinator 还会在独立的 2 秒定时器上**预先**拆出 Pending 段, 把拆分计算与落库移出"worker 完成"的关键路径, 减少空闲空档.

==== 域名连接策略: 记住服务器的脾气

同一域名反复试探多连接会触发风控, 因此 coordinator 维护一份域名级策略缓存, 并持久化到配置表跨重启保留:

[cols="2,2,5"]
|===
| 观察面
| 合并规则
| 作用

| `cap`(负面)
| 取更低值
| 服务器以 403/429 或惩罚性崩塌拒绝多连接后, 记录削减后的上限, 同域名后续任务直接封顶

| `hint`(正面)
| 取更高值
| 无拒绝信号的任务成功完成时, 记录实际维持过的规模, 后续任务以该规模作为 ramp 起点
|===

两面各自 24 小时过期. 负面观察恒压制正面提示: 只要还有未过期的上限记录, 起点提示就不得越过它. 这套机制把"这个站点该开几条连接"从每次重新猜测变成跨任务的经验积累.

==== 完整性不变式

无论怎样拆分与回滚, 分段表始终满足:

* 所有 `[start, end]` 区间**恰好覆盖** `[0, total_bytes - 1]`, 无空洞、无重叠
* 任意段的已下载字节不超过其区间长度

写盘用 `seek` 加 `write` 直接写入预分配的 `.fdownloading` 临时文件. 因此没有分片临时文件, 也没有完成后的合并拷贝, 这也是大文件能"下完即用"的原因.

=== 持久化与断点续传

状态保存在任务表与分段表中, 双后端支持 SQLite 与 PostgreSQL.

* SQLite 默认开启 WAL 与 `synchronous=NORMAL`: 进程崩溃不丢已提交事务, 断电最多丢最后几笔
* 分段行按 `(task_id, segment_index)` 复合主键存储, 与任务行在同一事务内变更
* 高频进度不逐帧入库, UI 进度约 200ms 推一次, 分段进度约 3 秒落一次盘

崩溃恢复的规则很直接:

. 从数据库重建分段集合, 已完成段直接标记完成
. 已落库但 worker 从未启动的拆分, 以 Pending 状态还原, 交给空闲 worker
. 若出现"父段已缩短但子段未写入"的空洞, 下载末尾的覆盖性校验会发现并判定失败, 任务从头重下

WARNING: 同一个数据目录只允许一个写入者. 引擎用 `<data_dir>/engine.lock` 取得排它租约, 第二个打开者会被拒绝, 避免两个进程同时写同一份临时文件与数据库.

=== 队列、并发与限速

队列是命名资源池, 每个队列拥有并发上限、默认保存目录、默认分段数与定时计划.

* 内置 `main` 与 `later` 两个队列; **主队列恒运行**, 停止与定时对它无效, 只允许暂停其中的任务
* 定时计划按星期的位掩码加起止时刻表达, 到点自动启停
* 队列切换任务归属时, 归属事件与排序事件分开推送, 避免客户端重建整张列表

限速是**全局令牌桶**:

* 按真实墙钟时间补充令牌, 消除定时器漂移
* 令牌最多攒到 250ms 的量, 既不限制正常抖动, 也避免空闲后突发
* 补充用 CAS 循环, 没有"读改写"竞态
* 限速作用在**读取侧**而不是写盘侧, 因此统计到的速度与限速口径一致
* 限速为 0 表示不限速; 单任务可设置临时覆盖值

=== 流媒体: HLS 与 DASH

点播流媒体的下载模型与普通文件不同: 它没有连续的字节区间, 只有一串分片.

==== HLS 分片调度

下载步骤:

. 解析 master 清单, 选择码率变体; 若变体声明了独立音轨(`EXT-X-MEDIA`), 优先取 `DEFAULT=YES`
. 并发拉取分片, **分片下载完立即归还连接许可**, 数据进入乱序重排窗口
. 由**唯一 writer** 按顺序追加到同一个 `.fdownloading` 文件
. 检查点按固定间隔节流写入, 暂停或出错前补写最新前缀

乱序窗口有三条约束:

* 领先写盘不超过并发数乘以 8 个分片
* 缓冲内存按可用内存分档: 低于 1.5 GiB 用 8 MiB, 低于 3 GiB 用 16 MiB, 其余 32 MiB
* 队首分片永远放行, 不会被窗口卡住

这样做的收益: **队首慢不会让其余连接空等**, 也不会产生成百上千个分片临时文件.

==== 音视频轨合并

HLS 与 DASH 都可能把音频单独成轨:

* 开跑前探测 ffmpeg 是否可用
* 可用时音轨与视频轨**并行下载**, 各自保留续传检查点
* 收尾用 `-c copy` 封装为 MP4, 不做转码
* 音轨失败会取消整个任务; mux 失败则保留视频, 另存音轨边车文件并写警告

直播录制走另一条路径: 按轮询窗口并发抓取新分片, 与点播共用同一套计量与读取侧限速.

=== P2P: BitTorrent 与 eD2K

==== BitTorrent

基于 librqbit 的**共享会话**: 同一进程内所有 BT 任务共用 DHT、UPnP 端口映射与连接池.

* **找源:** DHT、tracker、LSD、PEX 与 HTTP 源(webseed, BEP 19)并行
* **分片校验:** v1 种子用 SHA-1, v2 种子用 Merkle 树, 混合种子两者都校验; 校验失败的片记为坏片重下
* **私有种子:** 不追加额外 tracker(BEP 27), 不与公开网络混用
* **做种:** 上传速率单独采样, 采样间隔约 500ms, 保证状态栏显示不跳变
* **完整性校验:** 已完成的种子可以只读校验, 不改任务状态; 作种中的种子强制重校验前先摘出会话

会话级设置(DHT、端口、uTP、MSE)变更会重建会话并把在途任务重新挂载; 非会话级设置(tracker 列表)只影响新加入的种子, 不打断下载.

==== eD2K

eD2K 只做下载(leech), 但找源与校验同样完整:

* **找源:** 服务器 `GETSOURCES` + Kad DHT 兜底
* **HighID / LowID:** 通过 UPnP 争取公网可达; 仍为 LowID 时依赖服务器回调中继
* **校验:** 每个块做 MD4, 并维护 hashset 自校验; 校验不符的 peer 直接拉黑
* **根哈希:** 分块 MD4 组成根哈希, 块大小 9.28 MB, 末尾不足一块按幻影尾处理

=== 插件系统

插件是**可选、可失败的下载任务中间层**, 用 JavaScript 编写, 运行在 QuickJS 沙箱中.

它有三个正交能力面:

[cols="2,5"]
|===
| 平面
| 职责

| 订阅
| 声明 `providerId` 与入口, 导出 `subscribe(ctx)`, 自行完成平台请求与解析, 返回规范化的条目列表

| 解析
| 导出 `resolve(url, ctx)`, 返回直链、清单或 `null`; 清单会被裂变为任务组

| 通知
| `onStart` / `onDone` / `onError` / `onMetaProbed`, 全部 fire-and-forget, 失败只记日志
|===

解析面有四条关键约束:

* **惰性执行:** 每次启动或恢复都重跑, 天然规避直链过期
* **离开 actor:** 解析在 actor 之外执行, 结果经通道回流, 不冻结下载核心
* **失败关闭 (fail-closed):** 解析失败即判任务失败, 绝不把网页 HTML 当作视频存盘
* **预算受限:** 默认超时 10 秒(硬顶 30 秒), 默认内存 64 MiB(硬顶 512 MiB)

两段式解析用于网盘类站点: 初段返回文件清单, 引擎裂变为任务组; 用户勾选后, 二段用 `ctx.resolverItem` 换取每个文件的直链.

=== 对外接口

所有对外接口共用同一个 `ApiHost` 实现, 因此任意宿主都能提供完整能力:

[cols="2,2,5"]
|===
| 接口
| 端点
| 用途

| REST 管理 API
| `/api/v1/*`
| 任务、队列、订阅等管理操作

| OpenAPI
| `/api/v1/openapi.json`
| 机器可读的接口契约

| aria2 兼容 JSON-RPC
| `/jsonrpc`(HTTP 与 WebSocket)
| 复用 aria2 生态客户端

| MCP
| `/mcp`

MCP 实现的是**无状态 Streamable HTTP 子集**, 即 JSON-RPC 2.0 over `POST /mcp`, 与下载服务同端口, 不需要额外进程. 默认只监听本机 `127.0.0.1:17800`, 管理 API 与 MCP 需显式开启并携带访问令牌.

=== 浏览器集成

浏览器侧的下载接管经过统一捕获队列:

* 扩展在浏览器内拦截下载、嗅探流媒体地址, 再经 **Native Messaging** 交给 agent
* 用户脚本走 HTTP 接口提交同样的捕获结果
* 桌面客户端通过 `/rpc` 提交

三条来源汇入**同一个捕获与确认队列**, 因此去重、目标目录、命名规则只需实现一次.

=== 总结与注意事项

FluxDown 的设计可以概括为三句话:

* **引擎与界面彻底解耦:** 三个契约 trait 让同一份下载逻辑跑在桌面、移动端与无头服务器上
* **连接数是闭环控制的:** 容量规划给出上限, 渐进启动找到甜点, 惩罚检测负责回滚, 域名策略负责跨任务记忆
* **拆分是运行期的常态:** 段只是工作队列项, 慢段随时可以被拆开交给空闲 worker

关键要点:

* **分段数不等于连接数:** 上限只是天花板, 真正的并发由 ramp 与服务器反馈共同决定
* **Range 三态裁决保护配额型端点:** 未验证前不发 Range 请求
* **回滚与收缩是两套机制:** 回滚处理"扩容后崩塌", 收缩处理"起步就超限"
* **持久化只保证已提交事务:** SQLite 的 `synchronous=NORMAL` 在断电时可能丢最后几笔进度, 但不影响文件完整性
* **插件失败即任务失败:** 宁可报错也不产出错误的文件

常见误区:

* **手动把线程数调到最大并不更快:** 触发服务器按连接惩罚后, 总吞吐往往数量级下降
* **限速与测速同源:** 限速在读取侧生效, 所以"限速 1 MB/s 却显示 3 MB/s"通常意味着配置未生效, 而不是统计错误
* **删除任务不等于删除文件:** 完成记录清理只删数据库行, 文件由用户显式删除
* **无头部署需要注意空闲静默:** 无活动任务时引擎不做周期性磁盘读写, 以保证 NAS 硬盘能休眠; 依赖轮询的外部脚本应改为订阅事件
