== 阿里云PTS原理讲解

=== 概述

**PTS**(Performance Testing Service) 是阿里云提供的 SaaS 化分布式性能压测平台. 它面向开发者与运维人员, 解决自建压测环境成本高, 施压能力不足, 流量不够真实等问题, 让用户以较低的人力和资源成本构造接近真实业务场景的复杂流量, 快速衡量系统的性能, 容量与稳定性.

PTS 解决的核心问题:

* **施压能力:** 通过遍布全国的分布式施压节点, 突破单机压测工具的并发上限
* **成本控制:** 按需付费, 无需购买和维护物理压测集群
* **真实流量:** 从全国上百个城市和运营商的 CDN 节点发起流量, 模拟真实用户分布
* **可视化编排:** 零编码构造压测场景, 支持录制与脚本导入
* **可观测性:** 集成云监控与 ARMS, 实时采集客户端与服务端指标

=== PTS 是什么?

**PTS**:: 一款简单易用, 具备强大分布式压测能力的 SaaS 压测平台, 可模拟复杂业务场景, 快速精准调度不同规模的流量, 并提供多维度监控指标与日志记录.

**场景**:: 压测用例, 定义压测目标, 请求链路, 压测模式与量级, 是一次压测任务的最小编排单元.

**施压机**:: 也称压测引擎, 是实际产生并发请求的执行节点, 分布在全国多个地域与运营商网络.

**VU**:: Virtual User, 虚拟用户, 模拟一个真实用户独立发起请求的基本单位.

**RPS**:: Requests Per Second, 每秒请求数, 衡量吞吐量的核心指标.

**SLA**:: Service Level Agreement, 服务等级协议, 以响应时间, 成功率等阈值判定压测是否异常.

WARNING: PTS 的自研引擎与原生 JMeter 引擎能力不同, 其中 RPS 压测模式, 秒级启动, 实时调速, 定时压测等能力仅由自研引擎提供.

=== 核心架构

PTS 的架构围绕控制台, 调度中心, 分布式施压引擎与监控体系四个层面设计:

[plantuml, "PTS 架构概览", format=png]
----
@startuml
package "控制台 Console" {
  [场景编排] as scene
  [报告查看] as report
}

package "调度中心 Scheduler" {
  [任务调度] as dispatch
  [量级控制] as scale
}

package "分布式施压引擎" {
  [施压节点 1] as e1
  [施压节点 2] as e2

  [云监控] as cms
  [ARMS] as arms

scene --> dispatch : 下发压测任务
dispatch --> e1 : 分配流量
dispatch --> e2 : 分配流量
dispatch --> en : 分配流量

en --> cms : 上报指标

各组件职责:

* **控制台:** 提供可视化场景编排, 实时过程监控与压测报告查看入口
* **调度中心:** 负责压测任务的编排与下发, 动态调度施压节点, 控制整体量级
* **施压引擎:** 实际产生压测流量, 每个节点独立执行并上报指标, 可水平扩展
* **监控体系:** 集成云监控与 ARMS, 采集客户端与服务端指标, 支撑瓶颈定位

=== 压测模式

PTS 自研引擎支持两种核心压测模式:

[cols="2,3,3"]
|===
| 模式 | 定义 | 适用场景

| 并发模式
| 指定虚拟用户 VU 数
| 模拟固定在线用户数, 验证系统承载连接数

| RPS 模式
| 指定每秒请求数
| 直接以吞吐量为目标, 系统自动计算所需 VU
|===

两种模式的差异:

* **并发模式**关注同时在线用户数, 用户行为节奏由思考时间决定, 实际 RPS 由 VU 与业务耗时共同决定
* **RPS 模式**关注吞吐量, 系统根据目标 RPS 与单请求耗时自动推算出所需 VU 数并动态调整

TIP: 压测前若已有明确吞吐量目标(如订单系统需支撑 10000 RPS), 优先选择 RPS 模式; 若目标是验证最大并发连接数, 则选择并发模式.

==== 阶梯加压

为避免瞬间高并发击穿系统, PTS 支持按阶梯递增施压, 配置思路如下:

[source,yaml]
----
# 阶梯加压配置示例
压力模式: 阶梯递增
初始量级: 100 RPS
递增步长: 100 RPS
递增间隔: 60s
峰值量级: 1000 RPS
----

=== 施压流程

一次完整的 PTS 压测遵循以下流程:

. 在控制台准备压测 API 数据, 构造压测场景, 定义压测模式与量级
. 压测启动后, 后台调度中心自动调度压测数据, 任务与施压引擎
. 调度中心随机调度全国上百个城市和运营商的 CDN 节点发起压测流量
. 施压引擎向指定业务站点发起压测请求
. 集成云监控与 ARMS, 结合 PTS 自有指标实时采集压测数据
. 控制台实时展现数据, 压测结束后自动生成压测报告

----

@enduml
----

=== 压测创建方式

PTS 支持四种方式创建压测场景:

[cols="2,3,2"]
|===
| 方式 | 说明 | 引擎

| 零编码可视化编排
| 在控制台拖拽式构造请求链路, 定义参数与断言
| 自研引擎

| 云端录制器
| 通过 PTS Chrome 插件零侵入录制浏览器操作与接口
| 自研引擎

| 脚本导入
| 导入 JMeter(JMX), Postman(JSON), HAR, YAML, Swagger 脚本
| 自研引擎

| 原生 JMeter 引擎
| 直接运行 JMeter 脚本, 复用其插件生态
| JMeter 引擎
|===

NOTE: 前三种方式使用自研引擎, 具备 RPS 模式, 秒级启动, 实时调速, 定时压测与全国运营商网络流量等差异化能力.

=== 核心特性

* **分布式压测:** 施压节点遍布全国, 可按需水平扩展, 突破单机并发上限
* **RPS 吞吐量模式:** 直接以每秒请求数为目标施压, 支持实时调速
* **秒级启动与实时控制:** 压测过程中可随时启停与调速
* **定时压测:** 按计划周期自动发起压测, 常用于例行容量验证
* **SLA 管理:** 以响应时间与成功率阈值监控压测过程, 异常时告警通知
* **流量录制回放:** 通过 Chrome 插件或 Charles 录制线上真实流量并回放
* **可观测集成:** 指标写入 Prometheus, 支持自定义 Grafana 大盘; 集成云监控与 ARMS
* **压测报告:** 自动汇总场景指标, 业务详情, 监控数据与 API 采样日志

=== 总结与注意事项

要点归纳:

* PTS 是 SaaS 化分布式压测平台, 核心价值在于以低成本构造真实且大规模的压测流量
* 自研引擎是 PTS 的核心, RPS 模式, 实时调速等能力均依赖自研引擎
* 压测流程由调度中心统一编排, 施压引擎分布式执行, 监控体系实时采集

常见误区:

* **误区一:** 认为并发数越大越好. 实际应结合业务目标选择并发模式或 RPS 模式, 盲目加大并发可能导致系统被击穿而非发现瓶颈
* **误区二:** 忽略施压流量来源. 自建环境或非自研引擎压测时, 流量分布可能与真实用户不符, 影响结论可信度
* **误区三:** 仅关注平均响应时间. 应重点关注 P99 等分位指标与成功率, 结合 SLA 判定系统状态

最佳实践:

* 压测前明确目标: 吞吐量目标用 RPS 模式, 连接数目标用并发模式
* 使用阶梯加压逐步探顶, 避免瞬间高并发掩盖瓶颈位置
* 压测过程中结合云监控与 ARMS 同时观察服务端资源与业务指标
* 压测后以压测报告为基线, 建立容量规划与性能基线的持续跟踪

CAUTION: 对生产环境发起压测前, 务必确认目标站点承受能力, 避免压测流量引发线上事故.
