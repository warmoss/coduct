== HMAC讲解

=== 它是什么? 解决什么问题?

本质::
HMAC 是一种**密码学技术**, 用于同时验证**数据的完整性**和**数据的真实性**.

核心问题::
* **完整性:** 确保数据在传输或存储过程中没有被意外或恶意篡改(例如, 比特翻转、内容修改).
* **真实性/来源认证:** 确保数据确实来自声称的发送方(拥有共享密钥的一方), 而不是冒充者.

简单哈希的不足::
使用普通的哈希函数(如 MD5, SHA-1, SHA-256)可以验证完整性(如果哈希值变了, 数据就变了). 但是, 它**无法验证真实性**! 攻击者可以同时修改数据和重新计算哈希值, 接收者无法区分这是否是来自合法发送方的原始消息.

**HMAC 通过引入一个Secret Key(秘密密钥)来解决这个问题.** 只有拥有相同密钥的通信双方才能生成或验证正确的 HMAC 值.

=== 工作原理(简化过程)
HMAC 的核心思想是**将密钥与消息混合, 然后进行哈希运算**. 具体过程比简单的拼接要复杂一些, 以增强安全性(抵御某些类型的攻击). 其计算遵循 RFC 2104 标准定义:

[source, plaintext, linenums]
----
HMAC(K, m) = H((K' ⊕ opad) || H((K' ⊕ ipad) || m))
----

看起来很复杂? 让我们一步步分解:

. **密钥准备(K'):**

* 如果原始密钥 **K** 的长度小于哈希函数的块大小(Block Size, 例如 SHA-256 是 64 字节), 则在末尾填充 **0x00** 直到达到块大小.

* 如果原始密钥 **K** 的长度大于块大小, 则先用哈希函数 **H** 对 **K** 进行哈希, 然后用得到的哈希值(其长度等于哈希输出的摘要大小, 如 SHA-256 是 32 字节)填充 **0x00** 直到达到块大小.

* 最终得到一个长度等于哈希函数块大小的密钥 **K'**.

. **生成内填充密钥(i_key_pad):**

* 定义一个常量 **ipad**(inner pad), 其值为字节 **0x36** 重复块大小次数(例如, 对于 64 字节块大小, **ipad** 是 64 个 **0x36**).

* 计算: **i_key_pad = K' ⊕ ipad**(⊕ 表示按位异或操作).

. **内部哈希计算:**

* 将第一步得到的 **i_key_pad** 与原始消息 **m** 连接起来: **(i_key_pad || m)**.

* 对连接后的字符串应用哈希函数 **H**, 得到内部哈希结果 **H(i_key_pad || m)**.

. **生成外填充密钥 (o_key_pad):**

* 定义一个常量 **opad**(outer pad), 其值为字节 **0x5C** 重复块大小次数(例如, 64 个 **0x5C**).

* 计算: **o_key_pad = K' ⊕ opad**.

. **最终 HMAC 计算:**

* 将第四步得到的 **o_key_pad** 与第三步得到的内部哈希结果 **H(i_key_pad || m)** 连接起来: **(o_key_pad || H(i_key_pad || m))**.

* 对连接后的字符串再次应用哈希函数 **H**.

* 最终的输出就是 **HMAC** 值(也称为 MAC 或 Tag).

**关键点**

* **双重哈希:** HMAC 对数据进行了两次哈希处理.

* **密钥混合:** 密钥通过异或操作与常量 **ipad** 和 **opad** 混合, 然后分别用于内部和外部哈希过程. 这确保了密钥以非平凡的方式影响整个计算.

* **固定长度输出:** HMAC 的输出长度与其底层使用的哈希函数 **H** 的摘要长度相同(例如, 使用 SHA-256 时, HMAC 输出是 32 字节).

=== 如何使用?
假设通信双方 Alice 和 Bob 事先安全地共享了一个**秘密密钥 K**.

发送方(Alice)::

. 拥有要发送的消息 **m** 和共享密钥 **K**.

. 使用 **K** 和 **m** 计算 HMAC 值: **tag = HMAC(K, m)**.

. 将**原始消息 m 和计算出的 tag** 一起发送给 Bob.

接收方(Bob)::

. 接收到消息 **m'** 和 **tag'**(**m'** 和 **tag'** 可能在传输中被篡改).

. 使用本地存储的相同密钥 **K** 和接收到的消息 **m'** **重新计算** HMAC 值: **tag_calculated = HMAC(K, m')**.

. **比较:** 将 **tag_calculated** 与接收到的 **tag'** 进行比较.

* **如果 tag_calculated 严格等于 tag':**

** **完整性:** 消息 **m'** 极大概率与 Alice 发送的 **m** 完全相同(未被篡改).

** **真实性:** 消息 **m'** 极大概率确实是由拥有密钥 **K** 的 Alice 发送的(或至少是知道 K 的合法方).

* **如果 tag_calculated 不等于 tag':**

** 消息**一定**在传输过程中被篡改了(完整性破坏)**或者**是由不知道正确密钥 **K** 的人发送的(真实性破坏). Bob 应该**拒绝**这个消息.

=== 安全特性

依赖于底层哈希函数::
HMAC 的安全性很大程度上取决于其所使用的哈希函数 **H** 的安全性(抗碰撞性、原像攻击、第二原像攻击). 如果 **H** 被攻破(如 MD5, SHA-1 已被认为在抗碰撞性上不安全), 那么基于它的 HMAC 也不再安全.

依赖于密钥::
密钥 **K 必须保密**! 如果攻击者获得了 **K**, 他就可以伪造有效的 HMAC 值, 完全破坏认证. 密钥也应该足够长且随机.

抵御长度扩展攻击::
一些简单的构造(如 **H(K || m)**)容易受到长度扩展攻击. HMAC 的设计(特别是内部哈希步骤)使其能够抵抗这种攻击.

伪随机性::
一个设计良好的 HMAC(使用安全的哈希函数)在不知道密钥的情况下, 其输出应该看起来是随机的, 并且很难预测.

=== 常用哈希算法
HMAC 可以与各种加密哈希函数结合使用.常见的组合包括:

* **HMAC-MD5:** 已不安全, **不推荐使用**.
* **HMAC-SHA1:** 安全性降低, 存在理论上的弱点, 在新应用中**应避免使用**.
* **HMAC-SHA256:** **目前最广泛推荐和使用的组合**. 提供 256 位安全性(输出 256 位).
* **HMAC-SHA384/HMAC-SHA512:** 提供更高的安全级别(输出 384 或 512 位), 适用于需要极强安全性的场景.
* **HMAC-SHA3-256/HMAC-SHA3-512:** 使用更新的 SHA-3(Keccak)家族哈希算法, 也是安全的选择.

=== 应用场景
HMAC 因其简单、高效和安全性, 被广泛应用于各种需要消息认证的场景:

API 认证 (RESTful, Web Services)::
服务器给客户端分配 API Key (Secret). 客户端在请求中包含参数和计算出的 HMAC. 服务器用相同的 Secret 重新计算 HMAC 并比对, 验证请求的完整性和来源. 这是防止 API 滥用和伪造请求的核心机制.

JSON Web Tokens (JWT)::
JWT 可以选择使用 HMAC (如 HS256, HS384, HS512) 作为签名算法. 服务器用密钥生成签名, 接收方用相同密钥验证签名, 确保 JWT 内容未被篡改.

网络协议安全::
在 SSL/TLS 的早期版本和一些 VPN 协议中, HMAC 被用于构造消息认证码(如在密码套件中).

软件更新验证::
下载软件包时, 提供方通常会提供文件的哈希值(有时是 HMAC)供用户验证下载的文件是否完整且来自可信源(需安全获取 HMAC 值).

文件/数据完整性校验(带认证)::
在存储或传输敏感数据时, 除了存储数据本身, 还存储其 HMAC(密钥需安全保管).读取时重新计算并比对 HMAC, 确保数据未被修改且来源可信.

会话管理::
有时用于保护会话 Cookie 的完整性.

=== 重要注意事项(最佳实践)
. **选择安全的哈希算法:** **强烈推荐使用 HMAC-SHA256 或更高强度的组合(如 HMAC-SHA384, HMAC-SHA512, HMAC-SHA3)**. 避免 HMAC-MD5 和 HMAC-SHA1.

. **密钥管理至关重要:**

* 密钥必须**保密**! 绝对不能硬编码在客户端代码或配置文件中(如果客户端不可信).

* 使用安全的密钥存储解决方案(如硬件安全模块 HSM、密钥管理服务 KMS、安全的服务器端存储).

* 密钥应该**足够长且随机**(例如, 至少 256 位, 即 32 字节).

* **定期轮换密钥**(虽然轮换后旧的已签名的消息验证会失败, 但能降低长期密钥泄露的风险). 轮换策略需要仔细设计.

. **比较操作:** 比较接收到的 **tag'** 和自己计算出的 **tag_calculated** 时, **必须使用恒定时间比较(constant-time comparison)函数**. 这是为了防止**计时攻击**. 普通字符串比较(如 **str1 == str2**)在发现第一个不匹配字节时就返回, 攻击者可以通过测量验证时间差来逐步猜测出正确的 MAC 值. 安全库(如 Python 的 **hmac.compare_digest()**)会确保比较时间只取决于长度, 不取决于内容.

. **不要只依赖 HMAC 进行加密:** HMAC **仅提供认证(完整性和真实性)**, **不提供机密性**! 原始消息 **m** 是以明文形式传输/存储的. 如果需要保密, 必须**额外使用加密**(如对称加密 AES 或非对称加密).

=== 总结
HMAC 是一种基于哈希函数和共享密钥的、高效且广泛应用的密码学原语, 用于解决消息的**完整性**和**真实性**认证问题. 其安全性依赖于底层哈希函数的强度和密钥的保密性. **HMAC-SHA256** 是当前最推荐的标准组合. 在使用时, 务必遵循安全最佳实践, 特别是关于密钥管理和比较操作的安全性. 它是构建安全通信和系统(如 API 认证、JWT)的基石之一.
