== PageToken讲解

PageToken 是一个在分页查询中使用的令牌(通常是一个字符串), 它用来标识和获取下一页或上一页的数据. 它的主要目的是为了让分页查询更高效、更稳定, 尤其是在处理大量数据时.

=== 为什么需要 PageToken? (传统分页的问题)
在理解 PageToken 之前, 先看看传统的分页方式(基于偏移量的分页)及其缺点:

* **传统方式:** **LIMIT offset, count** (SQL) 或 **page=2&size=10** (API).

** **例如:** 要获取第 11 到第 20 条记录, 会使用 **LIMIT 10, 10**.

* **缺点:**

** **性能问题:** 数据库在使**LIMIT 100000, 10**时, 仍然需要先扫描前 100000 条记录, 然后丢弃它们, 再返回最后的 10 条. 数据量非常大时, 效率极低.

** **数据不一致性:** 如果在两次分页请求之间, 有数据被**新增或删除**, 当前页的数据可能会" 漂移" . 例如, 你刚看完第 1 页(第1-10条), 此时有一条新数据插入到了最前面. 当你请求第 2 页(第11-20条)时, 实际上你拿到的是原来的第10-19条, 因为新增数据导致所有数据的偏移量都向后移动了一位. 这会导致你重复看到一条数据(原来的第10条)或漏掉一条数据(原来的第11条).

=== PageToken 如何工作? (基于游标的分页)
PageToken 是实现 **基于游标的分页(Cursor-based Pagination)** 的核心. 它不依赖偏移量, 而是依赖一个唯一的、稳定的" 锚点" (即游标).

工作原理::

. **首次请求:** 客户端发起一个列表请求, 通常可以指定每页的数据量(**page_size**).

. **服务器响应:** 服务器返回第一页数据, 并在响应体中包含一个 **next_page_token**(或类似名称的字段). 这个 **Token** 通常是**最后一条记录的某个唯一、有序的标识符**(如 ID、创建时间时间戳等)的加密或编码形式.

. **后续请求:** 要获取下一页数据, 客户端将收到的 **next_page_token** 作为参数(如 **page_token=abc123...**)在下一个请求中发回给服务器.

. **服务器解析:** 服务器解密这个 Token, 知道客户端的上一页最后一条记录是什么, 然后执行一个高效的查询: "**给我获取在这个特定记录之后(或之前)的 N 条记录**" .

. **循环直到结束:** 重复步骤 2-4, 直到服务器不再返回 **next_page_token**, 这表示已经没有更多数据了.

一个简单的 SQL 类比::

** **传统分页:** SELECT * FROM items ORDER BY created_at DESC LIMIT 20 OFFSET 100; (性能差)

** **基于游标的分页:** SELECT * FROM items WHERE created_at < ‘上一页最后一条的时间' ORDER BY created_at DESC LIMIT 20; (性能极佳, 利用了索引)

=== PageToken 的优点
* **高性能:** 查询条件总能利用索引, 避免了扫描和跳过大量无效数据, 非常适合无限滚动或深度分页的场景.

* **数据一致性:** 由于分页是相对于一个固定的" 锚点" (游标)进行的, 即使在分页过程中有数据增删, 也不会影响当前查询页的结果. 你看到的是请求那一刻的" 数据快照" .

* **适用于实时数据:** 非常适合动态变化的数据流, 如社交媒体动态、新闻推送、日志等.

=== PageToken 的缺点
* **无法跳转到特定页码:** 客户端只能一页一页地顺序遍历(下一页或上一页), 不能直接跳到特定页. 这是为性能和一致性付出的代价.

* **实现稍复杂:** 服务器端需要设计如何生成和解析 Token(通常是对游标值进行加密或 Base64 编码), 并编写相应的查询逻辑.

* **Token 泄露信息:** 虽然通常是编码后的, 但 Token 可能包含最后一条记录的信息(如 ID), 如果未加密, 可能会有信息泄露的风险.

=== 实际应用示例(Google APIs)
许多大型科技公司的 API 都使用 PageToken, 最典型的是 Google. 例如 Google Cloud Storage 列出文件:

第一次请求::

[source, http, linenums]
----
GET /storage/v1/b/my-bucket/o?maxResults=50
----

响应::

[source, json, linenums]
----
{
  "items": [ ... ], // 50 个文件
  "nextPageToken": "CiBoYXBweQoYbWlzY2hpZXZvdXNfbWFuYWdlcgQMCg0KDQ=="
}
----

获取下一页的请求::

[source, http, linenums]
----
GET /storage/v1/b/my-bucket/o?maxResults=50&pageToken=CiBoYXBweQoYbWlzY2hpZXZvdXNfbWFuYWdlcgQMCg0KDQ==
----

=== 总结

[cols="1,3,3"]
|===
|特性|传统偏移分页 (Offset-based)|基于游标分页 (Cursor-based / PageToken)

|**原理**
|使用 OFFSET 跳过前 N 条
|使用 WHERE 基于游标过滤

|**性能**
|大数据量时差
|**大数据量时极佳**

|**数据一致性**
|差(易受增删影响)
|**好(数据快照)**

|**跳转页码**
|支持
|**不支持**

|**适用场景**
|数据量小、静态、需跳页
|**数据量大、动态、顺序遍历**

|===

=== 结论
PageToken 是现代 API 设计中处理大型数据集分页的**最佳实践**. 它通过牺牲直接跳转页码的灵活性, 换来了巨大的性能提升和极强的数据一致性, 非常适合移动应用和 Web 应用中的无限滚动加载.
