== Nginx超时讲解

Nginx 作为反向代理与静态资源服务器, 几乎参与了每一条请求链路的各个阶段. 超时 (Timeout) 是 Nginx 保证连接与资源不被异常占用的核心机制: 一旦某个阶段在约定时间内没有进展, Nginx 就会主动中断, 释放连接与工作进程资源. 本文系统梳理 Nginx 各场景下的超时指令, 解释其含义, 作用阶段与配置建议.

[[nginx-timeout-overview]]
=== 超时概述

==== 为什么需要超时

Nginx 采用**事件驱动 + 异步非阻塞**的架构, 单个 worker 进程即可同时处理成千上万个连接. 这意味着任何一个连接都不能无限期占用资源:

* 恶意客户端只建立连接而不发送数据, 会长期占用连接与内存
* 上游服务故障或响应缓慢, 会导致请求长时间悬挂, 耗尽连接池
* 慢速读写 (Slow HTTP) 攻击通过极慢的发送速率拖垮服务器

超时机制通过**在关键阶段设置时间上限**, 及时回收异常连接, 是 Nginx 高可用性的重要保障.

==== 超时的分类

按请求经过的阶段, Nginx 超时可分为三类:

客户端连接超时:: 处理客户端请求与响应阶段, 如读取请求头, 请求体, 发送响应, 长连接保活
上游代理超时:: 与上游服务器交互阶段, 如建立连接, 转发请求, 读取响应
基础设施超时:: DNS 解析, SSL 握手, HTTP/2 连接管理等辅助环节

=== 客户端连接超时

客户端连接阶段涉及多个超时指令, 其作用位置如下图所示:

==== client_header_timeout

client_header_timeout:: 读取客户端**请求头**的超时时间, 默认 60s, 上下文为 http, server

若客户端在该时间内未发送完整请求头, Nginx 返回 **408 (Request Time-out)**. 该指令主要防止客户端只建立 TCP 连接却迟迟不发送数据.

==== client_body_timeout

client_body_timeout:: 读取客户端**请求体**的超时时间, 默认 60s, 上下文为 http, server, location

IMPORTANT: 该超时仅指**两次连续读操作之间的间隔**, 而非整个请求体传输的总耗时. 只要客户端持续有数据到达, 即使传输很慢也不会超时; 一旦中断超过该时间, 连接将被关闭.

==== send_timeout

send_timeout:: 向客户端**发送响应**的超时时间, 默认 60s, 上下文为 http, server, location

与 `client_body_timeout` 类似, 该超时同样仅指**两次连续写操作之间的间隔**. 超时后连接被关闭, 可有效抵御 Slow HTTP 读攻击.

==== keepalive_timeout 与 keepalive_time

keepalive_timeout:: 长连接**空闲保活**的超时时间, 默认 75s; 第二个可选参数用于设置响应头 `Keep-Alive: timeout=time`
keepalive_time:: 限制单个 keep-alive 连接上处理请求的**总时长**, 默认 1h, 需 Nginx 1.19.10+ 版本

`keepalive_timeout` 决定空闲连接能存活多久, 而 `keepalive_time` 则给连接设置了硬性的生命周期上限, 防止连接被无限复用导致资源不均衡.

客户端连接超时指令汇总如下:

[cols="1,1,2,3"]
|===
| 指令 | 默认值 | 上下文 | 说明

| `client_header_timeout`
| 60s
| http, server
| 读取请求头超时

| `client_body_timeout`
| 60s
| http, server, location
| 读取请求体超时 (读间隔)

| `send_timeout`
| 60s
| http, server, location
| 发送响应超时 (写间隔)

| `keepalive_timeout`
| 75s
| http, server, location
| 长连接空闲超时

| `keepalive_time`
| 1h
| http, server, location
| 长连接总时长上限
|===

[[nginx-upstream-timeouts]]
=== 上游代理超时

当 Nginx 作为**反向代理**时, 与上游服务器的交互同样需要超时保护. 这些指令以 `proxy_` 为前缀, 对应 FastCGI, uWSGI, SCGI, gRPC 等协议也有同构指令 (前缀分别为 `fastcgi_`, `uwsgi_`, `scgi_`, `grpc_`).

==== proxy_connect_timeout

proxy_connect_timeout:: 与上游服务器**建立连接**的超时时间, 默认 60s

WARNING: 该值通常**不能超过 75s**, 这是 Nginx 官方文档明确的限制. 设置过大会使请求在无法连接的上游前长时间阻塞.

==== proxy_read_timeout

proxy_read_timeout:: 从上游服务器**读取响应**的超时时间, 默认 60s

该超时仅指**两次连续读操作之间的间隔**. 对响应缓慢或需要长时间计算的上游, 需要适当调大该值, 否则会被误判为超时.

==== proxy_send_timeout

proxy_send_timeout:: 向上游服务器**发送请求**的超时时间, 默认 60s

该超时仅指**两次连续写操作之间的间隔**.

==== proxy_next_upstream_timeout

proxy_next_upstream_timeout:: 将请求**重试到下一台上游**的总时间上限, 默认 0 (不限制)

当配置了上游故障重试时, 该指令防止请求在多台上游之间无限重试.

[[nginx-other-timeouts]]
=== 其他关键超时

除客户端与上游代理外, Nginx 在基础设施层面也提供若干超时指令.

resolver_timeout:: DNS **解析**超时, 默认 30s
ssl_handshake_timeout:: SSL **握手**超时, 默认 60s, 需 Nginx 1.19.5+ 版本
http2_idle_timeout:: HTTP/2 连接**空闲**超时, 默认 3m, 需 Nginx 1.19.7+ 版本
http2_recv_timeout:: 等待客户端发送更多数据的超时, 默认 30s, 需 Nginx 1.19.7+ 版本
lingering_time:: 关闭连接前处理客户端额外数据的超时, 默认 30s

NOTE: HTTP/2 的超时指令通常还需要配合 `http2_max_requests` 等参数共同管理连接生命周期.

[[nginx-timeout-config]]
=== 配置示例

以下配置展示了常见场景下 Nginx 超时参数的综合设置:

[source,nginx]
----
http {
    # 客户端连接超时
    client_header_timeout 10s;      # <1>
    client_body_timeout   30s;      # <2>
    send_timeout          30s;      # <3>
    keepalive_timeout     65s;      # <4>
    keepalive_time        1h;       # <5>

    # DNS 解析与 SSL 握手
    resolver 223.5.5.5 valid=30s;
    resolver_timeout 5s;            # <6>
    ssl_handshake_timeout 10s;      # <7>

    server {
        listen 443 ssl;
        server_name example.com;

        location /api/ {
            proxy_pass http://backend;

            # 上游代理超时
            proxy_connect_timeout 5s;        # <8>
            proxy_send_timeout    30s;       # <9>
            proxy_read_timeout    60s;       # <10>
            proxy_next_upstream_timeout 10s; # <11>
        }
    }
}
----
<1> 读取客户端请求头, 最长等待 10s
<2> 读取请求体, 两次读操作间隔不超过 30s
<3> 发送响应, 两次写操作间隔不超过 30s
<4> 空闲长连接保持 65s
<5> 单个长连接总时长上限 1h
<6> DNS 解析超时 5s
<7> SSL 握手超时 10s
<8> 与上游建立连接最长 5s
<9> 向上游发送请求, 写间隔不超过 30s
<10> 从上游读取响应, 读间隔不超过 60s
<11> 多台上游重试的总时间上限 10s

[[nginx-timeout-principles]]
=== 设置原则与最佳实践

超时值的设置需要平衡**用户体验**与**资源保护**, 核心原则如下:

* 客户端阶段的超时通常可适当缩短, 正常用户发送请求头或请求体只需毫秒级
* `proxy_read_timeout` 需要覆盖上游的最长处理时间, 过短会导致正常请求被误杀
* `proxy_connect_timeout` 应远小于 `proxy_read_timeout`, 快速失败才能及时切换上游
* 区分"总时间"与"间隔"两类语义, 避免误配置
* 生产环境建议基于监控数据 (如 P99 响应时间) 动态调优

常见误区:

* 误以为 `client_body_timeout` 是传输整个请求体的总时限, 实际它是两次读操作间的间隔
* 将 `proxy_connect_timeout` 设置为超过 75s, 违背 Nginx 的内置约束
* 忽略 `keepalive_time`, 导致长连接被无限复用
* 使用 HTTP/2 时沿用 HTTP/1.1 的超时策略, 未配置 `http2_idle_timeout`

[[nginx-timeout-summary]]
=== 总结

Nginx 超时机制贯穿请求的每个阶段, 是保障服务稳定性与资源利用率的关键设计:

* 客户端连接超时 (`client_header_timeout`, `client_body_timeout`, `send_timeout`, `keepalive_timeout`) 防止异常客户端占用资源
* 上游代理超时 (`proxy_connect_timeout`, `proxy_send_timeout`, `proxy_read_timeout`) 保障反向代理场景的快速失败
* 基础设施超时 (`resolver_timeout`, `ssl_handshake_timeout`, `http2_*`) 覆盖辅助环节

理解每类超时的**作用阶段**与**间隔语义**, 是正确配置 Nginx 超时的前提.
