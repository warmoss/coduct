== Nginx超时讲解

=== 核心概念: 为什么需要超时?
超时机制主要为了解决以下问题:

. **资源释放:** 防止空闲或僵死的连接长期占用服务器资源(如内存、文件描述符), 导致资源耗尽.

. **提高性能:** 避免后端服务或上游服务器响应缓慢时, 拖累整个系统的响应速度.

. **增强可靠性:** 对故障进行隔离, 确保单个服务的缓慢或故障不会像多米诺骨牌一样导致整个系统雪崩.

. **改善用户体验:** 给客户端一个明确的失败响应, 而不是让用户无限期地等待.

=== Nginx 主要超时参数详解
Nginx 的超时配置可以大致分为三类: **客户端相关**、**代理相关** 和 **上游相关**. 下图清晰地展示了这些超时配置在请求生命周期中所处的位置:

下面我们根据这个生命周期, 详细讲解每个阶段的关键参数.

=== 客户端相关超时
这些参数控制着 Nginx 与客户端(如浏览器、移动应用)之间的连接行为.

. **client_header_timeout**

* **含义:** 定义读取客户端请求头(Request Headers)的超时时间.

* **场景:** 如果客户端在建立连接后, 迟迟不发送请求头(例如因为网络差或恶意攻击), 超过这个时间后, Nginx 将返回 **408 (Request Time-out)** 错误.

* **默认值:** **60s**

* 建议: 通常保持默认即可. 在遭受慢速攻击时, 可以适当调低.

. **client_body_timeout**

* **含义:** 定义读取客户端请求体(Request Body)的超时时间.

* **场景:** 客户端发送了请求头后, 传输 **POST** 等方法的请求体时速度过慢, 超过这个时间, Nginx 同样返回 **408** 错误.

* **默认值:** **60s**

* **建议:** 如果应用有文件上传等功能, 且用户网络环境较差, 可以适当调高. 否则保持默认.

. **keepalive_timeout**

* **含义:** 定义**保持连接(Keep-Alive)** 的超时时间. 在一个 TCP 连接上, 客户端完成第一个请求后, 可以在此超时时间内继续发送后续请求, 无需重新建立连接.

* **场景:** 设置连接保持空闲的最长时间. 超过这个时间, Nginx 将关闭连接.

* **默认值:** **75s**

* **建议:** 适当调高此值(如 **30s** 到 **60s**)可以显著减少 TCP 握手开销, 提升性能, 尤其对于需要加载大量资源的网站. 设置过低则失去了 Keep-Alive 的优势.

* **相关配置:** **keepalive_requests** - 一个保持连接上最多可以服务的请求数量, 默认 **1000**.

. **send_timeout**

* **含义:** 定义向客户端**发送**数据的超时时间.

* **场景:** 客户端已经准备好接收数据, 但 Nginx 在此时段内没有发送任何数据给客户端, 连接将被关闭.

* **默认值:** **60s**

注意: 这个超时是针对**两次连续的发送操作**, 而不是整个响应传输. 如果客户端每隔一秒接收一个字节, 那么这个总时间可能会远超 **send_timeout**.

=== 代理相关超时 (Upstream/Proxying)
当 Nginx 作为反向代理(使用 **proxy_pass**)时, 以下参数控制着它与上游服务器(如 Tomcat, Node.js, PHP-FPM, 另一个 Nginx)的交互行为. **这是调优的重点.**

. **proxy_connect_timeout**

* **含义:** 定义 Nginx **与上游服务器建立 TCP 连接**的超时时间.

* **场景:** 上游服务器宕机、端口不对或网络不通时, Nginx 无法在指定时间内建立连接.

* **默认值:** **60s**

* **建议:** **通常应该设置得较低**, 例如 **4s** 或 **8s**. 如果上游服务在同一个机房, 甚至可以设置为 **2s**. 长时间的重试会阻塞请求, 导致 Nginx worker 进程被占满.

. **proxy_send_timeout**

* **含义:** 定义 Nginx **向上游服务器发送请求**的超时时间.

* **场景:** Nginx 已经与上游建立连接, 但在发送请求包时, 上游处理能力已满, 来不及接收数据.

* **默认值:** **60s**

* **建议:** 如果上游服务处理压力大或网络带宽紧张, 可以适当调高. 但通常 **60s** 足够.

. **proxy_read_timeout**

* **含义:** 这是**最重要也是最常用**的代理超时. 它定义 Nginx **等待上游服务器返回响应**的超时时间.

* **场景:** 上游服务器已经成功接收请求, 但处理过程非常缓慢(例如复杂的数据库查询), 超过这个时间仍未返回任何数据.

* **默认值:** **60s**

* **建议:** **根据具体业务需求调整**.

** 对于 API 接口, 可以设置为 **10s** 或 **30s**.

** 对于文件导出、长轮询(Long Polling)等需要长时间处理的任务, **必须将此值调大**(如 **300s**, **600s**), 否则任务会中途失败.

** 可以在 **location** 块中为特定接口单独设置.

=== 其他重要超时
. **resolver_timeout**

* **含义:** DNS 解析器的超时时间. 当使用 **proxy_pass** 指向一个域名, 或者使用 **resolver** 指令时生效.

* **默认值:** **30s**

* **场景:** DNS 服务器响应慢或无响应.

. **FastCGI 相关超时 (与 proxy_* 类似)**

* 当 Nginx 与 PHP-FPM 协作时, 有一组对应的参数:

** **fastcgi_connect_timeout**

** **fastcgi_send_timeout**

** **fastcgi_read_timeout** (非常重要, 作用同 **proxy_read_timeout**)

* 它们的含义和用法与 **+proxy_*+** 系列完全一致, 只是对象从上游服务器变成了 FastCGI 进程管理器.

=== 配置示例
[source, plaintext, linenums]
----
http {
    # 客户端相关超时
    client_header_timeout   10s;
    client_body_timeout     10s;
    # 第一个是客户端保持时间, 第二个是响应头"Keep-Alive: timeout=30"的值
    keepalive_timeout       30s 30s;
    send_timeout            10s;

    # 上游代理相关超时 (通常配置在 location 或 server 块中)
    proxy_connect_timeout   5s;
    proxy_send_timeout      15s;
    proxy_read_timeout      30s;

    # 定义一个上游服务器组
    upstream my_backend {
        server 10.0.1.10:8080;
        server 10.0.1.11:8080;
    }

    server {
        listen 80;

        # 常规代理 location
        location / {
            proxy_pass http://my_backend;
            # 继承 http 块中的 proxy_* 超时设置
        }

        # 一个需要长时间处理的 API 接口, 单独设置更长的读超时
        location /api/long-running-task {
            proxy_pass http://my_backend;
            proxy_read_timeout 300s; # 5分钟
        }

        # 处理 PHP 请求的 location, 使用 FastCGI 超时
        location ~ \.php$ {
            fastcgi_pass 127.0.0.1:9000;
            fastcgi_read_timeout 30s; # 等待 PHP-FPM 执行脚本的超时
            include fastcgi_params;
        }
    }
}
----

=== 总结与最佳实践
|===
|超时参数|作用对象|关键场景|建议

|**client_header/body_timeout**
|客户端
|防止慢速攻击
|保持默认(60s)

|**keepalive_timeout**
|客户端
|连接复用, 性能关键
|根据业务调整(30-60s)

|**proxy_connect_timeout**
|上游服务器
|上游连接失败
|**设置较低(2-8s)**

|**proxy_read_timeout**
|上游服务器
|**上游处理缓慢**
|**根据业务灵活调整(API设短, 长任务设长)**

|**proxy_send_timeout**
|上游服务器
|上游接收能力不足
|保持默认(60s)通常足够

|===

核心原则::

. **区分对待:** 不要对所有请求使用统一的超时配置. 为常规请求和长任务请求设置不同的 **location** 和超时值.

. **连接超时短:** **proxy_connect_timeout** 应设置得较短, 快速失败.

. **读超时是重点:** **proxy_read_timeout** 和 **fastcgi_read_timeout** 是最常需要调整的参数, 务必与业务逻辑的处理时间匹配.

. **监控与日志:** 结合 Nginx 的 **error.log**(通常会记录 upstream timed out 错误)和访问日志, 观察超时情况, 并据此调整配置.

通过合理配置这些超时参数, 你可以极大地提升应用的韧性、可靠性和用户体验.
