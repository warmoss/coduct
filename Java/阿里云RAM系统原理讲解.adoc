== 阿里云RAM系统原理讲解

=== 什么是RAM

定义:: RAM(Resource Access Management, 资源访问管理) 是阿里云提供的**统一身份与访问管理**服务, 用于控制谁(身份)能以什么方式(权限)访问哪些云资源.

如果把阿里云比作一栋大楼, 那么:

* **主账号**就是大楼的**业主**, 拥有大楼一切空间和设施的完全所有权
* **RAM 用户**是业主发给员工的**门禁卡**, 可以精细控制谁能进哪个房间
* **RAM 角色**是**临时通行证**, 允许特定人员在特定时间进入特定区域
* **权限策略**是**规则手册**, 详细规定了每张门禁卡可以做什么、不可以做什么

RAM 的核心价值在于**最小权限原则(Principle of Least Privilege)**: 每个身份只获得完成工作所需的最小权限集, 避免因权限过大导致的安全风险.

=== 核心概念

==== 身份(Identity)

RAM 中的身份分为三类:

主账号(Account Owner):: 阿里云账号的**注册者**, 拥有该账号下所有资源的完全控制权限; 主账号权限过大, 不建议日常使用, 应创建 RAM 用户进行日常操作

RAM 用户(RAM User):: 在主账号下创建的**子账号**, 归属于该主账号, 本身没有任何权限, 需要**附加权限策略**后才能操作资源; 一个主账号下最多可创建 1000 个 RAM 用户(可提额)

RAM 角色(RAM Role):: 一种**虚拟身份**, 不直接关联具体人员或服务, 而是定义了一组权限的集合, 需要被**信任实体**(RAM 用户、阿里云服务、身份提供商)扮演后才能生效

==== 权限策略(Policy)

策略是权限控制的**核心载体**, 本质是一个 JSON 格式的文档, 定义了允许或拒绝的操作列表.

系统策略(System Policy):: 阿里云预定义的策略模板, 不可修改, 覆盖常见场景(如 AdministratorAccess、ReadOnlyAccess)

自定义策略(Custom Policy):: 用户按需编写的策略, 粒度更细, 可精确控制到具体资源实例和操作

==== 授权(Authorization)

授权指将策略附加(Attach)到身份上的过程. RAM 支持两种授权方式:

人员授权:: 直接将策略附加到 RAM 用户或 RAM 用户组

服务授权:: 通过 RAM 角色的信任策略, 允许阿里云服务扮演该角色获取权限

=== 权限策略语法

策略使用 JSON 格式, 遵循阿里云定义的语法规范:

[source,json]
----
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecs:DescribeInstances",
        "ecs:StartInstance",
        "ecs:StopInstance"
      ],
      "Resource": [
        "acs:ecs:*:*:instance/i-001",
        "acs:ecs:*:*:instance/i-002"
      ],
      "Condition": {
        "StringEquals": {
          "acs:SourceIp": ["10.0.0.0/8"]
        }
      }
    }
  ]
}
----

各字段含义:

* **Version:** 策略版本号, 目前固定为 `"1"`
* **Statement:** 策略语句列表, 每个语句包含 Effect、Action、Resource、Condition 等子字段
** **Effect:** `Allow`(允许) 或 `Deny`(拒绝), 决定是否授权
** **Action:** 操作的列表, 格式为 `<服务代号>:<操作名>`, 支持通配符 `*`(如 `"ecs:*"` 表示所有 ECS 操作)
** **Resource:** 资源列表, 格式为 `acs:<服务>:<地域>:<账号ID>:<资源类型>/<资源ID>`, 也支持通配符
** **Condition:** 条件约束(可选), 限制策略生效的上下文(如来源 IP、时间、MFA 状态等)

资源描述符(ACS ARN)格式详解:

[source,json]
----
acs:ecs:cn-hangzhou:123456789:instance/i-001
# ^   ^     ^           ^         ^
# |   |     |           |         +-- 资源ID
# |   |     |           +------------ 阿里云账号ID
# |   |     +------------------------ 地域(Region)
# |   +------------------------------ 服务代码
# +---------------------------------- Alibaba Cloud Service
----

=== 权限评估逻辑

RAM 的权限判断遵循**显式拒绝优先级最高**的原则, 评估流程如下:

. **收集策略:** 收集当前请求相关的所有策略(用户策略、组策略、角色策略等)

. **判断是否显式拒绝:** 如果任何一条策略中存在匹配的 `Deny` 语句, 直接返回拒绝

. **判断是否显式允许:** 如果存在匹配的 `Allow` 语句, 则允许该操作

. **默认拒绝:** 如果没有任何匹配的 `Allow` 或 `Deny` 语句, 默认返回拒绝

[plantuml, "权限评估流程", format=png]
----
@startuml
start
:收到请求(身份, 操作, 资源);
:收集所有关联策略;
:存在匹配的 Deny?;
if (存在匹配的 Deny?) then (是)
  :返回 Deny(拒绝);
  stop
endif
:存在匹配的 Allow?;
if (存在匹配的 Allow?) then (是)
  :返回 Allow(允许);
  stop
endif
:默认 Deny(拒绝);

@enduml
----

NOTE: 策略之间的叠加遵循"Deny 优先"原则, 即只要有一条策略拒绝了某个操作, 无论有多少条策略允许, 最终结果都是拒绝. 这是一个关键的安全设计.

=== RAM 角色与信任体系

==== 角色扮演流程

RAM 角色的核心机制是**角色扮演(Role Assumption)**, 它允许一个身份临时"变成"另一个身份来执行操作.

[plantuml, "RAM 角色扮演流程", format=png]
----
@startuml
actor "RAM 用户/ECS 实例\n/身份提供商" as Principal
participant "STS 服务" as STS
participant "RAM 角色" as Role
participant "目标云服务" as Service

Principal -> STS: 调用 AssumeRole 接口
note right: 携带角色ARN + 会话名称
STS -> STS: 验证请求者身份\n和角色信任策略
STS -> Role: 验证通过, 创建临时身份
STS --> Principal: 返回临时安全令牌\n(AccessKeyId + AccessKeySecret + SecurityToken)

Principal -> Service: 使用临时令牌访问资源
Service -> STS: 验证临时令牌有效性
STS --> Service: 令牌有效
Service --> Principal: 返回资源数据
@enduml
----

关键步骤解析:

. **发起扮演请求:** 身份(如 ECS 实例、另一个 RAM 用户)调用 `AssumeRole` API, 传入角色 ARN 和会话名称

. **信任策略验证:** STS(Security Token Service) 校验请求者身份是否在角色的信任策略(Trust Policy)中

. **发放临时令牌:** 验证通过后, STS 生成一个**临时安全令牌**, 包含 AccessKeyId、AccessKeySecret、SecurityToken 和过期时间

. **使用令牌访问:** 扮演者使用临时令牌调用阿里云 API, 云服务会验证令牌的有效性

. **令牌过期失效:** 临时令牌有有效期(默认 1 小时, 最长 12 小时), 过期后自动失效, 需重新扮演获取新令牌

==== 信任策略

角色的**信任策略(Trust Policy)** 定义了**谁能扮演该角色**, 其语法与权限策略类似:

[source,json]
----
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "RAM": ["acs:ram::123456789:root"],
        "Service": ["ecs.aliyuncs.com"]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
----

Principal 字段是信任策略独有的, 指定了被信任的实体类型:

* `RAM` - 阿里云 RAM 用户或角色
* `Service` - 阿里云服务(如 ECS、FC、SLB)
* `Federated` - 外部身份提供商(如企业 IdP、OIDC)

==== STS 临时令牌

STS 令牌是 RAM 角色扮演的核心产物, 具备以下特点:

临时性:: 有明确的过期时间(默认 3600 秒, 可通过 `DurationSeconds` 参数调整), 过期后自动失效, 降低了凭证泄露的风险

动态生成:: 每次调用 AssumeRole 都会生成一组全新的凭证, 且彼此独立

权限受限:: 临时令牌的权限 = **角色的权限策略** 与 **调用者自身权限**的交集(当调用者本身是 RAM 用户时)

=== 核心功能

==== 多因素认证(MFA)

MFA(Multi-Factor Authentication) 为账号提供额外的安全层, 在密码之外还需要**虚拟 MFA 设备**(手机 App 生成的动态验证码)或**硬件 MFA 设备**.

MFA 可在以下层面启用:

* **主账号 MFA:** 保护主账号登录, 防止主账号泄露
* **RAM 用户 MFA:** 要求特定 RAM 用户在登录控制台或调用 API 时验证 MFA
* **操作保护:** 对高风险操作(如删除资源、修改权限)开启二次确认

==== 用户组管理

RAM 用户组用于**批量管理权限**, 将权限策略附加到组而非逐个附加到用户:

[source,json]
----
{
  "Group": "developers",
  "Users": ["alice", "bob", "charlie"],
  "Policies": ["ReadOnlyAccess", "ecs:ManageInstances"]
}
----

组管理的优势:

* **简化授权:** 新用户加入组即可自动继承组权限
* **统一变更:** 修改组权限立即影响组内所有用户
* **角色分类:** 按职责分组(如 developers、admins、ops), 职责清晰

==== 单点登录(SSO)

RAM 支持通过 **身份提供商(IdP, Identity Provider)** 集成企业现有的身份系统:

* **SAML 2.0:** 企业使用自己的 Active Directory 或 Okta 等 IdP 进行认证, 通过 SAML 断言获取阿里云访问权限
* **OIDC:** 使用兼容 OpenID Connect 的身份提供商(如 GitHub、GitLab)进行认证

这种模式下, 阿里云不直接管理用户密码, 而是信任企业 IdP 的认证结果, 实现**一处登录、到处访问**.

=== 权限边界

**权限边界(Permission Boundary)** 是 RAM 的高级功能, 用于设置 RAM 用户或角色的**最大权限上限**.

[source,json]
----
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": [
        "ram:*",
        "ecs:DeleteInstances",
        "vpc:DeleteVpc"
      ],
      "Resource": "*"
    }
  ]
}
----

权限边界的工作逻辑:

. 用户的最终有效权限 = **权限边界策略** 与 **附加的授权策略** 的交集
. 即使授权策略授予了 `ram:*` 权限, 权限边界也会禁止修改 RAM 资源的操作
. 适用于**多账号管理场景**, 管理员给子账号设置权限边界, 防止其权限范围超出预期

=== 最佳实践

. **主账号仅用于创建 RAM 用户:** 日常操作使用 RAM 用户, 主账号只在必要时使用, 且务必开启 MFA

. **最小权限原则:** 从最小权限开始, 逐步按需增加, 避免使用 `AdministratorAccess` 等过宽的系统策略

. **优先使用用户组:** 通过组管理权限, 而非逐个附加策略到用户, 降低管理复杂度

. **使用角色而非长期密钥:** 对于 ECS 应用、Function Compute 等服务, 使用 RAM 角色 + STS 临时令牌, 避免在代码中硬编码 AccessKey

. **启用操作保护:** 对 DeleteDBInstance、DeleteVpc 等高风险操作开启 MFA 二次确认

. **定期审计权限:** 使用 RAM 的"权限审计"功能, 检查是否有闲置或过大的权限

. **设置权限边界:** 在子账号层面设置权限边界, 增加安全隔离层

=== 总结

* RAM 是阿里云的身份与访问管理核心, 基于**身份-策略-授权**三层模型
* **权限策略**使用 JSON 语法, 支持 Allow/Deny、资源级控制、条件约束
* 权限评估遵循 **Deny 优先 -> Allow -> 默认拒绝** 的三步逻辑
* **RAM 角色 + STS** 实现了安全的临时授权机制, 是云原生应用的首选方案
* **MFA、权限边界、SSO** 等高级功能构成了完整的安全防护体系
