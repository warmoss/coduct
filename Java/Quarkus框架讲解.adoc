== Quarkus框架讲解

=== 引言

传统 Java 框架(如 Spring Boot)在微服务和容器化场景下面临两大痛点: **启动慢**和**内存占用高**. Quarkus 正是为解决这些问题而生——它是一个专为 GraalVM HotSpot 和 Kubernetes 优化的 Java 全栈框架, 通过 **构建时处理** 机制将大量工作从运行时迁移到编译期, 实现毫秒级启动和极低内存消耗.

Quarkus 由 Red Hat 开发, 核心口号是 "Supersonic Subatomic Java", 强调:

* **超快启动** - 在 JVM 模式下秒级启动, Native 模式下毫秒级(0.01s 级别)启动
* **低内存占用** - Native 镜像内存消耗仅为传统框架的 1/10 到 1/5
* **容器优先** - 天然适配 Kubernetes 环境, 镜像体积小、部署快
* **双重模式** - 同一套代码同时支持 JVM 模式和 Native 模式

=== 核心概念

Quarkus 引入了一些关键概念, 理解它们是掌握框架的基础:

构建时处理(Build-Time Processing):: Quarkus 将传统框架在运行时完成的配置解析、依赖注入分析、代理类生成等工作提前到**编译期**完成. 这意味着应用启动时只需加载已经处理好的字节码, 大幅缩短启动时间.
扩展(Extension):: Quarkus 的功能模块化单元. 每个扩展对应一项技术集成(如 Hibernate、RESTEasy Reactive、Redis 等), 通过 `pom.xml` 或 `build.gradle` 声明式引入.
CDI 容器:: Quarkus 使用 **ArC**(ArC is CDI)作为依赖注入容器, 它是 Jakarta CDI 的子集实现. ArC 在构建时完成所有依赖分析和注入点验证.
GraalVM Native Image:: GraalVM 提供的一项技术, 将 Java 字节码编译成与平台相关的**原生可执行文件**. Native 镜像去除了 JVM 运行时负担, 启动无需类加载和 JIT 预热.
连续测试(Continuous Testing):: Quarkus 的开发模式提供即时测试反馈——修改代码后自动重新运行受影响测试, 无需手动触发.

=== 核心原理

==== 构建时处理机制

Quarkus 与传统框架最本质的区别在于**处理时机的转移**.

[cols="3*"]
|===
| 阶段 | 传统框架 | Quarkus

| 配置解析 | 运行时读取并解析配置文件(如 `application.yml`) | 构建时 `Augment` 阶段解析配置, 生成优化后的元数据
| Bean 发现 | 运行时扫描类路径, 构建 Bean 定义 | 构建时扫描所有类路径, 完成 Bean 验证和注入点分析
| 代理生成 | 运行时使用 CGlib/Javassist 创建动态代理 | 构建时生成所有必要的子类代理(如拦截器代理)
| 反射注册 | 运行时通过反射访问类和方法 | 构建时通过 `reflection-config.json` 预注册, Native 模式下受限
|===

这种前置处理带来了一个关键转变: Quarkus 应用的启动本质上只是**加载已准备好的数据结构**, 而不是进行复杂的初始化计算.

==== ArC 依赖注入

ArC 是 Quarkus 的依赖注入实现, 遵循 Jakarta CDI 2.0 规范但做了大量简化:

* **构建时验证** - ArC 在编译期检查所有注入点的合法性(如循环依赖、作用域不匹配), 而不是推迟到运行时
* **类型安全** - 充分利用 Java 编译期类型检查, 减少运行时 `ClassCastException`
* **基于 `beans.xml`** - 虽然 ArC 支持隐式 Bean 发现, 但推荐使用 `beans.xml` 明确声明 Bean 范围以加快构建速度
* **客户端代理** - 对 `@RequestScoped` / `@ApplicationScoped` 等作用域的 Bean, ArC 在构建时生成客户端代理类, 而非运行时动态生成

==== GraalVM Native 镜像支持

Quarkus 对 GraalVM Native 的支持是深度的框架级集成:

. **封闭世界假设(Closed-World Assumption)** - Native 镜像编译时假设所有类和字节码都已确定, 不需要动态加载. Quarkus 通过 `@RegisterForReflection` 注解和 `application.properties` 中的配置项告知 GraalVM 哪些类需要保留反射能力
. **代理类预生成** - Quarkus 扩展在构建时通过字节码生成技术(Byte Buddy)创建 Native 镜像所需的配置信息, 如反射配置、资源访问配置、JNI 配置等
. **Substrate VM** - GraalVM 的 Substrate VM 提供了一套有限的运行时组件实现(如线程管理、内存管理、GC), Quarkus 确保其代码路径不依赖完整的 HotSpot JDK

[source,xml]
----
<!-- 启用 Native 构建 -->
<plugin>
    <groupId>io.quarkus.platform</groupId>
    <artifactId>quarkus-maven-plugin</artifactId>
    <executions>
        <execution>
            <goals>
                <goal>build</goal>
                <goal>native-image</goal>  <1>
            </goals>
        </execution>
    </executions>
</plugin>
----
<1> `native-image` 目标触发 GraalVM 编译, 生成原生可执行文件

==== 响应式核心

Quarkus 的底层基于 **Eclipse Vert.x**——一个高性能的事件驱动网络框架. 这意味着:

* **事件循环(Event Loop)** - Vert.x 使用少量 I/O 线程处理大量并发连接, 而非传统的一请求一线程模型
* **非阻塞 I/O** - 所有 I/O 操作(数据库访问、HTTP 请求、消息队列)默认优先使用非阻塞 API
* **Mutiny** - Quarkus 推荐使用 Mutiny 响应式库(`Uni` / `Multi`)进行异步编程

[source,java]
----
import io.smallrye.mutiny.Uni;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;

@Path("/hello")
public class GreetingResource {

    @GET
    public Uni<String> hello() {        // <1>
        return Uni.createFrom()
            .item("Hello, Quarkus!")
            .onItem().delayIt()
            .by(Duration.ofMillis(100)); // <2>
    }
}
----
<1> 返回 `Uni<T>` 表示响应式端点, Vert.x 事件循环不会被阻塞
<2> 模拟延迟操作, 但不会占用线程等待

==== 扩展机制

Quarkus 功能的扩展性通过 **Extension(扩展)** 体系实现. 每个扩展本质上是一个在构建时参与处理的 Maven 模块:

[plantuml, "Quarkus 扩展加载流程", format=png]
----
@startuml
actor 开发者
participant "构建工具\n(Maven/Gradle)" as Build
participant "Quarkus Maven Plugin" as QMP
database "扩展仓库" as Registry

开发者 -> Build: quarkus:dev / quarkus:build
Build -> QMP: 执行扩展处理
QMP -> Registry: 加载已声明扩展
Registry --> QMP: 返回扩展元数据

== 构建时处理阶段 ==
QMP -> QMP: 解析每个扩展的\n字节码增强描述
QMP -> QMP: 生成反射配置\nJNI 配置\n资源配置
QMP -> QMP: 验证 CDI Bean 图\n无循环依赖

== 生成阶段 ==
QMP -> QMP: 生成启动类\n生成代理类\n生成配置快照
QMP --> Build: 输出增强后的工件

note right: 生成阶段的产物\n是编译后的优化字节码\n或 Native 可执行文件
@enduml
----

扩展主要承担以下职责:

* **字节码增强** - 在构建时修改用户类的字节码以注入横切逻辑(如事务管理、缓存、安全拦截)
* **配置贡献** - 向 Quarkus 全局配置系统注册自定义配置项, 提供 IDE 自动补全支持
* **资源处理** - 将特定资源文件(如 Hibernate 的 `persistence.xml`)预处理为优化后的元数据
* **Native 适配** - 为 GraalVM Native 编译提供所需的反射、资源、JNI 配置和运行时替换类

=== 工作流程

==== 开发流程

Quarkus 提供三种运行模式, 适应不同阶段:

. **开发模式(`quarkus:dev`)** - 启动 HotSpot JVM, 开启热重载. 修改代码后, 自动重新编译并替换运行中的类. 支持 Continuous Testing, 代码变更后自动运行受影响测试
. **JVM 模式(`quarkus:build`)** - 构建为标准的 Java JAR 包(胖 JAR), 在标准 JVM 上运行. 启动时间通常在 1-3 秒
. **Native 模式(`mvn package -Dnative`)** - 构建为 GraalVM Native 镜像, 启动时间在 0.01 秒级别, 内存占用极低. 需安装 GraalVM 和 Native Image 工具

==== 完整的 REST API 示例

以下是一个完整的 Quarkus REST API 开发示例:

[source,xml]
----
<!-- pom.xml 依赖声明 -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>io.quarkus.platform</groupId>
            <artifactId>quarkus-bom</artifactId>
            <version>3.8.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>io.quarkus</groupId>
        <artifactId>quarkus-resteasy-reactive</artifactId>  <1>
    </dependency>
    <dependency>
        <groupId>io.quarkus</groupId>
        <artifactId>quarkus-hibernate-orm-panache</artifactId> <2>
    </dependency>
    <dependency>
        <groupId>io.quarkus</groupId>
        <artifactId>quarkus-jdbc-postgresql</artifactId>    <3>
    </dependency>
</dependencies>
----
<1> 响应式 REST 端点扩展
<2> Hibernate ORM with Panache(简化数据访问层)
<3> PostgreSQL 驱动

[source,java]
----
import jakarta.persistence.Entity;
import io.quarkus.hibernate.orm.panache.PanacheEntity;

@Entity
public class Book extends PanacheEntity {            // <1>
    public String title;
    public String author;
    public int pages;

    public static Book findByTitle(String title) {   // <2>
        return find("title", title).firstResult();
    }
}
----
<1> 继承 `PanacheEntity` 自动获得 CRUD 方法, 无需编写 DAO
<2> Panache 的静态查询 API, 编译期验证字段名合法性

[source,java]
----
import jakarta.ws.rs.*;
import jakarta.ws.rs.core.Response;
import java.net.URI;

@Path("/books")
@Produces("application/json")
@Consumes("application/json")
public class BookResource {

    @GET
    public List<Book> list() {
        return Book.listAll();                       // <1>
    }

    @POST
    public Response create(Book book) {
        book.persist();                              // <2>
        return Response.created(URI.create("/books/" + book.id)).build();
    }

    @GET
    @Path("/{id}")
    public Book get(@PathParam("id") Long id) {
        return Book.findById(id);                    // <3>
    }

    @DELETE
    @Path("/{id}")
    public void delete(@PathParam("id") Long id) {
        Book.deleteById(id);
    }
}
----
<1> Panache 内置的 `listAll()` 方法
<2> 继承的 `persist()` 方法简化插入操作
<3> 通过 `findById()` 按主键查询

==== 配置管理

Quarkus 配置系统遵循 **MicroProfile Config** 规范, 在构建时完成配置解析:

[source,properties]
----
# application.properties
quarkus.http.port=8080
quarkus.datasource.db-kind=postgresql
quarkus.datasource.jdbc.url=jdbc:postgresql://localhost:5432/mydb
quarkus.hibernate-orm.database.generation=drop-and-create

# 配置多环境支持
%dev.quarkus.datasource.jdbc.url=jdbc:postgresql://localhost:5432/devdb
%prod.quarkus.datasource.jdbc.url=jdbc:postgresql://prod-host:5432/proddb

# 自定义配置注入
myapp.greeting=Hello
----

[source,java]
----
import jakarta.enterprise.context.ApplicationScoped;
import org.eclipse.microprofile.config.inject.ConfigProperty;

@ApplicationScoped
public class GreetingService {

    @ConfigProperty(name = "myapp.greeting")  // <1>
    String greeting;

    public String greet(String name) {
        return greeting + ", " + name + "!";
    }
}
----
<1> 构建时注入配置值, 支持类型转换、默认值、可选性

=== 与 Spring Boot 对比

[cols="3*"]
|===
| 维度 | Quarkus | Spring Boot

| 启动时间(JVM) | ~1-2s | ~5-10s
| 启动时间(Native) | ~0.01s | ~0.1-0.3s (Spring AOT)
| 内存占用(Native) | ~10-30MB | ~30-100MB
| 处理时机 | 构建时优先 | 运行时优先
| 响应式支持 | 一等公民(Vert.x + Mutiny) | WebFlux 可选
| 规范标准 | Jakarta EE + MicroProfile | Spring 生态
| 扩展/生态 | ~300+ 扩展 | 极其丰富的第三方集成
| Kubernetes 集成 | 深度内建 | 需额外配置
|===

NOTE: Spring Boot 3.x 引入 GraalVM 支持(Spring AOT)后, 在启动性能和镜像大小上大幅改进, 但在"构建时处理"的深度和一致性上仍逊于 Quarkus. Quarkus 从设计之初就以构建时处理为基石, 而 Spring 是在现有框架上附加 AOT 处理, 两者在成熟度和架构一致性上有本质差异.

=== 总结

Quarkus 通过 **构建时处理** 这一核心理念, 从根本上解决了 Java 在云原生时代的启动慢、内存高等痛点:

* **构建时处理**是 Quarkus 的灵魂——它将配置解析、Bean 分析、代理生成等从运行时迁移到编译期, 这是与其他 Java 框架最本质的差异
* **GraalVM 集成**是 Quarkus 的加速器——Native 镜像带来极致性能和极低资源消耗, 适合 Serverless、边缘计算等场景
* **响应式 + 命令式双模式**是 Quarkus 的灵活性——开发者可根据场景选择合适的编程模型, 无需框架切换
* **扩展生态**是 Quarkus 的可持续性——丰富的扩展覆盖了主流中间件和云服务集成

WARNING: Quarkus 的构建时处理虽然带来性能优势, 但也意味着**某些动态特性受限**. 例如动态类加载、运行时反射(未预注册)、动态代理等在 Native 模式下无法正常工作. 在使用第三方库时需确认其 Quarkus 扩展支持情况.

TIP: 对于新项目或在微服务架构中部署的应用, Quarkus 是一个优秀的选择. 但对于已有 Spring Boot 应用的迁移, 需要评估 Quarkus 扩展的覆盖范围和 API 兼容性. 建议新微服务优先采用 Quarkus, 存量系统逐步迁移.
