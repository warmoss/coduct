== Java内存模型讲解

=== 为什么需要 Java 内存模型 (JMM)?
在直接理解 JMM 是什么之前, 我们必须先明白它要解决什么问题.

==== 硬件的挑战: 内存架构的复杂性
现代计算机(如多核 CPU)为了提升性能, 普遍采用了以下架构:

* **多级缓存:** 每个 CPU 核心都有自己的高速缓存(L1, L2 Cache). 它们用于缓存主内存中的数据.

* **缓存一致性协议:** 虽然存在像 MESI 这样的协议来保证多个缓存之间数据的一致性, 但它并不能保证**实时性**.

* **指令重排序:** 编译器和处理器为了优化性能, 可能会对指令的执行顺序进行重排, 只要最终结果在单线程环境下是正确的.

这些优化在单线程下完美无缺, 但在多线程环境下就会带来问题: **一个线程的修改, 可能无法被另一个线程立即、正确地看到**.

==== 软件的需求: 跨平台的内存访问保证
Java 的口号是 "Write Once, Run Anywhere". 这意味着 Java 需要屏蔽掉不同操作系统和硬件架构在内存模型上的差异. 程序员不应该为了程序能正确并发, 而去关心代码是运行在 x86 还是 ARM 处理器上.

**JMM 的诞生就是为了解决这两个核心问题:**

* **为程序员提供一个统一的、标准化的内存模型**, 让我们知道在并发环境下, 写入什么时候对其他线程可见.

* **禁止某些类型的编译器重排序和处理器重排序**, 为代码的执行顺序提供一定的保障.

**简单来说: JMM 是一套规范, 它定义了多线程程序中, 对共享变量的读写操作应该如何与内存交互, 以及在这些操作之间, 什么样的顺序性是必须保证的.**

=== JMM 的核心概念: 抽象结构
JMM 并没有直接描述硬件内存架构, 而是抽象出了自己的一套模型.

==== 主内存与工作内存

* **主内存:** 存储所有的共享变量. 这是一个逻辑概念, 包含了硬件上的主内存、缓存等.

* **工作内存:** 每个线程都有自己的工作内存. 工作内存中存储了该线程使用的变量的**主内存副本**.

线程对变量的所有操作(读、写)都必须在**工作内存**中进行, 而不能直接读写主内存中的变量. 不同线程之间也无法直接访问对方工作内存中的变量.

这个模型听起来很像 CPU 的多级缓存架构, 但它是一个更高级别的抽象, 涵盖了缓存、写缓冲区、寄存器等硬件优化.

==== 内存间的交互操作
JMM 定义了 8 种原子性的操作来完成主内存与工作内存之间的交互:

* **lock(锁定):** 作用于主内存变量, 将其标识为一条线程独占状态.

* **unlock(解锁):** 作用于主内存变量, 释放被锁定变量.

* **read(读取):** 作用于主内存变量, 将变量值从主内存传输到线程的工作内存.

* **load(载入):** 作用于工作内存变量, 将 read 操作得到的值放入工作内存的变量副本中.

* **use(使用):** 作用于工作内存变量, 将变量值传递给执行引擎(如进行计算).

* **assign(赋值):** 作用于工作内存变量, 将从执行引擎接收到的值赋给工作内存变量.

* **store(存储):** 作用于工作内存变量, 将工作内存中一个变量的值传送到主内存中.

* **write(写入):** 作用于主内存变量, 将 store 操作从工作内存中得到的变量值放入主内存的变量中.

这些操作必须满足一定的规则, 例如: **read** 和 **load**、**store** 和 **write** 必须成对出现; 不允许一个线程丢弃它最近的 **assign** 操作(即变量在工作内存中改变了之后必须把该变化同步回主内存)等.

=== JMM 的三大特性
JMM 围绕三个核心特性来构建: **原子性、可见性、有序性**.

==== 原子性

* **定义:** 一个或多个操作, 要么全部执行成功, 要么全部不执行, 中间不会被任何因素打断.

* **JMM 的保证:**

** 对于基本数据类型(long 和 double 在非 64 位 JVM 上除外)的读写操作是原子性的.

** 使用 synchronized 关键字可以保证大段代码的原子性. 其背后的 monitorenter 和 monitorexit 字节码指令, 就对应了 JMM 中的 lock 和 unlock 操作.

==== 可见性

* **定义:** 当一个线程修改了共享变量的值, 其他线程能够**立即**得知这个修改

* **JMM 的保证与实现方式:**

** **volatile 关键字:** 这是保证可见性的最直接方式. 当一个变量被声明为 volatile 后, 对该变量的写操作会**立即刷新到主内存**, 并且会使其他线程工作内存中该变量的缓存副本**失效**, 从而强制它们重新从主内存读取最新值.

** **synchronized 关键字:** 在释放锁之前, 会将工作内存中修改过的共享变量刷新到主内存. 所以, 一个线程在进入 synchronized 块时, 会获得锁并清空工作内存, 从主内存重新加载变量; 退出时, 会刷新变量到主内存并释放锁.

** **final 关键字:** 被 final 修饰的字段, 在构造器一旦初始化完成, 并且构造器没有把 "this" 的引用传递出去(this 引用逃逸), 那么其他线程就能看到 final 字段的值.

==== 有序性

* **定义:** 程序执行的顺序按照代码的先后顺序执行.

* **挑战:** 指令重排序会破坏有序性.

* **JMM 的保证与实现方式(Happens-Before 规则):**

** JMM 为程序员提供了一个**强内存模型**, 即 **Happens-Before** 规则. 它并不禁止所有重排序, 而是规定了一些**禁止重排序的场景**. 如果操作 A Happens-Before 于操作 B, 那么 A 操作的结果对 B 可见, 且 A 的执行顺序排在 B 之前.

=== Happens-Before 规则
这是 JMM 的精髓, 理解了它, 你就理解了 JMM 对有序性的保证.

* **程序次序规则:** 在一个线程内, 按照控制流顺序, 书写在前面的操作 Happens-Before 于书写在后面的操作.

* **管程锁定规则:** 对一个锁的 unlock 操作 Happens-Before 于后续对这个锁的 lock 操作.

* **volatile 变量规则:** 对一个 volatile 变量的写操作 Happens-Before 于后续对这个变量的读操作.

* **线程启动规则:** Thread 对象的 start() 方法调用 Happens-Before 于此线程的每一个动作.

* **线程终止规则:** 线程中的所有操作都 Happens-Before 于对此线程的终止检测(如 Thread.join() 方法返回).

* **线程中断规则:** 对线程 interrupt() 方法的调用 Happens-Before 于被中断线程的代码检测到中断事件的发生.

* **对象终结规则:** 一个对象的初始化完成(构造器执行结束)Happens-Before 于它的 finalize() 方法的开始.

* **传递性:** 如果 A Happens-Before B, 且 B Happens-Before C, 那么 A Happens-Before C.

**Happens-Before 与 as-if-serial 语义的关系:**

* as-if-serial 是针对单线程的: 不管怎么重排序, 单线程程序的执行结果不能被改变.

* Happens-Before 是针对多线程的: 它给程序员一个承诺, 只要遵守这些规则, 那么写操作的结果对读操作一定是可见的. 它允许那些不会改变程序执行结果的重排序.

=== 实战: volatile 与 synchronized 在 JMM 中的表现

[cols="1,5,4"]
|===
|特性|synchronized|volatile

|**原子性**
|可以保证大块代码的原子性
|**不能**保证非原子操作的原子性(如 i++)

|**可见性**
|保证. 通过解锁前刷新变量到主内存, 加锁时清空工作内存.
|保证. 写操作立即刷新, 读操作直接读主内存.

|**有序性**
|保证. 一个变量在同一个时刻只允许一条线程对其进行 lock, 使得持有同一个锁的两个同步块只能串行进入.
|保证. 通过禁止指令重排序(内存屏障).

|===

**volatile 的底层实现: 内存屏障**

JVM 会在 volatile 写操作之后插入一个 **StoreLoad** 屏障, 在 volatile 读操作之前插入一个 **LoadLoad** 屏障. 这些屏障会阻止屏障两侧的指令进行重排序, 并强制刷新 CPU 缓存.

=== 总结
* **JMM 是什么?** 一个规范, 定义了 Java 程序在多线程环境下的内存访问行为.

* **JMM 为什么存在?** 屏蔽硬件差异, 为开发者提供一致性的并发内存视图.

* **JMM 的核心是什么?** 围绕**原子性、可见性、有序性**三大特性, 通过 **Happens-Before 规则** 来具体实现和描述这些特性.

* **如何正确并发?** 作为开发者, 我们应该理解 Happens-Before 规则, 并正确使用 synchronized 和 volatile 等工具, 让 JMM 来为我们处理底层的复杂问题, 而不是试图自己去猜测和控制指令的执行顺序.
