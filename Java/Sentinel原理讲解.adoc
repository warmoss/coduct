[[sentinel-principles]]
== Sentinel原理讲解

Sentinel 是阿里巴巴开源的一款面向分布式服务架构的**流量控制与熔断降级**组件, 以流量为切入点, 从**流量控制, 熔断降级, 系统自适应保护**等多个维度保障服务稳定性. 本文深入解析 Sentinel 的核心原理, 包括 Slot Chain 责任链机制, 滑动窗口统计, 以及各类限流与熔断算法的实现思想.

[[sentinel-what]]
=== 是什么与为什么

==== 是什么

Sentinel 是一个**轻量级, 高可用**的流量治理组件, 主要能力包括:

* **流量控制 (Flow Control):** 根据 QPS, 并发线程数等指标对资源调用进行限流
* **熔断降级 (Circuit Breaking):** 当依赖服务不稳定时快速失败, 保护自身
* **系统自适应保护 (System Protection):** 从系统整体负载 (Load, CPU, RT 等) 出发进行保护
* **热点参数限流 (Param Flow):** 针对请求参数中的热点数据进行精细化限流
* **黑白名单 (Authority):** 基于调用来源进行访问控制

与 Hystrix 相比, Sentinel 的规则可以在运行时**动态修改**, 无需重启, 且统计粒度更细, 提供了更丰富的限流算法.

==== 为什么需要

在微服务与分布式架构中, 服务间依赖复杂, 一个环节的故障或突发流量可能引发**雪崩效应**. Sentinel 在调用链入口进行统一拦截与实时统计, 当流量异常时快速做出**限流, 熔断**等决策, 从而:

* 防止突发流量打垮服务
* 隔离不稳定的下游依赖
* 保护系统整体资源不被耗尽

[[sentinel-core-concepts]]
=== 核心概念

在深入原理之前, 先明确 Sentinel 的几个核心概念:

Resource (资源):: Sentinel 保护的最小逻辑单元, 可以是方法, 接口或任意代码段, 通过资源名唯一标识
Entry (入口):: 一次资源访问的句柄, 由 `entry()` 方法返回, 需要在 `finally` 中调用 `exit()` 释放
Context (上下文):: 一次调用链的上下文, 保存当前调用的入口节点与来源信息
Node (节点):: 用于统计的度量单元, 保存某一维度的实时指标数据
Rule (规则):: 定义限流, 熔断等行为的阈值与策略, 可动态加载

[[sentinel-slot-chain]]
=== 核心架构: Slot Chain 责任链

Sentinel 的核心是将一次资源访问抽象为一条**处理器责任链 (ProcessorSlotChain)**. 每个 Slot 负责一个独立的关注点, 请求依次穿过所有 Slot, 完成统计, 校验与决策.

==== Slot Chain 的组成

默认的 Slot 链由 `DefaultSlotChainBuilder` 构建, 按顺序包含以下 Slot:

[cols="1,3"]
|===
| Slot | 职责

| `NodeSelectorSlot`
| 构建调用树, 为当前资源创建或查找 `DefaultNode`

| `ClusterBuilderSlot`
| 构建资源的 `ClusterNode`, 聚合同一资源在所有上下文中的统计

| `LogSlot`
| 记录异常日志, 用于排障

| `StatisticSlot`
| 核心统计槽位, 调用后续 Slot 并收集 RT, 成功数, 异常数等指标

| `AuthoritySlot`
| 黑白名单校验

| `SystemSlot`
| 系统自适应保护校验

| `FlowSlot`
| 流量控制校验, 不通过则抛出 `FlowException`

| `DegradeSlot`
| 熔断降级校验, 不通过则抛出 `DegradeException`
|===

IMPORTANT: `StatisticSlot` 位于 `FlowSlot` 与 `DegradeSlot` 之前, 即**统计先于校验执行**. 该设计使得无论请求最终被放行还是被拒绝, 其流量特征都会被准确记录, 从而保证滑动窗口统计的完整性.

一次 `entry()` 调用在 Slot Chain 上的执行顺序如下:

[[sentinel-core-components]]
=== 核心组件剖析

==== SphU 与 CtSph

`SphU` 是 Sentinel 对外暴露的静态门面, 提供 `entry()` 与 `exit()` 方法, 真正的实现位于 `CtSph`:

[source,java]
----
public class SphU {
    public static Entry entry(String name) throws BlockException { // <1>
        return Env.sph.entry(name, EntryType.OUT, 1, OBJECTS0);
    }

    public static void exit(Entry entry) throws ErrorEntryFreeException {
        Env.sph.exit(entry); // <2>
    }
}
----
<1> 申请资源访问, 若被限流或熔断则抛出 `BlockException`
<2> 释放资源, 结束统计

`CtSph` 的核心职责:

* 通过 `ContextUtil` 获取或创建调用上下文 `Context`
* 从 `SlotChainProvider` 中获取资源对应的 `ProcessorSlotChain`
* 触发 Slot Chain 的 `entry()` 与 `exit()` 流程

==== Node 体系

Sentinel 的统计指标由不同类型的 `Node` 承载, 它们共同构成一棵**调用树**:

[cols="1,3"]
|===
| Node 类型 | 说明

| `StatisticNode`
| 最基础的统计节点, 内置滑动窗口计数器, 记录 QPS, RT 等

| `DefaultNode`
| 每个资源在**特定上下文**中的统计节点, 位于调用树中

| `ClusterNode`
| 同一资源在**所有上下文**中聚合后的统计节点

| `EntranceNode`
| 每个上下文的入口节点, 是调用树的根
|===

典型结构: 一个 `Context` 对应一个 `EntranceNode` 作为根, 根下挂载各个资源的 `DefaultNode`; 每个资源另有一个全局唯一的 `ClusterNode` 汇总全部调用.

==== 规则管理器

规则通过 `RuleManager` 统一加载与缓存:

* `FlowRuleManager` 管理流量控制规则
* `DegradeRuleManager` 管理熔断降级规则
* `SystemRuleManager` 管理系统保护规则
* `AuthorityRuleManager` 管理黑白名单规则

规则支持通过控制台 (Sentinel Dashboard) 或 API **动态下发**, 更新时构建新规则集并原子替换, 无需重启应用.

[[sentinel-sliding-window]]
=== 统计原理: 滑动窗口算法

准确的实时统计是限流与熔断的基础. Sentinel 使用 `LeapArray` 实现**滑动窗口**统计, 将一段时间窗口切分为多个固定长度的桶 (bucket).

==== LeapArray 原理

* 默认窗口总长为 **1000ms**, 分为 **2 个桶**, 每个桶 **500ms**
* 每个桶内聚合该时间段内的指标, 如通过数, 拒绝数, RT 等
* 统计时只累加当前窗口内有效桶的数据, 过期桶会被滚动重置

其核心实现简化如下:

[source,java]
----
public abstract class LeapArray<T> {
    protected final int windowLengthInMs; // <1>
    protected final int sampleCount;      // <2>
    protected final int intervalInMs;     // <3>
    protected final AtomicReferenceArray<WindowWrap<T>> array;

    public WindowWrap<T> currentWindow(long timeMillis) {
        long timeId = timeMillis / windowLengthInMs;
        int idx = (int)(timeId % array.length());
        long windowStart = timeId * windowLengthInMs;
        while (true) {
            WindowWrap<T> old = array.get(idx);
            if (old == null) {
                // 桶不存在, CAS 新建
                WindowWrap<T> window = new WindowWrap<>(windowLengthInMs, windowStart, newEmptyBucket());
                if (array.compareAndSet(idx, null, window)) {
                    return window;
                }
                Thread.yield();
            } else if (windowStart == old.windowStart()) {
                return old; // 命中当前桶
            } else if (windowStart > old.windowStart()) {
                // 桶已过期, CAS 重置
                WindowWrap<T> window = new WindowWrap<>(windowLengthInMs, windowStart, newEmptyBucket());
                if (array.compareAndSet(idx, old, window)) {
                    return window;
                }
                Thread.yield();
            } else {
                return new WindowWrap<>(windowLengthInMs, windowStart, newEmptyBucket());
            }
        }
    }
}
----
<1> 单个桶的时间跨度
<2> 桶的数量
<3> 整个窗口总时长, 等于 windowLengthInMs * sampleCount

NOTE: 滑动窗口采用**环形数组 + CAS 无锁**实现, 桶的定位通过 `timeId % array.length()` 计算, 避免了窗口整体移动时的大规模数据搬迁, 兼顾了统计精度与并发性能.

[[sentinel-flow-control]]
=== 流量控制原理

==== 限流维度

`FlowRule` 支持两种限流维度:

QPS (每秒请求数):: 基于滑动窗口统计的每秒通过请求数进行限流
并发线程数:: 基于当前正在处理的线程数进行限流, 线程计数通过 `StatisticSlot` 中 `ThreadLocal` 累加与释放实现

==== 三种流控效果

`FlowRule.controlBehavior` 决定被限流时的处理方式:

[cols="1,1,3"]
|===
| 效果 | 常量 | 说明

| 快速失败
| `CONTROL_BEHAVIOR_DEFAULT`
| 超过阈值立即抛出 `FlowException`, 默认方式

| Warm Up
| `CONTROL_BEHAVIOR_WARM_UP`
| 冷启动预热, 使用令牌桶算法, 让系统流量缓慢爬升至阈值

| 匀速排队
| `CONTROL_BEHAVIOR_RATE_LIMITER`
| 漏桶算法, 请求按固定速率排队通过, 适合削峰填谷
|===

==== 流控模式

`FlowRule.strategy` 定义限流作用的对象范围:

直接模式 (STRATEGY_DIRECT):: 仅针对当前资源本身限流
关联模式 (STRATEGY_RELATE):: 当关联资源达到阈值时对当前资源限流, 常用于读写分离场景
链路模式 (STRATEGY_CHAIN):: 仅对指定调用入口的链路生效, 需要配合 `NodeSelectorSlot` 统计入口信息

[[sentinel-circuit-breaker]]
=== 熔断降级原理

==== 熔断器状态机

熔断降级基于**断路器模式**, 状态迁移如下:

[plantuml, "熔断器状态机", format=png]
----
@startuml
skinparam backgroundColor #FEFEFE

[*] --> CLOSED
CLOSED --> OPEN : 熔断条件触发
OPEN --> HALF_OPEN : 时间窗口到期
HALF_OPEN --> CLOSED : 探测请求成功
HALF_OPEN --> OPEN : 探测请求失败
CLOSED --> CLOSED : 正常通过
OPEN --> OPEN : 快速失败
@enduml
----

* **CLOSED (关闭):** 正常放行, 同时统计请求指标
* **OPEN (打开):** 直接拒绝请求, 快速失败, 不访问下游
* **HALF_OPEN (半开):** 熔断时间窗结束后放行少量探测请求, 成功则关闭熔断器, 失败则重新打开

==== 三种熔断策略

`DegradeRule` 支持三种熔断策略:

[cols="1,3"]
|===
| 策略 | 判定条件

| 慢调用比例 (Slow Request Ratio)
| 响应时间超过 `RT` 阈值的请求占比超过设定值, 且统计窗口内请求数大于最小请求数

| 异常比例 (Exception Ratio)
| 异常请求占总请求的比例超过设定阈值

| 异常数 (Exception Count)
| 统计窗口内异常请求的绝对数量超过设定阈值
|===

配置示例:

[source,java]
----
DegradeRule rule = new DegradeRule("orderService");
rule.setGrade(RuleConstant.DEGRADE_GRADE_RT); // <1>
rule.setCount(200);                            // <2>
rule.setTimeWindow(10);                        // <3>
rule.setMinRequestAmount(5);                   // <4>
rule.setSlowRatioThreshold(0.5);               // <5>
DegradeRuleManager.loadRules(Collections.singletonList(rule));
----
<1> 策略: 慢调用比例
<2> RT 阈值 200ms
<3> 熔断时长 10s
<4> 最小请求数
<5> 慢调用比例阈值 50%

[[sentinel-system-protection]]
=== 系统自适应保护

系统保护 (`SystemRule`) 不针对单个资源, 而是从**系统整体**负载出发进行保护, 当以下任一指标触发阈值时拒绝后续入口流量:

* Load1: 系统一分钟平均负载
* CPU 使用率
* 平均响应时间 RT
* 并发线程数
* 入口 QPS

其实现通过 `SystemRuleManager` 周期性地采集系统指标, 并在 `SystemSlot` 中完成校验, 适合作为全局兜底保护.

[[sentinel-usage]]
=== 使用示例

引入依赖 (以最新稳定版 1.8.8 为例):

[source,xml]
----
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-core</artifactId>
    <version>1.8.8</version>
</dependency>
----

定义资源并加载限流规则:

[source,java]
----
public class SentinelDemo {
    public static void main(String[] args) {
        // 加载限流规则: 每秒最多放行 10 个请求
        FlowRule rule = new FlowRule("hello");
        rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        rule.setCount(10);
        FlowRuleManager.loadRules(Collections.singletonList(rule));

        while (true) {
            Entry entry = null;
            try {
                entry = SphU.entry("hello"); // <1>
                System.out.println("请求通过");
            } catch (BlockException e) {     // <2>
                System.out.println("请求被限流");
            } finally {
                if (entry != null) {
                    entry.exit();            // <3>
                }
            }
        }
    }
}
----
<1> 申请访问资源
<2> 被限流时捕获 `BlockException`
<3> 释放资源, 务必在 finally 中执行

TIP: `entry()` 返回的 `Entry` 必须在 `finally` 中调用 `exit()`, 否则线程计数不会释放, 导致并发线程数限流失效.

[[sentinel-summary]]
=== 总结与注意事项

* **统一入口:** Sentinel 在 Slot Chain 中集中处理统计与校验, 实现无侵入的流量治理
* **无锁统计:** 滑动窗口使用环形数组 + CAS, 在保证精度的同时获得高并发性能
* **动态规则:** 规则可在运行时下发, 满足弹性伸缩与实时调优需求

常见误区与最佳实践:

* 不要在循环内创建资源, 资源名应保持稳定, 避免统计节点无限增长
* `exit()` 必须与 `entry()` 成对出现, 且放在 `finally` 中
* 限流应优先作用于入口资源, 避免在内部深层调用重复限流
* 生产环境建议结合 Sentinel Dashboard 统一管理与监控规则
