== Xray原理讲解

Xray (又称 Xray-core, Project X) 是 V2Ray 的**社区分支**, 在继承 V2Ray 全部功能的基础上引入了多项革命性改进. 它不是一个简单的协议实现, 而是一个**高性能代理运行时**, 核心创新在于 **XTLS 传输技术**和 **VLESS 协议**, 旨在解决传统 TLS 代理的性能瓶颈和流量特征可识别问题.

=== 设计理念

Xray 的设计围绕三个核心目标:

* **极致性能:** 通过 XTLS 的"直接流解密"技术, 大幅减少加解密开销, 相比传统 TLS 代理性能提升数倍.

* **更隐蔽的流量特征:** VLESS 去除 VMess 的固定加密层, 将加密任务完全交给底层 TLS, 减少特征指纹; Reality 技术则进一步伪装 TLS 握手为访问正规网站的流量.

* **向前兼容:** 完全兼容 V2Ray 的配置格式和 VMess 协议, 用户可无缝迁移.

=== 核心技术: XTLS

XTLS (Xray TLS) 是 Xray 最重要的技术突破. 理解它需要先了解传统 TLS 代理的问题.

==== 传统 TLS 代理的性能瓶颈

在典型的 TLS 代理(V2Ray + TLS, Trojan 等)中, 数据传输路径如下:

. 客户端应用 -> 本地代理(未加密)
. 本地代理 -> (TLS 加密) -> 远程代理服务器 -> (TLS 解密) -> 目标服务器
. 目标服务器 -> (TLS 加密) -> 远程代理服务器 -> (TLS 解密) -> 本地代理 -> 客户端应用

在这个过程中, **远程代理服务器需要对 TLS 进行两次完整的加解密操作**: 一次是与客户端的 TLS, 一次是与目标服务器的 TLS (如果目标也是 HTTPS). 这在高并发场景下会消耗大量 CPU 资源.

==== XTLS 的优化原理

XTLS 的核心思路是: **数据经过代理服务器时, 不需要在内存中完成完整的加解密**, 而是利用操作系统内核能力直接在数据流层面处理.

具体来说, XTLS 引入了 **Uplink/Downlink 分离**机制:

* **Uplink (客户端 -> 服务器):** 数据在代理服务器上只需验证 TLS 头部, 验证后直接以加密形态转发给目标服务器, 无需解密后重新加密.

* **Downlink (服务器 -> 客户端):** 数据从目标服务器经代理服务器返回时, 同样以加密形态直接透传回客户端. 由于 XTLS 的握手阶段已协商好密钥, 客户端可以自行解密.

这让代理服务器的角色从"主动加解密中间人"转变为"智能流式转发器", 大幅降低 CPU 开销.

==== XTLS 的流式模式

XTLS 支持多种流式模式, 以适应不同的深度包检测 (DPI) 环境:

* **XTLS Direct:** 直接透传模式, 性能最高, 但流量特征最明显(直接暴露 TLS 流).

* **XTLS Splice:** 利用 Linux 内核的 `splice` 系统调用, 在**内核空间**直接完成数据转发, 完全不经过用户空间缓冲区. 这是 XTLS 性能最高的模式, 但仅支持 Linux 平台.

* **XTLS Vision:** 增强型流式模式, 在 Direct/Splice 基础上对 TLS 记录层进行**长度填充随机化**, 消除标准 TLS 流的固定长度特征, 抵抗基于流量长度分析的 DPI 检测.

=== VLESS 协议

VLESS (VMess-LESS, 意为"更轻量的 VMess") 是 Xray 引入的轻量级传输协议.

==== 与 VMess 的关键区别

* **无内建加密:** VMess 自带完整的加密层(AES-256-CFB, ChaCha20-Poly1305), VLESS 不提供任何内建加密, 完全依赖底层传输层(TLS)提供机密性.

* **更小的握手开销:** VMess 握手需要交换加密参数、Nonce、时间戳等, VLESS 的握手仅在 UDP 连接时需要一个额外的 Packet 头部, TCP 连接则完全不需要额外握手.

* **无时间同步要求:** VMess 要求客户端与服务器时间误差在 120 秒内, VLESS 取消了这一要求, 简化了配置维护.

* **更少的特征字节:** VMess 协议头部包含固定的认证数据和加密参数, 容易被 DPI 识别; VLESS 的协议头部极其精简, 几乎没有可识别的固定特征.

==== VLESS 的适用场景

* **配合 TLS/XTLS 使用(推荐):** VLESS + TLS/XTLS 是当前最主流的配置组合, 兼具高性能和高隐蔽性.

* **裸 VLESS (不推荐):** 不配置 TLS 时, VLESS 流量完全明文传输, 仅适用于内部可信网络.

=== Reality 技术

Reality 是 Xray 引入的一项**连接伪装技术**, 目标是解决 TLS 代理的"服务器指纹"问题.

==== 问题的由来

即使使用了 TLS 加密, DPI 系统仍可通过以下方式识别代理:

* **TLS 证书特征:** 自签名证书或非同寻常的证书签发机构(e.g., 某个知名 CDN 的子证书)会被标记.
* **TLS 握手特征:** 服务器的 TLS 版本、密码套件、ALPN (Application-Layer Protocol Negotiation) 等参数与常见浏览器的"标准"握手特征不符.

==== Reality 的工作原理

Reality 通过以下机制解决上述问题:

. **目标伪装 (Target):** 服务器在 TLS 握手阶段**不提供自己的证书**, 而是向客户端返回一个真实正规网站的 TLS 握手数据(如 `www.microsoft.com` 或 `www.cloudflare.com`). DPI 观察到的 TLS 握手与访问正规网站无异.

. **无服务器证书:** 服务器自身不需要任何 TLS 证书, 也不需要管理证书续期. 证书验证在客户端完成, 客户端通过 `serverName` 验证伪装目标的证书.

. **短效 Session ID:** Reality 使用**临时生成的短效 Session ID** 进行连接标识, 避免持久化的 Session ID 模式被追踪.

. **公私钥验证:** 虽然使用了正规网站的 TLS 握手数据, 但 Xray 客户端和服务器之间仍通过一对**固定的公私钥**进行加密验证, 确保只有授权客户端才能使用该代理.

Reality 使得代理服务器在 DPI 视角下"看起来像"一个普通的 HTTPS 访问目标网站的用户, 而非一个代理服务器.

=== gRPC 传输支持

Xray 在传输层增加了对 **gRPC (gRPC Web)** 的支持:

* **gRPC 长连接:** 利用 HTTP/2 的多路复用特性, 通过 gRPC 隧道传输代理流量.
* **CDN 友好:** gRPC Web 可以被大多数 CDN 正确转发, 适合通过 CDN 隐藏代理服务器 IP.
* **与 WebSocket 的比较:** gRPC 比 WebSocket 更节省连接资源, 但需要服务端和客户端都支持 HTTP/2.

=== Fallback 增强

Xray 在 V2Ray Fallback 机制上做了重大改进:

* **多级 Fallback:** 支持根据 SNI (Server Name Indication) 将不同域名的请求 fallback 到不同的后端服务.
* **协议嗅探 Fallback:** 根据请求的协议类型(HTTP/1.1, HTTP/2, gRPC 等)决定 fallback 目标.
* **强制 Fallback:** 即使请求能正常处理, 也可以根据策略强制 fallback, 进一步提升伪装效果.

配置示例:

[source, json]
----
{
  "inbounds": [
    {
      "port": 443,
      "protocol": "vless",
      "settings": {
        "clients": [{"id": "uuid-here"}],
        "decryption": "none",
        "fallbacks": [
          {
            "dest": 8080,
            "xver": 1
          },
          {
            "name": "example.com",
            "dest": 8081,
            "xver": 1
          },
          {
            "alpn": "h2",
            "dest": 8082,
            "xver": 1
          }
        ]
      },
      "streamSettings": {
        "network": "tcp",
        "security": "xtls",
        "xtlsSettings": {
          "alpn": ["http/1.1", "h2"]
        }
      }
    }
  ]
}
----

=== FQDN 路由

Xray 支持 **FQDN (Fully Qualified Domain Name)** 直接路由, 无需先进行 DNS 解析:

[source, json]
----
{
  "routing": {
    "domainStrategy": "AsIs",
    "rules": [
      {
        "type": "field",
        "domain": ["domain:example.com"],
        "outboundTag": "proxy"
      }
    ]
  }
}
----

`domainStrategy` 支持的策略:

* `AsIs:` 仅依赖 FQDN 匹配, 不进行 DNS 解析. 性能最高, 但无法做 IP 级别的规则匹配.
* `IPIfNonMatch:` 先尝试域名匹配, 若未命中再解析 DNS 进行 IP 匹配. 兼顾性能和精确度.
* `IPOnDemand:` 立即解析所有域名为 IP, 以 IP 规则匹配. 精确度最高, 但 DNS 请求量大.

=== 总结

* Xray 是 V2Ray 的社区分支, 继承了 V2Ray 的全部能力并引入了多项核心创新.

* **XTLS** 是 Xray 最核心的技术突破, 通过 Uplink/Downlink 分离和内核转发(Splice)大幅降低代理服务器的加解密开销.

* **VLESS** 协议精简了 VMess 的握手和加密层, 配合 TLS/XTLS 使用时可获得更高性能和更低特征可识别性.

* **Reality** 技术通过伪装 TLS 握手为目标正规网站, 解决了代理服务器 TLS 证书指纹被 DPI 识别的问题.

* **gRPC 传输支持** 和 **多级 Fallback** 增强了 Xray 在 CDN 部署和流量伪装方面的灵活性.

* 目前 Xray 已成为社区的主流选择, V2Ray 原项目已基本停止维护. 新项目应优先选择 Xray.
