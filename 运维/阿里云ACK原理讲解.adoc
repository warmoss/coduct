== 阿里云ACK原理讲解

阿里云容器服务 ACK(Alibaba Cloud Container Service for Kubernetes)是阿里云提供的托管式 Kubernetes 服务, 兼容原生 K8s API, 同时深度集成阿里云 IaaS 能力(ECS, VPC, SLB, 云盘/NAS/OSS 等). ACK 的核心价值在于: 将控制面的运维交给阿里云, 用户只需管理 Worker 节点和运行业务负载, 大幅降低 K8s 集群的搭建和运维成本.

=== 核心概念

ACK 托管版(Managed Kubernetes):: 控制面(API Server, etcd, Scheduler, Controller Manager)由阿里云托管, 用户无需为 Master 节点付费, 也无需关心控制面的升级和高可用. 用户只需管理 Worker 节点(ECS)和 Pod.

ACK 专有版(Dedicated Kubernetes):: 用户自行购买 ECS 作为 Master 节点, 控制面部署在用户 VPC 内, 用户对集群有完全控制权. 适用于对安全合规有极高要求的场景.

ACK Serverless版(ASK):: 完全无需管理节点. 用户直接提交 Pod, ASK 在阿里云弹性容器实例(ECI)上运行 Pod, 按 Pod 实际使用的 vCPU 和内存秒级计费. 适合批处理, CI/CD, 突发流量等场景.

ACK Edge(边缘容器):: 将 K8s 集群扩展到边缘节点, 支持云边协同, 适用于 IoT, CDN, 边缘计算等场景.

节点池(NodePool):: 一组配置相同的 ECS 节点集合. 支持多可用区, 多种实例规格, 弹性伸缩和自动修复.

==== 控制面

控制面由阿里云全托管, 部署在阿里云账号的隐藏 VPC 中, 用户无需感知. 核心组件:

* *API Server*: 通过公网或内网 SLB 暴露, 支持 RAM/RBAC 双重鉴权
* *etcd*: 阿里云托管的高可用 etcd 集群, 自动备份和恢复
* *Cloud Controller Manager(CCM)*: 负责对接阿里云云资源, 如自动创建 SLB, 挂载云盘, 管理 VPC 路由等, 这是 ACK 区别于自建 K8s 的核心组件

==== 数据面

数据面是用户 VPC 内的 ECS 实例(Worker 节点), 运行标准的 Kubelet, Kube-proxy 和容器运行时(containerd). 用户完全掌控节点配置、安全组和网络策略.

=== 核心原理

==== 集群网络模型

ACK 使用 Terway 或 Flannel 两种 CNI 网络插件:

Terway:: 阿里云自研的高性能 CNI 插件, 直接使用阿里云 ENI(弹性网卡)为 Pod 分配 IP.
+
* *优势*: Pod 直接使用 VPC IP, 与 ECS, RDS 等云资源网络直通, 无需 NAT 转换, 性能更高; 支持 NetworkPolicy
* *原理*: Terway 为每个 Pod 创建专属的 ENI 或 ENI 辅助 IP, Pod 网络栈直连 VPC 交换机

Flannel:: 开源 CNI 方案, 使用 VXLAN 或 host-gw 模式.
+
* *优势*: 简单稳定, 不消耗额外 ENI 配额
* *劣势*: 性能略低于 Terway; 不支持 NetworkPolicy

[NOTE]
====
生产环境建议使用 Terway, 性能更优且支持网络策略. Flannel 适用于 ENI 配额受限或追求简单部署的场景.
====

==== 服务发现与负载均衡

ACK 的服务暴露方式分为三层:

ClusterIP:: 集群内部访问, 通过 Kube-proxy(iptables/IPVS)实现 Pod 间负载均衡.

NodePort:: 在每个节点上开放一个固定端口, 通过 `<NodeIP>:<NodePort>` 访问.

LoadBalancer:: 通过 CCM 自动创建阿里云 SLB(Server Load Balancer), 将外部流量分发到后端 Pod.
+
* *原理*: 创建 `type: LoadBalancer` 的 Service 时, CCM 自动调用阿里云 API 创建 SLB 实例, 并将所有 Worker 节点加入 SLB 后端. CCM 持续监听 Pod 和 Node 变化, 动态更新 SLB 后端列表.

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
  annotations:
    service.beta.kubernetes.io/alibaba-cloud-loadbalancer-spec: "slb.s1.small"  # <1>
spec:
  type: LoadBalancer
  ports:
    - port: 80
  selector:
    app: nginx
----
<1> 通过 annotation 指定 SLB 规格, CCM 解析并创建对应规格的 SLB

Ingress:: ACK 集成 ALB Ingress Controller 或 Nginx Ingress Controller, 实现七层路由, SSL 卸载和域名转发.

==== 存储管理

ACK 通过 CSI(Container Storage Interface)插件对接阿里云存储服务:

[cols="3*"]
|===
| 存储类型 | 对应阿里云产品 | 适用场景

| 块存储(Block)
| 云盘(Disk)
| 数据库, 有状态应用, 单 Pod 读写

| 文件存储(File)
| NAS
| 共享存储, 多 Pod 读写, AI 训练

| 对象存储(Object)
| OSS
| 日志, 静态资源, 备份归档
|===

* *动态卷供给*: 用户创建 PVC(PersistentVolumeClaim)时, CSI 插件自动调用阿里云 API 创建对应的云盘或 NAS 文件系统, 并绑定到 Pod
* *静态卷供给*: 预先在阿里云创建存储资源, 手动创建 PV 后绑定

==== 弹性伸缩

ACK 提供三层弹性伸缩能力:

. *Pod 水平伸缩(HPA)*: 基于 CPU, 内存或自定义指标, 自动调整 Deployment/StatefulSet 的副本数
. *节点伸缩(Cluster Autoscaler)*: 当 Pod 因资源不足无法调度时, 自动向节点池添加 ECS 节点; 当节点利用率持续过低时, 自动移除空闲节点
. *垂直伸缩(VPA)*: 自动调整 Pod 的 resource requests/limits, 适合难以预估资源用量的场景

弹性伸缩的工作流程:

[plantuml, "ACK 弹性伸缩流程", format=png]
----
@startuml
actor 用户
participant "ACK 集群" as ack
participant "HPA" as hpa
participant "Cluster Autoscaler" as ca
participant "阿里云 ESS" as ess

用户 -> ack: 配置 HPA 策略 (min=2, max=10, cpu=60%)
hpa -> ack: 持续采集 Metrics
hpa -> ack: CPU > 60%, 增加副本数

ack -> ca: Pod 处于 Pending (资源不足)
ca -> ess: 调用 ESS API, 扩容节点
ess --> ca: 新 ECS 节点就绪
ca --> ack: 节点加入集群
ack --> ack: Scheduler 将 Pending Pod 调度到新节点

@enduml
----

==== 安全体系

ACK 的安全模型覆盖以下几个层面:

* *访问控制*: 支持阿里云 RAM 鉴权(集群管理操作)和 K8s RBAC 鉴权(集群内资源操作)双重体系
* *网络隔离*: 通过 NetworkPolicy 实现 Pod 间流量控制; 通过安全组实现节点级防火墙
* *镜像安全*: 集成容器镜像服务 ACR, 支持镜像扫描和加签
* *审计*: 集成操作审计 ActionTrail, 记录所有 API 调用; 支持 K8s Audit Log 输出到 SLS 日志服务
* *密钥管理*: Secret 加密存储, 支持集成 KMS 对 Secret 进行信封加密

=== 与自建 Kubernetes 对比

[cols="3*"]
|===
| 对比维度 | 自建 K8s | ACK 托管版

| 控制面运维
| 需自行部署和维护 Master 节点, etcd 集群, 处理升级和故障
| 阿里云全托管, 免运维

| 高可用
| 需自行搭建多 Master 高可用架构
| 控制面默认多可用区高可用, SLA 99.95%

| 云资源集成
| 需自行开发或配置云厂商对接(存储, 网络, 负载均衡)
| CCM/CSI 内置集成, 开箱即用

| 弹性伸缩
| 需自行安装配置 Cluster Autoscaler
| 控制台一键开启, 与 ESS 原生集成

| 安全合规
| 需自行加固 etcd, 审计, 加密
| 内置 RAM/RBAC, KMS 加密, ActionTrail 审计

| 成本
| 需承担 Master 节点 ECS 费用(通常 3-5 台)
| 控制面免费, 仅需支付 Worker 节点费用
|===

=== 最佳实践

* *集群规划*: 按环境(开发/测试/生产)创建独立集群, 按业务域划分命名空间, 避免单集群过大(建议不超过 2000 节点)
* *网络选择*: 生产环境优先使用 Terway, 开启 NetworkPolicy 实现微服务间访问控制
* *节点池管理*: 按用途(通用/计算型/GPU)划分节点池, 配置不同的伸缩策略和污点容忍
* *可观测性*: 集成阿里云 ARMS(Prometheus)采集指标, SLS 采集日志, 使用 AHAS 进行混沌工程和限流降级
* *安全基线*: 启用 PodSecurityPolicy/PodSecurity, 禁用特权容器, 镜像必须来自私有 ACR 仓库, 定期扫描 CVE
* *备份策略*: 使用 velero 定期备份集群资源和持久卷数据到 OSS, 确保灾难恢复能力

=== 总结

ACK 本质上是在开源 Kubernetes 之上叠加了阿里云 IaaS 的深度集成层. 其核心原理可以概括为:

. *控制面托管*: API Server, etcd, Scheduler 由阿里云运维, 用户零负担
. *云资源对接*: 通过 CCM 和 CSI 插件, 将 SLB, 云盘, NAS, VPC 等云资源映射为原生 K8s 对象
. *弹性能力*: HPA + Cluster Autoscaler + ESS 三级联动, 实现从 Pod 到节点的全链路自动伸缩
. *安全增强*: RAM/RBAC 双重鉴权 + KMS 加密 + NetworkPolicy, 满足企业级安全合规要求

理解 ACK 原理的关键在于: 它不是 K8s 的魔改版本, 而是在标准 K8s 基础上通过插件化的方式(CCM, CSI, CNI)融入阿里云底座, 同时将控制面运维复杂度交给云厂商. 从自建 K8s 迁移到 ACK 的改造成本极低, 因为 ACK 完全兼容原生 K8s API 和生态工具(kubectl, Helm, Istio 等).
