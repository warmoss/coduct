== 阿里云SAE原理讲解

阿里云 Serverless 应用引擎(SAE, Serverless App Engine)是一个面向应用的 Serverless PaaS 平台, 支持 Spring Cloud, Dubbo, HSF 等主流微服务框架. 它底层基于 Kubernetes, 但屏蔽了 K8s 的节点管理, 网络配置和运维复杂性, 开发者只需关注应用代码和业务逻辑, 无需操心底层基础设施.

SAE 的核心价值在于: 对开发者零改造, 对运维零集群管理, 对资源按需付费.

=== 核心概念

应用(Application):: SAE 中的基本管理单元, 代表一个可独立部署和运行的微服务. 每个应用关联一组实例(Instance).
实例(Instance):: 应用的一个运行副本, 对应底层一个 Pod. SAE 自动管理实例的创建, 销毁和健康检查.
命名空间(Namespace):: 逻辑隔离单元, 用于隔离不同环境(如开发, 测试, 生产)的应用和配置.
弹性伸缩:: SAE 根据 CPU, 内存, QPS, RT 等指标自动调整实例数量, 实现秒级弹性扩缩容.
发布策略:: 支持分批发布, 灰度发布(金丝雀), 蓝绿发布等多种变更策略, 降低发布风险.

=== 核心架构与原理

SAE 的架构可分为三层:

[plantuml, "SAE 架构分层", format=png]
----
@startuml
skinparam componentStyle rectangle

package "SAE 控制面" {
  [应用管理] as app_mgmt
  [弹性伸缩] as auto_scale
  [发布管理] as deploy
  [监控告警] as monitor
}

package "SAE 数据面 (Kubernetes)" {
  [Pod] --> [微服务容器]
  [Pod] --> [Sidecar (日志/监控)]
  [Service] --> [Pod]
}

package "基础设施层" {
  [ECS/ECI/神龙] as infra
}

app_mgmt --> deploy
auto_scale --> infra
deploy --> infra
monitor --> infra

@enduml
----

==== 控制面

控制面是 SAE 的管理大脑, 负责接收用户请求(创建应用, 配置伸缩规则, 触发发布等), 并将其翻译为底层 K8s 资源的操作. 控制面主要包含:

* *应用编排*: 将用户的应用配置(镜像, 环境变量, 启动命令, 健康检查等)转换为 K8s Deployment 或 StatefulSet
* *流量调度*: 管理 K8s Service 和 Ingress, 实现微服务发现和负载均衡
* *弹性伸缩引擎*: 监控指标数据, 执行伸缩决策, 调用底层 API 调整副本数
* *发布编排*: 按照用户指定的发布策略, 逐步替换旧版本实例

==== 数据面

数据面是实际运行业务流量的部分. SAE 的数据面直接复用 K8s 生态:

* 每个应用实例对应一个 K8s Pod, 内部运行用户的应用容器
* Pod 内自动注入 Logtail Sidecar 用于日志采集, 以及 ARMS Agent 用于应用监控
* 通过 K8s Service 实现实例间负载均衡

==== 基础设施层

SAE 支持多种底层计算资源:

* *ECS*: 用户自有或 SAE 托管的 ECS 实例, 适合稳态工作负载, 成本可控
* *ECI(弹性容器实例)*: 阿里云提供的 Serverless 容器实例, 无需管理节点, 按秒计费, 适合突发流量场景
* *神龙裸金属*: 提供更高性能和隔离性

=== 弹性伸缩原理

SAE 的弹性伸缩是秒级响应的, 其核心流程如下:

. 监控数据采集: SAE 持续采集每个实例的 CPU, 内存, 应用 QPS, RT 等指标
. 策略评估: 弹性伸缩引擎周期性(默认 15 秒)评估指标是否触发伸缩规则
. 决策执行: 触发伸缩后, 调用底层 K8s API 调整 Deployment 的 replicas 字段
. 实例就绪: 新实例启动并通过健康检查后, 自动注册到服务发现, 开始接收流量

弹性策略支持三种模式:

[cols="1,2,2"]
|===
| 策略类型 | 触发条件 | 适用场景

| 定时伸缩
| 按 cron 表达式在指定时间扩缩容
| 周期性流量高峰, 如每天 10:00 促销开始

| 指标伸缩
| CPU/内存/网络/QPS/RT 等达到阈值
| 不可预测的流量波动

| 混合伸缩
| 定时 + 指标组合, 取最大副本数生效
| 需要保障底座的弹性场景
|===

[IMPORTANT]
====
SAE 的弹性伸缩与 HPA(Horizontal Pod Autoscaler)原理类似, 但 SAE 封装了 HPA 的配置细节, 提供更简洁的控制台操作. 同时 SAE 集成了 AHAS 的流量控制和熔断降级能力, 在扩容不够快时能保护后端服务不被击穿.
====

=== 发布策略原理

SAE 支持多种发布策略, 每种策略的核心差异在于流量切换的方式:

==== 分批发布

将实例分成多个批次, 依次替换. 每批次替换后等待指定的时间或手动确认, 再继续下一批.

[plantuml, "分批发布流程", format=png]
----
@startuml
participant "用户" as User
participant "SAE 控制面" as SAE
participant "旧实例组" as Old
participant "新实例组" as New
participant "流量入口" as LB

User -> SAE: 触发分批发布(批次=3)
SAE -> New: 启动批次1新实例
New --> SAE: 健康检查通过
SAE -> LB: 批次1流量切换到新实例
SAE -> Old: 停止批次1旧实例
note right: 等待人工确认或指定时间
SAE -> New: 启动批次2新实例
SAE -> LB: 批次2流量切换到新实例
SAE -> Old: 停止批次2旧实例
note right: 等待人工确认或指定时间
SAE -> New: 启动批次3新实例
SAE -> LB: 全部流量切换到新实例
SAE -> Old: 清理所有旧实例

@enduml
----

==== 灰度发布(金丝雀发布)

通过流量比例或请求头规则, 将一小部分流量引导到新版本, 验证无问题后再全量切换.

工作原理:

. 部署新版本实例(通常 1~2 个)
. 配置灰度规则, 如 "10% 流量" 或 "header:version=v2"
. SAE 控制面修改 K8s Service 的 Pod 选择器或 Ingress 规则, 按规则分发流量
. 观察新版本监控指标, 确认无误后执行全量切换

[NOTE]
====
SAE 灰度发布的底层依赖 K8s 的 Service 多 Label Selector 机制和 Ingress Controller 的流量切分能力. 对于 Spring Cloud 或 Dubbo 应用, SAE 还可以结合微服务框架内置的负载均衡(如 Ribbon)实现更细粒度的流量控制.
====

=== 应用生命周期管理

[plantuml, "SAE 应用生命周期", format=png]
----
@startuml
[*] --> 创建中: 提交应用配置
创建中 --> 运行中: 实例启动成功
运行中 --> 变更中: 更新配置/镜像/伸缩
变更中 --> 运行中: 变更完成
运行中 --> 发布中: 触发发布
发布中 --> 运行中: 发布完成
运行中 --> 缩容到零: 无流量时自动缩零
缩容到零 --> 启动中: 首个请求到达
启动中 --> 运行中: 实例就绪
运行中 --> [*]: 删除应用
@enduml
----

SAE 的应用生命周期涵盖从创建到销毁的全过程. 关键机制包括:

* *缩容到零*: 对于非 Web 应用或配置了闲置回收的应用, 当一段时间无请求时, SAE 会将实例数缩减为 0, 节省成本. 当新请求到达时, SAE 会自动冷启动实例
* *无损下线*: 停止实例前, SAE 先从服务发现中摘除该实例, 等待存量请求处理完成(默认 30 秒), 再终止容器. 这避免了正在处理的请求被中断
* *健康检查*: 支持 HTTP 探针和 TCP 探针, 探活失败时 SAE 自动重启该实例

=== 微服务治理集成

SAE 深度集成了阿里云微服务引擎(MSE)和链路追踪(ARMS), 提供开箱即用的微服务治理能力:

[cols="1,3"]
|===
| 能力 | 原理

| 服务注册与发现
| SAE 内置 Nacos 服务注册中心, 应用实例启动后自动注册, 无需额外部署和维护

| 配置管理
| 支持托管 Nacos 配置中心, 应用可实时监听配置变更, 无需重启

| 流量防护
| 集成 Sentinel, 提供限流, 熔断, 降级, 系统自适应保护能力

| 链路追踪
| 自动注入 ARMS Agent, 无代码侵入地采集调用链数据

| 应用监控
| 提供 JVM GC, 线程池, 数据库连接池等指标监控和告警
|===

=== SAE 与 ACK 的关系

SAE 和 <<阿里云ACK原理讲解.adoc#, ACK (容器服务 Kubernetes 版)>> 是互补关系而非替代关系:

[cols="1,2,2"]
|===
| 维度 | SAE | ACK

| 定位
| 面向应用的 Serverless PaaS
| 面向容器的 K8s 托管服务

| 用户关注点
| 应用代码和配置
| Pod, Service, Ingress, Node 等 K8s 资源

| 集群管理
| 无需管理, SAE 托管
| 需要管理 Master 和 Worker 节点

| 弹性效率
| 秒级(含 ECI)
| 受节点扩容速度影响(分钟级)

| 灵活性
| 在 SAE 的抽象层内操作
| 完整的 K8s API 和生态

| 适用场景
| 微服务应用, Web 应用快速部署
| 需要深度定制 K8s 调度和网络的场景
|===

[NOTE]
====
SAE 底层本身运行在 ACK 集群之上. 可以理解为: SAE 是 ACK 的上层封装, 用"应用"概念替代了"Pod/Deployment/Service"等 K8s 原语, 降低了使用门槛.
====

=== 总结

SAE 的核心价值在于 *用 Serverless 体验跑微服务*:

* *零改造*: 不用修改代码, 不用写 Dockerfile, 直接上传 JAR/WAR/镜像即可部署
* *零运维*: 免去 K8s 集群管理和节点维护, SAE 全托管
* *按需付费*: 支持缩容到零和按量付费, 仅为实际使用的资源买单
* *生态集成*: 与 MSE, ARMS, SLS, AHAS 等阿里云中间件产品无缝集成

适用场景:

* Spring Cloud / Dubbo 微服务应用的一站式部署和治理
* 传统 Web 应用(如 Spring Boot)迁移上云, 免去容器化改造
* 有弹性需求但不想运维 K8s 集群的团队
* 需要灰度发布, 分批发布等精细化发布能力的场景

不适用场景:

* 需要定制 K8s 调度策略(如拓扑分布, 亲和性)的复杂场景
* 依赖特权容器或宿主级系统调用的应用
* 需要细粒度控制网络策略(如 NetworkPolicy)的场景——这些建议直接使用 ACK

[IMPORTANT]
====
SAE 的应用设计原则: 应用应无状态, 状态数据外置到数据库或缓存; 启动速度应尽可能快(建议 60 秒内完成启动), 以充分发挥弹性伸缩的优势; 优雅下线逻辑应处理 SIGTERM 信号, 配合 SAE 的无损下线机制.
====
